# 詞彙表編輯規則

`GLOSSARY.md` 的**主要消費者是 `domain-modeling` skill**，其餘用途都是順手應用。skill 會在術語確定的當下直接改寫本檔，格式與它不一致就會越寫越亂——所以格式一律以 skill 為準，不要為了任何附屬工具（檢查腳本、CI）改動它的形狀。

## 格式權威

- **規範**：GFF dev-toolkit 的 `domain-modeling` skill 附的格式說明 `reference/glossary-format.md`，以它為準。
- **完整範例**：本 repo 根目錄的 [`GLOSSARY.md`](../../GLOSSARY.md)。規範只示範詞條本體，`Relationships`、`Flagged ambiguities` 兩節與 `_Avoid_` 括號界線的實際寫法，看這份。
- **標記用英文**：GFF 規範的範例用中文標記（`## 詞彙`、`_避免使用_`），本 repo 沿用英文標記（`## Language`、`_Avoid_`），以下方「結構」節為準。
- **上游出處**：GFF 版改編自 mattpocock-skills 的 `domain-modeling`（MIT 授權）。查格式的來龍去脈時才需要看上游，日常編輯不必安裝。

## 結構

```
# {Context}          一兩句描述這個 context 是什麼
## Language          詞條本體，以 ### 分群
## Relationships     概念之間的關係，條列
## Flagged ambiguities  曾有歧義的詞 ＋ 如何解決（未解決的標「尚未釐清」）
```

詞條格式：

```
**正式名**：
定義，一到兩句。說明它「是什麼」，不說它「怎麼運作」。
_Avoid_: 甲、乙（界線說明）、丙
```

## 硬規則

- **不放實作細節**：欄位名、表名、Enum 值一律不進詞條。詞與欄位的對應住在 schema comment。唯一例外是檔頭舉例說明「什麼叫識別字」。
- **定義一到兩句**。寫不下的脈絡放 `Relationships`，未定的爭議放 `Flagged ambiguities`。
- **不放變更紀錄**（「2026-08 起改用⋯」）與待辦。那些屬於 git log 與 `docs/plans/`。
- `_Avoid_` **可以帶括號界線**（`玩家（指平台使用者時）`）——那是上游作者自己的寫法，不是本 repo 擴充。但界線是寫給人讀的語境提示，不是給機械判定用的免責條款。
- **同一個詞不要出現在兩個詞條的 `_Avoid_` 裡指向不同正式名**；真有跨概念的詞，記進 `Flagged ambiguities`。

## 本 repo 的正式名裁決

| 正式名 | 不用 | 理由 |
|---|---|---|
| 無縫錢包 | 單一錢包 | 業界標準譯法（seamless wallet）。repo 現行大量使用「單一錢包」，刻意讓詞彙表領導現實 |
| 站點 | 白標、站台 | 一個站通常就是一個網站 |
| 金流商戶 | 通道商戶 | 一個金流商戶掛好幾條通道、代收代付同時支援——通道隸屬於商戶 |

判準：**有業界標準的詞，詞彙表領導現實；純內部用語則尊重現況。**

## 引用原文時照抄

介面上實際顯示的文字（後台按鈕、狀態名）與代碼裡的字面值（欄位名、三方回調事件名）保留原樣，不套用 `_Avoid_`。列在 `_Avoid_` 的英文，擋的是「拿它當中文行文裡的名詞用」。
