# 附錄：金流商整合的常見缺陷類型

> ← [金流商接入完整操作流程](index.md)

這份文件整理接金流商時反覆出現的十二類缺陷。每一類說明四件事：會看到什麼現象、為什麼會發生、正確的做法、怎麼找出既有程式有沒有這個問題。

這裡只講類型與原理，不列哪一家目前有哪個問題。逐家的清單在風險發現資料檔（`docs/reports/data/payment-risk-findings.json`），每筆發現的 `category` 欄位對應這裡的一類。

## 先認識兩張單的狀態

後面的缺陷，多數都是「把單推到錯的狀態」。先看兩張表。

### 存款單（`OrderStatusEnum`）

| 狀態 | 意思 | 之後的回調還會不會被處理 |
|---|---|---|
| 0 | 剛建立，等金流商回調 | 會 |
| 1 | 回調確認成功，尚未入帳 | 不會 |
| 2 | 失敗 | 不會 |
| 3 | 已入帳 | 不會 |
| 4 | 回調成功但金額與存款單不符，等待人工確認 | 不會 |

共用的 `checkDepositOrderStatus()` 只放行狀態 0 的存款單。存款單一旦離開狀態 0，之後同一張單的回調一律當成「已處理過」回成功，不再改動。

### 提款單（`WithdrawalOrderStatusEnum`）

| 狀態 | 意思 | 能不能重新發起代付 |
|---|---|---|
| 3 | 已審核，等待發起代付 | 可以 |
| 21 | 已送出，結果還不知道 | 不行，鎖住等查證 |
| 22 | 金流商已受理，等回調 | 不行 |
| 24 | 金流商付款成功 | 終態 |
| 29 | 金流商拒絕 | 可以。29 不是終態 |

21 與 29 的差別是關鍵：21 是「不知道有沒有成功，先鎖著」，29 是「確定沒成功，可以再送一次」。把不確定的結果寫成 29，就等於允許同一筆錢付第二次。

## 一、代付送出後，把「不是成功」一律當成「明確拒絕」

**現象**：同一張提款單付了兩次。

**成因**：代付請求送出後，金流商當下的回應其實有三種：受理、明確拒絕、結果不明（系統錯誤、逾時、上游沒有回傳結果）。程式只分「成功」與「其他」，把結果不明也判成拒絕，提款單轉 29。後台重新發起代付後，若第一次其實已經成立，就付了兩次。

**正確做法**：採白名單制。

| 金流商的回應 | 判定 | 提款單狀態 |
|---|---|---|
| 成功碼 | 受理 | 22 |
| 白名單內的碼：能證明金流商沒有建單的（餘額不足、限額、帳號無效、認證失敗等） | 明確拒絕 | 29 |
| 其他所有碼、缺少欄位、逾時、連線例外 | 結果不明 | 21，由查單或人工定案 |

白名單的每一個碼都要有金流商文件或實測的依據。「訂單號重複」這類碼不能列入：重複代表那個單號已經在金流商那邊建立過。「處理中」也不能列入，例如 B3Wallet 的 `409 IDEMPOTENCY_IN_PROGRESS`。

「結果不明」要在送請求的那一段判斷並拋例外，也就是 `processPayout()` 的 `performRequest` 閉包，寫法見 `A3Pay/Withdrawal.php`。共用層只把這裡拋出的例外當成結果不明，讓提款單停在 21。不要在 `interpretResult` 裡拋：那裡拋出的例外會被當成明確拒絕、轉 29，等於沒修。`PayoutResult` 建構時的型別錯誤也算在內，例如三方單號是數字、錯誤訊息不是字串。

**怎麼發現**：看該金流商 `Withdrawal.php` 傳給 `processPayout()` 的 `interpretResult`。若寫法是「等於成功碼就成功，否則就回錯誤訊息」，而且沒有列舉拒絕碼的常數，就是這一類。

## 二、代付被拒絕，但錯誤訊息是空字串，被當成已受理

**現象**：提款單停在 22 等回調，三方單號是空的，回調永遠不來，也沒有告警。會員一直沒收到款。不會重複出款。

**成因**：各家解讀同步回應後，回給共用層一個成功旗標與一段錯誤訊息。共用層判斷有沒有受理時只看錯誤訊息是不是空的（`WithdrawalPayoutService::settleSyncResult()`）。金流商拒絕時若錯誤訊息欄位剛好是空字串，就被當成受理。

各家取錯誤訊息常用 `$result['msg'] ?? '預設文字'` 這種寫法。`??` 只在欄位不存在或是 null 時才取預設值，欄位存在但內容是空字串時不會。

**正確做法**：

- 共用層以成功旗標判斷受理，不以錯誤訊息是否為空判斷。這一項決定提款單的狀態對不對。
- 各家取錯誤訊息時保證結果不是空字串，例如取值後用 `?:` 補預設文字。這一項只影響後台看到的錯誤訊息：共用層改對之後，空的錯誤訊息仍會讓提款單正確轉 29，但後台顯示的會是「未知異常」，看不出金流商拒絕的原因。

**怎麼發現**：

- 程式面：看 `interpretResult` 的 `errorMessage` 是不是只用 `??` 串接。
- 資料面：找狀態是 22、但最新一筆代付請求紀錄（`withdrawal_payout_records`）標成金流商拒絕（`is_success_payout = -2`）的提款單。只看「22 且三方單號是空的」不準：有些金流商受理時本來就不回三方單號，正常在途的單也會符合。
- 歷史面：金流商拒絕的請求紀錄，`info_1` 存的是「金流商名稱 response error: 錯誤訊息」。錯誤訊息那一段是空的，就代表這個問題發生過。

## 三、代付回調把「不是成功」一律標成失敗

**現象**：與第一類相同，同一張提款單付了兩次。

**成因**：金流商的代付回調可能帶「處理中」「待支付」這類還沒定案的狀態。程式只分成功與其他，把還沒定案的也標成失敗，提款單轉 29，之後被重新發起。

**正確做法**：三態判定。

| 回調的狀態 | 判定 | 動作 |
|---|---|---|
| 金流商文件明列的成功碼 | 成功 | 轉 24 |
| 金流商文件明列的失敗碼 | 失敗 | 轉 29 |
| 其餘（處理中、未知碼） | 未定 | 不動提款單，回成功讓金流商之後再送 |

共用的 `resolveWithdrawalOutcome()` 就是做這個判定，成功碼集與失敗碼集都要有文件依據。金流商文件只寫「某碼成功，其他失敗」時，仍要把文件列得出的處理中狀態另外歸到未定。

**怎麼發現**：看 `WithdrawalCallback.php` 的狀態判斷是不是 `if (成功) {...} else {失敗}`，沒有第三條路。

## 四、代收回調把「不是成功」一律標成失敗

**現象**：會員已付款，存款單卻是失敗，錢沒有入帳。

**成因**：金流商可能先送一次「等待付款」或「處理中」的回調，付款完成後再送成功的回調。程式把第一次標成失敗（狀態 2）。存款單離開狀態 0 之後，後面那次成功回調會被當成已處理而略過。

**正確做法**：代收回調同樣採三態。

- 明確成功：呼叫 `updateDepositOrderSuccess()`。
- 金流商文件明列的失敗碼：呼叫 `updateDepositOrderFailed()`。
- 其餘：不動存款單，回成功，等之後的終態回調。

失敗只認金流商文件明確寫出的失敗碼。`make:payment` 產生的骨架是二分寫法，接入時要依金流商的狀態表改成三態。

**怎麼發現**：看 `DepositCallback.php` 的狀態判斷是不是 `if (成功) {...} else { updateDepositOrderFailed }`。再對照金流商文件的狀態表，確認有沒有非終態的狀態碼。

## 五、回調的真實性沒有防線

**現象**：沒有付款的存款單被標成成功並入帳，或代付被偽造的回調改成失敗後重新發起。

**成因**：回調網址是對外的，任何能連到它的人都能送請求進來。程式必須有辦法確認回調真的來自金流商，而且內容沒有被改過。常見的漏洞有五種：

1. 金流商有提供回調簽名，程式沒有驗。
2. 有驗簽，但簽名內容不包含金額或狀態。看過一次合法回調的人可以改金額或狀態後重送。
3. 有驗簽，但簽名內容不包含我方單號，程式又是用沒被簽名的單號找單。一筆合法回調改掉單號，就能套到另一張同金額的單。
4. 金流商用加密代替簽名，但解密函式為了相容未加密的 API 回應，對未加密的內容也放行，回調共用了同一個函式。
5. 金流商什麼都沒提供，程式也沒有補任何替代做法。

**正確做法**：金流商不一定有提供簽名，所以要求不是「一律驗簽」，而是「回調驗簽與來源 IP 白名單，至少要有一項由我方實際檢查」。金流商的安全設計不是我方能控制的。金流商兩項都不提供時，不算我方缺陷，改標為「不建議對接的金流商」，由 PM 決定是否繼續使用。依金流商提供的能力決定：

| 金流商的情況 | 要做的事 |
|---|---|
| 有提供回調簽名 | 必須驗，比對用 `hash_equals()`。驗簽前先用 `findMissingCredentials()` 確認密鑰已設定，密鑰是空的時候簽名可以離線算出來 |
| 簽名不含我方單號 | 找到單之後，比對單上存的三方單號與回調帶的三方單號是否相同 |
| 沒有簽名，有查單 API | 回調後向金流商查單，以查到的狀態與金額為準 |
| 沒有簽名，內容有加密 | 回調路徑要求內容必須是加密結構，不是就拒絕。不要和解讀 API 回應共用會放行未加密內容的函式 |
| 沒有簽名，有提供回調來源 IP 清單 | 在程式內限制回調來源 IP，白名單沒設定時一律拒絕。在該金流商的文件記明「真實性只靠來源 IP」 |
| 簽名與來源 IP 清單都不提供 | 不算我方缺陷。在該金流商的文件與風險報告標明「不建議對接」，交給 PM 決定 |

回調路由掛的 `DetectIp` 只記錄來源 IP，不做比對，正式站的入口也沒有限制來源 IP。所以來源 IP 的限制必須在程式內做，不能假設部署層會擋。Dev 環境能收到回調，只能證明金流商的 IP 連得進來，不能證明其他 IP 會被擋下。

**怎麼發現**：對每一家回答三個問題。回調進來後靠什麼確認是金流商送的？那道防線保護了哪些欄位？程式拿來找單、判斷成功、決定金額的欄位，是不是都在被保護的範圍內？

## 六、回調金額的比對有缺口

**現象**：會員少付卻照存款單金額全額入帳，或回調帶什麼金額就入帳什麼金額。

**成因**：共用的 `updateDepositOrderSuccess()` 會拿傳入的金額與存款單金額比對，不同就轉狀態 4。缺口出在傳進去的是什麼：

1. **比錯欄位**：金流商回調同時帶「請求金額」與「實付金額」，程式傳的是請求金額。請求金額是我方下單金額的回聲，比對一定相符。
2. **缺欄位時不比對**：金額欄位取不到時傳 null，共用方法遇到 null 會跳過比對；或取不到時改拿存款單自己的金額去比。
3. **完全不比對**：刻意傳 null，或沒有呼叫共用方法也沒有自己比。
4. **拿未受保護的金額改寫存款單**：回調金額沒有被簽名或查單保護，程式卻直接用它覆寫存款單金額並重算入帳金額。

**正確做法**：

- 金流商回調有實付金額欄位時，比對要用實付金額。兩個欄位的語意要向金流商確認，也要拿正式站的歷史存款單核對。名稱像「最終金額」的欄位，可能是扣掉金流商手續費後的商戶實收，不是會員付了多少；拿它來比對，每一筆都會被判成金額不符。
- 成功回調缺少金額欄位時，拒絕或轉待人工確認，不要當成金額相符。
- 沒有被簽名或查單保護的金額，不可以直接拿來改寫存款單或入帳。
- 金流商會在金額上加零頭、需要以實付金額入帳時，設定可接受的差額上限，超出上限轉待人工確認。重算入帳金額的公式要和建單時的 `OrderService` 一致。

**怎麼發現**：看 `updateDepositOrderSuccess()` 的 `amount` 參數傳了什麼，再對照金流商文件的回調欄位表，確認那個欄位是不是實付金額。搜尋回調程式內有沒有直接寫入 `amount` 或 `point`。

## 七、敏感資訊外洩

**現象**：金鑰、登入密碼、認證 token、會員的收款帳號與戶名出現在 log、版本庫或會員看得到的錯誤訊息裡。看得到的人就拿得到，拿到金鑰之後，即使是有驗簽的金流商也能被偽造回調。

**成因**：

- 送出請求用的 `Http::logAction()` 會記錄請求與回應的內容。內容的遮罩要呼叫端自己帶 `maskKeys` 才會生效，沒帶就原樣寫出。金流商把金鑰放在請求內容裡時，就整包進了 log。
- 請求標頭有內建遮罩，但只認得清單內的標頭名稱。金流商用自訂標頭帶金鑰時不會被遮。
- 驗簽失敗時為了除錯，把組簽名的原始字串或正確的簽名寫進 log。原始字串裡含密鑰。
- 連線失敗時，把金流商的完整網址與原始回應塞進錯誤訊息，這段訊息會直接回給會員。
- 初始化資料檔（`app/Console/Commands/CashFlow/Data/providers/`）或程式註解裡留了真實的商戶號與金鑰。進了版本庫就清不掉，版本歷史裡一直看得到。

**正確做法**：

- 請求內容若帶有金鑰、密碼、token，呼叫 `logAction()` 時帶上對應的 `maskKeys`。
- 自訂標頭帶憑證時，把標頭名稱加進 `MaskTrait` 的敏感標頭清單，不要在呼叫端另立清單。
- 驗簽失敗的 log 不寫組簽名的原始字串，也不寫我方算出的正確簽名。
- 回調內容進 log 前經過 `Common::maskCredentials()`。
- 回給會員的錯誤訊息只用固定的英文訊息，金流商網址與原始回應改寫進 log，寫之前先遮罩。
- 初始化資料檔的憑證欄位一律留空字串，憑證只在後台填。註解需要範例值時用明顯的假值。已經進版本庫的真實憑證，請金流商換發。

**怎麼發現**：看該金流商送出的請求參數與標頭裡有沒有憑證本身，再看對應的 `logAction()` 有沒有帶 `maskKeys`。搜尋驗簽失敗分支裡的 log 寫了什麼。搜尋 `ApiException` 的訊息裡有沒有拼接網址或回應內容。看初始化資料檔的憑證欄位是不是空的。

## 八、代付回調找單與狀態守衛

**現象**：代付請求逾時、但金流商其實已受理的單，之後的回調一直被拒收，提款單停在 21 等人工。或者已經是 29、已退款、已人工處理的提款單，被晚到的回調改寫。或者回調查不到紀錄時程式直接報錯，交易沒有回滾也沒有告警。

**成因**：

- 用「三方單號＋我方交易號」兩個條件一起查代付紀錄（`findAndLockPayoutRecordByThirdPartyNo()`）。三方單號只在同步回應受理時才寫回紀錄，請求逾時時它是空的，兩個條件就對不上。共用層的設計是「停在 21 的單由回調定案」，這個查法讓這條路走不通。人工若在此期間判成失敗並重新發起，就是重複出款。
- 取得提款單後沒有呼叫 `checkWithdrawalOrderStatus()`，不管提款單現在是什麼狀態都照回調改寫。
- 查不到紀錄時沒有分支處理，後續程式拿 null 去用而拋 `TypeError`。外層只接 `Exception`，`TypeError` 不是它的子類，接不到。
- 收到處理中或退款這類結果不明的回調時，把代付請求紀錄寫成「回調失敗」。

**正確做法**：

- 只用我方交易號查代付紀錄（`findAndLockPayoutRecord()`）。紀錄的三方單號是空的，就補寫回調帶來的值；不是空的，才比對兩者是否一致。
- 取得提款單後、改動之前，先呼叫 `checkWithdrawalOrderStatus()`；接到 `WithdrawalOrderException` 時回滾，並交給 `handleWithdrawalOrderException()` 回應。
- 查無代付紀錄時回滾並回失敗字串；外層改接 `Throwable`。
- 結果不明的回調回滾後直接回成功碼，不更新代付請求紀錄。
- 需要向金流商回查時，回查放在交易外，不要在持有資料列鎖的交易內打外部請求。

**怎麼發現**：看 `WithdrawalCallback.php` 找代付紀錄用的是哪個方法、帶了幾個條件。搜尋有沒有呼叫 `checkWithdrawalOrderStatus()`。看 `catch` 接的是 `Exception` 還是 `Throwable`。

## 九、放款前反查端點

**現象**：有些金流商在放款前，會回頭打我方的反查網址，確認「這筆代付是不是你們發的、要不要放款」。我方回的格式不是金流商要的，結果有兩種：金流商嚴格比對時，放款全數卡住；金流商只看 HTTP 200 時，我方的拒絕反而被當成放行。

**成因**：

- 各家的反查類別（`WithdrawalQuery.php`）回傳「回應字串＋HTTP 狀態碼」的陣列，控制器 `WithdrawalQueryController` 看到陣列就整包回成 JSON。金流商收到的永遠是 HTTP 200 加一段 JSON，不是文件要求的純文字，拒絕時的狀態碼也被丟掉。
- 反查驗簽的對象跟同一家其他地方不一致，例如對密文驗簽，其他地方卻是對解密後的明文簽名，驗簽可能永遠失敗。
- 反查比對金額時用原生浮點數。

**正確做法**：

- 控制器以回應字串當純文字內容、以反查類別給的狀態碼回應。
- 反查的驗簽對象與該家代付回調一致，先確認金流商簽的是明文還是密文。
- 金額比對走 `Common::numCompare()`。
- 測試要經過控制器，只測反查類別本身驗不到實際回給金流商的內容。

**怎麼發現**：看該家有沒有 `WithdrawalQuery.php`。有的話，對照金流商文件要求的回應格式，再看控制器實際回了什麼。

## 十、送給三方的請求內容有誤

**現象**：會員收到的款比提款金額少；金流商收到空的或錯的銀行碼；請求帶著寫死的測試手機號與 email；新站照初始化資料檔配置後，程式讀不到某個設定。

**成因**：

- 金額直接捨去小數，或用原生浮點數格式化。
- 查不到三方銀行碼時，仍把空字串送出去；或銀行碼根本沒有轉換成金流商要的代碼。
- 開發時的測試值（手機號、email、固定合成值）沒拿掉。
- 送出格式與官方規定不同，例如官方要表單格式，程式送 JSON。
- 初始化資料檔的設定鍵名，與程式實際讀的鍵名不一致。
- 前置步驟失敗（例如取認證 token 失敗）時，代付請求根本沒送出，提款單卻停在 21 等人工定案。
- 出站請求關閉了 SSL 憑證驗證。

**正確做法**：

- 金額格式化走 `Common::` 的運算方法。金流商不收小數時，在送出前擋下並回明確錯誤，不要捨去。
- 送出前取銀行碼，用 `=== ''` 判斷有沒有取到（`"0"` 是合法的銀行碼，不能用 `empty()`），沒取到就不送請求並回明確錯誤。這道檢查逐家加，而且只加在真正送出轉碼結果的分支，不放在共用層統一擋。有些代付路徑本來就不送轉碼結果，例如 DgPay、TtPay 的馬幣人工通道送的是銀行全名，共用層統一擋會誤擋這些合法的單。
- 請求裡的會員資料一律取自會員或訂單，不寫死。
- 初始化資料檔的鍵名以程式讀取的為準。
- 前置步驟失敗時回明確失敗，或把它移進請求階段，讓代付請求紀錄先建立。

**怎麼發現**：看 `Withdrawal.php` 與 `Deposit.php` 組參數的地方：金額怎麼格式化、銀行碼怎麼取、有沒有寫死的值。比對初始化資料檔的鍵名與程式讀的鍵名。

## 十一、錯誤處理與告警

**現象**：金流商回了非預期的內容，程式拋出 `TypeError` 或「未定義的陣列鍵」，訂單卡住，告警看不懂或根本沒發。或者失敗回調已經處理完，卻回失敗字串給金流商，金流商一直重送、告警一直響。或者告警寫的是另一家金流商的名字，排查的人找錯地方。

**成因**：

- 取外部回應的欄位前沒檢查欄位在不在、型別對不對。
- 告警與「結果不明」的處理只接 `Exception`，接不到 `TypeError` 這類 `Error`。
- 回應字串選錯：訂單已經在交易內定案，卻回失敗字串。
- log 與告警的前綴寫死成字串，子類別繼承之後沿用了母類別的名字。
- 回調缺少必要欄位時，程式直接報錯回 500，而不是文件規定的失敗回應。

**正確做法**：

- 取外部欄位先檢查存在與型別；缺欄位時走獨立分支，丟固定英文訊息的 `ApiException`。
- 需要攔下所有錯誤的地方改接 `Throwable`。
- 訂單狀態已在交易內定案後，一律回成功字串，讓金流商停止重送。
- log 與告警的前綴用 `$this->getDriverName()`，不寫死。
- 回調缺少必要欄位時，回文件規定的失敗回應。

**怎麼發現**：搜尋 `catch (Exception`；看處理外部回應的程式是不是直接取 `$response['欄位']`；搜尋寫死的金流商名稱字串；看失敗分支最後回的是成功字串還是失敗字串。

## 十二、文件與資料檔失準

**現象**：照文件排查或設定，結果與程式行為不符；文件寫的方法、欄位、狀態判定已經不存在或改了。

**成因**：

- 程式改了，文件沒有跟著改。最常見的是代付回調改成三態之後，文件還寫「不是成功就算失敗」。
- 文件從另一家金流商複製過來，名稱與設定鍵沒改。
- 沒有呼叫端的方法、走不到的分支、已標棄用的方法殘留在程式裡。

**正確做法**：

- 改程式的同一個 MR 一起更新該家的 `api.md` 與 `integration.md`。`api.md` 放金流商原文的整理，`integration.md` 記我方已驗證的落差與踩坑。
- 沒有呼叫端的方法與走不到的分支直接刪掉。

**怎麼發現**：逐項對照文件與程式。全面重審時用 apis-toolkit 的 `report-payment-audit` skill。

## 接新金流商時的檢查順序

1. 回調靠什麼確認是金流商送的？（第五類）
2. 那道防線有沒有涵蓋金額、狀態、我方單號？（第五、六類）
3. 回調的狀態碼裡有沒有非終態？代收、代付各自怎麼處理？（第三、四類）
4. 代付同步回應的哪些碼能證明沒有建單？（第一類）
5. 錯誤訊息的取值會不會是空字串？（第二類）
6. 請求內容、標頭、錯誤訊息、資料檔有沒有帶憑證或會員資料？log 有沒有遮？（第七類）
7. 代付回調用什麼找紀錄？有沒有檢查提款單狀態？（第八類）
8. 金流商有沒有放款前反查？回應格式對不對？（第九類）
9. 金額、銀行碼、會員資料怎麼放進請求？有沒有寫死的值？（第十類）
10. 金流商回了非預期內容時，會不會報錯卡單？告警看得懂嗎？（第十一類）
11. 文件與初始化資料檔跟程式一致嗎？（第十二類）
