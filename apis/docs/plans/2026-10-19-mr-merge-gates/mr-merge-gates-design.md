# MR 合併關卡改造：設計

這份文件記錄 MR 合併前三道關卡改成 CI 檢查的已定案決策。工單：target/ticket_tasks#1837（主單 target/tickets#4519）。「PM 確認」檢查的現行實作見 MR !2436（`.gitlab-ci/pm-confirm/`）。比較圖（現在／改善後／優化後三欄）：https://claude.ai/artifact/5FJgb5Aw4UKd3PMzBzNxCH

## 前提

| 決策 | 理由 |
|---|---|
| 專案設定開啟「Pipelines must succeed」，不把 skipped pipeline 當成功；master 禁止直接 push | GitLab 社群版不能強制核准，pipeline 是唯一擋得住合併的地方，這兩項設定是 CI 關卡生效的前提 |
| 這套檢查只防疏忽，不防刻意繞過 | 檢查程式在 MR 自己的分支裡，作者改得到；要防刻意繞過，得另外由可信的伺服器端控制 |

## 三道關卡

| 決策 | 理由 |
|---|---|
| 審核人核准、PM 確認、QA 驗收三道關卡都改成 CI 檢查 | 交給 pipeline 判斷，人不必記得哪一步還沒做 |
| 三道檢查拆成三個 CI 工作（job），各有自己的試行／正式開關 | 一道誤擋時只關那一道，不影響另外兩道 |
| 不再手動按 ▶ 執行檢查 | 檢查隨 MR pipeline 自動跑 |
| 三道都切到正式模式的 repo，才不再開 Draft；還有任何一道在試行，就照舊用 Draft | 試行模式下檢查沒過也能合併，這時 Draft 仍是唯一的擋板 |
| 切到正式模式時，所有待合併的 MR 都要開新的 MR pipeline | 模式在 pipeline 建立時就決定，舊 pipeline 重試仍是原本的模式（`pm-confirm.yml` 檔頭說明） |
| 合併維持人工按 | 合併時機（例如週五不合）仍由人決定 |

## 重新檢查

| 決策 | 理由 |
|---|---|
| 條件補齊或有變動後，作者按「Run pipeline」開一條新的 MR pipeline，不按「重試」 | 重試只重跑失敗的工作，已經通過的關卡不會重查；新 pipeline 三道全部重查。代價是 test 也會重跑（約 9 分鐘） |
| 合併後檢查照樣保留，抓「合併前沒有重查」的情況 | 手動重查會有人忘記，合併後檢查是補位 |
| webhook 自動觸發重查留到第二階段 | 要另外架接收服務並準備寫入權杖；社群版會不會把跨專案的父子單變動都發出來，還沒驗證 |

## 各關卡的通過條件

| 關卡 | 通過條件 | 理由 |
|---|---|---|
| 審核人核准 | 沿用現有規則：改到的每個領域，名單取聯集，作者以外任一人核准即過；既有的 PHP 檔只改註解或排版的免核准 | 沿用已生效的審批制度，不改規則 |
| PM 確認 | 完整沿用 MR !2436 的規則：主單有「0. PM確認」，且最後加上它的人在 PM 名單裡；豁免條件同 !2436 | QA 與 PM 共用同一套工單解析，免得兩套各自漂移 |
| QA 驗收 | 主單底下標題含「- 測試」的子單全部關閉，關閉的人屬於 `team-roster.yaml` 的「測試」群組，且關閉時間晚於 MR 最後一次推 commit 的時間 | 比照 PM 確認檢查「加標籤的人必須是 PM」的做法，防止作者自己重開再關；用時間先後對應版本，QA 的作業方式不用改 |
| QA 驗收：沒有測試子單 | 查詢完整成功、確定一張都沒有，才直接通過；查詢出錯或結果不完整一律不通過 | 查詢失敗不能當成零張 |
| QA 驗收：豁免 | 和 PM 確認共用同一份豁免規則：全部 commit 都是 docs／style／chore／test／revert 免檢；只掛線上問題單的 MR，每張都查得到就免檢 | 這些 MR 沒有功能可測，線上問題單也沒有測試子單的流程；共用一份規則，兩道才不會各自漂移 |
| 多張主單 | 每張主單都要通過 | 同 PM 確認現行做法 |
| 一張主單掛多張 MR | 任一張 MR 推新 commit，整張主單的測試子單都要重測；子單重開期間，同主單的其他 MR 也暫時不通過，這是刻意接受的代價 | 一張主單通常就是一個功能，任一邊的程式改了，QA 本來就該重測整個功能 |

## hotfix

| 決策 | 理由 |
|---|---|
| 三道關卡的 hotfix 都只認分支名稱 `hotfix/` 開頭，不再認「hotfix」標籤 | 分支名稱在開分支時就定了，事後不能隨手貼上來繞過；每個人、每支工具都看得到 |
| 核准檢查的 hotfix 放行後，照舊發 Slack 提醒審核人在 1 個工作天內補審 | 緊急放行仍要有人事後看過 |
| 核准檢查從認標籤改成認分支名稱前，先通知 RD | 這是已經生效的規則，改了會影響 RD 的急修流程 |

## 推新 commit 之後

| 決策 | 理由 |
|---|---|
| 審核人核准失效，須重新核准（維持現行） | 審過的不是最新的程式 |
| QA 驗收也失效：要由測試群組的人重開子單、測完再關 | QA 測過的不是最新的程式 |
| 新增「合併後檢查 PM 確認」，比照現有的「合併後檢查核准」 | 只改 MR 描述不會重跑 pipeline；合併後檢查只能事後發現問題，擋不了合併 |
| 合併後檢查 PM 確認，查的是「合併當下」主單有沒有「0. PM確認」：用標籤異動紀錄，以合併時間截斷 | 查現在的狀態的話，合併後才補貼會被當成通過，合併後正常移除又會被誤報；合併後檢查核准也是用合併時間截斷 |

## Slack 通知

| 決策 | 理由 |
|---|---|
| 另開一個「待審 MR」頻道，通知都發在這裡 | 不混進既有討論頻道 |
| RD 確認最後一版時，Agent 在 RD 的 session 裡問「要發嗎」，每張 MR 都問；回答要發就 tag QA | 這是 RD 本來就要做的確認，不算打斷 |
| 這張 MR 不需要 QA（沒有測試子單，或 hotfix）時，回答要發就不 tag QA，改成直接 tag 審核人與 PM | 沒有「QA 關子單」這個動作，通知要在同一個提問裡補上，不另外加機制 |
| RD 回答「不要」：只在下次部署、或 RD 主動要求時再問 | 避免同一張 MR 一直被問 |
| RD 回答「都不用發」：在 MR 貼「不自動通知」標籤，之後不再問；這個標籤只管通知，不影響檢查 | 用標籤記住決定，換 session 也不會再問 |
| QA 關閉測試子單時，由 QA 自己在頻道 tag 審核人與 PM | QA 最清楚什麼時候測完 |

## 推行順序與前置工作

| 決策 | 理由 |
|---|---|
| 先在 APIs 試行，跑穩再搬到 agent-backend | 先在一個專案確認不會誤擋 |
| 「跑穩」的條件：試行至少 2 週，期間的誤擋都已修好，而且最後 1 週沒有新的誤擋；每道關卡各自計算，達標的那道就可以切正式 | 有明確的終點，又留有觀察期 |
| `team-roster.yaml` 補每個人的 `slack_id` | Slack tag 人需要 Slack 帳號 id |
| 「待審 MR」頻道由 RB 建立 | 由 RB 決定頻道成員與設定 |
| 三道都切到正式模式的 repo，release-workflow 開 MR 時不再開成 Draft | Draft 已不是關卡，留著只會多一步手動拿掉 |

## 實測依據

- pipeline 層的「重試」會重跑 `allow_failure` 失敗的 CI 工作：pipeline 狀態是 success 時照樣有效。成功的工作不會重跑。實測對象是 MR !2436 的 pipeline 53189：「需要審核人核准」工作 357713（`allow_failure`、failed）重試後產生新工作 357784；「PM 確認檢查」工作 357668（success）沒有重跑。
