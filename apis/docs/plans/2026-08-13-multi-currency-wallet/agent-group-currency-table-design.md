🔴 **三個判讀要點**（屬實作範疇，不寫進 `GLOSSARY.md`）：

1. **可用幣別在第一版不是關卡**（決策 4），只有預設幣別真的生效；要到第五期 5.3 才成為關卡。唯一的例外是會員互轉（09-09 RB 裁決，見 11.5），那一個點會提前用到它。
2. **入帳比例的方向是「1 單位通道幣別 → 多少錢包幣別」**，`OrderService.php:76` 直接 `$amount × $rate`。方向寫反就是金額直接錯。
3. **「組別」單獨出現時一律指代理組別**；講幣別組別或支付組別要把前綴寫全，因為一句話裡常常同時出現兩種。

⚠️ 一個已知但**不在本案處理**的混用：`AgentVendor` 模型把 `agent_id` 的註解寫成「營運商系統編號」，而同一張 `agents` 表在其他地方都稱「代理」。範圍超出多幣別案，只記錄不修。

## 1. 為什麼不直接填舊欄位

`organizations.currency_id`（組織的幣別欄位）目前有四條取值路徑在讀。所以「把它填一個值」不是單純填一個值，而是一次改變四件事：

| 取值路徑 | 誰在用、用來做什麼 | 這次之後 |
|---|---|---|
| `Member::currencyId()`（`app/Models/Member.php:323-328`）**直接讀** | 決定新會員的錢包算哪個幣別 | **改讀新表** |
| `Agent::currencyId()`（`app/Models/Agent.php:233-238`）**直接讀** | 被下面兩個服務當取值來源 | 🔴 **不動，繼續讀舊欄位**（原因見下方警語） |
| ↳ `MemberRegisterLimitService.php:247` **經 Agent accessor 間接讀** | 查註冊限制（例如同一個 email 能不能重複註冊） | 不動 |
| ↳ `MemberFieldSettingService.php:433` **經 Agent accessor 間接讀** | 查註冊頁與登入頁要顯示哪些欄位 | 不動 |
| `AuditOrphanParentCommand.php:90` **直接讀** | 每日稽核判「這個會員的幣別解析得出來嗎」 | **要跟著改**（見第 6 節） |
| 舊後台的股東報表（在 API_Agent 專案，APIs 這邊碰不到） | 把下線業績換算成美元寫進報表 | 不動 |

> 🔴 **這裡有一個很容易踩的坑（09-08 Bonn 校閱抓到）**
>
> `agents` 資料表**沒有** `currency_id` 這個欄位。所以程式裡寫 `$agent->currency_id`，實際上跑的是 `Agent::currencyId()` 這個取值方法，而它讀的就是組織的幣別欄位。
>
> ⇒ **只要 `Agent::currencyId()` 改讀新表，註冊限制與註冊欄位設定就會跟著改讀新表**，本文件想避開的副作用就原封不動回來了。
>
> ⇒ 所以設計是：**只改 `Member::currencyId()`，`Agent::currencyId()` 一個字都不動。** 兩者是各自獨立的方法，Member 版直接讀組織、不經過 Agent 版，所以改一個不會動到另一個。

「一次改變四件事」的實際後果，用 Task 7 的十個組織來看：只要把舊欄位從 0 填成 MYR，底下的註冊限制就會**立刻開始生效**。受影響的代理數以 `phase2-organization-currency-proposal.md`（已刪，見第 62 行附近的 git 查閱點）（已被本檔取代、09-18 刪除，原文 `git show 05e3a4d30:docs/plans/2026-08-13-multi-currency-wallet/phase2-organization-currency-proposal.md`） 為準（⚠️ 該檔對 vworldbn 有 573／580／581 三個口徑未收斂，影響盤點 8.4 另有一種算法給 111，引用前要先確認口徑）——重點不是數字大小，而是**這跟多幣別錢包一點關係都沒有，是被順便打開的**。

把「錢包幣別」這一件事搬到新表、而且**只搬 Member 那一條路徑**，其餘三條原地不動。**這樣建列就不會打開註冊限制那些設定。**

## 2. 這個設計長什麼樣子：比照現有的代理組別模式

專案裡已經有一套成熟的「組別」模式，這次直接沿用，不發明新的。

**現有模式的三個部件**（09-09 六站唯讀實查）：

| 部件 | 實例 |
|---|---|
| `agents` 上一個 `xxx_group_id` 欄位 | 共七個：`customized_setting_group_id`、`cash_flow_group_id`、`sms_gateway_group_id`、`chat_group_id`、`vendor_customize_group_id`、`member_field_setting_group_id`、`email_gateway_group_id`（`app/Models/Agent.php:82`、`:84`） |
| 組別主表 `agent_groups`（表註解「代理設置分組組別」） | 用 `agent_group_type` 區分用途，**登記處是 `app/Enums/Agent/AgentGroupTypeEnum.php`**：1 個性化設置、2 支付設置、3 簡訊、4 聊天、5 遊戲商個性化、6 註冊登入設置、7 電子郵件設置。每列自帶 `organization_id`（所屬組織）與 `is_default`（是否為預設組別）。⚠️ **資料庫欄位註解只寫到 4，已經過期**，要看號碼一律以 Enum 為準 |
| 明細表帶 `agent_group_id` | 例如 `vendor_customized_items.agent_group_id`，欄位註解直接寫「代理組別 vendor_customize_group_id」 |

**幣別照這個模式落地**：

```
會員 → 他的上層代理 → 代理掛的幣別組別 → 組別底下標記為預設的那個幣別
members.parent → agents.currency_group_id → agent_group_currencies(is_default=1, status=1) → currencies.id
```

⚠️ **跳數與舊鏈相同（都是兩跳）**：舊鏈是「代理 → 組織 → 組織的幣別欄位」，新鏈是「代理 → 組別 → 組別的幣別明細」。改掛組別**不會讓查詢變快**，它換來的是粒度，不是效能。（09-09 Bonn 校閱更正：原稿寫「少一跳」沒有出處，且與本檔第 6 節「跳數沒有增加」自相矛盾；舊鏈跳數定義見影響盤點。）

### 掛組別比掛組織好在哪

| | 掛組織（09-08 原設計） | 掛組別（09-09 改採） |
|---|---|---|
| 粒度 | 一個組織只能有一種預設幣別 | **同一個組織底下，不同代理樹可以有不同的幣別設定** |
| 與現有系統的一致性 | 新開一張跟誰都不像的表 | 跟其他五種代理設定同一套模式、同一個後台管理方式 |
| 組織這一層還在嗎 | 是主體 | 仍然在——`agent_groups` 自帶 `organization_id`，只是不再是唯一的分界 |
| 代價 | 每個組織建一列即可 | **每個代理都要指定組別**，六站十萬級代理要回填 |

⭐ 粒度變細對 vworldbn 這種情況直接有用：那個組織底下除了主樹之外另有一棵 `vsmy88` 樹，掛組織時兩棵只能共用一種幣別，掛組別就能分開設。

## 4. 上線順序（五步，做完一步才做下一步）

1. **建表與加欄位** — 建 `agent_group_currencies`，`agents` 加 `currency_group_id`（預設 0）。此時沒有任何程式讀它們，零風險。
2. **建組別** — 在 `agent_groups` 建 `agent_group_type = 8` 的列，每個組織至少一個；需要分樹的組織可以多建幾個。
3. **建幣別明細** — 每個組別建列。已經有幣別值的組織直接把舊欄位的值搬過來；幣別是 0 的十個組織逐個決定（見第 7 節）。
4. **回填代理** — 把 `agents.currency_group_id` 指到對應組別。🔴 **前置條件：建代理的四個入口必須先改好並發版**（見 11.4），否則回填完成後新建的代理又是 0，稽核永遠歸不了零。

   回填本身不需要爬代理樹——每個代理身上都有 `organization_id`，按組織對應即可（分批跑）：

   ```sql
   UPDATE agents a
     JOIN agent_groups g ON g.organization_id = a.organization_id
                        AND g.agent_group_type = 8
      SET a.currency_group_id = g.id
    WHERE a.currency_group_id = 0;
   ```

   ⚠️ 這段是草稿、**未在任何環境跑過**：一個組織若有多個 `type = 8` 組別，這句會撞到多重匹配，實作時必須補上「每個組織只取一列」的條件。需要分樹的少數子樹（例如 vworldbn 組織下的 vsmy88）另外用 `hierarchy_path` 前綴單獨指定。
5. **稽核驗證再切換** — 跑命令掃三種錯（代理沒指組別、組別沒預設幣別、組織對不起來），數字都必須是 0，才讓 `Member::currencyId()` 改讀新表。

⚠️ **第 5 步是不可逆的分水嶺**：切換之後，指不到組別、或組別沒有預設幣別的代理，底下就建不了錢包。所以第 5 步之前的數字必須真的是 0，不能「大致上都建好了」。

**現在能做到哪一步**：第 1～2 步可以馬上開工。第 3 步之後卡在兩個組織還沒有答案——vworldbn 與 MMGames（等業務回答）。GFF USDT 已於 09-09 解除（見第 7 節）。

## 5. 表結構

### 5.1 新表 `agent_group_currencies`

```php
SchemaMonitor::create('agent_group_currencies', function (Blueprint $table) {
    $table->bigIncrements('id')->comment('流水號');
    $table->integer('agent_group_id')->comment('代理組別ID (agent_groups.id，agent_group_type=8)');
    $table->integer('currency_id')->comment('幣別ID (currencies.id)；不接受 0');
    $table->tinyInteger('is_default')->default(0)->comment('是否為該組別預設幣別 0:否 1:是');
    $table->smallInteger('display_unit')->default(1)->comment('顯示單位 1:元 1000:千元；只影響呈現，帳本一律存元');
    $table->tinyInteger('status')->default(1)->comment('狀態 0:停用 1:啟用');
    $table->timestamp('created_at')->useCurrent()->comment('建立日期');
    $table->timestamp('updated_at')->useCurrentOnUpdate()->useCurrent()->comment('更新日期');
    $table->integer('admin')->default(0)->comment('更新者ID');

    $table->unique(['agent_group_id', 'currency_id'], 'uk_agent_group_currency');
    $table->index(['agent_group_id', 'status'], 'idx_agent_group_status');
});
```

### 5.2 `agents` 加欄位

```php
$table->integer('currency_group_id')
      ->default(0)
      ->comment('幣別設置組別ID (agent_groups.id，agent_group_type=8)；0=未設定')
      ->after('member_field_setting_group_id');

$table->index('currency_group_id', 'idx_agents_currency_group_id');
```

⚠️ `agents` 是十萬級的表（VWorld 76,997、TPower 44,725），加欄位要走 `ALGORITHM=INSTANT`，比照第一期對 `member_wallets` 的做法。

🔴 **索引不可省**（決策 15）。後台要能回答「哪些代理屬於這個組別」，沒有索引就是全表掃描。`agents` 上現有的七個組別欄位每一個都有自己的索引，這是專案既有慣例。加索引不是 INSTANT 操作，但這張表只有十萬列量級，屬於秒級的 online DDL（**耗時未實測**）。

### 5.3 逐項說明

| 欄位／設定 | 說明 |
|---|---|
| `is_default`（明細表） | 這是第一版唯一真的會被讀的欄位。查「這個組別的預設幣別」就是查 `is_default = 1` 且 `status = 1` 的那一列 |
| `is_default`（`agent_groups`） | 這是**另一件事**：標記「這個 type 底下哪一個組別是預設組別」。09-09 實查 VWorld：每種 type 全表只有 1 列標記，語意是全站唯一而不是每組織一個。幣別 type 要不要照這個做，開工時再定 |
| `display_unit`（09-17 新增，決議㉜） | 千分制是顯示方式，不是另一種幣別。這一欄記「這個組別的這個幣別要用元還是千元呈現」，取值 1 或 1000（實作時封裝成 Enum，不寫魔術數字）。**後端所有金額運算、儲存、API 回傳一律是元，這一欄完全不參與計算**；API 把它跟金額一起帶出去，由前端負責格式化，以及把玩家輸入的「50」換成 50,000 再送出。後台 SR 報表的顯示單位也讀這一欄，玩家端與該組代理看到的數字才會一致。因為唯一鍵是「組別＋幣別」，同一組別不可能同時出現 VND 與 KVND 兩種呈現。🔴 這一欄可以事後修改而不影響帳，這正是它不該參與計算的原因 |
| `status` | **第一版沒有任何程式讀它**，是為第五期的允許清單預留的。刻意先放進去，因為第五期一定會用到，而且這張表很小、加欄位的成本低。⚠️ 若第五期最後沒用上，它就是死欄位，屆時要刪掉而不是留著 |
| 唯一鍵 | 「同一個組別不能對同一種幣別建兩列」。這是全案最不可改的東西，上線後要改就是大工程 |
| 不建外鍵 | 比照設計決策 19（專案既有做法） |
| 沒有 `rate` 欄位 | 匯率已經有兩個地方在記（金流商設定、遊戲商設定），第三個會是災難 |
| 沒有 `currency_code` 字串欄位 | 只存編號。同時存編號和文字代碼，兩邊遲早會對不上（`vendor_infos` 已經為此付出過代價） |

## 8. USDT 對應 USD（09-09 RB 裁決）

> ⛔ **09-17 整節撤回（決議㉚）**：與 PM 開會後 RB 改判 **USDT 是獨立的錢包幣別，不對應 USD**；TON 這類不錨定美元的虛擬貨幣也可以開戶，由 `agent_group_currencies` 的勾選決定。已進 master 的落地（別名契約 `'USDT' => 'USD'`、`CurrencyEnum` 白名單排除 USDT）要改回。8.1 的旁證數字與 8.2 的稽核假警報分析仍是事實，但不再支持任何現行決策；以下原文保留供追溯。

**裁決**：USDT 就是對應 USD 幣別。原本懸著的「加密貨幣算不算錢包幣別」這一題，到此解除。

**落地方式**（比照 `HKB → HKD` 的處理，見決議㉔）：

| 項目 | 處置 |
|---|---|
| 別名契約 `database/data/currency_aliases.php` | `normalize` 加 `USDT => USD`，並把 `USDT` 從 `crypto` 分類移出 |
| `vendor_infos.currency` 字串 | **不動**。字串直接進三方 payload，這是既有約束 |
| `vendor_infos.currency_id` | 解析成 USD 的編號（版控 id 23） |
| GFF USDT 組織（VWorld 20） | 幣別組別的預設幣別＝USD |
| `currencies` 主檔的 `USDT`（id 10） | 保留該列、本期不動；它不再是解析目標，是否停用另議 |
| `TON`（id 20）、`BUSD`（id 13） | 🔴 **不比照**。TON 的換算率是 1.36～1.8（代收 1.36／代付 1.5，實測區間）、不錨定美元，當成 USD 會讓金額尺度直接錯掉；BUSD 主檔已是停用狀態。兩者維持 `crypto` 分類、不作為錢包幣別 |

**影響面**（09-09 VWorld 唯讀實查）：

| 幣別字串 | 商戶數 | 啟用中 | rate |
|---|---|---|---|
| `USD` | 29 | 14 | 全部 1 |
| `USDT` | **4** | **2** | 全部 1 |
| `TON` | 0 | 0 | — |
| `BUSD` | 0 | 0 | — |

兩邊 rate 都是 1，所以**不需要做任何金額換算**——這與 GFF USDT 帳本單位的推算結果一致（該組織的 USDT 通道換算率就是 1）。

### 8.1 這個裁決的旁證（09-09 實查）

VWorld 那 4 家 USDT 商戶全叫 `WM-fongamer`、`MT(fongamer)`、`SpadeGaming-fongamer`、`Funky-fongamer`；而 USD 商戶裡也有一大批同業務線的（`PNG-Fongamer`、`JDB-fongamer`、`FaChai-fongamer`、`CQ9-fongamer`、`PGSoft-fongamer`、`PPlive-fongamer`、`SG-fongamer` 等）。**同一條 fongamer 業務線，只是不同遊戲商填了不同字串** ⇒ 本來就該是同一種幣別。

✅ **「一幣別一商戶」不會被打破**：實查**沒有任何 `vendor_id` 同時掛 USD 與 USDT**，正規化後不會產生「同一遊戲商同一幣別兩列」。

### 8.2 部署空窗期的稽核假警報（09-09 Bonn 校閱提出）

🔴 **別名契約上線之後、該站補上 USD 主檔列之前，每日稽核會由綠轉紅。**

原因：USDT 原本落在 `crypto` 分類（`currency_id = 10`、**不阻斷**）；改 normalize 成 USD 之後，該站主檔還沒有 USD 那一列 ⇒ 判定變成 `enum_only`（`currency_id = null`）。而 USDT 有 **2 家啟用中商戶**，依 `AuditVendorInfoCurrencyCommand.php:73-79` 會計入 `blocked_codes` 並讓命令**回傳非零退出碼**。

⇒ **要先告知 ops 值班**：這段期間的紅燈是預期中的部署空窗，不是新缺陷；補上 USD 主檔列（跑 seeder）之後就會恢復。**最乾淨的作法是讓別名契約與主檔 seeder 同批部署**。

🔴 **前置條件**：VWorld 生產庫目前**還沒有 USD 這一列**（09-09 實查，該站 `currencies` 只有 USDT 10、FON 11、BUSD 13 停用、TON 20）。USD 是 09-07 才進版控的 id 23，**要等 MR !2156 合併並部署到該站之後**，這條裁決才落得了地。

## 11. 繼承與後台操作（09-09 釐清）

> 這一節回答四個問題：新代理的組別從哪來、改了設定誰會跟著變、只想關掉一個幣別要按幾次、這些後台功能建在哪個專案。

### 11.1 新代理的組別從哪來

**做什麼**：建立代理時，把上層代理的 `currency_group_id` 複製一份給新代理。

**為什麼**：這是專案現有的作法。`agents` 上另外七個組別欄位全部都這樣處理——舊系統建代理的程式碼有一段註解直接寫著「以下這些設定 預設會與上級一致」，底下逐欄複製上層的值。資料也支持：VWorld 七萬多個代理裡，聊天、遊戲商個性化、會員欄位設定這三個組別欄位，停在資料庫預設值的是**零個**，每個代理身上都有實際的值。

**不採哪一種**：讀取時沿著代理鏈往上找第一個有值的祖先。那是 `agent_vendors` 這類明細表在用的機制，`agents` 上的單一組別欄位從來不走那套。採用它有兩個後果：`currency_group_id` 會變成 `agents` 上唯一一個讀法與眾不同的欄位；後台也無法再用一句 SQL 反查「哪些代理屬於這個組別」。

**要注意什麼**：頂層代理沒有上層可複製，必須人工指定。

### 11.2 改了設定，誰會跟著變

兩種「改設定」的傳播範圍完全不同：

| 改什麼 | 誰會跟著變 |
|---|---|
| **組別的幣別清單**（在 `agent_group_currencies` 加減一列） | 所有指向這個組別的代理**立即生效**，不需要任何同步動作 |
| **某個代理指向哪個組別**（改 `agents.currency_group_id`） | **只有被改的那一個**；它底下已經存在的代理維持原值 |

第一種會自動傳播，是因為建代理時複製的是「指向哪個組別」這個編號，不是幣別清單本身。清單只有一份，存在組別上。

第二種是換組別，已經存在的下層不會跟著換——這是現有七個欄位共同的行為，資料上看得到不一致的實例（見附錄）。所以**指派組別的端點必須提供「是否一併套用到下層」的選項**，前例是舊後台改遊戲商設定時的 `data_switch` 參數。

```sql
-- 一併套用到下層
UPDATE agents SET currency_group_id = ?, updated_at = NOW()
 WHERE id = ? OR hierarchy_path LIKE CONCAT(?, '/%');
```

⚠️ 最大的子樹涵蓋三萬多個代理，這句要分批，不能一次跑完鎖住整張表。

⭐ 一個降低風險的事實：**切換組別不會改變已經建好的錢包**。錢包建立時就把幣別寫進自己的欄位，之後不再回頭看代理設定。所以子樹要不要一併套用，影響的只有之後才註冊的會員。

### 11.3 只想關掉一個幣別，要按幾次

**問題**：組別是共用的。想讓某個代理少用一種幣別，照字面走要做五件事——建新組別、把原組別的幣別清單複製過去、改掉那一列、指派給該代理、再處理下層。只為了關一個幣別。

**做法**：後台不要求操作者理解「組別」這層。他在代理的幣別頁面直接勾選幣別，系統判斷怎麼落地：

| 情況 | 系統動作 | 操作者看到 |
|---|---|---|
| 這個組別只有他一個代理在用 | 直接改組別的幣別清單 | 「已更新」 |
| 這個組別還有別的代理在用 | 自動複製一份專屬組別，再指派給他 | 「已為此代理建立專屬設定」 |

**要注意什麼**：

1. 判斷「是不是唯一使用者」要在交易內鎖定，否則兩個管理員同時改同一個組別會互相覆蓋。
2. 這會讓組別數量隨微調成長。配兩個機制就夠：組別列表顯示「使用中代理數」（欄位有索引，一句 `COUNT` ＋ `GROUP BY`），以及儲存時若內容與某個現有組別完全相同就提示可直接沿用。
3. 舊後台已經有「從既有組別複製建立」的功能，但它是逐 type 寫死的分支，**目前不認得幣別組別**，複製出來會是空組別。要沿用就得補一段；不補的話 APIs 自己寫。

### 11.4 後台功能建在哪個專案

**做什麼**：幣別組別的後台功能全部建在 APIs，舊系統只加建代理那幾行。

**為什麼**：`agent_group_currencies` 是新表、`agent_group_type = 8` 是新號碼，舊系統既有邏輯完全碰不到它們，不會出現兩邊都要維護同一件事。前例是電子郵件組別（`type = 7`）的設置功能，已經建在 APIs，舊系統沒有跟著改。

**唯一必須改舊系統的地方**：建代理。代理是在舊後台建立的，APIs 攔不到。舊系統三個入口各加一行複製 `currency_group_id`，APIs 自己也有一個建代理路徑（會員升級為代理）要一併加。這一行不改變任何既有行為，但仍要走舊系統的發版排期，而且**必須排在回填之前**（見第 4 節第 4 步）。

**要新建的端點**（形狀可參考 APIs 現有的電子郵件組別路由）：

| 端點 | 做什麼 |
|---|---|
| 組別下拉 | 列出 `type = 8` 的組別給選單用 |
| 組別列表／新增／修改 | 組別本身的維護 |
| 組別複製 | 11.3 的自動複製靠它 |
| 幣別清單維護 | 增減組別的幣別、設定預設 |
| 指派給代理 | 帶「是否套用到下層」選項 |

**要注意什麼**：

1. 幣別是全新功能，沒有舊介面契約要相容，request／response 可以直接用 APIs 的現代寫法。
2. 代理指派若沿用舊後台的「編輯代理」表單，那支仍在舊系統。建議獨立成新端點，前端在幣別頁單獨呼叫，不去動既有表單。
3. 舊後台的組別列表**看得到** `type = 8` 的組別，管理員可能誤操作（例如按複製，得到空組別）。已規劃的稽核第二種錯（組別沒有預設幣別）正好擋這個，不需要另外做機制。
4. APIs 端要自己實作組別的組織範圍權限判斷，不能只搬 CRUD。

### 11.6 `agent_cash_flows` 的唯一鍵（09-10 拍板：不補）

**裁決**：加 `wallet_currency_id` 時**不補唯一鍵**，改補非唯一複合索引 `(agent_group_id, status, wallet_currency_id)`。

**理由：這張表在業務上不存在唯一性。**

一列 `agent_cash_flows` 代表的是「某個支付組別下的一個金流商商戶帳號」，不是「一條通道」。同一個組別、同一家金流商、同一種通道幣別，本來就可以掛好幾列——差別在 `name` 與 `info` 裡的商戶憑證。任何以「組別＋金流商＋幣別」為基礎的唯一鍵，都會把合法的多商戶分流配置擋掉。

**兩站實測（09-10，`deleted_at IS NULL`）**

| 候選唯一鍵 | VWorld（323 有效列） | TPower（264 有效列） |
|---|---|---|
| `(agent_group_id, cash_flow_id, currency_id)` | 撞 48 組／142 列，最多 10 列 | 撞 50 組／162 列，最多 8 列 |
| 再加 `cash_flow_info_id` | 撞 48 組／140 列 | 撞 50 組／162 列 |
| 再加 `name` | 撞 8 組／16 列 | 撞 1 組／2 列 |

兩個關鍵事實：

1. **`cash_flow_info_id` 幾乎全是 0**（TPower 264/264、VWorld 286/323），當不了區辨欄位。
2. **`name` 加進去也沒用**——它是後台可改的顯示字串，且剩下的 8 組經查證全是不同商戶帳號（見下）。

**那 8 組「同名重複」其實不是重複**：逐列比對 `info` 的 MD5（只比雜湊，不讀憑證內容），12 列得到 **12 個相異雜湊**，沒有任何一對相同。TPower 唯一那組（組別 688、`id` 132/133）亦為 `distinct_info = 2`。⇒ 這些是同一家金流商的**兩個商戶號**，用途是分流或備援。

真正的區辨鍵是 `info`（TEXT 型別的憑證欄位），它進不了唯一索引，也不該進。

**索引的取捨**：`(agent_group_id, status, wallet_currency_id)` 涵蓋現有 `idx_group_status` 的前綴，可直接取代它，同時服務新的查詢面「這個代理的錢包幣別能用哪些通道」。⚠️ 誠實標註：此表目前只有 300 列上下，**索引現階段的效能效益接近零**，加它是為多幣別拆列後的膨脹先留位置。

## 與既有決議的關係

- **這是設計決策 6 的修訂，不是純粹的細化**。原決策 6 寫「新增白名單表；**原本的組織幣別欄位保留當預設值**」，本設計把後半句改成「不再是錢包幣別的來源」——前半句（新增一張表）是細化，**後半句是推翻**。修訂理由見第 1 節。
- **不影響設計決策 5**（代理綁定遊戲商時要指定幣別）。兩者管的是不同的事：決策 5 講「這個代理的這家遊戲商用哪個幣別」，本設計講「這一群代理允許哪些幣別、預設哪個」。
- **決議㉕ 的表結構與掛載層級已被 09-09 裁決取代**，其餘原則（不給墊底值、只改 Member、舊欄位不動、上線靠順序保證）全部保留。
