## 一、這個案子在做什麼

現在一個會員只有一種幣別的錢。這次要改成：**一個會員可以同時擁有多種幣別的錢包**，例如同時有馬幣錢包和泰銖錢包，各自獨立記帳、互不相加。

會員在 App 上可以切換「我現在要用哪個幣別」，切換之後：

- 遊戲清單只顯示**有支援該幣別**的遊戲商
- 存款與提款通道只顯示**該幣別能用**的
- 投注、派彩、活動獎金都記在該幣別的錢包上

因為錢包是整個平台的地基，這個改動會連帶影響遊戲商設定、代理綁定、金流通道、注單統計、分潤報表等幾乎所有跟錢有關的地方。

## 三、目前系統長什麼樣

動手之前必須先講清楚現況，因為初版設計文件對現況判斷錯了三處，導致工作量估得太樂觀。以下都是查生產資料庫得到的結果：

### 錢其實只放在一個地方

系統裡有兩套錢包機制：舊的「單錢包」（錢放在 `members.balance`）和新的「多錢包」（錢放在 `member_wallets`）。代碼裡兩套都在，但實際查生產設定後發現：

> **多錢包機制早就全部關掉了。** VWorld 的 69 個代理群組、TPower 的 63 個，開關值全部是 0，連系統預設值也是 0。

所以**目前所有會員的錢都在 `members.balance`**，`member_wallets` 表裡只裝禮碼（泥碼）和活動獎金。這讓改動單純很多——不是要在兩套運作中的系統之間搬東西，而是一條單向的搬遷。

### `member_wallets` 現在的實際內容

| 錢包類型 | TPower | VWorld |
|---|---|---|
| 中央錢包（type=1） | 完全沒有資料 | 完全沒有資料 |
| 遊戲錢包（type=2） | 68,211 筆，**餘額全是 0** | 73,958 筆，其中 1,052 筆有餘額共 121,991.61 |
| 禮碼（type=1002） | 141,153 筆，10.7 萬有餘額 | 265,160 筆，33.4 萬有餘額 |

VWorld 那 1,052 筆有餘額的遊戲錢包，最後更新時間**全部停在 2024 年 6 月**——是當初關閉多錢包時留下來的，兩年沒動過。這批錢的處置屬於業務決策，本案不碰（見第八節）。

中央錢包（type=1，程式裡叫 `CODE_PC`）位置一直空著沒用過，剛好可以拿來放搬遷後的中央錢包。

### 舊系統也在寫這個欄位

`members.balance` 不只 APIs 在用。舊系統 **API_Agent 有 6 條路由會直接改這個欄位**（後台扣點、調帳、開分、補點、提款駁回退款、活動派彩），而且是還在維護的活專案。

這代表：**不能直接把 `members.balance` 改成唯讀的複製品**，因為舊系統會寫它。初版設計文件假設舊系統只讀不寫，這個假設是錯的。

（另外澄清：WEB_AgentBackend 不直接連資料庫，它是透過 API_Agent。所以要處理的是 API_Agent 和 RD-Studio-01 兩個系統，加上資料庫裡的 stored procedure。）

## 五、關鍵決策說明

### 決策 3：中央錢包搬家

**做什麼**：把「存款進來、提款扣走」的那筆錢，從 `members.balance` 搬到 `member_wallets` 表，放在類型 1（中央錢包）。搬完之後每個幣別各佔一筆記錄。

**為什麼不用原本規劃的「複製品」做法**：初版打算讓 `members.balance` 變成唯讀的複製品（新資料寫進 `member_wallets`，同時同步一份到舊欄位給舊系統看）。這個做法行不通，因為：

1. 舊系統會**寫**這個欄位，不只是讀。兩邊都能寫就一定會不一致
2. 更根本的是，`members.balance` 跟 `member_wallets` 裡的遊戲錢包**本來就是兩筆不同的錢**（會員要手動轉點才能移動），不是同一筆錢的兩種呈現。把後者「複製」成前者，等於把兩個資金池混為一談

所以改成正式搬遷，並用決策 18 的分階段方式處理舊系統。

### 決策 5：代理綁定的繼承規則

**現在的規則**：代理有上下層關係。查某個代理能玩哪些遊戲商時，系統會從該代理往上找，**用最近一層有設定的代理為準**，找到就不再往上。

**要改成**：同一套規則，但多加一個幣別維度——「這個代理在馬幣下能玩哪些」和「在泰銖下能玩哪些」各自獨立計算。

**⚠️ 這裡有個容易改壞的地方**：現在的順序是「先決定用哪一層代理，再檢查啟用狀態」。所以如果最近一層代理把某遊戲商停用了，上層代理即使有開，也**不會**遞補上來——這是刻意的設計。改寫時如果順序寫反（先過濾啟用狀態再找代理層），就會變成上層默默遞補，行為悄悄改變且很難發現。

**另外修正一個初版的誤判**：初版寫「現在的程式碼寫死了一個代理配一個遊戲商只能有一筆商戶帳號設定」。這是錯的，實際上多筆都會保留，專案裡有測試明確固定這個行為。所以這裡不是「拆掉限制」，而是「多加一個維度」。

### 決策 10：進行中的遊戲怎麼算幣別

**問題**：會員用馬幣進了遊戲，玩到一半在另一台裝置切換成泰銖。這時遊戲商回傳的注單和派彩，該算在哪個錢包？

**結論**：**看該局遊戲當初是用哪個商戶帳號開的，就算哪個幣別**，完全不理會會員當下切到什麼。

分兩種遊戲模式處理：

- **單一錢包**（下注直接扣平台餘額）：遊戲帳號本身就記錄了商戶帳號，回調時反查即可。這部分現有機制已經支援
- **轉帳錢包**（要先轉點進遊戲商）：**現在沒有地方記錄用了哪個商戶帳號**。轉帳記錄裡只有遊戲商編號，沒有商戶帳號，所以系統每次都是「重新查一次現在該用哪個」

第二種如果不修，會出現這個問題：會員用馬幣轉點進去 → 切換成泰銖 → 轉點回來，系統會用泰銖商戶帳號的匯率換算，**兩種幣別的匯率比值就是會員憑空多拿到的錢**，而且可以重複操作。所以轉帳記錄必須把商戶帳號和幣別存下來，轉回時照著記錄走，不能重新查。

### 決策 11：錢包什麼時候建立

**做什麼**：不預先建立。任何一種入金——存款、派彩、活動獎金、代理加點、遊戲商轉回、會員轉入——第一次用到某個幣別時才建立那筆錢包記錄。

**技術作法**：在同一個資料庫交易裡，用「會員＋類型＋幣別」三個條件去建立（有就拿既有的），再鎖定那筆精確的記錄。

**為什麼不採用初版的「分兩次提交」**：初版擔心併發時會鎖到不存在的記錄產生死結，所以想把建立動作獨立出來先提交。這個方案有兩個問題：

1. 呼叫的地方多半已經在一個大交易裡了，在裡面再開一層交易在 Laravel 只是個還原點，根本不會獨立提交，達不到目的
2. 就算真的獨立提交了，主交易失敗時那筆空錢包會留下來，跟「有錢才有錢包」的原則矛盾

而且唯一鍵改成三個一組之後，資料庫本身就會擋掉重複插入，不需要額外處理。

### 決策 15：幣別要傳到多遠

**做什麼**：從注單源頭開始帶幣別，一路傳到所有下游。

```
遊戲商注單 → 總注單 → 每日統計 → ┬ 團隊統計（分潤）
                                  ├ 代理統計（報表）
                                  ├ 泥碼統計
                                  ├ 階層獎金
                                  └ 成本費率
```

**為什麼不能只做前三層**：後面這些大多是真錢——泥碼兩站合計有 44 萬餘額、階層獎金是直接派給會員的、成本費率影響營收計算。只做一半會留下混幣相加的錢，而錢一旦算錯，事後很難逆推是哪一筆錯的。

**為什麼一定會混算**：遊戲的編號是掛在「遊戲商」層級的，不分商戶帳號。所以同一款遊戲在馬幣帳號和泰銖帳號底下，遊戲編號完全一樣，而統計是用「會員＋遊戲編號」分組——兩種幣別必然被加在一起。這不是機率問題。

### 決策 16：為什麼要先做前置

**做什麼**：在改資料表結構之前，先把散落各處的錢包寫入動作收斂到 `WalletService` 這個統一入口。

**為什麼非做不可**：初版假設錢包的存取已經集中在 `WalletService`，實際上並沒有——PHP 端有 28 處直接操作，資料庫裡還有 19 支 stored procedure 直接寫，另外有一整套平行實作的 `WalletRepository`。

如果沒收斂就先改唯一鍵，這些漏掉的地方**不會報錯**，而是默默把資料寫到「幣別欄位＝預設值」那一筆去。其中有些用的是「插入失敗就忽略」的寫法，連錯誤訊息都不會有。等發現時資料已經亂了。

### 決策 18：舊系統分階段處理

```
階段 0  前置：把錢包寫入收斂到單一入口（決策 16）
階段 1  資料表加幣別欄位、改唯一鍵
階段 2  中央錢包搬家；APIs 開始兩邊都寫，並啟用對帳排程監控差異
階段 3  APIs 全面改讀新的錢包表
階段 4  改造舊系統（API_Agent 6 條路由、RD-Studio-01）
階段 5  停止寫入 members.balance，欄位保留但凍結
```

好處是舊系統的改造可以獨立排程，不必跟 APIs 綁在一起上線，而且每個階段都能回頭。

> ⚠️ **09-03 補充**：階段 4 的「API_Agent 6 條路由、RD-Studio-01」是 `members.balance` 的寫入者清單。`member_wallets` 這張表的寫入者範圍更大——API_External、API_Frontend、RD-Studio-01、API_Agent 四個舊 repo 222 個寫入點（09-03 口徑；分 repo 明細、單分支下界與共用套件 `target/support` 加計以影響盤點 7.1 為單一來源），另六站生產每站 16～19 支 SP 直寫。階段 1 加幣別欄、改唯一鍵之後，這些寫入者建的錢包幣別是預設值、查詢會撈錯列，所以階段 4（＝決議清單的第五期 5.4 舊系統改造）要涵蓋它們。清單見 [`multi-currency-wallet-impact-inventory.md`](multi-currency-wallet-impact-inventory.md) 第七節。

**⚠️ 兩邊都寫的期間要注意**：兩個欄位的小數位數不同（舊的 4 位、新的 10 位），必須先講清楚進位規則，並且要有排程定期比對兩邊是否一致。

### 資料表

**要加幣別欄位的**：`member_wallets`、`members`（當前幣別）、`vendor_infos`、`agent_vendors`、兩種交易紀錄表、會員轉帳紀錄、活動錢包與其紀錄表、提款單、~~**126 張遊戲商注單表**~~（**09-03 決議⑭移除**：BR 不加欄位，幣別與商戶記在總注單）、總注單、各層統計表、泥碼相關三張表。

## 七、改資料表要注意的事

> ✅ **09-03 決議⑭：126 張遊戲商注單表不加欄位。** 本節關於 BR 的加欄位／建索引／migration 產生器段落**已不適用於 BR**，保留是因為同樣的坑（`SchemaMonitor` 靜默跳過、分區表唯一鍵限制、加索引不能 INSTANT）對第三期的 TBR 新表與第五期其他表仍然成立。決議全文見 `multi-currency-wallet-decisions.md` 第五節。

126 張注單表、約 1.95 億筆資料，這規模有幾個容易踩的坑：

**加欄位很快，加索引很慢**。加欄位可以用 MySQL 的秒級模式完成；索引沒辦法，12 張破百萬筆的表要個別排時間做。

**有個機制會讓 migration 靜默失效**。專案裡的 `SchemaMonitor` 預設超過 50 萬筆就**跳過不執行，但仍然記錄成已完成**，而且不會報錯。這代表欄位根本沒建成，程式跑起來才發現找不到欄位。每一張表都必須明確指定筆數上限或加進白名單——`config/custom.php` 裡的註解已經警告過這個坑。

**分區表的唯一鍵有限制**。MySQL 要求分區表的唯一鍵必須包含分區欄位，所以第六節那三張統計表要加幣別進唯一鍵之前，得先確認它們的分區狀態。

> ✅ **已查明（08-19 實測）**：`summary_bet_record_agents`／`_agent_teams`／`_by_days` **三張都不是分區表**，唯一鍵可直接加幣別，沒有分區限制。
>
> ⚠️ 但真正是分區表的是另外兩張：`total_bet_records`（LIST 依 `vendor_id`、298 分區）與 `summary_bet_records`（RANGE 依 `year(summary_time)`、12 分區）。這兩張若依 RD 側建議的方案 A **只加欄位、不動唯一鍵**，同樣不觸發此限制（方案 A vs B 會審待決，見文首快照聲明）。實測補充：分區表支援 `INSTANT ADD COLUMN`（45～110ms），但**改唯一鍵與加索引會回 `ERROR 1845`**，證實那兩件要重建表。

**126 張的 migration 要用程式產生**，不要手寫。但要先講清楚表清單從哪裡讀——從資料庫查是 126 張，從 migration 目錄數是 123 張，兩種讀法會漏表。

### 舊資料怎麼補

> ✅ **08-19 修正：注單鏈路的幣別欄位免回填。** 上線前注單本來就都是主幣別，`ADD COLUMN ... DEFAULT 主幣別` 的 `DEFAULT` 即正確語意（Gate 0 實證：52 萬列舊資料 100% 帶 DEFAULT）。這消滅了原本估算中最大的成本項。
>
> 下表仍然適用於**商戶帳號欄位**——那個欄位沒有「反正都一樣」的性質，必須實際回填。

| 欄位 | 從哪裡取 | 準不準 |
|---|---|---|
| 幣別 | 該會員所屬組織的幣別 | **準確**。因為改動之前全系統只有一種幣別，不可能有第二種 |
| 商戶帳號 | 優先從遊戲帳號表取（125 張裡有 115 張本來就記了），取不到才用代理綁定推算 | 前者接近當時的真實情況，後者是推算 |

**幣別不要從補完的商戶帳號反推**，直接取組織幣別就好——否則商戶帳號的推算誤差會傳染到幣別，把原本 100% 準確的欄位弄髒。

⚠️ **123 張注單表裡有 107 張沒有會員編號**（最大那張只有遊戲帳號），所以補資料實際上要經過「注單 → 遊戲帳號 → 會員 → 代理 → 組織」四層關聯，成本比單純批次更新高很多。

## 九、測試

現有 586 個測試檔裡有 43 個碰到錢包。依保護價值排序：

1. **遊戲進行中的幣別固定**（決策 10）——切換幣別後，進行中的注單仍算在原幣別。**這裡出錯就是直接的資金損失**，優先級最高
2. **錢包解析與建立**——三個條件組合能不能正確找到／建立錢包，含併發情況
3. **統計的幣別分組**——同會員同遊戲不同幣別必須分成兩筆；調帳比對不能跨幣別配對
4. **補資料腳本**——要能重複執行且有試跑模式。1.95 億筆錯一次很難救

**會被改壞的既有測試**：有個測試直接把 `members.balance` 當主錢包在驗證，決策 3 上線後它就變成錯的規格；錢包與遊戲商設定的測試資料產生器都沒有幣別欄位，要一起補。
