# 成長彩金計劃（漸進式彩金活動）

## 一、活動基礎

**活動名稱**：成長彩金計劃

**參與條件**：會員累計儲值達到指定金額後，自動開啟對應成長彩金。

**活動檔位表**

| 等級 | 累計儲值 | 成長彩金 |
|------|---------|---------|
| 新會員專享首儲 | - | 200%，最高 5888（不限時） |
| Lv1 | 1000 | 1888 |
| Lv2 | 3000 | 5888 |
| Lv3 | 5000 | 8888 |
| Lv4 | 10000 | 18888 |

**規則**

- 每個檔位僅可開啟一次。
- 達標後系統自動開啟。
- 每個檔位獨立計算。
- 必須完成當前檔位後，才開始計算下一檔位。

## 二、活動開啟

會員累計儲值達到對應金額後，系統自動執行：

- 彈窗提示「恭喜開啟成長彩金」。
- 建立活動記錄。
- 活動狀態改為【進行中】。

活動頁面顯示內容：

- 成長彩金總額
- 已解鎖金額
- 剩餘待解鎖金額
- 解鎖進度

## 三、彩金解鎖規則

僅統計指定遊戲投注。

| 遊戲 | 解鎖比例 |
|------|---------|
| 老虎機 | 0.3% |
| 捕魚 | 0.3% |
| 真人 | 0.1% |
| 體育 | 0.5% |

其他遊戲不計算。

**解鎖公式**：解鎖金額 = 有效投注 × 解鎖比例

**老虎機範例**

| 投注 | 解鎖 |
|------|------|
| 100 | 0.3 |
| 1,000 | 3 |
| 10,000 | 30 |
| 50,000 | 150 |
| 100,000 | 300 |

系統即時更新：已解鎖金額、剩餘金額、解鎖進度。

## 四、彩金領取

會員可隨時領取已解鎖彩金。

領取後的效果：

- 發放至真金錢包。
- 可立即使用。
- 可立即提款。
- 無需額外流水。

**領取範例**

成長彩金：1888
累計已解鎖：150
領取後：

- 真金錢包增加 150。
- 剩餘待解鎖 1738。

## 五、活動升級

達到更高儲值檔位時，系統自動開啟下一檔成長彩金。

**升級範例**

已開啟 1888 彩金 → 累計儲值達到 3000 → 自動開啟 5888 彩金。

**升級規則**

- 原活動繼續保留。
- 新活動獨立建立。
- 各檔位分別記錄。
- 當前檔位完成後，再開始計算下一檔位。

## 六、參與遊戲

**計算解鎖的遊戲**：老虎機、捕魚、真人、體育。

**其他遊戲**：不計算投注、不計算解鎖金額。

## 七、前端顯示

成長彩金頁面需顯示的內容：

- 目前成長彩金
- 已領取金額
- 剩餘待解鎖金額
- 解鎖進度（%）
- 活動剩餘時間
- 本次投注新增解鎖金額

投注完成後：即時動畫顯示新增解鎖金額。

## 十、風控規則

1. 每個檔位僅可開啟一次。
2. 活動到期自動結束。
3. 已解鎖金額永久有效，不可回收。
4. 僅統計指定遊戲投注。
5. 禁止哈希套利、真人對刷、輪盤刷水等異常行為。
6. 活動彩金不可轉贈、不可轉帳、不可兌換其他獎勵。
7. 後台需保留完整活動日誌，所有彩金、投注及狀態變更均可追溯稽核。

## 額外要求

1. 設計活動頁面（倒數計時很重要）。
2. 活動只能單獨進行（不能與其他活動同時參與）。
3. 儲值時需有引導提醒。

## 十一、實作現況與規則調整

實作過程中對原文規則做了幾處補充/調整，這裡記錄實際邏輯（跟原文有出入的地方以這裡為準）。資料表欄位與型別以 `database/migrations/` 底下 `create_event_progressive_jackpot*` 系列 migration 為準。

### 首儲的實際規則

- 「新會員專享首儲」在實作上是**獨立、不進累積儲值**的特殊檔位（`level=0`）：拿到首儲的這筆儲值金額本身不算進 `total_deposit_point`，首儲建立完就直接結束，不會跟 Lv1~Lv4 的判斷混在同一次計算裡。
- 首儲資格由後台代理設定 `first_deposit_type` 決定：
  - **1（創建帳號後第一筆）**：必須是該會員有紀錄以來真正的第一筆成功儲值；活動生效前就已經儲值過的會員，之後儲值一律不算首儲。
  - **2（活動開始後第一筆）**：不檢查歷史儲值，只要是這個會員在這個活動下第一次被追蹤到的儲值，就算首儲。
  - 未設定則等同 2。
- 首儲進行中（`status=0`）時，會員的任何儲值整批不處理（不累加金額、不建立新檔位），呼應「必須完成當前檔位後才開始計算下一檔位」；等首儲被領完、過期或鎖定後，儲值才恢復正常累加。
- `reward_percentage`（`reward_type=2` 百分比類型用）存的是**倍數**，200% 存 `2.0`，不是存 `200`；實際彩金 = 觸發這檔門檻的那筆儲值金額 × 倍數，封頂 `max_reward`。
- **API 輸出的百分比欄位一律 ×100 轉成前端顯示用數字**：`reward_percentage`（`EventProgressiveJackpotLevelCardResource`）與解鎖比例 `rate`（`EventProgressiveJackpotBetSettingResource`）在 DB 存的都是計算用的原始倍數/比例（200% 存 `2.0`、0.3% 存 `0.0030`），`EventProgressiveJackpotService::list()`/`buildLevelCards()` 在組回應時才轉成 `200.0000`/`0.3000` 這種前端可直接接 `%` 顯示的數字；`event_progressive_jackpot_bet_settings.rate` 用於 SP 解鎖金額計算（解鎖金額＝有效投注 × rate）時仍是原始比例，只有這支 API 回應的欄位值被轉換過，不影響 SP 計算邏輯。

### 檔位狀態機（比原文的「進行中、已完成、已過期、已關閉」4 種多兩種）

| 狀態 | 說明 |
|---|---|
| 0 進行中 | 正在累積解鎖金額，同一會員同時只會有一筆 |
| 1 等待解鎖 | 已達標建立，但上一檔還沒完成，排隊中（原文沒有這個中間態，是實作為了「必須完成當前檔位才算下一檔」規則而新增的） |
| 2 已完成 | 解鎖金額打滿，但可能還沒領完 |
| 3 已過期 | 對應「活動到期自動結束」風控規則 |
| 4 已鎖定 | IP/手機號/真實姓名重複，原文沒有明確提到重複帳號的處理方式，實作補上這個狀態 |
| 5 已關閉 | 已完成且領取完畢的終態，之後不再變動 |

**過期時間 (`expire_time`) 的實際算法**：不是在檔位「建立」當下就固定算好，而是在檔位**真正變成進行中(0)的那個時間點**才計算（`= 現在 + 該檔位設定的 expire_day`），等待解鎖(1)/已鎖定(4) 都是 `NULL`。原因：等待解鎖可能要等上一檔完成才會輪到自己，如果在建立當下就固定算 30 天後過期，等太久的話一啟用就已經過期了；所以無論是「補啟用最小等待解鎖檔位」還是「連鎖疊加啟用下一檔」，只要轉成進行中，都會重新起算一次過期時間。

### 重複帳號判斷（IP / 手機號 / 真實姓名）

原文沒有明確規則，實作邏輯：

1. 後台每個活動可以獨立開關 `ip_block`/`mobile_block`/`realname_block` 三種檢查。
2. **儲值時**：會員第一次被這個活動追蹤到（`user_details` 剛建立）的當下，比對其他會員在 `user_joins` 留下的 IP/手機號/真實姓名快照，命中的話把對方的 `member_id` 記到 `user_details.block_ip_member_id`/`block_mobile_member_id`/`block_realname_member_id`，這筆新建立的檔位直接是已鎖定(4)。
3. **領獎時**：因為儲值當下可能還沒有其他會員共用同樣的 IP/手機號/真實姓名（對方是之後才加入的），所以第一次領獎前會再檢查一次（`user_details.is_receive` 記錄是否已經檢查過，只檢查一次），命中的話把該會員名下還在進行中/等待解鎖的檔位全部鎖定，擋下這次領獎；已完成/已過期/已關閉/本來就已鎖定的檔位不會被這次判斷影響（保留給後台未來手動介入的空間）。
4. **真實姓名的來源是 `members.first_name`**，不查 `realname_validation_requests` 的審核紀錄。`SP_calc_event_progressive_jackpot_deposit`（儲值時的快照）與 `EventProgressiveJackpotService::assertNotDuplicateOnFirstReceive()`（領獎時的重複檢查）兩邊都讀這個欄位，維持一致。
5. **領獎時順便補正 `user_joins.realname` 快照**：建檔位當下（deposit SP）會員可能還沒通過實名驗證，`user_joins.realname` 存的是當時的值（可能是空的，或審核前隨便填的舊資料）；領獎前 `assertNotDuplicateOnFirstReceive()` 已經能拿到 `members.first_name` 這個通過驗證的正確值，這時會把該會員名下**所有**檔位（不分狀態）的 `user_joins.realname` 一併更新成正確值，確保之後別的會員做重複比對時，用的是這個會員最新、正確的真實姓名快照，而不是建檔位當下那筆可能不準的舊值。

### 投注解鎖計算的補充規則

- 除了原文列的老虎機/捕魚/真人/體育四種遊戲類型，實作額外排除 `vendors.is_free=1`（免盤費商戶）的投注，不計入解鎖流水，跟站內其他統計（如 `RankingService`）排除免盤費商戶的作法一致。
- 每小時排程（`SP_calc_event_progressive_jackpot_bet_records`）在計算解鎖量之前，會先檢查目前進行中的檔位是不是已經過期，過期的話先轉已過期(3)，再檢查有沒有下一檔在等待解鎖，有的話補啟用並套用這次的解鎖量，都沒有才捨棄這次流水。

### 領取金額上限防護

`receiveOne()` 在真正把錢發到會員餘額（`giveMemberReward()`）之前，會先檢查「這次領完之後的累積已領金額（`receive`）」不能超過這檔的彩金總額（`reward`）；超過就整筆拒絕、不派彩。`point`（已解鎖金額）理論上本來就不會超過 `reward`（`reward_type=2` 百分比檔位在建立時已用 `LEAST(儲值金額 × 倍數, max_reward)` 封頂），這道檢查是在真正動錢之前的最後一道防線，避免因未知原因（例如 `point` 被其他來源異常改大）超額派彩。

### 異動紀錄的查詢欄位

`event_progressive_jackpot_user_detail_logs`（累積儲值異動）與 `event_progressive_jackpot_user_join_logs`（檔位異動）都補上了 `level` 欄位，方便後台用檔位查詢相關訂單/異動：

- `user_join_logs.level`：這筆異動屬於哪個檔位，每筆異動都對應唯一一個檔位。
- `user_detail_logs.level`：這筆儲值訂單如果沒有跨過任何新檔位，記會員目前已建立過的最高檔位；如果一次跨過好幾檔（例如首儲後累積很久才儲值一大筆），會**依跨過的檔位數各寫一筆**，同一個 `order_id` 可能對應多筆 `user_detail_logs`，每筆的 `level` 不同、但 `before/after` 累積金額欄位是同一筆訂單的值（不會拆分金額）。
