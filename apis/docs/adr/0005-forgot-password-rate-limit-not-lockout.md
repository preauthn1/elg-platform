# 忘記密碼的次數限制採頻率限制，不鎖帳

會員忘記密碼流程（取得帳號列表、重設密碼）原本沒有任何次數限制，驗證碼只有 6 位數字，可以一直猜；檢核驗證碼那支也驗得了忘記密碼的碼，同樣沒有限制。2026-10 決定（target/tickets#4540）：這三支端點加頻率限制，分兩個具名限流器、額度互不干擾。重設密碼按會員帳號與 IP 各一把 key；取得帳號列表與檢核驗證碼共用一個限流器，按 IP 一把 key，請求有帶手機、信箱就各再加一把，不看會員帳號。檢核驗證碼遇到忘記密碼或找回密碼的碼，任何拒絕都與碼錯誤回完全相同的回應（包括網域、會員不符），不讓人從回應分辨碼是否猜中。IP 是 IPv6 時以所屬的 /64 網段當 key。每把 key 獨立計數，任一把超過就擋，回錯誤碼 2037；每把 key 在 3 分鐘的窗口內最多 10 次，超過就擋到窗口結束。不鎖帳：被擋的只是這段時間內的嘗試，帳號狀態完全不動。

## 考慮過的選項

- **計次鎖帳**（比照登入錯誤次數上限 5305、會員驗證碼錯 3 次鎖帳）：攻擊者只要知道帳號就能把別人鎖住，而且解鎖要人工處理，等於把防猜碼的機制變成鎖人的工具。
- **帳號加 IP 合成一把 key**：換一個 IP 額度就重置，對能輪換 IP 的攻擊者擋不住。拆成兩把各自計數，換 IP 會撞到帳號 key、換帳號會撞到 IP key。
- **取得帳號列表也用會員帳號當 key**：這支的表單驗證不收會員帳號，多帶的會員帳號會被丟掉；限流若讀它，攻擊者每次附一個不同的帳號就換到新額度。
- **收緊重設密碼的會員帳號驗證規則**（改成只收英數字、4 到 30 字，擋掉帶重音或全形、在 utf8mb4_unicode_ci 定序下與原帳號等價的寫法）：既有帳號並不都符合。Dev 環境實查 4816 個會員有 56 個不符（多數帶底線，也有不足 4 字或帶連字號的），其中 39 個已驗證手機或信箱，收緊後他們在取得帳號列表後、重設密碼時會被擋下。改為在限流 key 上做正規化：去重音、全形轉半形、轉小寫，讓等價寫法落在同一把 key。這只是近似定序，所以帳號 key 仍是輔助，主要防線是 IP key。
- **手機與信箱合成一把聯絡方式 key**（例如有手機用手機、沒有才用信箱）：查驗證碼是「手機或信箱」任一相符，攻擊者固定受害者的信箱、每次換一個格式合法的手機，就能一直換到新額度。所以兩者分開、各自計數。

## 後果

- 被擋的是短時間內的密集嘗試，正常使用者最多等 3 分鐘就能再試，不需要客服介入。
- 知道某個會員帳號（或手機、信箱）的人，可以用一直送垃圾請求的方式，讓那把 key 在每個 3 分鐘窗口內都被擋。影響只到該會員這段時間不能自助重設密碼，帳號本身不會被鎖、也不會掉；帳號這把 key 只是輔助，主要防線是 IP 那把。
- 誤擋時改 env 即可：`GUEST_RESET_THROTTLE_MAX` 調高次數、設 0 等於關閉，`GUEST_RESET_THROTTLE_DECAY_MINUTES` 調整窗口，不必回滾代碼。
- 計數放 redis（`config/cache.php` 的 `limiter`），多個 pod 共用同一份計數，不會因為請求分散到不同 pod 而失效。
- key 讀的是解密後的欄位，擋下時的 2037 訊息要跟著請求語系，`bootstrap/app.php` 因此把 DecryptRequest 與 DetectLanguage 排進 middleware priority、放在 ThrottleRequests 之前；所有掛這兩支的前台路由，它們都會早於 SubstituteBindings 執行。
- 限流不看結果：驗證碼對或錯都算一次。
- API_Agent 端（代理）同一個決定，用它既有的 RateLimitRequests 實作，規則是「1 分鐘 10 次、封 3 分鐘」。兩邊效果都是超過後 3 分鐘內擋，窗口定義不同是因為各自沿用既有工具，不是刻意設成不一樣。
