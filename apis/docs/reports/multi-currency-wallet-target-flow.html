一個會員、多種幣別錢包

19＋13＋7 項決策 5 份獨立評估 08-27 八項決議 六期計劃 內部討論稿

＊先讀這裡

這一節沒有技術細節。看完就知道這件事在做什麼，以及後面哪幾節跟你有關。

現在是這樣：一個會員只有一個錢包，而且只認一種幣別。那個幣別由他所屬的白標決定，會員自己不能選。想服務用別種幣別的玩家，只能另開一個站台。
要改成這樣：一個會員可以同時有好幾個幣別的錢包，在 App 上自己切換。切到泰銖，看到的就是泰銖的遊戲、泰銖的存款通道、泰銖的提款銀行、泰銖的活動。切換不影響已經送出的訂單。
為什麼這件事很大：難的不是「多開幾個錢包」，是「這筆錢是哪個幣別」要一路傳到最下游——玩家的每一筆注單、每天的統計、代理的分潤、對帳報表，全都要跟著記幣別。光是總注單就有 20.6 億筆。
怎麼做、做多久：切成六期，一期一期上，每期都能單獨驗收。前面幾期是打地基（把散落各處的錢包寫入收斂到同一個入口、把幣別資料整理乾淨），最後一期才真的開放玩家切換幣別。目前在第二期。
最大的風險在哪：舊系統也在寫同一批資料，而且它不知道有幣別這回事。所以每一期都要處理「新舊並存」，不能一次切換。這也是為什麼期數這麼多。
現在需要決定什麼：待拍板的項目集中在第 10 節，其中最關鍵的一題是有沒有硬性上線期限——有的話要準備一條「先求有」的降級路線。
接下來怎麼讀。只想知道結論，看第 1 節（現況）與第 2 節（玩家切換幣別後看到什麼）就夠了。想知道要花多久、分幾期，看第 9 節。要參與技術決策，才需要往下讀第 11 節以後。看到看不懂的代號，回第 0 節展開那張速查表查就好，不必從頭讀。

技術術語白話對照（08-27 新增，全文只在此處解釋一次）
fan-out
分區扇出		一次查詢被迫去翻「每一個分區」TBR 有 298 個分區，查詢若不帶 vendor_id 就得 298 個全開，光是規劃查詢就花 1,266ms
pruning
分區裁剪		fan-out 的反面：只翻用得到的那幾個分區分區鍵選對就會自動生效。SBR 依年份分區、查詢帶時間 ⇒ 只碰 1 個分區、掃 40 列
dispatcher
分流器		PHP 層的一段程式，依查詢條件決定該去查哪張表冷熱分離後，同一個報表查詢可能要查熱表、也可能要查某幾張月份冷表——由它算出來並在應用層合併結果
cohort
分批群組		把要遷移的對象分成幾批，一批一批上第四期不會一次把所有遊戲商切過去，而是分批切、每批觀察後再繼續
ODKU
撞鍵就改		ON DUPLICATE KEY UPDATE：insert 時如果撞到唯一鍵，改成更新那一列而不是報錯72／72 支轉檔 SP 的冪等就靠它——同一筆注單重跑會更新原列，不會變成兩列。它同時也是「注單可被事後修改」的來源
MDL
結構鎖		metadata lock：改表結構時 MySQL 對該表加的鎖就算 INSTANT 是秒級，仍會取一瞬間的獨佔結構鎖；replica 也要各自面對自己的鎖條件
INSTANT ／ INPLACEMySQL 改表結構的兩種演算法INSTANT＝只改字典、不碰資料，秒級；INPLACE＝要掃過資料但不重建整張表，在 20.6 億筆上是小時級
row version
列版本額度		每做一次 INSTANT 加／刪欄位就消耗一格的消耗品耗盡後該表就再也不能做 INSTANT，只能整表重建。多幣別只用掉 1 格
DR 工具

切換不影響已經送出的訂單：存款單與提款單建立時就把幣別寫進訂單，之後會員怎麼切都不影響入帳與扣款的歸屬。

活動不能跨幣別重複參加（08-18 補充）：同一檔活動會依幣別各建一份獎勵設定，會員不得同時跨幣別參與。現行活動 V2 的 ONLY_ONE_EVENT 限制同一時間只能參加一個活動，因此會擋住同時參與；但 HAS_JOIN 只比對單一活動編號。分幣別建立後，系統無法辨認它們屬於同一檔，仍需新增活動群組識別；細節依活動 V2 紀律與 PM 確認。

轉帳錢包沒有地方記：轉帳紀錄裡只有遊戲商編號，沒有商戶帳號，所以系統每次都是「重新查一次現在該用哪個」。這會產生下面這個風險。

解法：轉帳紀錄必須把商戶帳號和幣別存下來，轉回時照著紀錄走，不能重新查。

5注單與分潤鏈路

決定性理由更換分區鍵會打破注單的冪等性契約——這不是成本問題，是語意問題

MySQL 硬規則：分區表達式用到的欄位，必須存在於該表的每一個 PRIMARY KEY 與 UNIQUE KEY 之中。

TBR 現有 UNIQUE (vendor_id, bet_record_id)（08-19 實測 NON_UNIQUE=0 確認為唯一索引）。這是 72 支注單轉檔 SP 的冪等性防線——同一筆三方注單重複轉檔時，靠這個唯一鍵擋掉。

若改依時間分區，唯一鍵被迫變成 (vendor_id, bet_record_id, 時間欄)，唯一性就從「跨全部歷史唯一」降級為「同一時間值之內唯一」。同一筆注單以不同 summary_time 重跑轉檔，就會插進兩列而不報錯。

對注單表而言，重複列意味著重複計算輸贏與分潤。查詢效能不值得拿業務冪等性契約去換。原先「TBR 另建新表並改依時間分區」的建議因此撤回。

① 建立分區：預先建，不要臨時建

🔴 絕對不要建 MAXVALUE 分區——有 MAXVALUE 就不能 ADD PARTITION，只能 REORGANIZE，那是要重建資料的操作。VWorld SBR 的 p2025 = MAXVALUE 就是活生生的反例：2025 年起資料全塞同一區，現在動不了（已列在第 15 節「仍待拍板」）。

必須監控沒有 MAXVALUE 時，資料超出最後一個分區上界會讓寫入直接中斷

MySQL 會回 Table has no partition for value——是報錯，不是靜默塞錯區。所以守衛要設在「最大分區上界 < 今天 ＋ 緩衝」就告警，而不是等 INSERT 炸掉才知道。緩衝建議至少 2～3 個月。

② 剔除舊資料：DROP PARTITION，順序不可顛倒
ALTER TABLE total_bet_records_hot DROP PARTITION p202505;

硬性順序：搬進冷表 → 驗證 → 才准 DROP。

  • ✅ 秒級完成，表空間立刻歸還——這正是缺口 4（DELETE 不歸還表空間）的根治點。
  • ⚠️ 需要短暫的 MDL exclusive：長交易或長查詢會卡住它，而它等待期間會連帶擋住後續所有查詢。要設 lock_wait_timeout 並排在低峰時段。
  • 🔴 不可逆。驗證閘門必須是硬的：冷表筆數 ＝ 該分區筆數，加抽樣或 checksum 比對，任一不過就中止並告警。

這不是「分區本身不好」，而是「分區鍵選錯」。把 TBR 改為 RANGE 依時間（或依時間分區、vendor 做子分區），能讓上表前兩種主要查詢樣態都拿到 pruning。但 08-19 收斂後這條路已被否決——更換分區鍵會連帶打破 UNIQUE (vendor_id, bet_record_id) 的全域唯一性（分區鍵必須含於每個唯一鍵），而那是 72 支轉檔 SP 的冪等性防線。正確的緩解方向是削減分區數而非更換分區鍵，詳見上方「08-19 收斂」區塊。

問題一：TBR 多幣別後還需要匯率轉換嗎

結論：TBR 不需要換匯——因為換匯已經在更上游做完了。TBR 存的是「會員錢包幣別」的金額，計算方式維持現況、一行不改。

關鍵在於換算發生的層級：轉換在遊戲商層（Driver）入境即完成、一次到底，BR 之後的 TBR／SBR／報表全程不再換算。

層級金額語意要不要改
三方回傳三方自己的計價幣別與單位（可能是仙、千分、或另一種幣別）不變
遊戲商層（Driver）以 vendor_infos.rate 換算 → 寫入 xxx_bet_records。單位差與幣別差都在這一層吸收不變

為何不存三方原幣存原幣會讓 TBR 出現多幣別混列，且必須新建匯率歷史表

以 AlfaWin77 為例，若 TBR 改存三方原幣：4D 注單存 MYR、其餘存 IDR ⇒ 同一站台的 TBR 出現兩種幣別混列，SUM(bet) 直接失去意義，且要合計就得建匯率歷史表才能重現歷史報表。

存「會員錢包幣別」則完全避開這件事：換匯已在遊戲商層以當時的 rate 完成，屬已實現的換算，會計上正確、不需重算。而這也與「所有報表依幣別篩選」的需求完全一致——報表要的維度是會員幣別，不是三方計價幣別。

⇒ 若對帳需要回推三方原值，rate 快照就從「錦上添花」變成必要條件。這是「存會員錢包幣別」這個選擇的唯一代價，也是它唯一需要的配套。

待業務裁決集團層跨幣別總額怎麼呈現

同一站台內因為已在上游換算完，不存在跨幣別加總問題。唯一需要匯率的場景是「跨站台／跨幣別的集團總營收合計」。建議在報表層以當期匯率換算、不落 TBR——匯率會變，落地即失真。若業務確認不需要跨幣別合計，這件事整個不用做。

決議一：幣別的權威來源＝vendor_infos，一幣別一商戶

項目內容
拍板不同幣別的遊戲商戶是獨立的 vendor_info；會員的遊戲帳號按商戶建立 ⇒ 幣別隨 vendor_infos.currency_id 固定
解掉的問題「投注當下的幣別不見得是三方回調當下的幣別」——時間差問題因幣別綁在帳號而非會員狀態，自動消失
證據VWorld 已用此模式運作多年：vworldsg（新幣）、casino365（菲律賓）、co365th（泰國）、vworldvn（越南）、wintotoidn（印尼）各自獨立 vendor_info 與 account_prefix。不是新設計，是既有生產實績
實作利多72 支轉檔 SP 中 71 支已 JOIN vendor_infos（SP_transfer_event_record_pgs 亦已 JOIN）⇒ 帶幣別只需在 SELECT 加一欄現成的 JOIN 欄位

決議二：TBR 存「會員錢包幣別」的金額，換匯在遊戲商層完成

拍板：會員選擇某幣別錢包後，投注紀錄最終必須轉換為該幣別；轉換在遊戲商層（Driver）入境即完成、一次到底，BR 之後的 TBR／SBR／報表全程不再換算。因此 TBR 不需要換匯邏輯，現況算式一行不改。

08-27 二次更正 本決議初版寫成「TBR 存三方原幣金額、不做匯率轉換」，已修正。推翻原因：實測發現 vendor_infos.rate 同時承擔單位換算與匯率換算——AlfaWin77（IDR 站）的三個啟用中 4D 商戶是 currency=MYR、rate=0.00025（×4,000 換成 IDR）。若 TBR 存三方原幣，同一站台會出現 MYR 與 IDR 混列、SUM 失去意義，且必須新建匯率歷史表（詳見第 13 節）。
項目內容
多幣別下的自洽條件vendor_infos.rate 現在的語意是「對站台主幣別的率」。多幣別後一個 rate 撐不住兩種目標幣別——但決議一「一幣別一 vendor_info」讓這個問題自動消失：每個商戶只服務一種會員幣別，rate 語意自然升級為「對該會員幣別的率」
必然結果同一款遊戲要給兩種幣別會員玩 ⇒ 開兩個 vendor_info，各自 rate 指向不同目標幣別。VWorld 的 Vpower 開 8 個 vendor_info 正是此模式
強制配套TBR 逐筆快照 rate——rate 是後台可改的活資料，改後歷史注單不需重算（已實現的換算、會計正確），但無法回推三方原始金額。若對帳需要回推，此項為必要條件
待業務裁決同站台內無跨幣別加總問題。唯一需要匯率的是跨站台／跨幣別的集團總營收合計；建議在報表層以當期匯率換算、不落 TBR。不需要則整件事不用做

決議三：currencies 主檔只收標準幣別碼

項目內容
拍板主檔只收 ISO 4217 標準碼；千分制與仙位一律以 rate 表達，不佔獨立 currency_id
落地方式RB 08-27 定調：「KVND 應該在 vendor_infos.rate 做設定，vendor_infos.currency_id 維持 VND」——單位差一律由 rate 表達，currency_id 只放標準幣別。VND2(4)／KVND(5)／IDR2(7)／KIDR(8) 因此永遠不會被指向
刻意的「不一致」vendor_infos.currency（字串，送三方 payload）＝ KVND，而 vendor_infos.currency_id ＝ VND(3)——兩者外觀不一致是設計，不是資料錯誤。必須寫進欄位註解，否則下一位接手者會當成 bug 去「修」
四個變體 id 的處置不刪列、不加 DB 旗標；改在 CurrencyEnum 加「可作為會員錢包幣別」的集合方法，或以 config 白名單限制。理由：誤用途徑只有一條（後台設定組織幣別時從下拉選單選到），而該選單的資料來源本來就要新寫 ⇒ 代碼層白名單零 DB 變更、防線等效。例外：若營運需要不改代碼就能調整可開錢包的幣別，才值得加 DB 旗標
執行風險實測為零 08-27 查 12 張業務表（organizations／agent_cash_flows／banks／standard_banks／cash_flow_banks／orders／order_types／currency_names／agent_register_limits／agent_member_field_settings／shareholder_currency_rates／shareholder_api_infos），currency_id IN (4,5,7,8) 結果為空集合 ⇒ 四列為孤兒資料，停用不需任何資料遷移

決議四：歷史幣別要「填對」，不填預設值

拍板：新表遷移的 INSERT ... SELECT 時 JOIN xxx_accounts → vendor_infos.currency_id 把歷史幣別填對，不使用 DEFAULT 主幣別。

方案取捨此決議只有新表遷移案能達成

原表加欄位案的 ADD COLUMN ... DEFAULT 只能填單一預設值，會把 VWorld 既有的 SGD／PHP／THB／VND 注單全部標成 MYR（第 14 節更正二）。

因此本決議把「趁現在分表」從成本論據升級為正確性論據——不是「反正要動不如一起動」，而是只有遷移這條路能把歷史幣別填對。這是目前支持新表遷移案最強的獨佔理由，且與效能數字無關。

實作利多（08-27 掃描）：ia_bet_records 已有 currency_id 欄位（既存先例可參照）；另有多家遊戲商的 BR 已存三方回傳幣別——ace333／aes／ag／epic_sw／isb／sbo／wm／ygg／ppsw_game_rounds 有 currency、dg 有 currencyId、pg 有 Currency、pt 有 currency_code。對這些 vendor 幣別來源不必新增欄位，但四種命名寫法並存，對照時須正規化。

決議五：冷熱分離——熱表走實體表、冷表按月一張，套用既有 AbstractArchive

已定案 RB 08-27：熱表走實體表（不是 View），並套用現有 AbstractArchive 機制。復用檢查結果：機制形狀完全吻合，且已在生產運作。

紅線・已拍板冷熱分離會讓注單冪等契約從「全歷史不重複」退化為「只有最近三個月不重複」——以「冷表原則唯讀」化解

72／72 支轉檔 SP 的冪等靠 ON DUPLICATE KEY UPDATE 命中 UNIQUE (vendor_id, bet_record_id)。資料搬到冷表後，熱表就沒有那一列 ⇒ 同一筆注單若在三個月後重跑轉檔，ODKU 不會命中，會插入重複列。

這與「改時間分區破壞冪等」是同一個病、不同的入口——分區那條是 MySQL 強制唯一鍵含分區鍵所致，這條是資料實體被移出所致。換成冷熱分離不會讓這條規則消失。

RB 08-27 拍板（＝決議八）：冷表原則上只用於查詢，唯一的寫入路徑是指定的 artisan 命令；補跑舊注單不放行。
另兩個曾評估的方向同時否決：②「補跑前把該月冷表搬回熱表」（複雜且熱表尺寸失控）、③「建應用層冪等表」（最徹底但屬獨立專案，不進本案；已改列技術債方向）。

理由：轉檔 SP 處理的是近期注單（WHERE updated_at BETWEEN StartTime AND EndTime），三個月以前的補帳屬歷史修帳，走專用命令直接改冷表，比放寬冪等防線乾淨。未驗證 歷史補跑的實際頻率與最大回溯月數仍未查證（可撈 RD-Studio-01 執行 log 或 command_logs）——不影響本次拍板，但會決定那支 artisan 命令要做到多完整。

⚠️ 拍板未涵蓋的一條路徑（設計階段必須定義）：上述防線擋的是「人為指定舊區間重跑」。但遲結算（注單很久以前下注、最近才結算或改 payout_time）走的是正常日跑——SP 的時間區間落在最近三個月內、根本不算補跑，可是那一列可能早已在冷表 ⇒ ODKU 一樣撞不到。這不是「要不要禁止重跑」的問題，而是缺口 7「判定用哪個時間欄位、以及該改哪張表」必須明確定義。

套用到 TBR 的七個缺口（AbstractArchive 現況設計為 log 級資料，非注單級；缺口 5／6 為 08-27 交叉評估後補入，見第 16 節）

#缺口說明與建議
1🔴 chunkById 在 298 分區表上無法 pruning最嚴重。游標條件是 id > ?、不含 vendor_id ⇒ 每一頁都掃全部 298 個分區（第 12 節實測 planning 成本 1,266ms）。20.6 億筆 ÷ batchSize 1000 ＝ 約 206 萬頁，每頁付一次 fan-out。解法：外層迴圈逐 vendor_id、內層才 chunkById，讓每一頁都能 pruning

5🔴 migrateData() 整月搬遷包在單一 transactionAbstractArchive.php:82：DB::transaction(fn () => $this->migrateData(...))。對 log 表沒問題，對 20.6 億列是災難級（undo log 膨脹、鎖持有時間、replica lag）。transaction 邊界必須重寫為逐批提交＋checkpoint
6🔴 TBR 的 id 是下游身份，搬表會讓 relation 失效存 total_bet_record_id 的表共 6 張：total_bet_record_wallet_transaction_logs、transaction_log_total_bet_records、marquee_win_point_records、total_bet_record_transaction_logs、total_bet_record_promotion_wallet_logs、flow_limit_details。row 搬到冷表後，這些表只憑 ID 找不到資料 ⇒ 需要 hot／cold locator 或保留 ID 對照

結論：AbstractArchive 是正確的起點——骨架、參數化、排程整合、既有效能教訓可直接沿用，不需另造機制。但要補的不只兩項：分區表搬遷游標、首次全量搬遷工具、transaction 邊界重寫、TBR ID relation 對策，加上上方紅線的「補跑舊注單」規則。⚠️ 「它已在生產跑所以可套 TBR」是最危險的類比——它證明的是小型月表的 archive lifecycle，不是 20.6 億列 bootstrap、跨表全域唯一與 late mutation 的正確性。

決議六：SBR 走加欄位，但 delete 條件與 GROUP BY 同步加幣別

  1. GROUP BY 加 currency_id——否則兩種幣別被彙總成一列，金額直接混算
  2. delete 條件加 currency_id——否則重跑會把另一種幣別的列一起刪掉
