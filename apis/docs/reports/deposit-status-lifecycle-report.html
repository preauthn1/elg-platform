1狀態值總覽（OrderStatusEnum）

代收與線下訂單共用 app/Enums/OrderStatusEnum.php（Order model）。關鍵：回調確認成功是 1SUCCESS（未上分），真正加值後才進 3DEPOSIT_FINISHED。

值Enum case語意終態說明
0CREATED建立訂單—等待三方回調 / 後台審核；唯一可被回調修改的狀態
1SUCCESS建立成功，未上分—三方回調確認成功，等待加值（鎖分模式會停在此）
2FAILED失敗 / 審核不通過✓回調失敗、過期取消或後台拒絕
3DEPOSIT_FINISHED已上分✓餘額已加值，活動 / 流水 / 報表皆以此為準
4WAITING_MANUAL_DEPOSIT等待人工上分待人工回調成功但金額與訂單不符，轉人工確認

2生命週期狀態機

線上代收主流程走 APIs；自助開分的審核、手動上分、重置狀態走舊 API_Agent。

回調成功金額不符回調失敗

鎖分模式（event_mode > 0）：停在 1 成功 不上分，只發 TG 通知，需後台介入。
自助開分：會員轉帳後上傳截圖 0 → 1（待審核），由舊 API_Agent 後台審核：通過 → 上分 → 3、拒絕 → 2 失敗。會員取消、或收款帳號已不可用時 0 → 2。
4 待人工：人工確認金額後，在舊 API_Agent 後台手動上分（先寫 1 再上分）→ 3 已上分。手動上分對 3 以外的狀態都可用。
重置狀態：舊 API_Agent 後台可把 0 與 3 以外的單重置回 0。
關鍵差異 vs 代付：代收「回調成功」只到 1 SUCCESS，加值是獨立第二步（PaymentService::updateMemberBalance）才寫 3 DEPOSIT_FINISHED。

4上分機制 1→3

回調成功（status=1）後，由 DepositNotifyController 立即觸發加值；真正寫 3 DEPOSIT_FINISHED 在 PaymentService 內完成。

觸發鏈

  • 1. 回調入口 DepositNotifyController:71：呼叫 Provider depositCallback() → 訂單變 1（或 4/2）。
  • 2. 確認可上分 :83：僅當 status === SUCCESS(1) 才繼續，避免重複上分；會員在鎖分模式（:86）只發通知不上分。
  • 3. 上分 :91 processSuccessfulDeposit()（:128） → PaymentService::updateMemberBalance($order)。
  • 4. 加值並結案 PaymentService:209：先以 lockForUpdate() 重取訂單（:98），更新餘額、寫 TransactionLog，再設 3 + balance + pay_time + payment_cost。

上分時的連帶寫入（皆在同一交易內）

  • 會員餘額 / 多錢包餘額加值（Common::numAdd），寫 TransactionLog / WalletTransactionLog。
  • 訂單的支付商手續費 payment_cost（依渠道成本與最終點數計算；回調已寫實際值的沿用）。
  • 充值稽核流水 FlowLimit（依 DEPOSIT_FLOW_LIMIT_RATE）。
  • VIP 稽核流水 VipFlowLimit（倍數為 0 時直接 CALL SP_calc_member_vip_deposit_amount）。
  • 充值獎勵 CALL SP_event_deposit；若為首充再 CALL SP_event_invite_deposit 發下線獎金。
代理 vs 會員：order->agent_id > 0 時，updateMemberBalance() 在 PaymentService:83 轉交 updateAgentBalance()（:336，加值後同樣設 3，:403）；會員留在 updateMemberBalance()。兩者各自管理獨立交易並 lockForUpdate()。
