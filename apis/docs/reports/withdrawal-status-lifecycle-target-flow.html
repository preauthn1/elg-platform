一分鐘摘要

只想快速掌握這次改造的讀者看這一節就夠；細節與依據在後續章節。

面向重點
發生了什麼發版終止舊的應用程式實例（pod）時，進行中的代付請求連同資料庫紀錄一起消失——支付商已出款，我方後台卻查無代付單，訂單還退回「可再次發起代付」的狀態（op#2831，兩筆實例）。
核心改法把「發起代付」拆成兩段各自提交的短資料庫步驟，送出支付商請求的動作放在兩段之間。效果：第一階段提交後，訂單即以「代付提交中(21)」擋住重複發起；在那之前被中斷，可安全重新發起；請求紀錄建立之後被中斷，一定留有可查證的資料——不會再出現「支付商已出款、我方毫無痕跡」。
訂單狀態調整廢除「三方查證中(23)」；允許接收支付商回調通知的狀態改為「代付提交中(21)」與「代付處理中(22)」；支付商明確拒絕時一律轉「三方失敗(29)」，不再退回「通過(3)」。
營運影響後台在 21／22 移除「調整為等代付款(3)」按鈕，新增「填寫三方單號（支付商訂單編號）」（→22）與「修改為代付失敗」（→29）兩顆按鈕；標記失敗前必須先向支付商確認查無此單，否則重新發起會造成重複出款。
尚待確認「三方失敗(29)」不再接收回調的風險知悉、工程端人工補救命令的去留、如何主動發現停留在 21 的訂單（詳見第 5 節）。

1事故原因：資料庫事務把三方請求包在裡面

目前發起代付的整段處理，從鎖定訂單到送出三方請求，全部包在同一個資料庫事務（DB::transaction()，Agent/WithdrawalController.php:91）裡面，一路包到第 147 行才呼叫支付商送出 HTTP 請求。代付請求紀錄（withdrawal_payout_records）雖然刻意設計成「送出請求之前先建立一筆待處理紀錄，以便留下痕跡」，但它同樣在這個事務裡面。

發版時 Kubernetes 會逐步以新的 pod 取代舊的 pod。舊 pod 上的 PHP 程序被強制終止後，資料庫連線中斷，這個尚未提交的事務就會被資料庫回滾（rollback）——連原本要留下的痕跡也一起消失。結果就是支付商已經出款，我方卻查不到任何紀錄。

造成的結果：支付商已出款，我方完全沒有紀錄（後台查無代付單），而且訂單退回到還可以再次發起代付的狀態。除了對帳查不到之外，也存在第二次出款的風險。客服端看到的現象，就是工單描述的「支付商有代付單但系統查不到」。
事務被回滾的直接證據：資料庫的流水編號取用後即使回滾也不會歸還，「編號已被取用、資料列卻不存在」就是回滾的鐵證。兩次事故各留下一個永久缺號：
• 301553（2026-08-06，位於 09:35:11 與 09:35:30 兩筆之間）
• 307918（2026-08-11，位於 05:56:05 與 05:58:23 兩筆之間，時間均為 UTC）
兩個缺號的時間區間，正好包住 pod 被終止的秒數，也包住支付商後台那兩筆查無單的單號時間。
無法靠程式偵測來解決：程序被作業系統強制終止時，任何程式都無法攔截，也沒有任何收尾程式會被執行；事務回滾是資料庫端偵測到連線中斷後被動進行的，那個時間點我方已經沒有程式在運作。就算偵測得到，請求已經送出去收不回來、事務也還沒提交，沒有任何安全的補救動作可做。正確的方向是讓流程在任何一個時間點被中斷都是安全的，而不是設法在被中斷前搶救。
另一條防線已於 2026-08-14 落地（合併 master，待部署）：調整 PHP 服務的關閉行為，發版時先等進行中的請求跑完（上限 130 秒）再關閉——原本的設定是「收到關閉訊號就直接終止」，本次事故正是這個情境。但這只縮小風險窗口，無法消滅：超過等待上限、或機器層級的異常終止仍會強制中斷，因此本頁描述的事務邊界改造仍有必要（部署設定細節見 op#2831）。

2改造後的目標流程

把現在的單一長事務，拆分成兩個階段的短事務，並把送出三方請求的動作移到這兩個事務之外。第一階段事務負責鎖定訂單，並把「準備送出代付」這件事寫進資料庫並提交；接著在不被同一個事務包覆的情況下，建立代付請求紀錄、送出三方請求、依同步回應回填紀錄；最後由第二階段事務寫入本次處理後的訂單狀態。防止重複送出的責任，從「長事務持續鎖住訂單」改為「已經寫進資料庫的狀態 21」。

第二階段事務必須加上條件才寫入：事務拆分後會出現一個新的競爭狀況——支付商的回調有可能比第二階段事務更早送達，並且已經把訂單定案為 24。這時候比較晚回來的第二階段事務如果無條件覆寫，就會把已經定案的結果推翻。因此第二階段事務必須加上「訂單狀態仍為 21 時才寫入」這個條件。
防止重複送出的責任轉移：目前是靠「長事務加上鎖定訂單，而且這個鎖一直持有到三方請求結束」；改造後改為靠已經寫入資料庫的狀態 21（21 不在可發起代付的狀態清單 3／29 之內）。訂單鎖在第一階段事務提交後就釋放，不會再因為等待三方回應而長時間佔用資料庫資源。
順帶消滅的既有缺陷：目前「請求逾時就把訂單轉為 23 鎖住」這道保護本身寫在事務裡面，只要後續任何一個步驟拋出例外，這道保護就會跟著被回滾。過去曾實際發生一次（事件編號 op#2784）：轉為 23 之後，程式接著寫入代付請求紀錄的 info_1 欄位，因內容長度超過該欄位上限而拋出例外，導致同一事務內先前寫入的 23 也一併回滾，訂單退回可重送狀態。改造後 23 連同這條轉換一併廢除：結果未明時訂單本來就停留在已提交的 21，「保護被同一事務回滾」的問題不復存在。
廢除 23 之後的狀態語意：21 一個狀態承接「請求進行中」「流程被中斷」「結果未明」三種情況——三者的人工處理流程本來就相同（帶我方交易號到支付商後台查證：查無此單標記 29、查到此單補填三方單號轉 22），維持兩個狀態沒有額外資訊量。現有 23 訂單的過渡處理見第 5 節。
