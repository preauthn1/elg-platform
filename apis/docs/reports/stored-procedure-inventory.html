1盤點總覽

起因：決議 ⑥ 定調「受影響的 SP 改寫為 PHP 走 Queue」，但沒有人盤點過 SP 的全貌——包含到底有幾支、哪些還在跑、哪些其實已經沒人用。本份盤點回答這三題，並提供改寫成本的量化指標。

先講一個判準，否則整份盤點會被誤讀：SP 的呼叫來源有三處——① MySQL 排程器（EVENT）② 其他 SP 互相 CALL ③ 應用層程式碼。

資料庫層（①②）零引用的有約 220 支，但這不等於死代碼：SP_transfer_bet_record_* 那 73 支注單轉檔是由應用層呼叫的，ADMIN_* 那 123 支本來就是人工手動執行的維運工具（備份搬檔、資料檢查、清理），不掛排程是正常的。只有三處都沒有引用才是死代碼候選。

3複雜度與改寫成本

決議 ⑥ 要把 SP 改寫成 PHP＋Queue，成本不能只看支數。以下四個指標是從 ROUTINE_DEFINITION 實測統計出來的，用來判斷哪些適合改寫、哪些不適合。

指標支數／數值對改寫的意義
含 CURSOR 游標76 支（22%）游標＝逐列處理。改寫 PHP 時通常變成 chunkById() 迭代，語意可對應但要重新設計批次邊界與失敗續跑。這是改寫工作量的主要來源
含迴圈（WHILE／LOOP）103 支（29%）與游標常同時出現。迴圈內若有寫入，改寫時要決定「整批一個交易」還是「逐批各自交易」
含交易控制
（START TRANSACTION／COMMIT）		僅 11 支 最值得注意的一項：340 支沒有顯式交易控制，靠 MySQL autocommit 逐句提交。改寫成 PHP 時若直接包上 DB::transaction()，交易邊界與鎖持有時間都會改變——原本逐句提交的長時間批次作業，包成單一交易可能造成鎖等待甚至超時。這是改寫的隱形風險，不是照抄邏輯就好
含動態 SQL（PREPARE）僅 1 支好消息。動態 SQL 是改寫最痛的樣態，全庫只有 1 支
定義長度平均 4,410 字元
最大 48,123		超過 10,000 字元的有 23 支——這批是「改寫成本集中區」
呼叫其他 SP248 支定義含 CALLSP 之間耦合普遍。改寫必須整串一起改，不能單支抽出——否則 PHP 版與 SQL 版會混用同一份中間表

關鍵動態組字呼叫讓「靜態比對」無法窮舉注單轉檔 SP

RD-Studio-01 有 8 處把 SP 名稱用變數拼出來（$vendor_tname 組字），出現在 SummaryBetRecordCommand、NewSummaryBetRecordCommand、GetM8betBetRecord、GetLfc888BetRecord、GetWbetBetRecord、GetBolakk4dBetRecord、GetGfg2BetRecord、Tools/Summary/GameVendor。

交叉檢查4 支「應用層有呼叫，但 TPower 資料庫查不到」

  • SP_shareholder_payout_log——API_Agent 兩處呼叫（Shareholder/V2/ShareholderController、ShareholderController）
  • SP_reset_shareholder_share_by_agent——API_Agent 呼叫（ShareholderController）
  • SP_transfer_bet_record_terra、SP_transfer_bet_record_allbet——RD-Studio-01 呼叫

後兩支是遊戲商別，TPower 未接該遊戲商就屬合理。但前兩支是股東分潤功能、與遊戲商無關——在 TPower 呼叫這兩支會直接失敗。兩種可能：① 該段程式碼是死路徑（沒人走到）；② 是真實的線上錯誤但未被發現。建議另案查證，不屬多幣別改造範圍。

未驗證：本次只查 TPower 一站，其他白標可能有這兩支。
