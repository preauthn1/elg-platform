2生命週期狀態機

從會員申請到代付完成的完整流轉，分四階段：① 後台審核（舊 API_Agent）→ ② 處理通過 / 三方失敗單（發起代付 / 退款 / 已轉帳）→ ③ 代付執行（#4137 兩階段事務）→ ④ 三方回調 / 人工定案。節點上 ↩ 為後台手動回退、↻ 為再次發起代付、↺ 為原地更新不轉態（回邊詳見圖下註記）。

21 的四個出口（#4137 核心設計）：①三方回調自動定案 21→24 / 21→29——21 已納入放行集合（WithdrawalPayoutTrait.php:57，註解明載「結果未明／pod 中斷停留的單，回調正是定案依據」）；②後台「填寫三方單號」21→22（WithdrawalPayoutManualService.php:75，守衛 :67 僅允許 21）；③後台「修改為代付失敗」21/22→29（:131，守衛 :117-118）；④兜底命令 withdrawal:resolve-payout（ResolvePayoutOrder.php:142）。另有排程掃描每 5 分鐘掃出停留逾 10 分鐘的 21 單發告警（AlertStuckSubmittedWithdrawal.php:64、routes/console.php:80），本身不改狀態。
兩階段事務與 attempt token：第一階段短事務只做「校驗＋鎖 21＋寫 token」後立即提交（WithdrawalPayoutService.php:104），三方 HTTP 請求在事務外發出；第二階段另開事務寫回結果（:313 / :329）。此拆分即 op#2831 的根治——舊設計整段包在單一事務內，發版 rolling update 砍 pod 時整筆 rollback，造成「三方已出款、我方連 payout record 都沒留」。token 用途＝第二階段以「third_party_response 是否仍等於本次 token」判斷這個 21 是否仍屬本次發起（:242-266），不依賴秒級時間戳，同一秒內連續改狀態亦不誤判。
結果未知＝不轉態（#4137 改變點）：三方請求逾時／連線例外時，訂單停留 21 並發 BotNotify 告警（WithdrawalPayoutService.php:302，return 於 :307），不再轉 23。舊行為（21→23）已於 #4137 廢除——21 與 23 的人工處理流程本就相同，兩個狀態沒有額外資訊量。
↩ 三方同步明確拒絕：一律轉 29（#4137 改變點）：白名單制（結構完整＋驗簽通過＋業務碼在該 provider 明確拒絕白名單內＝可證未建單）成立時，不再還原發起前狀態（3 / 29），改為一律寫 29（WithdrawalPayoutService.php:313，同時清空 attempt token），可重新發起。舊 API_Agent 仍是還原原狀態（WithdrawalPayoutController.php:569），兩系統此處行為已分歧。
29 已移出回調放行集合（#4137 改變點）：WithdrawalPayoutTrait.php:71 對 29 的回調拒絕並告警。理由＝29 允許重新發起代付，若同時放行補送回調，會與新一輪發起產生競態。此舉推翻 fa73933ad（2026-04-30）「29 放行以防營運重發」的舊設計——改由 21／22 兩態承接回調定案，29 不再是回調可寫入的來源。
查單擴充點（21→22 的第五條路徑，尚未接入任何 provider）：WithdrawalPayoutQueryService::tryResolveSubmitted() 對停留 21 的單向三方查單，FOUND_ACCEPTED 時補回三方單號並轉 22（:147）。介面為 SupportsPayoutQuery，掛鉤在排程掃描告警之前；逐家 provider 接入屬另案（PayMate /query 為候選首家）。
↩ 後台回退按鈕（→3）：22→3 強制解除代付、4→3 退回通過，同走舊 reviewOrder 的 elseif ($order->status != 1 && $request->status == 3) 分支（:754），並非無副作用：①該單洗分紀錄 TransactionLog type 5 的 status 改為 9（:757）；②因 request.status != 4，check_time 為空時補寫 check_time／operator（:643-644）；③22→3 額外清空 third_party_order_no（:639）。狀態本身由 :795 $order->update($data) 寫入。21→3 這條路已不存在——舊系統對 21 的訂單一律拒絕（200205，見「舊後台審核 reviewOrder 深入」一節）。
終態：24 / 2 / 9。4 非終態（可 4→3）、29 非終態（可重試）、23 已移除（只剩舊後台端點認得，已無訂單可觸發）。
新舊系統分工：1 → 2 / 3（待審核 → 拒絕 / 通過）、退款 9、已轉帳 4 全部來自舊 API_Agent 的 reviewOrder 單一審核端點（後者兩項是對「通過(3) / 三方失敗(29)」訂單按鈕觸發，非從 1 直接退款）。代付段 21/22/24/29 新舊並存，但兩系統行為已分歧——同步明確拒絕時 APIs 轉 29、舊系統還原原狀態。#4137 的人工定案兩支接口（填寫三方單號／修改為代付失敗）只在 APIs（Agent/WithdrawalController.php:75 / :96），後台 WEB_AgentBackend 按鈕已改接這兩支；舊系統 #4090 的 23 兩端點已無訂單可觸發（23 已於 2026-09-16 移除）。舊後台對 21 的訂單一律拒絕操作（200205 守衛，2026-08-20 上線）。
