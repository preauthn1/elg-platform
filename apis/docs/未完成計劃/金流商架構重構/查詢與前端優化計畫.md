## 1. 簡化支付渠道查詢（第一批・已實作）

### 問題根因

原本由 `OrderType` 發起主要查詢，JOIN `agentCashFlowOrderTypes`、`agentCashFlow`、`cashFlow`、`orderTypeNames`，並在不同表重複檢查 `status`，形成 4 層巢狀 `EXISTS` 過濾鏈：最有選擇性的條件（`agent_group_id`）埋在第 2 層，優化器只能以 duplicate weedout 臨時表收斂，可讀性低且效能差。

### 方案（2026-08-07 拍板：平行 EXISTS，行為零變更）

直接以 `agentCashFlowOrderTypes` 為主表查詢：

- `type`／`status` 一律查**權威欄**：`cash_flows.type = 1` 騎驗 `cash_flows.status` 的同一個 EXISTS，額外成本為零（2026-08-07 codex 複審修正：不用 denorm 欄 `acf.cash_flow_type`——可為 NULL 且靠每日排程補償，不支撐即時查詢）；
- `order_types.status`／`cash_flows.status` 的**即時檢查保留**（巢狀深度 4 → ≤2 的平行／淺巢 EXISTS）。

**為何不是字面的「只剩 2 個 EXISTS」**（EXPLAIN 實測，TPower group 674）：

| 對照 | 結果 |
|---|---|
| 保留 status／type 即時檢查的成本 | 各為既有 semi-join 上的 `ref`/`eq_ref` 索引點查（微秒級），外層另有 60 秒快取 |
| 拿掉 status 檢查的行為變更 | 實測差 1 列：停用中渠道（`order_types.status=0` 的 AliPay）會外洩回充值頁 |
| 最終計畫（TPower＋VWorld 皆同） | `cf(idx_cash_flows_type) → acf(idx_agent_group_cash_flow) → acfot(idx_cashflow_status_type) → ot(PK)`，全鏈走索引；相比舊查詢**消除 duplicate weedout 臨時表**，僅剩 `ORDER BY` 對 ~200 列的 filesort（可忽略），既有索引足夠、不需新增 |

結論：各層 `status` 是營運的**獨立開關**（AliPay 案例證實），即時檢查天然尊重此語意；嚴格縮到 2 個 EXISTS 需先建 status 同步機制，收益微秒級、複雜度不成比例，不採。

### 重複 ACFOT 防線（2026-08-07 codex 複審補強，二審後升級 DB 約束）

- 語意契約：同 `(agent_cash_flow_id, order_type_id)` 至多一筆未軟刪列（啟停走 `status`，不以第二列表達）；**同群組跨 ACF**（同金流商多商戶號）掛同一 `order_type` 屬合法配置，前端查詢取最早建立（最小 id）——舊查詢無 `ORDER BY`、重複時行為未定義，此為**契約化**的確定性規則（非宣稱等價）；
- **終防線＝DB 層**：`is_live` virtual generated column（live=1／軟刪=NULL）＋ `uq_acfot_live_link` unique index，蓋住 Observer 蓋不住的併發 check-then-insert race、`restore()`（僅動 `deleted_at`）、cascade restore 的 bulk update（migration `2026_08_07_180000`）；
- **migration 自帶 preflight**：`up()` 先以與 unique index 完全同 scope（`deleted_at IS NULL`、不分 status）自檢重複，有即 fail loud 列出重複 pair——各站**部署當下**自動把關，正確性不依賴事前盤點的時效性；
- `AgentCashFlowOrderTypeObserver` guard 保留為 Eloquent 路徑的友善錯誤訊息層；
- 測試涵蓋：guard 循序五案例＋raw insert 繞過、restore 碰撞兩個 bypass 案例（皆 `QueryException` fail loud）。

### 證據附錄

**六站重複盤點・migration preflight**（範圍與 `uq_acfot_live_link` 一致：所有未軟刪列、**不分 status**——codex 終審指正原掃描誤加 `status=1` 後修正）。此掃描為資訊性快照；部署時的正確性由 migration 內建 preflight（同 SQL scope、fail loud）把關：

```sql
SELECT agent_cash_flow_id, order_type_id, COUNT(*) AS cnt,
       GROUP_CONCAT(id ORDER BY id) AS acfot_ids, GROUP_CONCAT(status ORDER BY id) AS statuses
FROM agent_cash_flow_order_types
WHERE deleted_at IS NULL
GROUP BY agent_cash_flow_id, order_type_id HAVING COUNT(*) > 1;
```

**最終查詢 EXPLAIN**——SQL 為 `OrderTypeService::getOrderTypes` 主查詢經 `toRawSql()` 取得的 production 原文（`select *`、含兩層 `deleted_at is null`），非人工精簡版：

```sql
EXPLAIN select * from `agent_cash_flow_order_types` where `status` = 1
and exists (select `id`, `cash_flow_id`, `rate` from `agent_cash_flows`
  where `agent_cash_flow_order_types`.`agent_cash_flow_id` = `agent_cash_flows`.`id`
  and `agent_group_id` = ? and `status` = 1
  and exists (select `id`, `name` from `cash_flows`
    where `agent_cash_flows`.`cash_flow_id` = `cash_flows`.`id` and `status` = 1 and `type` = 1)
  and `agent_cash_flows`.`deleted_at` is null)
and exists (select * from `order_types`
  where `agent_cash_flow_order_types`.`order_type_id` = `order_types`.`id` and `status` = 1)
and `agent_cash_flow_order_types`.`deleted_at` is null order by `id` asc;
```

### status 同步（2026-08-07 拍板：移除，不做）

原計畫「`cashFlow`／`OrderType` status 變更 → Event → Listener → `SyncOrderTypeStatusJob`（Redis 鎖）批量更新 `agentCashFlowOrderTypes.status`」**整項移除**：

- 其唯一目的（補嚴格 2 EXISTS 拿掉的即時檢查）已因採平行 EXISTS 而消失；
- ACF → ACFOT 的下架連動已由 `AgentCashFlowObserver` 上線（含審計、重啟不對稱、軟刪連動），CF／OT 來源若做盲目批量同步會與該設計哲學衝突（誤開營運個別停用的渠道）；
- 若未來有其他消費者需要 `ACFOT.status` 當彙總狀態再重新評估。

### 洗分頁面

- **問題**：`frontend/api/withdrawal/banks` 回傳資料過於龐雜，前端需自行過濾；且疑似錯誤調用 deposit 端點（需確認）。

| 項目 | 現況 | 目標 |
|---|---|---|
| 查詢參數 | 無過濾，回傳全部銀行 | 加入 `currency_id + order_type_id` 過濾 |
| 快取 key | 無或粒度過粗 | `withdrawal_banks:{agent_group_id}:{currency_id}:{order_type_id}` |
| 銀行名稱 | 逐筆查詢 | 以 `agentBanks + agentBankNames` 為主，名稱預先寫入快取 |
| N+1 防護 | 無 | Observer 監聽 `agentBankNames` 異動，主動清除對應快取 |

> 洗分 banks 端點的資料面（`banks` / `agent_banks` 收斂）由 [軌道①銀行收斂](./銀行收斂/) 處理；本軌只負責查詢參數、快取與回傳瘦身。
