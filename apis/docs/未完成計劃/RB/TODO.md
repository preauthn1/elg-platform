### §1-1 代付查表化開閘——逐站現況與前置

**這件事在幹嘛**：代付要把「會員選的銀行」換成「送給金流商的銀行代號」。現在的做法是拿一串 JSON 逐筆比字串，新做法改成查 `cash_flow_banks` 這張表。核心代碼已進 master（`62537ba96`），但**開關 `PAYOUT_BANK_LOOKUP_PROVIDERS` 是空的＝現在全部還走舊路**，所以 order-155 那類問題屬於「機制備好了、但還沒真的修好」。要開誰、什麼時候開，決策者是 PM。

**一站開閘要走三步**：①該 provider 設進 `PAYOUT_BANK_LOOKUP_PROVIDERS` 這個環境變數、部署即生效 ②驗那站零 drift ③零 drift 之後才把舊的 JSON 比對路徑拆掉。🔴 **2026-09-22 實查部署專案（gff-cicd，project 526）：正式站的 `.env` 由 `helm-charts/apis/.env.tpl` 樣板渲染，樣板裡沒有 `PAYOUT_BANK_LOOKUP_PROVIDERS` 這一行，各站 `values_<site>.yaml` 也搜不到** ⇒ 現在沒有任何正式站填得了這個開關。開閘前要先在部署專案加一行（比照樣板「# 開關」那一段的寫法，值從各站 values 檔取、預設空字串），再在要開的站的 values 檔填金流商名稱。那個專案在 SRE 手上，改動要走它的 MR。**AllPay 不可開**（parity 不過）。

🔴 **開閘必須逐站驗過，不能整批開**——同一個金流商在各站的資料落差極大，硬開會斷付。

🔴 **開閘還有一個全站前提，下表的「✅ 可開」都要先滿足它**（2026-09-16 圓桌會審補登）：master 的 `config/payment.php`（開關設定的註解）寫明，名單放進任何一家之前，查碼的兩條路徑與比對命令都要先改成「逐字相同才算命中」。✅ **2026-10-07 已滿足**：本分支經 MR !2377 合進 master 並發版（`release_202610071859`）。master 現在查表用 `BINARY` 逐字比對（`WithdrawalPayoutTrait::lookupProviderBankCodeFromTable()`），JSON 路徑用 `!==`（`convertPayoutBankCodeFromJson()`），比對命令 `cash-flow:verify-payout-bank-parity` 也用 `BINARY`。原本寫「清完缺口 PM 就能隨時開」**不成立**。VaderPay 與 TakaPay 自己查對照表、不經統一入口，它們的 `Withdrawal.php` 在 master 也已是 `BINARY`，見「VaderPay 與 TakaPay 代付不走銀行碼統一入口」那段。

### 2.1 PTSW 注單重複的最後一道防線（🟡 待實作・M・待立工單）

**這件事在做什麼**：PTSW 的注單表 `ptsw_deal_records` 要加一個複合唯一鍵 `(bet_id, transaction_code)`，讓資料庫本身擋掉重複寫入，順便統一各白標已經漂移不一致的表結構。

**它是「最後一道防線」不是主要防線**：前一案「重複回調 race 的前向防護」（在程式裡用 MySQL named lock 序列化）**已經收案**，紀錄見 [工作紀錄／已完成歸檔](工作紀錄/已完成歸檔.md) §6.1。這一道是**萬一程式那層漏了、資料庫還能擋住**。

**動手前的順序**：要先**清掉各站歷史上已經重複的列**，才加得上唯一鍵。

🔴 **加唯一鍵的同時必須一起改的一件事（原文稱「P1-2 約束」，指的就是這個 backstop 階段的實作約束）**：

`createDealRecord` 目前的寫法是「撞到唯一鍵錯誤（MySQL 1062）就接住、然後重新查一次既有列」。**現況是安全的**——有 named lock 序列化，競爭者一定已經 commit 才輪到你進交易，你的快照必然看得到它那列。

但**一旦加了唯一鍵，1062 就可能在鎖保護外被觸發**（例如鎖的 key 算法不一致、或跨 username 出現同一組 `(bet_id, transaction_code)` 的極端情形）。這時那次重新查會撈到 `null`——因為**你的交易快照時點早於競爭者 commit**（`DB::transaction` 預設 REPEATABLE READ）——接著 `throw $e` → 整個交易 rollback → INTERNAL_ERROR，**1062 從「明擺著的死路」變成「靜默吞錯」**。

⇒ **backstop 工單必須在那個 re-select 處改用 `READ COMMITTED` 或加 `lockForUpdate()`，不可以只加唯一鍵就了事。**

出處與完整論證見 `docs/reconcile/vendors/PTSW.md:746`（timo review 2026-07-08）。⚠️ 別寫成「§4」——那份檔案沒有全域編號：四個一級標題區塊裡，第一塊完全不編號，其餘三塊各自從 1 編起，**全檔因此有三個「## 4.」**（`:393`／`:634`／`:734`），光寫節號找不到。

**六站的編號與時間範圍全部零重疊**，這就是「孤本」的證據：紀錄庫那邊的編號一律從 1 開始（自己一套序號），時間一律停在 2025-11-20 19:32 到 19:33，剛好是 `b4c2775d9`（取消搬遷紀錄表）那個動作的時刻；主資料庫那邊則一律從 2026-04-30 才開始。中間空了五個月，誰也沒接上誰。

**為什麼會漏搬**：當初的搬運工具 `db:move-tables`（本案已刪除）的做法是「照樣建一張空表（`CREATE TABLE LIKE`），再把資料倒過去（`INSERT SELECT`）」，**全程不含 `DROP`／`DELETE`**，而且**只要目標已經存在就整張跳過**。偏偏主資料庫的 `command_logs` 從 `2025_09_08_074831` 那次結構變更起就一直存在 ⇒ **這張主表每次都被跳過，從頭到尾沒被複製過**。

對照組可以佐證：VWorld 的 `command_logs_202510` 兩邊都是 11,361 列，因為當時主資料庫沒有這張月份分表，所以複製成功了。

另外還有一些月份分表沒清：Alfawin77 的 `_202509`（39,038 列）與 `_202510`（93,937 列）、VPlus33 的 `_202509`（39,038）與 `_202510`（93,788）、VWorld 的 `_202510`（11,361，主資料庫有同樣筆數，代表這張有副本）。`activity_logs` 六站幾乎都是空的（只有 Yes2Win 12 列）。

#### 2.2.2 改法：分兩階段，不要一步刪掉

比喻：**先把東西搬到儲藏室貼上「準備丟」的標籤，放三個月沒人來要，再拿去丟。**

1. **第一階段**：把表改名（`RENAME TABLE <t> TO _deprecated_<t>`）。改名是瞬間完成、不多佔空間、隨時可以改回來。改名後任何程式來讀寫都會找不到，等於「停用但沒銷毀」。
2. **第二階段**：觀察期（建議至少三個月）過了、期間沒有人來索取，才真正刪除。

**同時要補的六件事**（會審提出，都是「讓這支命令不容易誤傷」）：

- [ ] **禁止再「沒指定就全掃」**：`--connection`（要對哪個資料庫動手）改成必填，拿掉「不指定就掃全部 8 條連線」的預設 `[Rorin C1／Timo／Marz]`
- [ ] **預設改成只看不做**：現在是預設就會刪，要反過來——真的要刪必須明講 `--execute` 並附上 `--reason`（理由）。跟同專案的 `repair-orphans` 一致 `[Rorin]`
- [ ] **加一道「你確定在對的環境嗎」的確認**：`confirmExecutionEnvironment()`，專案裡已經有 6 支命令在用 `[Rorin+Timo+Marz]`
- [ ] **補測試**：`resolvePrefixes()`（決定哪些表名可以碰的那段）至少三個案例。它目前是整批變更裡**唯一會做不可逆刪表、卻一個測試都沒有**的檔案 `[Rhyse+Rorin]`
- [ ] **出錯不要吞掉**：現在任何例外都被吃掉、回傳值永遠是「成功」；改成只要有一條連線不是乾淨結束就回失敗 `[Timo]`
- [ ] **查表清單時只認真表**：查詢資料庫目錄時限定 `TABLE_TYPE='BASE TABLE'`。紀錄分庫裡常有「捷徑」（VIEW）指回主資料庫，把捷徑當成表刪掉會出事 `[Timo]`

#### 2.2.3 執行時的七個限制（改造完成後逐站上線時仍然適用）

1. 🔴 **切了白標不等於切了紀錄庫**。設定上，`log` 這條連線只換掉「資料庫名稱」（`database`），**主機位址與帳密繼承共用設定 `$mysqlCommon`**（也就是 `DB_HOST`）；白標連線則是讀（`read`）與寫（`write`）兩邊都換、主機各自獨立。實測：指定 `-e DB_CONNECTION=VPlus33` 之後再用 `--connection=log`，列出來的仍然是開發環境的表。**你以為切到 VPlus33 了，其實紀錄庫還連在原地。**
2. 因此**要處理某一站正式環境的 `xsgcasino_log`，只能在那一站自己的執行環境裡跑**。
3. 🚫 **絕對不可以整個庫刪掉**：`access_log_third_party_*`（舊系統 API_Frontend 在寫）與 `access_log_agent_*`（api-internal 與 API_Agent 在寫）都還活著。
4. ⚠️ **保護機制靠的是「表名開頭」白名單，不是「結尾幾位數」**。舊註解說「六位數的比對規則不會誤傷八位數的分表」，這個前提**不成立**——`API_Frontend/Controller.php:156` 就有一張 `access_log_frontend_` 加 `date('Ym')` 六位年月的月份分表。要擴充白名單前務必重新評估。
5. ⚠️ **`resolvePrefixes()` 看起來有兩道條件，實際只有一道**。紀錄庫的名稱是由 `env('DB_DATABASE') . '_log'` 串出來的，必然以 `_log` 結尾，所以第二個條件永遠成立。隔離目前還有效，但**只剩一道防線**。
6. 上線前逐站確認 `ACTIVITY_LOGGER_DB_CONNECTION` 是空的，否則記錄套件會把 `activity_logs` 又寫回紀錄庫 `[Timo]`。
7. 兩個階段都做完、命令回報「沒有符合的資料表」之後，這支命令本身才可以刪掉。

### 2.12 會員 token 撤銷的兩項遺留（🟡 待實作・S）

> 來源：2026-08-07 `refactor/member-token-revoke` 的 Timo × Codex 雙審（修訂記錄原在 `2026-06-24-member-token-revoke` 的計劃文件（設計文件已依落實即刪除原則移除，用 git log 考古））。**兩項都是既有的債**，當時經裁決不併進那個 MR。

1. **撤銷 token 之後，舊 token 可能被別的請求塞回快取（Codex High#1）**：撤銷的流程是「先清快取、再 commit」，中間那個空檔如果有併發請求已經讀到舊的資料庫狀態，它就會把舊 token 寫回快取（`AuthMember.php` 是 cache-first）。該 MR 的「清兩次」只縮小了窗口、沒有根治。根治方向＝把快取鍵版本化，或讓 middleware 在快取命中時補查一次狀態。<br>⭐ **註：鎖帳這個場景有第二道防線**——`AuthMember` 每個請求都會回資料庫覆核 `member.status`。真正的暴露面是**踢線或重新登入之後，舊 session 靠著過期快取續命到 TTL 到期為止**。
2. **登入鎖定那條路徑不是原子的（Codex High#4）**：`LoginController.php:349-362` 的 `$member->save()`／`$statistics->save()`／`revoke()`／`MemberStatusLog::create()` 四個動作**裸奔、沒有包 transaction**（2026-09-08 實查校正；原記 `:311-325` 已漂移），跟 `lockMemberAndRevoke()` 是同一種形狀。收斂方向＝改用 `lockMemberAndRevoke($member, MemberStatusLogTypeEnum::LOGIN_PASSWORD_LIMIT)`。<br>⚠️ **改的時候要注意**：該段的 status 在前面的條件分支就先設好了，中間還夾了一個 `$statistics->save()`——要留意 `before_status`（`:360` 取用）的取值時序，以及 statistics 要不要一起納入同一個 transaction。

### 5.8 VIP 升等禮碼發不出去等 4 個既有缺陷（⏸️ RB 擱置，2026-09-15）

2026-09-15 查 2026-08-27 正式環境回退時順帶查到。**4 項都和那次回退無關，是本來就存在的缺陷**；RB 決定先記下來、暫不處理。以下只查過 TPower，查證過程記在 AI 記憶 `project_vip_deposit_amount_sp_latent_bugs`。

1. **會員 VIP 一次跨兩級升等時，禮碼獎勵發不出去（已有會員少拿獎勵）**
   - 什麼時候發生：會員一次跨兩級以上升等，而且中間那一級的升等獎勵是禮碼（只能下注、不能直接提領的籌碼）。
   - 發生之後：升級本身會寫入，但中間等級的禮碼沒有發，最高等級的待領獎勵紀錄也不會建立。錯誤被上層預存程序接住，只發一則 Telegram 通知。
   - 實際案例：錯誤通知表 `telegram_messages`（2020 年起都有保留）只出現過 1 次。2026-09-13 16:10 UTC，會員編號 1010472 從 VIP 1 級升到 3 級；2 級的 150 禮碼（應自動發放）和 3 級的 500 禮碼（應建立待領紀錄），在領獎紀錄表 `member_vip_prizes` 都查不到。
   - 原因有兩個，要一起修：
     - 用了沒有宣告的變數 `MemberId`（參數名其實是 `p_MemberId`），一執行到就報「Unknown column」。
     - 查會員的禮碼錢包時，拿錢包編號 `mw.id` 去比會員編號。只把變數名改對的話，可能讀到或改到別人的禮碼錢包，所以查詢和更新都要改成比 `member_id`。
   - 位置：`database/procedures/SP_calc_member_vip_deposit_amount.sql`（計算 VIP 升等分數與升等獎勵的預存程序）發獎迴圈裡處理禮碼的那段，約第 126～152 行；接住錯誤的是 `SP_calc_vip_flow_limit`。這段從 2025-06-23 第一次把預存程序備份進 repo 時就存在。
   - 解除擱置時要做：補發交 PM／營運決定（開 op 工單）；修預存程序要開分支走 MR；確認這位會員有沒有被人工補發；查另外 6 站有沒有發生過。

2. **存款單入帳時，呼叫同一支預存程序少帶一個參數**
   - 什麼時候發生：代理開啟 VIP，而且 VIP 流水倍數設為 0。一走到就報錯。目前有沒有代理這樣設：未查。
   - 位置：`app/Services/PaymentService.php` 約第 250 行只帶 1 個參數，正式庫這支預存程序要 2 個。

3. **VIP 經驗值功能（目前只在 develop）上線時，PHP 的呼叫會壞**
   - develop 上這支預存程序改成 3 個參數，但兩處 PHP 沒有跟著改：`app/Http/Controllers/Frontend/ThirdPartyController.php`（第三方介面替會員入帳，帶 2 個）和 `app/Services/PaymentService.php`（存款單入帳，帶 1 個）。
   - 同一個功能上線時還要決定：經驗值紀錄表 `member_vip_exp_logs` 裡，2026-08-27 回退前那一小時留下的 428 筆要不要清掉。清理不能直接改資料庫。

4. **新人挑戰設定表的 `status` 預設值和 master 不一致**
   - TPower 正式庫的 `newbie_challenge_configs` 是 2026-08-27 回退前，用這支 migration 的舊版建立的。master 上的同一支 migration 後來改成 `status` 預設 0（停用），正式庫現在仍是 1（啟用）。
   - 這支 migration 已經登記為執行過，之後跑 migrate 也不會修正。
   - 目前表裡只有一筆設定，2026-09-14 被更新過，沒有看到實際影響。
