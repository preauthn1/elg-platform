# 金流商代收回調盤點

校對日期：2026-10-02（對照 master 1282e9d36）｜狀態：AI 產生，尚未經人工逐家覆核

APIs 目前對接 37 家金流商。這份文件一家一列，整理代收（存款）這一側的四件事：

1. 專案內的 API 文件齊不齊。
2. 回調靠什麼確認是金流商送來的。
3. 回調金額與存款單不同時怎麼處理。
4. 回調會不會改寫存款單金額。

代付不在這份文件的範圍。各家需要修的問題與修法在風險發現資料檔（`docs/reports/data/payment-risk-findings.json`）；各類問題的原理在 `docs/金流接入流程/附錄-常見缺陷類型.md`。

## 覆核範圍

- 關鍵判定重讀過程式碼的有 19 家：A3Pay、AkPay、AntzPay、Ap8Pay、B3Wallet、BillionPay、CCPayment、DgPay、EasyPay、FPay、GMPay、Kira、MajesticPay、MaxPay、PayEssence、TngPin、VtPay、YeePay、ZPay。
- 其餘 18 家的內容來自分派出去的查證，附有檔案與行號，沒有逐一重讀。

## 名詞與判定方式

- 驗簽：回調附帶簽名，程式用密鑰重算後比對。簽名內容有沒有包含金額欄位，另外列一欄。
- 回查：收到回調後，程式主動呼叫金流商的查單 API，以查到的結果為準。
- 狀態 4：存款單的「等待人工確認」狀態（`WAITING_MANUAL_DEPOSIT`）。不會自動入帳，要有人在代理後台按「手動上分」。
- 憑證未配置時擋下：回調一進來是否先檢查密鑰有設定。標「沒有獨立檢查」不代表可以偽造，只代表沒有這道額外檢查。
- 金流商有沒有查單 API，以專案內的文件為準。文件沒寫標「文件未記載」，不代表金流商沒有提供。
- 程式內 IP 白名單只看金流商自己的程式。部署層的限制不在這份文件的範圍。
- 文件完整性只看有沒有這七類章節：代收下單、代收回調、代付下單、代付回調、簽名規則、查單、錯誤碼。沒有評內容品質。

### 依來源驗證方式分組

| 方式 | 家數 | 金流商 |
|---|---|---|
| 有驗簽，簽名含金額 | 24 | A3Pay、AkPay、AllPay、BigPayz、BillionPay、DgPay、EpicPay、FlashPay、GffPay、GlobePay、GMPay、LegendPay、MajesticPay、PayMate、PayPro、QuickPay、Sure、SurePay、TakaPay、TopPay、TrustPay、TtPay、VaderPay、YeePay |
| 有驗簽，簽名不含金額 | 4 | FPay、PayEssence、TngPin、ZPay |
| 有驗簽，金額取自回查 | 1 | CCPayment |
| 無簽名，靠解密或金鑰比對 | 4 | AntzPay、Kira、TgPay、VtPay |
| 無簽名，靠回查 | 1 | B3Wallet |
| 無簽名，也沒有回查 | 3 | Ap8Pay、EasyPay、MaxPay |

「無簽名，也沒有回查」的三家，金流商都沒有提供可用的回調驗簽方式。Ap8Pay 與 EasyPay 的文件寫明回調沒有簽名。MaxPay 的文件在回調欄位列了 hash，卻沒有寫回調的算法（PAYLOH v1.9，附在 target/tickets#4009），工單 target/tickets#3739 貼的代付回調實際範例也沒有 hash。

三家能用的防線只剩金流商的回調來源 IP。程式內沒有檢查，工單 target/tickets#4446 記載維運已確認正式環境入口也沒有限制來源 IP。這部分由 target/tickets#4446（Ap8Pay）與 target/tickets#4449（EasyPay、MaxPay）處理。

## 表三：回調金額的處理

預設行為：把回調金額與存款單金額比對到小數第 2 位，不同就轉狀態 4，不改寫存款單。多數金流商如此，下表只列出與預設不同的。

| 金流商 | 與預設不同的地方 |
|---|---|
| GMPay | 自行處理。回調帶原始金額時，實付多出 1.00 以內就改寫存款單金額與入帳金額並自動入帳，超出才轉狀態 4。沒帶原始金額時不比對 |
| A3Pay | 實付多出 0.10 以內時，改寫存款單金額、手續費、入帳金額；其餘照預設 |
| Ap8Pay | 不比對。無條件以回調金額改寫存款單金額、入帳比例、入帳金額 |
| TngPin | 不比對。回調成功時一律以回調金額改寫存款單金額、手續費、入帳金額 |
| MajesticPay | 不比對。只看金流商的補推旗標決定是否轉狀態 4 |
| CCPayment | 不適用。回調時才建立存款單，金額就是回查到的實收數量 |
| Kira、AntzPay | 回調缺少實付金額欄位時不比對 |
| VtPay | 回調缺少金額欄位時，拿存款單自己的金額比對，等於不比對 |
| AkPay、YeePay、ZPay、DgPay、TtPay | 有比對，但比對的欄位依文件說明是「請求金額」，回調另有「實付金額」欄位沒有用到。TPower 有 1 筆 AkPay 存款單實付 50.60、照 51 入帳 |
| EasyPay | 有比對，比對 `order_amount` 是對的。回調的 `final_amount` 文件寫成實際到帳金額，TPower 資料顯示是扣掉金流商手續費後的實收，不能拿來比對會員付款 |
| YeePay | 不判斷回調的結果碼，驗簽通過一律當成功 |

### 會改寫存款單金額的四家，寫法各不相同

共用流程沒有提供改寫金額的方法，四家都是在自己的回調處理裡直接寫入存款單。

| 金流商 | 入帳金額怎麼重算 | 和共用流程的關係 |
|---|---|---|
| GMPay | 實付金額 × 存款單的入帳比例。不重算手續費 | 不呼叫共用流程 |
| A3Pay | 實付金額 × 存款單的入帳比例，再扣掉重算後的手續費 | 先改寫，再呼叫共用流程 |
| Ap8Pay | 回調金額 × 金流商戶目前的入帳比例。不扣手續費 | 呼叫共用流程時刻意不傳金額，之後再改寫 |
| TngPin | 回調金額 × 金流商戶目前的入帳比例，再扣掉重算後的手續費 | 不呼叫共用流程 |

## 金流商有查單 API、但回調後沒有回查

共 22 家：A3Pay、AllPay、AntzPay、BigPayz、BillionPay、DgPay、EpicPay、FlashPay、FPay、GMPay、LegendPay、MajesticPay、MaxPay、PayEssence、PayMate（含 SpeedPay）、SurePay、TngPin、TopPay、TrustPay、TtPay、VtPay、ZPay。

其中 AllPay 與 PayMate 的程式已經實作查單，只是回調沒有用到。其餘 20 家程式內沒有代收查單的呼叫。

沒有回查不等於有漏洞。有驗簽且簽名含金額的金流商，回調真實性已經有簽名把關，回查是多一層保險。來源驗證弱、又沒回查的組合如下：

| 情況 | 金流商 |
|---|---|
| 金流商沒有提供回調算法，程式沒有限制來源 IP，無回查，金流商有查單 API | MaxPay |
| 解密可被繞過，無回查，規格檔有查單 API | VtPay |
| 簽名不含金額，無回查，金流商有查單 API | FPay、PayEssence、TngPin、ZPay |

## 狀態 4 之後的人工入帳

待人工確認的存款單由舊代理後台的「手動上分」處理（API_Agent 的 `order/manual-deposit`）。

- 只擋兩種情況：存款單已入帳、會員處於鎖分模式。
- 入帳時加的是存款單上現有的入帳金額，不會參考回調金額。
- 操作時會把 `orders.remark` 改寫成操作者的備註，原本存在裡面的回調內容會被蓋掉。回調內容另存於 log，資料庫內沒有其他留存。

相關工單：target/tickets#3527。

## 尚未確認的事項

- 各站部署層是否對代收回調網址限制來源 IP。
- 各家金流商目前在哪些站啟用。
- 「文件未記載」的 13 家，金流商實際上有沒有提供查單 API。
- 表三「比對的是請求金額」那幾家，欄位語意只依專案內文件判斷，沒有對照正式環境的回調內容。
- VtPay 的繞過只確認到解密類別的行為，沒有打整條回調路由重現。
- MaxPay 實際回調的狀態欄位是整數還是字串。程式是嚴格比對整數，若金流商送字串，成功回調會被判成失敗。
- 手動上分的行為是讀本機的共用套件原始碼得到的，各站實際部署的版本是否相同。
