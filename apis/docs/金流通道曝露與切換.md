# 金流通道曝露與切換

要換金流通道（世代切換、provider 替換、新舊並存）前先看這頁。**代收與代付的曝露機制不同，能用的手法也不同**——代收無法灰度、代付天然可灰度。

## 代收＝唯一化制（無法灰度）

`OrderTypeService::getOrderTypes()` 的篩選鏈：

```
acfot.status=1 AND acf.agent_group_id=會員的 cash_flow_group_id AND acf.status=1
AND cash_flow.status=1 AND cash_flow.type=1 AND order_type.status=1
→ orderBy('id')->get()->unique('order_type_id')->sortByDesc('sorts')
```

- ⚠️ **`unique('order_type_id')` 取 id 最小的那筆**（同金流商多商戶號＝合法配置時取最早建立）⇒ 同一個 order_type 下新舊並存時**永遠曝露舊的**，新的必須等舊的關掉才浮上來。**代收做不了灰度。**
  - 唯一化鍵是 `order_type_id` **單一欄位**（不含 cash_flow_id／幣別／acf），而排序的 `orderBy('id')` 是 **`acfot.id`** ⇒ 決定「留哪筆」的是**最小的 ACFOT id**。`sortByDesc('sorts')` 發生在 `unique()` **之後**，只影響顯示順序、不參與取捨（sorts 大但 acfot.id 大的那筆照樣被丟掉）。
  - ⇒ **掛不同 order_type 的通道彼此不壓制、可全部並存曝露**。整條前台鏈**沒有幣別過濾**（幣別綁在 order_type 上）。
- ⚠️ 新舊若掛**不同** order_type 就不會互相壓制，那時切換＝關舊 acfot ＋ 開新 acfot，且**會員看到的通道名稱與數量會變**（新協議的通道粒度可能更細，一條舊的對應多條新的）。
- **有 1 分鐘快取**（key 依 `cash_flow_group_id` ＋ `language_id`）⇒ 切換與回滾都是 **1 分鐘內**生效。

## 代付＝候選清單制（天然可灰度）

`WithdrawalPayoutService::resolveChannels()` → `fetchPayoutChannels(agent_group_id, currency_id)` → `filterChannels(bankCode, bankName, amount, currencyId)`，回傳**一組候選**由操作者挑。⇒ 新舊 ACF 可**同時**在候選中，能先抽少量真單驗新協議。

### 兩個階段看的是不同東西

| 階段 | 讀什麼 |
|---|---|
| 候選清單生成 | `agent_cash_flows.info['available_banks'][*].BankCode_ELG`（另檢 `info.min_amount` / `max_amount`） |
| 送單 | **部分 provider 會直接查 `cash_flow_banks`**——例如 TakaPay 無條件查該表取 `provider_bank_code`，缺列或該欄為空即直接回失敗；另有 allowlist `config('payment.payout_bank_lookup_providers')` 供共用轉碼 |

🔴 **所以「補 `cash_flow_banks` 是白做的」是錯的**——那只對候選清單生成成立。**兩個階段要分開講。**

### 排查候選時的陷阱

- ⚠️ 出款鏈**不檢查** `available_banks[*].status`，但可見性診斷工具**會**檢查 ⇒ **診斷結果與實際可出款性可能不一致**，別把診斷當單一事實來源。
- ⚠️ 候選查詢隱含 **`acf.deleted_at IS NULL`**（`AgentCashFlow` 有 SoftDeletes），且**只檢查 `cash_flows.type`、不檢查 `cash_flows.status`** ⇒ 手動重跑 SQL 要自己補 soft-delete 條件；停用 `cash_flows` 那一層**不會**讓 ACF 從候選消失。
- ⭐ **比對兩筆 ACF 的銀行配置是否相同，必須逐值比 `BankCode_ELG`**，不能只看 `JSON_LENGTH` 與 min/max——曾因此誤判兩筆「逐項相同」，實際一邊是 `Y2WBD01-03`、另一邊是 `BDT0001-03`。
- ⭐ **還要查該 provider 有沒有代付實作**：`PaymentService::getProvider()` 取 `substr(third_party_code, 2)` 對 `config('payment.provider')`；Driver 沒設 `$withdrawal` 時 `AbstractDriver::withdrawal()` 直接拋例外。
- 🔴 **候選為空＝代付根本無法發起**：`fetchPayoutChannels` 回空 → `filterChannels` 回空 → 驗證回「渠道不屬於本代理群組、幣別不符或已停用」，訂單**進不到 21**（停在 2 失敗／9 退款）。⇒ 看到某幣別「訂單有量但零 status=24、且無 21／22」，先查該（代理群組 × 幣別）有沒有 `status=1` 的 `type=3` ACF。
- ⚠️ **前端的提款銀行清單完全不查 ACF**（只查 `banks` 的 `agent_group_id` ＋ `status=1`）⇒ 銀行列與代付通道是**兩套獨立配置**、可長期不一致且無告警，會員「綁得上、出不了款」即由此而來。

## 回調不看 `acf.status`（切換安全的關鍵）

代收與代付的回調 controller 都只 `AgentCashFlow::find($id)` ＋ 檢查 `cashFlow->type`，**完全不檢查 `acf.status`**。

⇒ **停用舊通道不會擋掉未完成訂單的回調**，可以放心「關舊、讓在途單自然收乾」。

⭐ **驗簽憑證綁在回調 URL 的 acf id 上，與訂單、通道都無關**（跨 provider 通用）：下單時 `post_url` 由 `Common::depositCallbackUrl($acf->id)` 產生（路由 `deposit/notify/{agentCashFlowId?}`），回調進來即以該路徑參數 `find()` 取 ACF，用**那筆 ACF 的** `info` 驗簽。這正是「關舊 ACF 安全」的機制保證：舊單回調帶的是舊 acf id，仍用舊憑證驗簽。

🔴 **反面：一個 ACF 只能存一組回調憑證。** 若三方按通道發不同的 callback key（實例：某 provider 的網銀與 QR 兩條通道各有一組），把多通道併進同一筆 ACF ⇒ 其中一條的回調**必定卡在驗簽**、訂單不更新、玩家付款不上分，而且**建置階段零報錯**。⇒ **一通道一 ACF 是硬約束，不是風格選擇。**

⚠️ 兩個邊界：舊單若是**舊專案發起**的，回調打的是舊系統 URL、根本不經這兩支 controller ⇒ 舊路由仍要留；刪掉 provider 實作後，舊單回調會在 `getProvider()` 找不到 driver 而 500 ⇒ **退場必須等在途單清空**。

## 其他結構事實

- **`order_types.cash_flow_id` 存在**＝order_type 綁 cash_flow ⇒ `cash-flow:sync --rename-key=舊=新` 只能在**同一個 cash_flow 內**就地改 key（ot id 不變、關聯自動跟上），**不能把舊 cash_flow 的通道搬到新的**。
- 通道藍圖＝`app/Console/Commands/CashFlow/Data/cash_flows.php`（金流商本體）＋ `Data/providers/{Name}.php`（channels／banks／credentials 骨架），`cash-flow:sync` 照藍圖建 order_type。
- 代收回應型別以 `URL_REDIRECT` 為主流，`HTML_FORM` 只剩少數 provider ⇒ 型別改變不需動前端。
- 🔴 **「ACFOT `status=1` ＋ order_type `status=0`」是刻意的備用配置，不是孤兒**：前台會因 `withWhereHas('orderType', status=1)` 濾掉而不曝露，要啟用只需打開 order_type。但 `check:cashflow-orphans` 會把它報成「類型停用」，而 `fix:cashflow-orphans` 的處置是**把 ACFOT 一併下架** ⇒ 會把備用配置清掉。**跑 fix 前先確認那些列是不是備用配置。**
- 🔴 **憑證錯配是既有工具的偵測盲點**：某通道的 ACFOT 掛到「憑證不屬於該通道」的 ACF 底下時，orphan 檢查不會報（那個 order_type 是啟用的），而且「跨 ACF 掛同一個 order_type」本身合法（同金流商多商戶號）。判準需要「哪個合約名對應哪條通道」的三方合約知識，**無法一般化成 SQL 或命令** ⇒ 建通道後要**人工核對**「每筆 ACFOT 的 order_type 所屬通道 vs 其 ACF 的憑證」。會不會實際生效只取決於它的 acfot.id 是不是最小＝**巧合，不是保護**。
