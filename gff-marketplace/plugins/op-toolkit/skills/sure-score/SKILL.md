# sure-score：工單開工把握度評分（SURE）

一句話版本：**看一張線上問題單，回答「RD 拿現有資訊，能不能直接動工」，給一個 0 到 95 的信心指數，並列出補什麼能加幾分。**

## 名詞速查

| 名詞 | 意思 |
|---|---|
| RD | 研發人員，也就是接單動工的人 |
| op_tickets | GitLab 專案 `target/op_tickets`（project 492），放線上問題單 |
| tickets | GitLab 專案 `target/tickets`（project 365），放需求單；目前不評分 |
| rubric | 評分表：每個維度看什麼、各種情況給幾分 |
| 維度 | 評分的面向，線上問題單有五個：標題描述、可定位性、現象描述、處理訴求、佐證資料 |
| 底檔 | 每個維度先依現況選定的「基本盤」分數，同一維度只能選一檔 |
| 額外分 | 底檔達 ±0 之後，符合條件再疊加的加分 |
| delta | 某個維度最後的加減分數（底檔加額外分） |
| 內容分 | 由語言模型依 rubric 評出的分數，從 50 起算 |
| 格式檢查 | 由固定規則的檢查程式跑的硬規範（站台可否解析、label 是否互斥等），不進分數 |
| 貼上歸零 | 判定內文是複製貼上的對話原文時，所有加分取消、扣分照舊 |
| 有效內文 | 內文去掉連結、markdown 符號、與標題重複的句段、空白之後剩下的字數 |
| trace id | 系統追蹤編號，拿它能在 log 系統直接查到那次請求 |
| GCP log | 部署在 Google Cloud 的日誌系統，可用 trace id 查 |
| TG 群 | Telegram 群組 |
| bot 殼 | 未來自動跑評分並回貼工單的程式外殼（目前暫緩） |
| SSOT | single source of truth，唯一權威版本；本文就是 SURE 評分規則的 SSOT |

## 這支 skill 在量什麼

北極星是資深 RD 第一次讀這張單的體驗：內容經開單者**整理、用自己的話總結**（不是轉述通訊軟體上的訊息）、**現象與期望**清楚（不知原樣至少寫平台方希望的樣子）、**追蹤參數與系統佐證**齊備、有 trace id 就附 log。**看完單不用東問西問就能動工。** 分數衡量的是離這個狀態多遠；分數描述「任務材料的到位程度」，**不評價開單者**。

本 skill 是 SURE 評分規則的 SSOT：互動 session 與 SURE bot（容器化 `claude -p`）共用同一份 rubric。**目前定位：供 RD 在 Claude Code CLI 手動執行**，把總分當「開工信心指數」輸出在終端機上（bot 自動回貼暫緩）。

## 計分模型（v0.33 雙軌制）

**內容分**與**格式檢查**分開輸出、互不影響。

- **內容分**：從 **50 分**起算，每個維度依**該維度專屬階梯**計分。底檔互斥取一、額外分符合就疊加（各維階梯見 rubric 表）。**額外分一律要底檔達 ±0（含以上）才計**：底檔為負代表該維基本盤沒過，加分不啟動，無任何例外。**全部達標但零加分＝50，仍屬建議補件**：及格（60）要靠加分掙到（至少 +10），優良（80）需要 +30 的亮點。
- **複製貼上的單拿不到任何加分**：`pasted` 判定為 `high` 時，五個維度的**加分全部歸零、扣分照舊**（每個維度的 delta 取 min(delta, 0)）；`mid`／`low` 不影響分數。**簡體字占比 ≥60% 為主要判斷，條件成立即判 high。**
- **超低品質單拿不到任何加分**（由檢查器判定）：**有效內文不足 75 字** → `low_quality: true`，效果同貼上歸零，五個維度**加分全部歸零、扣分照舊**（每個維度的 delta 取 min(delta, 0)，rules 註明「超低品質歸零」）。**有效內文的算法**：內文依序去除 ① markdown 圖片與連結語法、裸 URL ② markdown 語法符號（`#`、`>`、`\`、`*` 等）③ **與標題重複的句段**（標題正文去掉站名前綴後按逗號切段，4 字以上的段落在內文原樣出現就剔除；內文把標題再抄一次不算新資訊，這是防「抄標題撐字數」）④ 所有空白，剩餘字元數即是；標題本身不計入。設計意圖：有效字數少到這個程度的內文，載不動「RD 不用東問西問就能動工」所需的資訊量。這個數字可由 bot 殼用固定規則先算好再餵給模型（殼層訊號代碼 OP-E）。
- **得分判定一律以文字為準**：位置、現象、訴求、證據等資訊若只存在於附圖、沒有用文字描述一次，該項不得分。**圖只能佐證文字，不能替代文字**（各維底檔與加分皆適用）。
- 顯示符號由 delta 對映（僅呈現用）：▼▼ ≤−10｜▼ −1～−9｜＝ ±0｜▲ +1～+5｜▲▲ ≥+6。
- **格式檢查**（第一層硬規範）：**不進分數**，輸出「合規 ✓」或待修清單。待修項分兩級：B 是「照開單規範補上即可，一分鐘能完成的事」；W 是提醒，只進補件清單。回貼時兩軌並列。

## 邊界

- **只評不寫**：不修改工單、不回貼 comment（bot 自動回貼暫緩；目前一律把結果以 CLI 格式輸出在對話）。
- **目前階段只評 `target/op_tickets`（project 492）**。`target/tickets`（需求單，project 365）暫不評分：收到需求單時說明「需求單目前不在 SURE 評分範圍」即可；PM rubric 保留於下方備用（未啟用）。其他 repo 的單先問使用者。

## 流程

1. **取單**：使用者貼內容直接用；只給連結或單號時經 gitlab MCP `get_issue`（`project_id=365` 或 `492`）取 title、description、labels。
2. **判單型**：op_tickets → OP rubric；tickets → 目前階段不評分（說明後結束）。
3. **跑格式檢查**：依單型跑對應的檢查器，目前只有 op_tickets 的檢查器。把單存成只有一筆的 JSON 陣列，跑 `node <skill 目錄>/reference/layer1-checker.mjs <檔案> op`（`<skill 目錄>` 即 skill 載入訊息列出的 Base directory）。檢查器直接讀 `iid`、`title`、`description`、`labels` 四個欄位，這四個都要有：使用者貼內容時，沒有的欄位填空字串，`labels` 沒有就填空陣列（有的話是標籤名稱的字串陣列）。簡體占比與有效內文字數一律用檢查器印出的數字，不自己數；檢查器只在達到門檻時才印出這兩個數字（簡體占比 ≥60%、有效內文不足 75 字），沒印出代表未達門檻。**檢查器是必跑步驟**：跑不起來（沒有 node、JSON 格式錯誤、指令報錯）就停下來，把錯誤訊息回報給使用者，不評分；不可以改用自己估算的數字繼續評。
4. **逐維度計分**（下表）：對照該維度階梯選定底檔（互斥取一）、逐項核對額外分，記錄命中的 `rules`（規則清單）、`missing`（缺什麼）與 `quotes`（加分佐證原文）。
5. **輸出**：CLI 信心指數格式（見「輸出格式」）。信心指數當主標、**每個維度各一行**（符號＋delta＋一句判分依據）、算式（50±…＝總分）、貼上／短文／格式三行狀態，最後附依「補一步能加幾分」排序的補分清單。**不可只給總分或算式**：讀者要能看出每一分是怎麼來的。JSON 僅 bot 模式輸出（見附錄）。

## OP rubric（op_tickets 線上問題單）

各維上限：title +10｜locatability +10｜symptom +10｜ask +5｜evidence +10。**總分上限 95**（50＋45）。

| key | 維度 | 底檔（互斥取一） | 額外分（可疊加） |
|---|---|---|---|
| `title` | 標題描述 | **只加不扣**：有填 ±0；只有一槽（無論成分齊否）±0；兩槽都有但僅一槽成分齊備 +3；兩槽成分都齊 +5。**總結性前置檢查**：標題與內文重疊 ≥80%（原句照搬＝搬運非總結），**或標題內含任一從內文原樣照搬的整行**（如遊戲代碼行；防「內文越碎、標題越容易通過」的漏洞）→ **整維直接 ±0**，加分階梯與額外分都不啟動 | 標題標明**前台或代理後台**（哪一側系統）+5 |
| `locatability` | 可定位性 | −15：白標站台與查詢對象（玩家帳號或單號）皆缺／−10：站台與對象有、但**以貼圖提供**／−5：站台與對象缺其一或要用猜的（帳號未標明是會員帳號還是遊戲帳號、類型要從截圖確認亦屬此檔）／±0：站台與對象**以文字提供** | （底檔 ±0 才計）發生時間、trace id 或有效額外參數 +5。**有效參數＝trace id＋五類實體的屬性值**：遊戲、遊戲商、代收代付 order、會員／玩家、代理（值須能在我方系統查到該實體；遊戲商客服工單號、關聯 GitLab 單連結不算）；前台或代理後台**路徑** +5。路徑須**寫明是哪一側系統**（前台／代理後台／哪個後台）＋頁面位置，只寫選單路徑（「遊戲商管理 > 遊戲管理」）沒說在哪個系統不算 |
| `symptom` | 現象描述 | −15：現象幾乎空白／−10：內容無法組成可閱讀的述句（關鍵詞、斷片堆疊，讀不出主詞與發生什麼事；例：遊戲代碼行＋「沒圖片」「上正式了」的電報式碎片，多個對象狀態交錯要 RD 自行拼裝。**碎片不等於整理過的自述**，此檔不啟動任何加分）／−5：只有現象（沒寫規格）／±0：現象＋規格皆有。**規格的定義**：問題／查證單＝本來應該怎樣，須含可對照的依據（預期數據只在截圖不算）；新需求／設定變更單（本無原樣可言）＝**平台方希望的樣子**，連希望的樣子都沒寫才落 −5。**對話原文照貼（文字或截圖）不算現象描述**：現象僅存在於對話貼文時，依可讀性落 −5～−15 | （底檔 ±0 才計）現象與規格為**自述且組織清楚的文字**：現象／已排除／訴求可依序讀出，讀者無需自行重組因果、無行話歧義（且非只貼圖、非照抄對話或圖、與附圖內文字重疊 <80%）+5；**可讀但零散（資訊交錯、順序要讀者自己拼）拿不到此加分**；補充**複現步驟** +5 |
| `ask` | 處理訴求 | −10：看不出要做什麼、也沒有完成條件／−5：方向模糊需先確認（「協助處理」而查證、恢復數據、補發皆有可能）／±0：看得出要做什麼、但沒寫完成條件（**附了素材不等於寫了完成條件**：素材對應哪個版位／範圍未寫仍屬此檔）／+3：有完成條件但不明確（「我不要這款遊戲了」：刪除還是下架？）；只列目標值或配置表、沒有動作動詞（是要調整？還是已設定未生效要排查？）亦屬此檔／+5：完成條件明確，無需回頭確認即可動工 | 無 |
| `evidence` | 佐證資料 | **只加不扣**（底檔互斥取一）：沒附任何截圖 ±0（log 歸額外分另計）／有附但與描述對不上 ±0／**只附對話截圖（聊天紀錄畫面）±0**：對話是轉述不是系統證據，重點請整理成文字／有系統截圖（系統畫面、注單、報表）但無完整成句說明 ±0（**圖沒有用文字描述一次，不得分**）／**有系統截圖且配了完整說明、與現象描述完全對得上 +5**（說明須為**完整成句**：來源標籤「SR11」、片語「沒圖片」不成句不算，落「無完整成句說明 ±0」那一檔；多張系統截圖時每張都要有；對話圖不計入判定） | 附 GCP log 連結或 log 本文 +5。**單內已有 trace id 而未附 log 連結時，`missing` 必列「補 GCP log 連結即可 +5」**：有 trace id 的單，log 連結是明確期待 |

- **TG 群／聯絡人不列入內容分**，由格式軌以 W 提醒代查：沒留不扣分，回貼提示「補上 TG 群或聯絡人，RD 卡住時即可直接回查」；有留可入 `quotes` 佐證但不加分。

### `title` 維度計分法（詞性拆解先行，僅 op）

1. **總結性前置檢查**：去掉 `[站名]`／`【站名】` 前綴後，若標題正文原樣（或近原樣）出現在內文（內文只是把標題複寫一次、或標題把內文整段搬上來，重疊 ≥80%），**或標題內含任一從內文原樣照搬的整行**，則**整維 ±0 結案**：標題至少要是內容的**總結**，搬運不是總結。互動時以「標題句能否在內文找到幾乎相同的原句」判定；bot 殼可先用字元片段重疊率以固定規則算好餵入。
2. 通過前置檢查後，把標題正文做**詞性拆解**，標出四類成分：主體名詞｜謂語動詞・狀態詞｜請求・動作動詞｜受詞（標的）。
3. 對照兩個槽位，**槽位要成分齊備才算成立**：
   - **現象槽**＝主體名詞＋謂語。主體不可省：「顯示權限不足」缺了「什麼東西／哪個功能」顯示，槽不成立。
   - **訴求槽**＝動作動詞＋**直接賓語**。「分配給其他子帳號」只有間接賓語（給誰），缺直接賓語（分配什麼），槽不成立。
   - **祈使句主詞可省**（「請協助」「幫忙」「勞煩」開頭，動作者＝受託的 RD，屬中文慣例）。
   - 此維度**僅 op 單適用**：需求單標題常只寫模組名稱，不評標題。
4. 計分（**只加不扣**）：有填標題＝±0；**只有一槽（無論成分齊否）＝±0**；兩槽都有但僅一槽成分齊備＝+3；兩槽成分都齊＝+5。成分殘缺不扣分，只是拿不到加分；佔位詞標題由格式檢查器的「G-1」項提醒，不進內容分。
5. **額外分**：標題標明**前台或代理後台**（哪一側系統）再 +5。RD 掃 issue 列表第一眼就知道往哪查。
6. `quotes` 必附拆解結果讓計分可驗證，例：`玩家(名)＋下注(動)＋未確認(狀)＋被扣款(動)→現象槽✓`。
7. 「簡短」不在此重複評：長度由格式軌把關；「協助處理」這類無具體標的的泛動詞不計訴求槽。

## 評分紀律（八條）

1. **評資訊存在與否，不評長度**：長文不等於清楚，一句話含站台＋單號＋訴求就能達標甚至加分。
2. **自由文字等價於模板欄位**：標題裡的訂單號、內文散寫的帳號都算數，不要求特定格式。
3. **`??` 是合法待補標記**（開單規範明訂），視為**達到該檔要求**（±0），不當缺漏扣分；在 `missing` 註明「待定」即可。但該欄位若正是底檔本體（如站台與對象整欄 `??`），仍計低於。
4. **內文空白以標題計**：標題仍載有資訊（站台、主題），能達標的維度照計達標，不另外扣分。
5. **`missing` 一律前瞻式**：「補上『應派彩金額』後 RD 即可直接查證」；禁止回顧式批評（「未提供」「缺乏」開頭的句子改寫成補上什麼會怎樣）。
6. **不評價人**：輸出不得出現對開單者的形容（好壞、粗心、不專業）；分數是任務材料的屬性。
7. **`quotes` 佐證加分**：計任何加分規則必引原文（截短）說明加在哪，讓加分可驗證。
8. **拿不準寧可往「±0 檔」方向靠**：兩檔之間猶豫時取靠近 ±0 的那檔，並把不確定性寫進 `missing` 的 suggestion；扣分與加分都要有明確依據。

## 輸出格式（CLI，RD 手動執行）

輸出目的是讓 RD 在終端機一眼看到**開工信心指數**與每一分的來源。純文字、等寬對齊、不用 markdown 表格。範本：

```
SURE 開工把握度 ── op_tickets #3026
[TPOWER] 这个玩家为什么在 领取免费100分的活动 又可以拿充值轮盘奖励呢

  信心指數  45 / 95   😓 建議補件
  ──────────────────────────────────────
  ＝ 標題描述  ±0   標題句幾乎原樣出現在內文，屬於搬運而不是總結
  ＝ 可定位性  ±0   站台與帳號以文字提供，兩個精確時間也已寫明
  ▼ 現象描述  −5   只寫了發生的現象，「本來應該怎樣」沒有寫成文字
  ＝ 處理訴求  ±0   查證標的可以辨識，但完成條件沒有寫明
  ＝ 佐證資料  ±0   四張系統截圖都沒有配上成句的文字說明
  ──────────────────────────────────────
  算式  50 − 5 ＝ 45
  貼上  high：簡體占比 100%，且殘留「您好」開頭的問候語
  短文  未觸發（有效內文 ≥75 字）
  格式  ✓｜提醒：補上 TG 群或聯絡人

  怎麼補分（依補一步能加幾分排序）
  1. 用繁體、自己的話改寫內文（解除貼上歸零）……… 45 → 53
  2. 補一句規格：為何不該疊領、依哪條活動設定 …… → 63
  3. 圖中 ErrorCode 抄成文字＋附 GCP log ……………… → 73
  4. 每張截圖配一句成句說明 ………………………………… → 78

  等級：🙂 ≥80 優良｜😐 60–79 及格｜😓 <60 建議補件
```

規則：
- **一律依範本輸出**：區塊順序與結構照上方範本，不自行增減段落或另創版面。
- **一律寫完整句子**：每維依據、狀態說明、補分建議都要是有主詞動詞、讀一遍就懂的完整句子。不用關鍵詞堆疊、不用「＋」號串片語、**不用「＝」「→」這類符號代替「屬於」「就是」的文字敘述**、不過度斷句。評分工具對工單的要求是「碎片不等於整理過的自述」，自己的輸出要守同一標準。
- **評語中立、理性、客觀**：每維依據、狀態說明與補分建議只陳述可查證的事實（哪項資訊有寫、哪項缺、寫在哪裡）；不使用主觀評價或情緒性用語（如「敷衍」「隨便」「品質很差」）。
- **標頭兩行**：第一行「SURE 開工把握度 ── 專案 #單號」，第二行標題原文不刪節。
- **信心指數行**是主角：`總分 / 95`＋emoji＋等級字樣。
- **每維一行**：符號（▼▼／▼／＝／▲／▲▲）＋維度名＋delta＋一句判分依據。**只陳述該維度發現了什麼**（哪項資訊有寫、哪項缺、缺在哪裡），**不說明歸零與計分機制**：不寫「貼上歸零」「短文歸零」「原可 +N」這類敘述。被歸零的維度同樣只寫發現；歸零這件事由下方「貼上／短文」狀態行呈現，解除後能拿回多少由補分清單的分數走向呈現。
- **狀態三行**：貼上（high／mid／low＋依據）、短文（觸發時附有效字數）、格式（✓ 或待修項＋W 提醒）。
- **補分清單**：前瞻式、依「補一步能加幾分」由高到低排序、每步標出補完後的分數走向；禁止回顧式批評。
- 排序與統計以內容分為主鍵，格式當 flag。

## 附錄：bot 模式 JSON（暫緩，殼層自動回貼用）

```json
{
  "project": "op_tickets | tickets",
  "iid": 2994,
  "base": 50,
  "dimensions": [
    {
      "key": "locatability",
      "delta": 5,
      "rules": ["±0 站台與對象以文字提供", "+5 發生時間「今天」"],
      "quotes": ["Jyo1994", "JIV00002354"],
      "missing": [
        { "item": "查詢頁面路徑", "suggestion": "補上前台或代理後台路徑後，RD 免找入口，可再 +5" }
      ]
    }
  ],
  "total": 56,
  "grade": "excellent | pass | fail",
  "light": "green | yellow | red",
  "pasted": "high | mid | low",
  "low_quality": false
}
```

- `total` = 50 ＋ Σ各維度 `delta`，上限 95。**格式（第一層）不影響 `total`**。`rules` 列出命中的階梯規則，呈現符號由 delta 對映。
- `pasted`：判斷內文是否為對話原文複製貼上。**主要判斷（固定規則）**：標題＋全文可判別字中**簡體占比 ≥60%**（樣本 ≥5 字；即殼層訊號代碼 OP-D）→ 直接判 `high`，附占比數據。**輔助判斷（語言模型）**：視角錯位（「我」指玩家而非開單者、「我方／你們」混用）、問候殘留（「您好」）、口語對話語氣、逐字轉貼感；足夠明確時亦可獨立判 `high`，附 quotes。`mid`＝僅部分段落疑似（如末句引一句原話、主體自寫）／`low`＝皆無。**`high` 時五維加分全部歸零、扣分照舊**（dimensions[].delta 直接記歸零後的值、rules 註明「貼上歸零」）；mid／low 不影響分數。注意：「我」指開單者本人操作（如運營自己換圖後開單）屬視角一致，不構成語言模型側的 high；但簡體占比達標仍機械成立。
- `low_quality`：**有效內文**不足 75 字（計字規則見上方計分模型：去超連結、markdown 符號、標題複寫段後計）→ `true`，五維加分全部歸零、扣分照舊（同 pasted=high 的合成方式，兩者可同時成立、效果不疊加）；≥75 字 → `false`。附字數於 rules（例「超低品質歸零（有效內文 56 字 <75）」）。
- 等級與燈號（內容分）：🙂 **≥80 優良**（需 +30 亮點）｜😐 **60–79 及格**（至少 +10，及格是掙來的）｜😓 **<60 建議補件**（含「全達標但零加分」的 50）。
- **格式軌**：由 bot 殼跑第一層硬規範（station 可解析、label 互斥、`??` 語法紅線），輸出獨立的 `format: { to_fix: [], reminders: [] }` 與內容分並列；to_fix 為空即「格式 ✓」，訊息一律前瞻式（補上什麼即可）。互動模式一律跑 [reference/layer1-checker.mjs](reference/layer1-checker.mjs)（`node <skill 目錄>/reference/layer1-checker.mjs <檔案> op`，內含全部檢查項與嚴重級，是第一層規則的 SSOT），跑不起來的處理見「流程」第 3 步。
