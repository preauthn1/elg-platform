# 改既有工單描述

一句話版本：**小改用 `update_issue_description_patch`，先試跑看改動、使用者同意再送出；大改把描述存成本機檔案，在本機改完、給使用者看過改動再送回。兩種都不把描述全文抓進對話。**

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 描述 | 工單標題底下那一大段內容，GitLab 欄位叫 `description` |
| patch | 只送「把哪段字換成哪段字」，不送整份描述；工具是 `mcp__plugin_gitlab-mcp_gitlab__update_issue_description_patch` |
| 試跑（`dry_run: true`） | patch 只算出改動、不寫入，回傳一份帶上下文的 diff（新舊對照） |
| 描述檔 | 工單小工具 `save_issue_description` 存下來的本機檔案，大改時在這裡改 |
| 工單小工具 | `gitlab-mcp` plugin 附的 `gitlab-workitem` server，工具名稱以 `mcp__plugin_gitlab-mcp_gitlab-workitem__` 開頭 |

## 為什麼不抓全文

需求單動輒幾千字，每次為了改幾個字就用 `get_issue` 把全文讀進對話，很耗費，也容易在長內文裡改錯地方。小改只送要換的那幾段；大改讓全文待在本機檔案，對話裡只看結構與改動。

## 第 1 步：選小改還是大改

| 情況 | 走哪條 |
|---|---|
| 改幾個字、換一兩句、加一行（例如加示意圖連結） | 小改 |
| 動到整個章節、重排段落、整份濃縮 | 大改。這時一段一段 patch 反而更耗費 |

## 第 2 步（小改）：用 patch

這步只送要換的那幾段字。

1. **先探出要改的那一段長什麼樣。** 不要用 `get_issue` 抓全文。拿一小段確定只出現一次的字串當 SEARCH，REPLACE 寫成同一段字串後面加 `__PROBE__`，用 `dry_run: true` 試跑。回傳的 diff 會把那一段的上下文印出來，不會寫入。
2. **寫 patch。** 格式（`patch_type: search_replace`，可以放好幾個區塊）：

   ```
   <<<<<<< SEARCH
   要被換掉的原文
   =======
   換成的新內容
   >>>>>>> REPLACE
   ```

   - SEARCH 要跟原文一字不差。粗體的 `**` 常在前面的輸出被吃掉，憑印象硬寫會找不到，一律以試跑印出的原文為準。
   - 有好幾個區塊時，**具體字串的替換排在範圍大的替換前面**，否則會互相吃掉。
   - 同一段字串出現不只一次時，預設會直接失敗；確定每一處都要換才加 `allow_multiple: true`。
3. **預覽。** 用 `dry_run: true` 跑正式的 patch。先用白話列出改了哪幾段、各改成什麼，回傳的 diff 附在後面供核對。使用者回 `y` 才用 `dry_run: false` 送出。
4. **送出後不必重讀全文。** 回應裡有 `status: success` 與改動摘要就算完成，用一句白話回報使用者：#單號 的哪幾段已經更新。

## 第 2 步（大改）：存成檔案，改完再送回

這步讓全文只待在本機檔案裡。

1. **存檔。** `mcp__plugin_gitlab-mcp_gitlab-workitem__save_issue_description`（`project_id`、`iid`）。回傳檔案路徑、字數、行數與標題，先核對標題是不是要改的那張單。
2. **留一份對照。** 用 Bash 複製一份：`cp <路徑> <路徑>.orig`，送出前用來比對改動。
3. **看結構，不讀全文。** 章節結構用 `grep -n '^#' <路徑>`；要看某一段用 `sed -n '<起>,<迄>p' <路徑>`。
4. **在本機改。** 用 Edit 工具，改之前先用 Read 帶 `offset`／`limit` 只讀要改的那幾行。中文內容不要用 `perl -i` 改：它會靜默失效，檔案沒變也不報錯。
5. **預覽。** 先用白話列出改了哪幾段、各改成什麼，再附上 `diff -u <路徑>.orig <路徑>` 的改動部分供核對。使用者回 `y` 才送出。
6. **送回。** `mcp__plugin_gitlab-mcp_gitlab-workitem__update_issue_description_from_file`（`project_id`、`iid`）。回傳改前改後字數與 `verified`，`verified: true` 才算完成；完成後用一句白話回報使用者：#單號 的描述已經更新，改完幾字。
   - 回報「存檔之後被改過」：代表有人在網頁上改了這張單的描述。不要直接加 `force`，先告訴使用者，請他二選一：「重新抓網頁上的最新版再改（本機改的會放棄）」，這時加 `overwrite: true` 重新存檔；或「用這次的版本蓋掉網頁上的修改」，這時才加 `force: true`。問的時候用這兩句白話，不要把參數名丟給使用者。
7. **收尾。** 刪掉 `.orig` 對照檔。

## 改的時候要守的規則

這些規則來自 PM 成員 Frank 的開單規則。**動手改之前，先讀 `../pm-ticket-create/reference/writing-quality.md`**：字數上限、精簡八條，以及「產出一律白話、不用速記」一節都寫在那裡。

- **直接刪掉被取代的內容。** 不留 `~~刪除線~~`，也不寫「原本是…改成…」；想留痕跡就在工單發一則留言。
- **改完要在字數上限內**：需求單 3,000 字，問題單 1,500 字。大改看 `update_issue_description_from_file` 回傳的字數。該工具回傳的字數含空白（`gitlab-workitem-mcp.js` 的 `charCount` 用 `Array.from(s).length`），判斷是否超過上限時，改用 `../pm-ticket-create/reference/writing-quality.md` 的計字命令對描述檔重算，口徑是不算空白。超過就先砍（先砍緣由、再砍重複的表格、最後砍決策過程，規格不砍），使用者同意才套用。只給開發看的實作資訊（建表 SQL 這類）可以先問使用者要不要搬到開發子任務的內文，搬走的部分不算主單字數（見 `../pm-ticket-create/reference/subtask-patterns.md` 的「子任務的內文寫什麼」）。
- **精簡八條同樣適用**，例如粗體一段最多一處、緣由最多 3 行。
- **改出來的內容一律白話、不用速記。** 不寫 skill 內部代號、慣用縮寫表以外的縮寫、能換成中文的英文行話；使用者講的是表外的縮寫，先問全名。
- **濃縮只刪內容，不縮字。** 要省字數就刪整句或整段，不要把詞縮成縮寫、代號或英文，例如不要把「轉帳錢包」寫成 TW。改到的段落裡原本就有速記的，順手換成白話。
- **示意圖連結放在描述最上面**，只寫一行：`> 示意圖：<artifact 網址>`。

## 範圍

- 只改 `target/tickets` 與 `target/ticket_tasks` 工單的**描述**。
- 改標題、標籤、負責人、起訖日不在本 skill 的範圍。

## 禁止事項

- 不用 `get_issue` 把描述全文讀進對話。
- 使用者看過改動、回 `y` 之前，不寫入。
- 沒有使用者確認，不加 `force: true`。
- 不把探路用的 `__PROBE__` 送進工單：送出前確認要寫入的新內容裡沒有這個字。
