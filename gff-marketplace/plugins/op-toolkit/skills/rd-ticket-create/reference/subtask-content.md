# 開發子單與測試子單寫什麼

一句話版本：**主單寫做什麼、做到怎樣算完成；開發子單寫怎麼做，測試子單寫怎麼測。子單不重述範圍、不改寫預期結果，每一項都用主單的需求編號對回去。**

多問題修復單例外：預期結果與原因寫在各組開發子單，見 `bugfix-schema.md` 的「一次修多個問題」。

分工的總表在 `../../pm-ticket-create/reference/subtask-patterns.md` 的「子任務的內文寫什麼」，這份文件只放 RD 寫子單用的骨架。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 主單 | 需求本體那張單，用 PM 的角度寫；範圍與預期結果只寫在這裡 |
| 開發子單 | 標題以「- 開發」「- APIs開發」「- 開發(APIs)」「- 前端」這類結尾的子任務，寫給 RD |
| 測試子單 | 標題以「- 測試」「- APIs測試」「- 測試(APIs)」這類結尾的子任務，寫給 QA |
| 需求編號 | 主單「作法」裡 `### N.` 的那個 N；修復單沒有編號時用「預期結果第 N 條」 |

## 開發子單

### 新功能單

```markdown
### 需求 N. <需求標題>

<邏輯與細部流程：資料從哪裡來、寫到哪裡、交易怎麼包、錯誤怎麼處理>

<details><summary>資料表結構</summary>

<建表 SQL 或欄位異動>

</details>

## 部署順序
1. <先上哪一支、要跑什麼命令>
```

### 修復單

```markdown
## 修法
<改成怎樣、為什麼這樣改>

## 要改的地方
- <檔案或模組>：<改什麼>

## 部署順序
1. <有順序要求才寫>
```

### 多問題修復單

```markdown
主單：[target/tickets#<主單號>](http://example.invalid:1688/target/tickets/-/work_items/<主單號>)（驗收以本單預期結果為準）

## 問題發生原因
<一到兩句寫出問題的方法或端點與它錯在哪；條列「入口：」「觸發：」>

## 影響範圍
<對象、數量、有沒有實際損失，一條一行>

## 預期結果
1. <修完應該看到什麼，能直接判定過或不過>

## 修法
<改成怎樣、為什麼這樣改>

## 要改的地方
- <檔案或模組>：<改什麼>

## 部署順序
1. <有順序要求才寫>
```

寫的時候：

- 沒有對應內容的段落整段省略，不留空標題。
- 長的 SQL、設定值、輸出包進 `<details>`。
- 程式位置寫檔名與方法名，不寫行號：行號一改程式就對不上。
- 主單「上線配合事項」寫的那一句，在這裡展開成步驟。

## 測試子單

### 新功能單

```markdown
### 需求 N. <需求標題>

**測試步驟**
1. <從哪一頁、什麼條件開始；資料怎麼造>
2. <做什麼動作>
3. <看哪裡，對照主單需求 N 的預期結果>
```

### 修復單

```markdown
## 重現步驟（修之前）
1. <怎麼做會看到主單「問題發生原因」寫的問題>

## 驗證步驟（修之後）
1. <同樣的操作>
2. <對照主單預期結果第 N 條>
```

寫的時候：

- 每一項最多 5 行，照 `../../pm-ticket-create/reference/writing-quality.md` 的精簡八條。
- 只寫「怎麼測」，不寫「做不做」、不重抄預期結果：寫「對照主單需求 2 的預期結果」，不要再抄一次預期結果的內容。
- 造不出資料的，寫出怎麼造，例如「請開發插一筆測試資料」。
- 動過的測試資料，寫出測完怎麼復原。

## 補寫時發現主單有 PM 不需要的細節

補寫子單時，主單裡常常有只給開發或測試看的內容，例如建表 SQL、鎖的順序、測試步驟。

修復單主單「問題發生原因」裡的方法名、端點路徑、資料表欄位是骨架要求寫的，不列成要搬的細節。

1. 把這些段落列進預覽的「建議從主單搬到子單」區塊：原文開頭幾個字、要搬到哪一張子單、搬完主單留哪一行指過去。
2. **使用者同意才搬。** 不同意就只寫子單，主單不動。
3. 只搬細節，**不動範圍與預期結果**：做什麼、不做什麼、做到怎樣算完成，一律以主單現有的寫法為準。補寫時覺得範圍不對，在回報裡提出來，由使用者找 PM 討論，不在子單裡另寫一個版本。
4. 搬的時候先把內容寫進子單，再改主單；主單照 `pm-ticket-edit` 的改法改（小改用 patch 先試跑，大改存成檔案改完再送回）。

## 寫進 GitLab 的方式

| 情況 | 怎麼寫 |
|---|---|
| 子單內文是空的 | `mcp__plugin_gitlab-mcp_gitlab__update_issue`（`project_id=544`、`issue_iid`、`description`），寫完用 `get_issue` 讀回比對 |
| 子單已經有內容 | 照 `pm-ticket-edit` 的改法，不整份覆蓋；先在預覽列出原有內容要保留還是改寫，使用者決定 |
| 主單要搬走細節 | 照 `pm-ticket-edit` 的改法 |
