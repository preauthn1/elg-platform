# op_tickets Label 體系

> Project: `target/op_tickets` (id 492)。本表反映 2026-05 既有 label，未來新增由 PM 維護。
> 與 `target/tickets` (GFF) 的 `0. 未分配 / 0.0 計費 / 0.2 優先` 體系完全不同。

---

## 1. 優先級（必選一）

🔴 **每一張 op 單都必須帶一個，不分開單來源**：維運轉單、客服轉單、開發自己開的技術單、接手舊單尾巴的新單，全部適用。

| Label | 含義 | SLA |
|---|---|---|
| `.P0 緊急(四小時內)` | 影響營運 / 玩家資金 / 大量會員 | 4 小時 |
| `.P1 高優先(24小時)` | 單一站台核心功能異常 | 24 小時 |
| `.P2 中優先(3個工作日)` | 一般 bug / 改善 | 3 工作日 |
| `.P3 低優先` | 不影響營運的小問題 | 無 |

> Mode B 建單預設 `.P2`；客服 / 維運表達「緊急」「玩家在等」「資金問題」時提升至 P1 / P0。

**開發自己開的技術單怎麼選**（2026-09-09 補）：看的是「這件事還在不在惡化」與「有沒有人在等」，不是缺陷本身聽起來多嚴重。

| 情境 | 級別 |
|---|---|
| 還在持續產生新的錯帳／新的損失 | `.P1` 起跳；金額大或影響大量會員用 `.P0` |
| 程式已修並發版、不會再新增，剩追回或人工複核 | `.P2` |
| 純粹等三方回覆、或只影響報表呈現不影響金額 | `.P3` |

⚠️ **`update_issue` 的 `labels` 是覆蓋不是追加**：替既有工單補優先級時，要把它原本的標籤全部一起帶上，否則會被清掉。

```
站方平台:Wintoto
站方平台:Yes2win
```

> **站方平台標籤怎麼對到要查的白標**：這步在決定工單的資料要去哪個白標的 DB 查。白標的正式名稱、別名、連線與資料範圍，只記在白標 registry（記錄白標事實的唯一檔案，由 `apis-toolkit` plugin 提供，放在該 plugin 的 `registry/whitelabels.metadata.yaml`；第 2 步要交接的兩支 skill 也在 apis-toolkit，沒安裝就兩者都用不到），這裡不另外抄，照下面三步做：
>
> 1. 拿標籤冒號後的站名，比對 registry 每個白標的正式名稱（`canonical`）與別名（`aliases`），不分大小寫。
> 2. 對到之後，把該白標的正式名稱交給 `whitelabel-db-query`（唯讀查資料）或 `whitelabel-container-exec`（跑 artisan 命令），連線與資料範圍由它們依 registry 處理。registry 標 `sharesConnection: true` 的白標跟其他白標共用同一個 DB，查資料一定要切出該白標的範圍，只切連線會混進其他站台的資料。
> 3. 對不到任何白標時，先問使用者要查哪個白標，不要猜。目前 registry 對不到的標籤如下（registry 補上後以比對結果為準）：`77WIN-VW`、`7Shwe`、`AUK99`、`SBS77`、`TPOWER-PNG`、`TPOWERHK`、`Vietwin88`。

## 9. Mode B Label 決策樹

```
1. 站方平台 ← 從 station 欄位映射（一定有）
2. .P? ← 從 user AskUserQuestion 拿（一定有）
3. 遊戲商 ← 若 vendor 欄位非空才掛
4. 問題類別 ← 從 user AskUserQuestion 拿（可多選，可不選）
5. 問題狀態 ← 不掛（PM 後續更新）
6. 4.狀態 ← 不掛（開發後續更新）
7. 1.項目 / 2.類別 / 3.優先度 ← 不主動掛（避免與 .P? 重複）
```

## 10. Mode A Label 讀取重點

收單時優先看：
- **`.P?` / `3.優先度:`** → severity
- **`站方平台:`** → station
- **`遊戲商:`** → vendor
- **`問題狀態:` / `4.狀態:`** → 當前處理階段
- **`問題類別:`** → 進一步分類（輔助 domain 判斷）
