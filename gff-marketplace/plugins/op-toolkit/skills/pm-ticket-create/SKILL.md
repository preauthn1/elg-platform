# GFF 工單建立流程（固定流程 v2）

一句話版本：**PM 要開一張 GFF 需求單時，照固定順序問完該問的問題、用 PM 的角度把內文填進對應的骨架、算好要拆哪幾張子任務與掛哪些標籤，先印一份預覽給使用者看，使用者回「y」才真的寫進 GitLab。主單寫需求與預期結果；開發子任務只放固定開頭（主單連結、示意圖連結、上正式條件），測試子任務寫每項需求的測試步驟。名單檔判定開單的人是 RD 時，轉到 `rd-ticket-create`。替既有主單補拆子任務時，先查主單現有的子任務，再走同一套子任務流程（見「補拆子任務模式」）。**

> 目標 project：parent（主單）建在 `target/tickets`（365）、子任務建在 `target/ticket_tasks`（544）。

## 觸發與分流

- **觸發說法**：「開工單／建工單／開 issue／target/tickets 新增／幫 X 站開單／PM 開單／工單拆子任務／拆 ticket task／指派 work item task／[GFF]／幫這張單補拆子任務／幫 #單號 補開開發跟測試子單」。
- **🚫 轉走 `rd-ticket-create`**：開單的人是 RD（名單檔的後端、前端組）、說「開修復單」，或要替既有子單補寫內文（開發子單、測試子單）。
- **流程固定、不即興**：要問哪些問題由 `reference/questions.yaml` 決定、工單內文照 `reference/description-schema` 的骨架填、子任務固定建在 `target/ticket_tasks`、所有 GitLab 呼叫經 GitLab MCP 照 `reference/api-cheatsheet.md` 的步驟順序執行。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| target/tickets | GitLab 專案（project 365），放 GFF 需求單的主單 |
| target/ticket_tasks | GitLab 專案（project 544），放拆出來的子任務，與主單跨 project 掛階層 |
| parent／主單 | 需求本體那張單，標題以 `[GFF]` 開頭，內文放全部資訊 |
| 子任務（subtask） | 從主單拆出的「-開發」「-測試」等工作單，一張一個負責人 |
| 母單／子單 | 主單與子任務的另一套叫法，意思完全相同。使用者用哪一套稱呼，題目、預覽與回報裡的敘述文字就跟著用同一套，不要來回換。只換敘述文字：questions.yaml 定好的選項文字、預覽的區塊名稱、GitLab 標籤與里程碑的原名都照舊不動 |
| work item | GitLab 對 issue 與 task 的統稱；建主單和子任務用的都是 `create_work_item`。主單的類型是 `issue`，子任務的類型一律是 `task`：子任務建成 `issue` 會掛不上主單 |
| 姐妹單 | 同一個需求要上多個站台時，每站各開一張主單，彼此用 `relates_to` 連結互相參照 |
| MCP | 讓 Claude 直接呼叫 GitLab 的接口，由 `gitlab-mcp` plugin 提供，工具名稱以 `mcp__plugin_gitlab-mcp_gitlab__` 開頭 |
| 工單小工具 | `gitlab-mcp` plugin 附的 `gitlab-workitem` server，工具名稱以 `mcp__plugin_gitlab-mcp_gitlab-workitem__` 開頭；掛父子關係（`attach_child_items`）、列子任務（`list_child_items`）、讀改起訖日（`get_work_item_dates`／`set_work_item_dates`）都用它，因為上游的 `update_work_item` 在公司 GitLab 一律失敗 |
| 補拆子任務模式 | 主單已經存在，只替它補建子任務、掛上父子關係；流程見「補拆子任務模式」一節 |
| PAT | personal access token，登入 GitLab API 的個人金鑰，由 `gitlab-mcp` plugin 管理，本 skill 不自己拿 |
| questions.yaml | `reference/questions.yaml`，列出要問使用者的問題與順序，題目編號 Q0～Q7。「你這次是以 RD 還是 PM 的身分開單」（Q0）只在名單判斷不出開單身分時問，答 RD 就轉到 `rd-ticket-create`；「主單的負責人要不要改」（Q7）只在補拆子任務模式問。RD 開單才問的題目在 `rd-ticket-create` |
| 開單身分 | 開這張單的人是 RD 還是 PM。拿 whoami 的帳號對名單檔判斷；PM 走本 skill，RD 轉到 `rd-ticket-create` |
| rd-ticket-create | 同一個 plugin 裡 RD 用的開單 skill：RD 開修復單或新功能單，以及替既有子單補寫開發與測試內容 |
| 預期結果 | 每一項需求完成後應該看到什麼，寫在主單，是唯一的驗收標準；測試步驟寫在測試子單，不寫在主單 |
| 內部工具 | 不屬於任何站台的內部系統：Olympus，以及 GM（GFF-Marketplace，Claude Code 的 skill 市集）。標題寫成 `[GFF][Olympus]<主題>` |
| 分類（category） | 需求屬於哪一類，決定內文用哪份骨架：A 金流商、B 遊戲商、Bp 簡訊／OTP、C 功能優化、D 系統維護 |
| schema／骨架 | `reference/description-schema/<分類>.md`，定義該類需求的內文有哪些段落與欄位 |
| 子任務 pattern | `reference/subtask-patterns.md` 裡的組合，例如 `BACKEND` 是「-開發＋-測試」兩張 |
| label | GitLab 標籤。主單一律掛 `0.0不收費`，子任務都有負責人時再掛 `0. 分配QA` ＋ `0. 分配開發`（有人待認領就掛 `0. 未分配`），另加優先級；子任務只掛 `0. 分配開發` 或 `0. 分配QA` |
| 名單檔 | GFF-Marketplace 根目錄的團隊名單 `team-roster.yaml`，記錄每個人的稱呼、GitLab 帳號、使用者 ID、組別（後端、前端、測試、PM），指派子任務時從這裡點選，也用來判斷開單身分。它不在 plugin 裡，裝 plugin 時不會帶到本機，一律用 `get_file_contents(project_id="target/gffv3/gff-marketplace", file_path="team-roster.yaml", ref="main")` 讀；讀不到就停下來回報，不憑記憶填帳號 |
| 里程碑（milestone） | 主單所屬的專案里程碑：TTN 的需求掛「TTN項目」，新代理後台的修正與優化掛「新代理後台」；子任務不掛 |
| 內文品質規則 | `reference/writing-quality.md`，規範篇幅上限、精簡八條、預期結果與測試步驟各放哪，以及所有寫出去的文字要白話、不用速記 |
| 速記 | 只有參與討論的人才看得懂的寫法：skill 內部代號、慣用縮寫表以外的縮寫、能換成中文的英文行話。給人看的文字一律不用 |
| 排期推算 | `reference/scheduling.md`，從開發起訖日推算測試與主單的起訖日 |
| 示意圖（artifact） | 需求單描述最上面那張圖，發成 claude.ai artifact；產製與分享規則見 `ticket-artifact` skill |
| PREVIEW／預覽 | 寫進 GitLab 之前印出來的完整內容，使用者回 `y` 才執行 |
| `??` | 內文裡「還不知道、待補」的合法標記，比編造好；一律寫成 `?? 待補：<缺什麼>`，讓讀單的人知道缺的是什麼 |
| self-assign | 指派給建單的人自己 |

## 前置條件

本 skill 走 **GitLab MCP 路徑**（`gitlab-mcp` plugin 提供的 `mcp__plugin_gitlab-mcp_gitlab__*` tool）。所需：

| 項目 | 說明 |
|---|---|
| `gitlab-mcp` plugin | 已安裝並設定好（`op-toolkit` 的 `plugin.json` 已宣告 `dependencies: ["gitlab-mcp"]`，裝 op-toolkit 會自動帶）。PAT 由該 plugin 注入，本 skill 不自取 token |
| 平台支援 | 不限 OS（MCP 由 plugin 啟動）。PAT 設定見 `gitlab-mcp` plugin 的 README |
| GitLab PAT | scope=api，由 gitlab-mcp 管理；設定的唯一權威版本見其 README |
| 網路 | 通到 `example.invalid:1688`（內網或 VPN） |

新環境第一次跑前若 `/mcp` 看不到 `gitlab` 與 `gitlab-workitem` 兩個 server，依 gitlab-mcp README 設定 PAT 並 `/reload-plugins` 後再回來。

## 0. Skill 必須遵守的契約

1. **照階段順序執行**：Phase 0 → 1 → 2 → 3 → 4 → 5 → 6。每個階段完成才能進下一個。
2. **不自作主張**：要問的問題、欄位、API 步驟、label、子任務後綴全部由 reference/ 內的 schema 決定，skill 不得新增或刪除。
3. **預覽強制**：任何寫入前必走 Phase 4 預覽 ＋ 使用者明確回 `y` 才能寫入。
3.5 **內文品質必檢**：Phase 2 填完內文後、進 Phase 4 之前，必須依 `reference/writing-quality.md` 自檢篇幅、精簡八條與速記，結果印在預覽；超過字數上限就在預覽標 `✗ 擋下`，砍到上限內才能送出，刪哪些要使用者同意。
4. **失敗即停**：任何步驟的中止條件觸發 → 立即停止、不繼續後續步驟；先用一句白話告訴使用者哪一步失敗、已經建好哪些，再附上原始回應。
5. **走 MCP**：所有 GitLab 操作經 `mcp__plugin_gitlab-mcp_gitlab__*` 與 `mcp__plugin_gitlab-mcp_gitlab-workitem__*` tool；PAT 由 gitlab-mcp 注入，skill 不自取 token、不裸 curl。
6. **給人看的文字一律白話**：問使用者的題目與選項、預覽、完成回報、錯誤訊息，以及寫進 GitLab 的標題與內文，都照 `reference/writing-quality.md` 的「產出一律白話、不用速記」一節寫，因為讀這些文字的工程師、測試人員與開單者都沒參與過這次討論。

## 1. Phase 0：偵測觸發詞、檢查環境、從訊息先猜幾個答案

開始之前先讀 `reference/writing-quality.md` 的「產出一律白話、不用速記」一節。從這一步起，對使用者說的每一句話都照它寫。

### 1.1 觸發條件
訊息含以下任一語意時啟用：
- 「開工單／建工單／開單／PM 開單」
- 「target/tickets 上新增／GitLab issue／ticket #xxxx」
- 「拆子任務／拆子單／ticket_tasks／拆 work item task／指派 QA／指派開發」
- 「[GFF]」「[<站名>] 開單」
- 「幫這張單補拆子任務／幫 #單號 補開開發跟測試子單／這張母單開 RD 跟 QA 的子單」→ 主單已存在，改走「補拆子任務模式」（母單＝主單、子單＝子任務，見名詞速查）

### 1.2 環境檢查（preflight）
- `mcp__plugin_gitlab-mcp_gitlab__whoami`：驗 PAT 有效，記下 `author_username`（建單人，下一步用來判斷開單身分）。只取 `username`，回傳裡的 Email、真實姓名等欄位不轉述
- `mcp__plugin_gitlab-mcp_gitlab__list_labels`（`project_id=365`, `search=0.0不收費`）：驗需求單專案看得到。不用 `get_project`：它的回傳帶有專案的 runner 權杖明文，會被帶進對話內容

whoami 失敗 → 中止，提示「Claude 連不上公司 GitLab，可能是 GitLab 個人金鑰（PAT）過期或還沒設定。請照 gitlab-mcp 的安裝說明設定好之後再試一次。」；list_labels 回 403 或 404 → 中止，提示「你的 GitLab 帳號看不到需求單專案（target/tickets），請找 GitLab 管理員確認權限。」

### 1.3 判斷開單身分
這一步決定要不要轉到 `rd-ticket-create`。拿 `author_username` 對名單檔 `team-roster.yaml`：

| 帳號在名單檔的組別 | 開單身分 | 後面怎麼走 |
|---|---|---|
| PM | PM | 照本 skill 往下走，一律需要 QA 驗收 |
| 後端、前端 | RD | 告訴使用者「你是 RD，改用 RD 開單的流程」，載入 `rd-ticket-create`，本 skill 不往下問 |
| 測試，或名單裡沒有這個帳號 | 判斷不出來 | 問「你這次是以 RD 還是 PM 的身分開單？」那一題（Q0）；答 RD 一樣轉到 `rd-ticket-create` |

比對帳號時大小寫要完全一致。不用 git 設定的使用者名稱判斷：那是各台電腦自己填的文字，不一定等於 GitLab 帳號。

### 1.4 從首段訊息先猜（preflight inference）
依 `reference/questions.yaml#preflight` 從使用者首段訊息推斷 `station`（站台或內部工具）、`category`（分類）、`vendor_name`（廠商名）。
內部工具除了看訊息，也看開單時所在 repo 的 git remote 路徑有沒有工具名稱。訊息明講了站台或工具時以訊息為準，git remote 只在訊息沒提到時參考：RD 常在 GM 的 repo 裡替站台開單。推斷後 **必須** 用文字向使用者確認：

> 我從你的訊息判斷：站台是 TPower、分類是金流商、廠商是 MangoPay，對嗎？不對的話請直接更正。

使用者確認或更正後進 Phase 1。

## 2. Phase 1：問路由問題（依 questions.yaml）

「路由問題」是決定這張單走哪條路的幾個問題：哪個站台、哪一類需求、優先級、要拆哪種子任務、有沒有截止日。載入 `reference/questions.yaml`，依 `order` 逐題詢問，每題使用 `AskUserQuestion`。選項一律用 questions.yaml 寫好的中文顯示文字（`label`，子任務題用 `display`），畫面上不出現代碼（例如 `PARENT_ONLY`）；題目不附檔案路徑。

### 2.1 選項超過 4 個怎麼問
`AskUserQuestion` 上限 4 個選項。questions.yaml 標 `ask_strategy: two_stage` 的題目分兩段問：
- 第一段用 4 個高階分組（如「特定站台／所有站台共用／內部工具／回報表單」）
- 第二段依第一段結果再問細項

### 2.2 Phase 0 已推斷的欄位
**跳過**對應問題，不要重複問。

### 2.3 收答完成檢查
依 `questions.yaml#validation` 規則檢查組合合理性：
觸發 `action: warn` → 文字提示但不擋；觸發 `action: abort` → 要求使用者重答。

### 2.4 決策樹快照（Q0～Q6 是 questions.yaml 的題目編號）

```
Q0 開單身分 → 只在「判斷開單身分」那一步判斷不出來時問：PM 往下走；RD 轉到 rd-ticket-create

Q1 給誰的 ─┬─ SITE（特定站台）→ 複選站台（stage_b_sites）
           │     ├─ 選 1 站 → SINGLE（單站台）→ 進 Q2
           │     └─ 選 2 站以上 → MULTI（多站姐妹單）→ 進 Q2（每站各建一張）
           ├─ ALL_SITES（所有站台共用）→ station=""（不帶站名）→ 進 Q2
           ├─ INTERNAL_TOOL（內部工具）→ 選 Olympus 或 GM（stage_b_internal_tool）→ 進 Q2
           ├─ FORM（新版後台回報表單）→ station=""（不掛站別）＋ 問表單實際項次 → 進 Q2
           └─ 自填其他站台（須在白名單內）→ 進 Q2

Q2 分類   ─┬─ A  金流商      → 骨架 A-payment      → 進 Q3
           ├─ B  遊戲商      → 再問 Q2b 錢包類型 → 骨架 B-game-vendor → 進 Q3
           ├─ Bp 簡訊／OTP   → 骨架 Bp-sms-otp     → 進 Q3
           ├─ C  功能優化    → 骨架 C-feature      → 進 Q3
           └─ D  系統維護    → 骨架 D-maintenance  → 進 Q3

Q3 優先級 → 對應 label_value
Q4 子任務 → 對應 subtask-patterns.md 內的 pattern；再確認要改哪幾個 repo，兩個以上時每個 repo 各一張開發、一張測試（見 subtask-patterns.md「同一個功能要改好幾個 repo 時」）；開發子任務逐張從名單點選負責人
Q5 排期   → 選填；收開發起訖日，再問 Q5b 測試結束日抓當天、下一個工作日或自己指定，其餘依 reference/scheduling.md 算出，算出來的日期避開國定假日
Q6 里程碑 → TTN項目／新代理後台／不掛（只掛主單）
```

## 3. Phase 2：填工單內文（依 description-schema/<分類>.md）

### 3.1 載入骨架
依 Q2 結果讀 `reference/description-schema/<schema>.md`：
- 解析 front-matter YAML manifest（章節 ＋ 欄位定義）
- 解析底部 markdown 骨架
- 功能優化類接著判斷這張單是修復、優化、新增還是重構（規則見 `C-feature.md` 開頭），再收示意圖與其他欄位：字數上限與示意圖是否必填都看這個結果

### 3.2 欄位填寫順序
依 manifest `sections` 順序，逐欄位向使用者收集。只問必填欄位；選填段落（例如上線配合事項、名詞定義、不在本單範圍、待確認、附件）不主動問，使用者的訊息或討論裡已經有內容才填，沒有就整段省略，並在預覽的內文區塊列一行「省略的選填段落：<段落名稱>」，使用者想補再補：
- 標題類（TG 群、商戶、API URL）：直接問
- enum 欄位（只能從固定選項選的）：用 AskUserQuestion 列選項
- secret 欄位（金鑰、密碼這類機密）：必須先問「這個欄位要先放待補文字、之後再私訊提供，還是現在就貼真的值？」
  - 預設選待補文字（`?? 由 PM 私訊提供`）
  - 貼真的值時，要使用者明確確認「這是測試環境用的值，或已經遮蔽過的值」才接受
- text_lines（IP 白名單、國碼這類多行清單）：使用者貼多行
- 問每個必填欄位時，使用者都可以回「先留待補」：填 `?? 待補：<缺什麼>`，並記下這一格是使用者自己選的待補。這種欄位不算進需求完整性逼問的五條訊號，逼問時也不問它
- 測試步驟（怎麼造資料、按哪裡、看哪裡）不寫進主單，寫進測試子單；只給開發看的實作資訊（建表 SQL、程式位置）不寫進任何一張單，開發子單只放固定開頭。規則見 `reference/subtask-patterns.md` 的「子任務的內文寫什麼」
- 領域名詞用正名：填寫內文時，幣別、代理組別、金額換算這類平台名詞，有 APIs checkout 就以其根目錄 `GLOSSARY.md` 詞彙表為準、避開它列為避免使用的別名；沒有 checkout 就照使用者原詞，不猜正名。工具參數名、欄位名、三方回調的字面值照抄

### 3.2.5 示意圖（需求單必備）

需求單的內文最上面要放示意圖連結。討論期把欄位定案之後，**先做出示意圖，再寫文字規格**。
怎麼畫、怎麼發布、怎麼設成公司全員看得到，全部寫在 `ticket-artifact` skill，這裡不重複。

三種情況：

- 使用者已經有連結 → 直接填進 `MOCKUP_LINK` 欄位。
- 還沒有 → 用 `AskUserQuestion` 問「這張單還沒有示意圖，要先做示意圖，還是先開單、之後再補？」，選項兩個：「先做示意圖」（照 `ticket-artifact` skill 做完再回來填連結）與「先開單，之後補示意圖」。選先開單就填 `?? 待補示意圖`，預覽標 `⚠ 無示意圖`。
- 這張單沒有任何畫面變動 → 整段省略。例如純粹修問題、後端或文件的改動、內部工具沒有畫面的改動、只讓頁面載入變快的效能優化。這條優先於骨架裡「優化、新增、重構時示意圖必填」的規定。作法收完之後，如果作法會讓畫面多出或改變元件（例如分頁、按鈕、欄位），回頭改問示意圖那一題。

### 3.2.6 內文品質自檢（印預覽之前一定要跑）

欄位填完之後、印預覽之前，照 `reference/writing-quality.md` 逐項檢查這五件事：

- 有沒有超過字數上限
- 精簡八條有沒有違反
- 每一項需求是不是都有「預期結果」，而且主單裡沒有測試步驟（測試步驟要放測試子單，見 `description-schema/_schema-contract.md` 規則 9）
- 內容慣例有沒有照做（正負值上色、單號不加千分位、日期不知道就留空）
- 有沒有速記：skill 內部代號、慣用縮寫表以外的縮寫、能換成中文的英文行話。標題裡使用者的原文不改，在預覽提示

檢查結果列進預覽的「內文品質」區塊。
**超過字數上限時預覽標 `✗ 擋下`，不送出**：照 `writing-quality.md` 的順序提出刪減版本（先緣由、再重複的表格、最後決策過程，規格不砍），使用者同意後才套用，回到上限內才能送出。使用者同意之前，不自行刪除任何內容。只給開發看的實作資訊（建表 SQL 這類）可以改放開發子任務的內文、不算主單字數，一樣要使用者同意（見 `subtask-patterns.md` 的「子任務的內文寫什麼」）。
功能優化類的預期結果寫在「作法」裡每一項需求的正下方，不另立章節（見 `description-schema/C-feature.md`）。來自新版後台回報表單的單，先照 `writing-quality.md` 的「來自回報表單的單怎麼處理」七步查證。

### 3.2.7 需求完整性逼問（有條件啟動）

這一步問的是「這個需求本身有沒有想清楚」，跟上一步管的東西不同。上一步（內文品質自檢）看的是文字寫得好不好：篇幅、精簡八條、速記，全是文字層面的事，沒有任何一關在看需求講不講得通。內文裡的 `?? 待補` 又是合法標記，等於允許模糊開單；`op-toolkit:sure-score`（工單把握度評分）則是事後才跑，單都開完了才告訴你 RD 看不懂。這一步補的就是這個缺口：寫進 GitLab 之前，把明顯沒想清楚的地方問出來。

**只在偵測到模糊訊號時啟動，不是每次開單都跑。** 開單是高頻動作，每次都攔一輪會變成擋路的關卡。

#### 什麼時候啟動（命中任一條就啟動）

1. 內文裡的 `?? 待補` 有 3 處以上，或任何一個必填欄位整欄只有待補文字。欄位裡有內容、只夾著一兩句待補的，算進「3 處以上」，不算整欄待補。示意圖的 `?? 待補示意圖` 不算進 3 處（示意圖另有 ⚠ 標記）。逐欄收集時使用者回「先留待補」的欄位，不算進這一條，也不算進下面其他四條。
2. 需求主體那一段只有一兩句話，短到 RD 看不出要改什麼。功能優化類看「作法」段落，其他分類看該骨架對應的需求主體段落。
3. 有需求項缺「預期結果」，或預期結果只寫了待補文字。這項上一步已經查過，直接沿用它的結果，不要重查一次。
4. enum 欄位（只能從固定選項選的那種）選了「其他」，但沒有補充說明。
5. 內文出現沒有定義的模糊量詞：優化、加快、改善、調整一下這類詞，既沒有數字也沒有驗收條件。只看內文；標題裡當作類型動詞的「優化」不算。

五條都沒命中就跳過這一步，預覽的「需求完整性」區塊寫「未觸發」。有使用者自選待補的欄位時，不論有沒有觸發，都在這一區另列一行「你選擇先留待補：<欄位>」。

#### 怎麼問

一律照下面這份清單問，**不叫起 `dev-toolkit:design-grilling`**。那支 skill 是 RD 接單後、寫程式前用的：它會一輪一輪問到沒有隱含假設，再進計劃模式交出實作計劃，跟開單要的「問一輪就回預覽」互相衝突。需要深挖的設計問題，留給 RD 接單後說「規劃 <主單網址>」再處理。

- **只問命中訊號的那幾處**，不從頭盤點這個需求的所有設計決策。
- **最多一輪**：命中的幾處一次問完，收到回答就結束，不追加第二輪。開單場景不適合長訪談。
- 每題編號、每題附上你的推薦答案。推薦答案只寫該怎麼回答（例如「給一個秒數上限」），不寫具體的規格值（例如「3 秒」），因為使用者直接接受的話，就等於替他編了規格。格式如下：

```
❓ **Q1** - **<題目標題>**：<題目內容>

➡️ <你的推薦答案>
```

| 命中的訊號 | 要問的問題 |
|---|---|
| `??` 待補 3 處以上，或必填欄位整欄只有待補文字 | 這幾處待補，現在問得到答案嗎？問不到的話，缺的到底是什麼、要找誰補？ |
| 需求主體太短 | 這句話要 RD 動到哪裡、改成什麼樣子？講得出一組具體的前後對照嗎？ |
| 缺預期結果 | 這項做完之後，應該看到什麼才算對？講得出能直接判斷過或不過的結果嗎？ |
| enum 選了「其他」沒補充 | 「其他」指的是哪一種？補一句讓 RD 看得懂的說明。 |
| 模糊量詞沒有數字 | 「<原文那個詞>」要到什麼程度算做到？有沒有數字或驗收條件？ |

#### 問完之後只會有兩種結果

- **使用者補實**：把回答填回原本那個欄位。
- **明確轉成待補**：使用者答不出來、或說之後再補時，把該處寫成 `?? 待補：<缺什麼>`，讓讀單的人知道缺的是什麼。
- 問了好幾題、使用者只回答其中幾題時，每題分別判斷：回答完整對得上的題目算補實；同一句回答對得上好幾題時，只填進最貼切的那一個位置，其他題照沒答到處理，免得同一件事寫兩次；沒回答或只回答一部分的題目，沒答到的部分視同答不出來，轉成待補並列進預覽的「仍待補」。

**不可以替使用者編內容**（見「紅線」那一節的第一條）：使用者沒講的東西，不要自己補一個聽起來合理的版本填進去。

#### 邊界

- **不新增也不刪除欄位**：逼問只針對已經填好的內容，不擴充表單。某個問題非得多開一個欄位才放得下的話，那就不問（見「Skill 必須遵守的契約」第 2 條：欄位由 schema 決定）。
- **不是硬閘**：跟字數超標的 `✗ 擋下` 不一樣。使用者說「先這樣開」就照原樣往下走，不算進「擋下的項目」，只在預覽的「需求完整性」區塊標明命中了哪幾條訊號、哪些還沒補。

問答的結果列進預覽的「需求完整性」區塊。逼問後內文有補實任何內容，就重跑一次上一步的內文品質自檢（字數、精簡八條、速記），再印預覽。

### 3.3 紅線（違反 → 中止）
見 `reference/description-schema/_schema-contract.md` 紅線表，摘要：
- `??` 不可包進 markdown `[](...)` 或 `![](...)` 語法
- secret 預設用待補文字（`?? 由 PM 私訊提供`）
- 收摺區強制 `<details>`

### 3.4 站台特定欄位（多站姐妹單模式）
姐妹單模式下，**每站重新收集**：商戶 ID、API URL、Callback URL、Account Prefix、IP。
**共用**：TG 群、分類、優先級、子任務模式、截止日、廠商通用文件。

## 4. Phase 3：決定子任務與標籤

### 4.0 查主單現有的子項（對既有工單補開子任務時一定要做）
這支 skill 建立全新主單的時候，主單必然還沒有任何子項，這一步跳過。
**使用者要求對既有工單補開子任務時，這一步一定要做。**
完整規則見 `reference/subtask-patterns.md` 的「建子任務前一定要先查主單現有的子項」，
實際怎麼呼叫見 `reference/api-cheatsheet.md` 的 Step 1.5（用小工具 `list_child_items`），整體流程見「補拆子任務模式」。

八個重點：

- 已經關閉的子項也要一起查。
- 「同一張」看的是對應同一個 repo、同一種角色（開發或測試），而且是同一批或同一期，不是後綴字面一樣；例如 ` - APIs開發` 與 ` - 開發(APIs)` 算同一張，不同批號或不同期別則不算。
- 同一張而且還開著時，不要建，回報既有那張單。
- 同一張但已經關閉時，先用 `AskUserQuestion` 問使用者，三個選項：「已完成，不建」「重新打開原本那張」「另開一張新的」；不可自行補開。
- 比對後綴時，有空格的 ` - 開發` 與沒空格的 `-開發` 算同一個後綴；線上的舊子任務多半沒有空格。
- 舊子任務一張涵蓋好幾個 repo 時（例如涵蓋前後端的 ` - 測試`），不能沿用成共用的一張，每個 repo 都要有自己的一張；先用 `AskUserQuestion` 問使用者舊單怎麼處理：「舊單改成只對應其中一個 repo，其餘 repo 另建」或「關閉舊單，每個 repo 都另建」。
- 不可以憑印象就認定這張主單沒有子任務。
- 一句指示涵蓋好幾張主單時，每一張各自查。

查證結果列進預覽的「既有子任務」區塊。

### 4.1 子任務清單
依 Q4 ＋ `reference/subtask-patterns.md` 決定要建幾張子任務、每張的標題後綴、預設負責人。

### 4.2 確認負責人存在
**開發子任務的指派對象必須先問使用者**，skill 不可自行決定：用 `AskUserQuestion` 列出名單檔 `team-roster.yaml` 裡對應組別的成員讓使用者點選。
測試子任務預設 `Benwu`，不另外問，使用者要改派時從測試組點選。
主單指派給開單的 PM 本人。RD 開單時主單給誰由 `rd-ticket-create` 決定。規則見 `reference/subtask-patterns.md` 的「指派規則與名單」。
主單指派給開單者本人時不必再查帳號：Phase 0 的 whoami 已經證實這個帳號存在。

對每個子任務負責人：`mcp__plugin_gitlab-mcp_gitlab__list_project_members`（`project_id=<subtask_id>`, `query=<username>`, `include_inheritance=true`）。
一定要帶 `include_inheritance=true`：多數成員的權限是從群組繼承的，不帶這個參數會查回空清單，把真實成員誤判成查不到。
找不到 → 標 `⚠ 待認領`，預覽明示，主單改掛 `0. 未分配`。`create_work_item` 用 `assignee_usernames`（名稱）指派，本步僅作存在性驗證。

### 4.2.5 算出起訖日
照 `reference/scheduling.md`，從使用者給的開發起訖日與 Q5b 的選擇把其餘日期算出來：

- 測試開始日 ＝ 開發結束日
- 測試結束日 ＝ 當天、開發結束日的下一個工作日，或（大型系統類）使用者指定
- 主單結束日 ＝ 測試結束日的下一個工作日
- 主單結束日落在週四到週日 → 順延到下週一以後的第一個工作日

「下一個工作日」一律用工單小工具 `next_workday` 查，國定假日、補假、連假都會跳過；不要自己加一天推算。使用者自己填的日期（開發起訖日等）用 `check_workdays` 查，落在放假日或早於今天（`today_taipei`）只在預覽提醒、不改。工具回錯誤時標 `✗ 排期算不出來`，不自己推算。細節見 `scheduling.md`。

例外：

- 不拆子任務的單（`PARENT_ONLY`）排期那一題改問主單起訖日；結束日照樣套順延規則。

算出來的日期與依據列進預覽的「排期」區塊，每個日期後面加星期（取自工具回傳的 `weekday`）。
這些日期**不是建議值**：使用者只能改開發起訖日或 Q5b 的選擇，改了就照算法重算，主單日期不接受直接改成別的日子。

### 4.3 決定標籤
依 `reference/label-conventions.md#mapping`：
- 主單：一律掛 `0.0不收費`，再加（Q3 優先級 label）。子任務同一輪建好、而且每一張都有負責人時，加 `0. 分配QA` ＋ `0. 分配開發`；
  `subtask_pattern = PARENT_ONLY`（不建子任務），或有任何一張子任務待認領時，改掛 `0. 未分配`。
- 子任務：只掛角色標籤（`0. 分配開發`／`0. 分配QA`），**不繼承主單的 `0.2 *` 與 `0.0不收費`**

對所有 label 跑存在性檢查（`list_labels`，見 label-conventions.md）。MCP 用 label **名稱**指派，不需 label_id；缺 label → 提示，不自動建。

### 4.4 決定里程碑
依 Q6：TTN 的需求掛「TTN項目」，新代理後台的修正與優化掛「新代理後台」，其餘不掛；子任務一律不掛。
里程碑編號每次都用名稱查：`mcp__plugin_gitlab-mcp_gitlab__list_milestones`（`project_id=<parent_id>`, `title=<里程碑名稱>`），
取回傳的 `id`（全域編號）當 `create_work_item` 的 `milestone_id`。**不要用網址上的里程碑編號**，那是專案內的 iid，填進去會指到別的里程碑。查不到 → 預覽標 `✗ 里程碑不存在`，不寫入。

## 5. Phase 4：預覽（強制，寫入前的最後一關）

統一預覽格式（單站台版）。`rd-ticket-create` 也沿用這份格式，所以範本裡保留了 RD 開單才會出現的寫法（開單身分 RD、不需要 QA 驗收）；本 skill 印出來的開單身分一律是 PM。區塊名稱與說明照下面的中文寫，不要改回英文；`<...>` 換成實際內容：

```
========== 預覽（開需求單）==========
主單建在    ：target/tickets（專案 365）
子任務建在  ：target/ticket_tasks（專案 544）

標題        ：<標題>    <標題格式 ✓/✗；主題寫法 ✓/⚠/不適用>
標籤        ：<標籤清單>    <每個標籤都已存在 ✓/✗>
              （派工標籤依據：<子任務都有負責人 → 分配開發＋分配QA｜不拆子任務或有人待認領 → 未分配｜RD 自己做、不需要 QA 驗收 → 只掛分配開發>）
里程碑      ：<TTN項目｜新代理後台｜不掛>    <依名稱查到 ✓/✗；不掛時只寫「不掛」，後面的查核結果拿掉>
開單身分    ：<RD｜PM>（<名單檔判定｜你選的>）    QA 驗收：<需要｜不需要>
主單負責人  ：<帳號>（<開單的你｜你點選的 PM>）

排期（照固定規則推算）：
  開發子任務：<開始日>(星期) ~ <結束日>(星期)   （你指定的）<落在放假日時加 ⚠ <日期> 是<假日名稱>；早於今天時加 ⚠ <日期> 早於今天>
  測試子任務：<開始日>(星期) ~ <結束日>(星期)   （開始日＝開發結束日；結束日抓當天、下一個工作日或你指定，寫出是哪一種；跳過放假日時寫出跳過了哪些）
  主單      ：<開始日>(星期) ~ <結束日>(星期)   （結束日＝測試結束日的下一個工作日；跳過放假日時寫出跳過了哪些；有順延時寫出原日期與順延後的日期）
  （沒有排期時，整區只寫「⚠ 無排期」；工具回錯誤時算得出的日期照印、算不出的標 ✗，最後一行寫「✗ 排期算不出來：<錯誤原文>」，算進擋下的項目）

內文（<分類的中文名，例如功能優化>）：
  示意圖    ：<網址｜⚠ 無示意圖｜省略（沒有畫面變動：<哪一種，例如效能優化>）>
```

`y` → 進 Phase 5；`n`，或「擋下的項目」不是 0 → 回 Phase 2 補欄位。

**預覽之後又改了內容，就重印預覽再問一次。** 預覽印出後使用者常會接著討論方案、改負責人、改內文；只要送出的內容和最後一份預覽不一樣，先前的 `y` 就不算數。改完把完整預覽重印一份、重新問 `y`，送出的內容必須等於最後一份預覽（見「紅線」的「預覽是契約」）。

**範本裁剪規則**：不適用的那一步從「送出後依序執行」整行拿掉，不留空殼，剩下的步驟重新編號。某一步括號裡列的項目沒有要帶時，從括號裡拿掉那一項，例如不掛里程碑時第 1 步寫「標籤、負責人、起訖日一次帶入」。不拆子任務（`PARENT_ONLY`）時，「要建的子任務」列「無」，加一行「⚠ 之後要由 PM 手動拆子任務、補負責人」，並拿掉「建 N 張子任務」與「把子任務掛到主單底下」兩步，讀回檢查只檢查主單。RD 自己做、不需要 QA 驗收（`RD_SELF`，只有 `rd-ticket-create` 沿用這份預覽時會遇到）而且只改一個 repo 時，裁剪方式與不拆子任務相同，另外：
- 「子任務建在」那一行拿掉；「要建的子任務」那一行寫「無（本單不需要 QA 驗收）」，不加「之後要由 PM 手動拆」那一行。
- 排期區塊只列一行主單，寫「（你指定的，不順延）」。

`RD_SELF` 改到兩個以上 repo 時，不套上面的裁剪：保留「子任務建在」「建 N 張子任務」「把子任務掛到主單底下」，「要建的子任務」逐張列出各 repo 的 ` - 開發(repo名稱)`（負責人是開單的 RD），不列測試子任務；排期區塊另列各開發子任務一行。

不拆子任務（`PARENT_ONLY`）時，排期區塊同樣只列一行主單。各種情況的排期寫法範例見 `reference/scheduling.md` 的「預覽要長什麼樣」。
- 「PM 接手後要補」照常保留，RD 自己的單同樣可能要補附件或改計費標籤。

「既有子任務」區塊只在補拆子任務模式列出；建新主單時整區拿掉。不是多站姐妹單時（`Q1 ≠ MULTI`），拿掉「姐妹單兩兩互相連結」那一步與「姐妹單」那一行。
沒有觸發需求完整性逼問時，「需求完整性」區塊只留一行「未觸發」（有自選待補時再加「你選擇先留待補」那一行）：其餘三行不要留成空殼，整區也不要拿掉。

## 6. Phase 5：正式寫入 GitLab

依 `reference/api-cheatsheet.md` Step 2..5 逐步執行（走 `mcp__plugin_gitlab-mcp_gitlab__*` 與工單小工具 `mcp__plugin_gitlab-mcp_gitlab-workitem__*`）。

### 6.1 單站模式
1. Step 2 `create_work_item` 建主單（labels、assignee、milestone、start／due 一併帶入）→ 記下 `parent_iid`
2. Step 3 `create_work_item` 對每張子任務（`type` 一律 `task`；labels、assignee、start／due 一併帶入，不帶 milestone）→ 記下 `subtask_iids[]`。子任務建成 `issue` 時，下一步掛父子會失敗，GitLab 回「不允許新增此類型的父項」。這種失敗照「失敗即停」停下回報，並提出補救：用 `convert_work_item_type` 把該子任務轉成 `task`，再重跑 Step 3.1。使用者同意才做。轉型不會動到標籤與負責人，所以不必關單重建（參數見 `api-cheatsheet.md` 的 Common pitfalls）
3. Step 3.1 工單小工具 `attach_child_items` 把全部子任務掛到主單底下（跨 project），回傳 `verified: true` 才算掛好
4. Step 4 跳過（無姐妹單）
5. Step 5 `get_issue` 核對標題、標籤、負責人；`list_child_items` 核對父子關係；`get_work_item_dates` 核對起訖日（REST 讀不到起始日）

### 6.2 跨站姐妹單模式
依 `reference/cross-site-link.md`：對 `sites` 列表逐站跑 Step 2..3.1，最後 Step 4 `create_issue_link` 以 `relates_to` 互連。

### 6.3 失敗處理
任一步驟失敗 → 停止後續步驟。先用一句白話說明哪一步失敗、已經建好哪些（附網址），原始回應附在後面給工程師查；要不要手動補，由使用者決定。失敗原因是子任務建成 `issue` 時，回報裡一併提出「轉成 `task` 再重掛」的補救（見 6.1 第 2 點），仍由使用者決定做不做。

## 6.5 Phase 5.5：到 Slack 通知開發提測

建單、掛子任務、日期都核對完之後，依 `reference/slack-notify.md` 到 Slack 對應頻道發通知，@ 負責開發的人。

- 頻道看標題的站別標記，對照表在 `reference/title-format.md` 的「站點縮寫與 Slack 頻道」；只有 `[GFF]` 的貼 `#gff-general`。

- **發送前先把擬好的內容給使用者確認**，使用者回 y 才送；使用者在開單指示裡已經明說要發的，視為同意。
- 開發子任務沒有結束日時不發，在完成回報裡提醒使用者。

## 7.5 補拆子任務模式（主單已存在）

這個模式替已經開好的主單補建子任務。主單不重建、內文不改（改內文走 `pm-ticket-edit`）；只改預覽列出、使用者同意的主單標籤、負責人與起訖日。要把實作資訊放進補建的開發子任務時，主單那一行「寫在某某子單」也算改內文，同樣走 `pm-ticket-edit`。

| 步驟 | 做什麼 | 用的工具 |
|---|---|---|
| 1. 讀主單 | 標題、標籤、里程碑、負責人、開關狀態；起訖日另外讀，因為 REST 讀不到起始日 | `get_issue`、`get_work_item_dates` |
| 2. 查既有子任務 | 包含已關閉的，照「查主單現有的子項」那一節的八個重點判斷要不要建 | `list_child_items` |
| 3. 問子任務 | Q4 子任務模式、要改哪幾個 repo（兩個以上時每個 repo 各一組，見 subtask-patterns.md）、開發負責人（從名單點選）、Q5 排期與 Q5b、Q7 主單負責人要不要改（補拆模式專用題，預設不改；使用者已指明就不問） | `AskUserQuestion` |
| 4. 算出主單要改的 | 派工標籤：子任務都有負責人時，把 `0. 未分配` 換成 `0. 分配開發`＋`0. 分配QA`；負責人：使用者要改派時列出改前改後；起訖日：照 `scheduling.md` 算出的主單日期跟現有的不同時，列出改前改後 | 無 |
| 5. 預覽 | 用 Phase 4 的格式，拿掉建主單那一步，另列「主單要改的」：標籤、負責人與起訖日各寫改前改後 | 無 |
| 6. 寫入 | 建子任務（`type` 一律 `task`）→ 掛父子關係 → 改主單標籤與負責人 → 改主單起訖日 | `create_work_item`、`attach_child_items`、`update_issue`、`set_work_item_dates` |
| 7. 驗證 | 子項清單、主單標籤、負責人、起訖日都跟預覽一致 | `list_child_items`、`get_issue`、`get_work_item_dates` |

注意事項：

- 子任務標題用主單**現在的**標題，去掉尾端的表單項次再加後綴（見 `title-format.md`）。
- `update_issue` 的 `labels` 會整批取代主單的標籤。一定要帶「主單現有標籤，扣掉 `0. 未分配`，加上派工標籤」的完整清單，不能只帶要新增的。
- 改主單負責人用 `update_issue` 的 `assignee_ids`，它收的是使用者的數字編號，不是帳號。先用 `list_project_members`（主單專案、`query=<帳號>`、`include_inheritance=true`）查回傳的 `id` 再帶入；帳號的大小寫要和名單檔一致。
- 主單已經關閉 → 先停下問使用者要不要繼續。
- 主單已有子任務時，照「查主單現有的子項」那一節判斷：不是同一張的照常建立，不動既有的；舊子任務涵蓋好幾個 repo 時，照那一節先問使用者舊單怎麼處理。
- 一句指示涵蓋好幾張主單時，每一張各自跑這七步，各自預覽。

## 8. 紅線（違反 → 停止）

- 🚫 **不要替使用者編內容**：description 欄位留 `?? 待補：<缺什麼>` 比編造好
- 🚫 **不要塞 checkbox 子任務在 description**：子任務一律走 work item Task。唯一的例外是「上線配合事項」段：那裡的勾選項是上線前後要配合的事，不是子任務，照骨架寫成 `- [ ]`
- 🚫 **不要省略 `[GFF]` prefix**
- 🚫 **不要主動掛 `0.1 待同步*`**（PM 職權）；`0.0不收費` 則是主單一律要掛的標籤，要主動掛
- 🚫 **不要自行決定開發子任務的指派對象**（一律先問使用者，從名單點選；測試預設 Benwu，可改派；例外只有 `PHASED` 與 `RD_SELF` 跨 repo 的開發子任務，見 `reference/subtask-patterns.md`「指派規則與名單」）
- 🚫 **子任務不要掛 `0.2 *`、`0.0 *` 與里程碑**（只有主單才掛）
- 🚫 **不要自動修改現有工單**：建新單時不動任何既有工單；補拆子任務模式只改預覽列出的主單標籤、負責人與起訖日，以及預覽列出的舊子任務處理（舊的共用子任務改標題、或關閉，見 `reference/subtask-patterns.md`「建子任務前一定要先查主單現有的子項」），使用者回 `y` 才改，改完讀回確認；改工單內文走 `pm-ticket-edit`
- 🚫 **不要呼叫 `update_work_item`**：它在公司 GitLab 一律失敗（已隱藏）；掛父子關係用 `attach_child_items`，改起訖日用 `set_work_item_dates`
- 🚫 **不要在 secret 欄位裸寫真值**（除非使用者明確確認）
- ✅ **跨站工單分開建**（Leah 慣例：N 站 ＝ N 張主單 ＋ 互連 relates_to）
- ✅ **預覽是契約**：使用者按 `y` 後 skill 不能偏離預覽內容
- ✅ **未確認資訊用 `?? 待補：<缺什麼>` 純文字**（不可包 markdown link 語法）
