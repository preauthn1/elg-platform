# 子任務要拆幾張、給誰做

一句話版本：**子任務建在另一個專案，標題是主單標題加 ` - 開發` 或 ` - 測試`；要改兩個以上的 repo 時，每個 repo 各開一張開發、一張測試；測試預設給 Benwu，開發給誰一定要先問，兩者都從名單點選。**

子任務的工作項類型一律 `task`。建成 `issue` 會掛不上主單，補救方式見 `api-cheatsheet.md` 的 Common pitfalls。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 主單 | 需求本體那張單，建在 `target/tickets` |
| 子任務 | 從主單拆出來的工作單，建在 `target/ticket_tasks`，一張一個負責人 |
| 專案（project） | GitLab 上放工單的地方，每個專案有自己的編號 |
| 拆解模式（pattern） | 這個需求要拆成哪幾張子任務的組合，例如 `BACKEND` 就是「開發 ＋ 測試」兩張 |
| 後綴 | 接在主單標題後面的角色文字，例如 ` - 開發` |
| 指派（assignee） | 這張單交給誰做 |
| 階層（hierarchy） | 主單與子任務的父子關係，在 GitLab 上叫「子項」 |
| 預覽（PREVIEW） | 寫進 GitLab 之前先印出來給人看的完整內容 |

> ⚠️ **這裡有個跟一般 GitLab 用法不同的地方**：子任務**不是**建在主單同一個專案，而是建在獨立的 `target/ticket_tasks`（專案編號 544）。兩邊靠 GitLab 的父子關係欄位連起來，GitLab 支援跨專案掛父子。

## 拆解模式對照表

每個模式列出三件事：標題後綴、預設指派給誰、預設掛什麼標籤。

⚠️ **後綴前面是 ` - `，分隔線前後各一個半形空格，不是緊貼的 `-`。** 子任務標題還要把主單尾端的表單項次去掉，完整規則見 `title-format.md` 的「子任務標題規則」。

⚠️ **測試子任務預設指派給 `Benwu`（顯示名 Ben，編號 87），需要時從名單的測試組改派（例如 zoe）；開發子任務要給誰，一律先問使用者，不可自行決定。** 表格裡標「必問使用者」的就是這個意思，不預設人名；選項來自名單檔，見「指派規則與名單」。

### 同一個功能要改好幾個 repo 時，每個 repo 各一組子任務

選完拆解模式之後，再確認這個功能要改哪幾個 repo（程式碼倉庫，例如 APIs、agent-backend、API_Agent、WEB_CustomerServiceSocket）。**要改兩個以上的 repo 時，每個 repo 各開一張開發子任務、一張測試子任務**，不把好幾個 repo 合在同一張子任務裡。

- **為什麼**：一張子任務包了好幾個 repo，做完其中一個 repo 時，這張單沒辦法如實關閉。PM 是看子任務的開關狀態決定什麼時候關主單，子任務提早關掉，PM 就會以為整個功能都做完了。實例：`target/tickets#4519` 的 CI 子任務 `target/ticket_tasks#1837` 同時包了 APIs 與 agent-backend，APIs 上線後就被關掉，但 agent-backend 還沒做。
- **後綴**：照下面各模式表格的寫法；表格沒有列到的 repo，寫成 ` - 開發(repo名稱)`、` - 測試(repo名稱)`。開發子任務一律用 ` - 開發(repo名稱)`，包含 agent-backend 這類前端 repo；只有使用者指明這張要派給前端組時，才寫成 ` - 前端(repo名稱)`（名單檔的 `suffix_to_group` 用後綴決定從哪一組點選負責人）。例如 APIs 與 agent-backend 都要加同一道 CI 檢查，就開 ` - 開發(APIs)`、` - 測試(APIs)`、` - 開發(agent-backend)`、` - 測試(agent-backend)` 四張。
- **只改一個 repo 時**，照模式表格原本的後綴，不加 repo 名稱。
- **表格裡的 `Agent` 只代表一個 repo**：代理那一側有三個 repo：API_Agent、舊代理後台 WEB_AgentBackend、新代理後台 agent-backend。Agent 那一側只改其中一個時，照表格的 Agent 後綴，預覽的 repo 欄位寫明是哪一個；改到兩個以上時，Agent 那一組改成每個 repo 各一組 ` - 開發(repo名稱)`、` - 測試(repo名稱)`，例如 ` - 開發(API_Agent)`、` - 測試(API_Agent)`、` - 開發(agent-backend)`、` - 測試(agent-backend)`。
- 要改哪幾個 repo 看不出來時，問使用者，不要自己猜。預覽的「要建的子任務」逐張列出每張對應哪個 repo。

### `PHASED`：分好幾期進行的大型改造（2026-09-02 新增）
| # | 標題後綴 | 預設指派 | 標籤 |
|---|---|---|---|
| 1..N | `第<N>期：<期別主題>`（要幾張、每期叫什麼由使用者決定） | **指派給開單的人自己**（Step 0 拿到的 `author_username`） | `0. 分配開發` |

這個模式用在要分好幾期推進的架構級改造。實際案例：

- 多幣別錢包：主單 `target/tickets#4244` → 子任務 `target/ticket_tasks#1265` 到 `#1270`
- 能力治理：主單 `target/tickets#4278` → 子任務 `#1273` 到 `#1275`

**它的指派邏輯跟其他模式相反**：其他模式是 PM 開單、指派給開發或測試人員；`PHASED` 的架構案通常是工程負責人自己來開單，所以預設指派給自己，不設固定人名。要指派給別人的話，在預覽之前講明。

其他跟一般模式不一樣的地方：

- **一期一張，不成對。** 沒有 ` - 測試` 子任務，測試人員要介入的時候再另外開。同一期要改兩個以上的 repo 時，這一期每個 repo 各開一張，標題最後加上 `(repo名稱)`。
- **期別一律用中文寫「第零期、第一期…」**（2026-09-02 RB 裁定）。起算是第零期的話，不可以自己推成第一期。
- **標題不帶 `[GFF]` 開頭**（2026-09-02 RB 裁定，只限這個模式的子任務；主單與其他模式照舊一定要帶）。格式是 `<主題> 第<N>期：<期別主題>`，例如 `多幣別錢包 第零期：契約凍結與寫入者歸屬`。
- **子任務內文可以寫該期的內容**（這一期要做什麼、要交付什麼、過關條件、前置作業）。沿用設計文件的階段時，寫出階段的中文名稱與內容，不要只寫階段編號。這偏離了「子任務內文預設留空」的通則，因為每一期負責的事情都不一樣，不可能全部集中寫在主單。但**還是要問過使用者才能填**。
- 已經做完的期別事後補開時：建單 → 掛父子關係 → 隨即關單，內文帶上收尾證據，例如合併請求的編號。
- 每一期可以各自設結束日，不用跟主單一致。
- **這是「開發子任務必問指派」的例外之一**，因為架構案通常是工程負責人自己開單；另一個例外是 `RD_SELF` 跨 repo 時的開發子任務，見「指派規則與名單」。

### `PARENT_ONLY`：不建子任務
- 一張子任務都不建。
- 預覽一定要提示「⚠ 之後要由 PM 手動拆子任務、補負責人」。

### `RD_SELF`：RD 自己做、不需要 QA 驗收
- 一張子任務都不建。這張單本來就不需要測試子任務，不是留給 PM 之後拆。
- 例外：要改兩個以上的 repo 時，每個 repo 各開一張 ` - 開發(repo名稱)` 子任務，指派給開單的 RD，仍然不開測試子任務。只改一個 repo 時照上一條，不建子任務。
- 只有 `rd-ticket-create` 會用這個模式：RD 開單、而且這張單選了「不需要 QA 驗收」時才會走到，不在子任務那一題列出。`pm-ticket-create` 不會走到這裡。
- 主單指派給開單的 RD 自己，掛 `0. 分配開發`（見 `label-conventions.md`）。
- 主單起訖日就是 RD 給的開發起訖日，不取下一個工作日、不順延（見 `scheduling.md`）。
- 預覽寫「本單不需要 QA 驗收，不建子任務」，不出現「之後要由 PM 手動拆」的提示。照上面的例外開了各 repo 的開發子任務時，改寫「本單不需要 QA 驗收，只建各 repo 的開發子任務」。
- 常見的例子：GM（GFF-Marketplace）的單、只改文件的單。Olympus 的單預設走主單加子單、主單指派給 PM，「需要 QA 驗收」排第一並標推薦；RD 仍可選「不需要」。

## 建子任務前一定要先查主單現有的子項

**建立任何子任務之前，先查這張主單已經有哪些子項，包含已經關閉的那些。**

怎麼查：用工單小工具 `mcp__plugin_gitlab-mcp_gitlab-workitem__list_child_items`（`project_id=<parent_id>`, `iid=<parent_iid>`）。它直接列出主單現在的子任務與開關狀態，包含已關閉的，不必從活動記錄拼湊。

查到之後怎麼判斷：

「同一張」看的是**對應同一個 repo、同一種角色（開發或測試），而且是同一批或同一期**，不是後綴字面一樣。同一件事可能有好幾種寫法，例如 ` - APIs開發` 與 ` - 開發(APIs)` 都是 APIs 的開發子任務，算同一張。分批（`BATCH`）的不同批號、分期（`PHASED`）的不同期別，即使 repo 與角色相同，也不算同一張。

| 既有子項的狀態 | 要做什麼 |
|---|---|
| **還開著，而且是同一張** | **不要建**，回報已經存在，附上那張單的編號與網址 |
| **已關閉，而且是同一張** | **先問使用者**，三個選項：「已完成，不建」「重新打開原本那張」（用 `update_issue` 的 `state_event: reopen`）「另開一張新的」；**不可自行補開** |
| 對應的 repo 或角色不一樣 | 照常建立 |

比對後綴時，有空格的 ` - 開發` 與沒空格的 `-開發` 算同一個後綴。線上的舊子任務多半沒有空格，只比對有空格的寫法會漏抓，結果重複開單。

**舊子任務涵蓋好幾個 repo 時，照 repo 拆開，先問舊單怎麼處理**：照「每個 repo 各一組子任務」之前的寫法開的舊子任務，一張可能涵蓋好幾個 repo，例如舊的 ` - 測試` 涵蓋前後端、` - 開發(Agent+CS)` 涵蓋 Agent 與客服 socket。這種舊單不能沿用成好幾個 repo 共用一張，每個 repo 都要有自己的一張。用 `AskUserQuestion` 問使用者舊單怎麼處理：「舊單改成只對應其中一個 repo（標題加上 repo 名稱），其餘 repo 另建」「關閉舊單，每個 repo 都另建」。改舊單標題或關單都要列進預覽，使用者回 `y` 才做。

另外三條：

- **不可以憑印象、也不可以憑先前對話就認定這張主單沒有子任務**，每次都要當場查。
- 一句指示同時涵蓋好幾張主單時，**每一張各自查**，不可以拿其中一張的結果推論其他張。
- 查證結果要列進預覽的「既有子任務」區塊。工具回報子項清單沒列完（`children_truncated`）時標 `⚠ 子項清單未列完`，交給使用者決定要不要繼續。

**為什麼要這樣**：曾經沒查證就判定 `#4210`「還沒有子任務」，結果多開了 `#1202` 與 `#1203`。實際上前一天已經有 `#1192` 與 `#1193` 了，事後得把多開的兩張關掉。

## 指派規則與名單

- **測試子任務預設指派給 `Benwu`**（顯示名 Ben，編號 87），不另外問；PM 要改派時，從名單的測試組點選。
- **開發子任務要給誰，一定要先問使用者。** skill 不可自行決定，也不可從模式對照表猜人名。例外只有兩個：`PHASED`，以及 `RD_SELF` 改到兩個以上 repo 時開的各 repo 開發子任務（指派給開單的 RD）。
- **主單給誰，看開單身分與要不要 QA 驗收**（PM 那一列由 `pm-ticket-create` 處理，RD 兩列由 `rd-ticket-create` 處理）：

  | 開單身分 | 要不要 QA 驗收 | 主單指派給 | 子任務 |
  |---|---|---|---|
  | PM | 一律要 | 開單的 PM 自己（Step 0 拿到的 `author_username`） | 照子任務那一題選的模式 |
  | RD | 要 | PM，從名單的 PM 組點選 | 照子任務那一題選的模式；開發子任務的選項把開單的 RD 排第一並標推薦，仍要點選 |
  | RD | 不要 | 開單的 RD 自己 | `RD_SELF`：只改一個 repo 時不建；改兩個以上 repo 時每個 repo 各建一張開發子任務，指派給開單的 RD |

- **開單身分怎麼判斷**：拿 whoami 的帳號對名單檔，照 `role_by_group` 對回 RD 或 PM。帳號屬於測試組、或名單裡沒有這個帳號時，問一次「你這次是以 RD 還是 PM 的身分開單？」。判定是 RD 時，`pm-ticket-create` 轉到 `rd-ticket-create`。

名單是 GFF-Marketplace 根目錄的 `team-roster.yaml`（讀法見 `../SKILL.md` 名詞表的「名單檔」），每人一筆：稱呼、GitLab 帳號、使用者 ID、組別（後端、前端、測試、PM），不放真實全名。

- 問開發子任務給誰時，用 `AskUserQuestion` 列出對應組別的成員讓使用者點選，不要讓使用者打字。後綴對應哪一組，看名單檔的 `suffix_to_group`（例如 ` - 開發` 對後端組、` - 前端` 對前端組）。
- 使用者用稱呼講人名時（例如「給 honzer」），照名單的 `call_names` 對回 GitLab 帳號。
- 建單前還是要用 `list_project_members` 確認帳號存在，**找不到就回報，不要去猜一個長得很像的帳號**。
- 名單以外的人：使用者用選項外的自填方式給帳號時，同樣先驗證存在才用。

⚠️ **帳號的大小寫必須完全正確。** 實際帳號是 `Frank` 卻寫成小寫 `frank`，GitLab 會回 `User 'frank' not found`，**整張單建立失敗，內文要重打一次**。名單檔裡的帳號都已照 GitLab 上的大小寫寫好。

## 建單前要驗證指派對象存在

預覽階段，skill 一定要對每一張子任務的指派對象執行：

```
mcp__plugin_gitlab-mcp_gitlab__list_project_members(project_id=<subtask_project_id>, query=<username>, include_inheritance=true)
```

- 帳號不存在、或沒有權限 → 在預覽標 `⚠ 負責人待認領（先指派給開單的人）`，並請使用者確認要不要用退路。
- **退路規則**：指派對象缺失時，改指派給開單的人自己。**預覽一定要寫明「待認領」，不能默默跳過。**
- 有任何一張子任務待認領時，主單掛 `0. 未分配`，不掛派工標籤（見 `label-conventions.md`）。

## 標籤怎麼跟主單同步

- 子任務**不掛**優先級標籤（`0.2 *`），優先級只掛在主單。
- 子任務的階段標籤由模式決定（`0. 分配開發` 或 `0. 分配QA`），**不用**主單的 `0. 未分配`。
- 子任務**不跟著掛**主單的計費標籤（`0.0 *`），那個只掛在主單。

## 日期怎麼跟主單同步

- 子任務與主單的開始日、結束日照 `reference/scheduling.md` 算出來，**不是整批照抄主單**：
  - 測試子任務的開始日就是開發子任務的結束日。
  - 主單的結束日是測試子任務結束日的下一個工作日，再套順延規則。
- `PHASED` 的每一期可以各自設結束日，不用跟主單一致。
- 使用者沒設日期 → 主單與子任務都不設，預覽標 `⚠ 無排期`。

## 子任務的內文寫什麼

**主單用 PM 的角度寫需求與預期結果；開發子單只放固定開頭；測試子單寫測試步驟。** 範圍（做什麼、不做什麼）與預期結果只寫在主單，子單不重述、不改寫。分配表見 `writing-quality.md` 的「預期結果寫在主單，測試步驟寫在測試子單」。

| 子單 | 寫什麼 | 誰寫 |
|---|---|---|
| 開發子單 | 只放固定開頭（見下方）。不寫代碼分析：不追檔案路徑、行號、API、欄位、資料表、實作要點，這些交給開發自己做 | `pm-ticket-create` 開單時一起寫 |
| 測試子單 | 測試步驟：怎麼造資料、按哪裡、看哪裡，每一項對回主單的需求編號與預期結果 | `pm-ticket-create` 開單時一起寫 |

開發子單固定內容：

```markdown
主單：[target/tickets#<主單號>](http://example.invalid:1688/target/tickets/-/work_items/<主單號>)（需求以主單為準）
示意圖：<artifact 連結>

> 上正式條件：測試驗收完成，且主單已掛上 `0. PM確認`。
```

- 測試子單開頭同樣寫「主單：[target/tickets#<主單號>](http://example.invalid:1688/target/tickets/-/work_items/<主單號>)（需求以主單為準）」。主單描述不寫子單連結，GitLab 的子項區塊已經會顯示（多問題修復單例外：主單問題清單表要連到各組開發子單，開發子單開頭改寫「驗收以本單預期結果為準」，測試子單開頭改指同組開發子單的預期結果，見 rd-ticket-create 的 `reference/bugfix-schema.md`）。
- 子單內容不算進主單的字數上限。
- 預覽的子任務那一行要列出內文放了什麼、幾個字。
- 主單需求改了，同一輪就要改測試子單，編號一一對應。
