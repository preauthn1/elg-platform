# 工單內文怎麼寫（所有分類共用）

一句話版本：**工單是寫給工程師動工用的，不是寫給自己留紀錄用的。寫出去的每一句話都要白話、不用速記，沒參與討論的人讀一遍就懂。寫完先檢查有沒有超過字數、每項需求有沒有預期結果、主單有沒有混進測試步驟、有沒有速記，再送出。**

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 工單 | GitLab 上的一張需求或問題單，工程師照著它動工 |
| 內文（description） | 工單的內容本體，也就是標題底下那一大段 |
| 主單 | 需求本體那張單，用 PM 的角度寫；好幾種讀者都要看的內容放這裡 |
| 子任務 | 從主單拆出來的工作單，例如「開發」「測試」各一張；PM 不需要知道的細節放這裡 |
| 分類 | 這張需求屬於哪一類，決定內文用哪份骨架：A 金流商、B 遊戲商、Bp 簡訊或 OTP、C 功能優化、D 系統維護 |
| 骨架（schema） | `description-schema/<分類>.md`，規定該類需求的內文有哪些段落與欄位 |
| 預期結果 | 這項需求完成後應該看到什麼，寫在主單，是唯一的驗收標準 |
| 測試步驟 | 測試人員怎麼造資料、按哪裡，寫在測試子單 |
| 示意圖（artifact） | 放在內文最上面的那張圖，畫的是做完之後畫面長什麼樣 |
| 預覽（PREVIEW） | 寫進 GitLab 之前先印出來給人看的完整內容 |
| 速記 | 只有參與討論的人才看得懂的寫法：skill 內部代號、自己縮短的詞、能換成中文的英文行話。所有寫出去的文字都不能用，規則見「產出一律白話、不用速記」一節 |

## 這份文件在整個流程的哪一步

- 欄位填完之後、印預覽之前，對照這份文件檢查一次。
- 檢查結果寫進預覽的「內文品質」區塊。
- 欄位有哪些不歸這份文件管，那是各分類骨架的事。
- 最後一節「產出一律白話、不用速記」管的是所有寫出去的文字，不只工單內文：題目、預覽、完成回報、錯誤訊息都算，所以 skill 一開始就要照它寫。

## 這些規則是怎麼來的

- PM 在 2026-09-18 量了 10 張已經開出去的單，平均 6,200 字。
- 其中 `#4306` 寫到 10,730 字，而且全篇有 210 處粗體。
- 同一段時間的 `#4378` 只用 1,747 字就把一張新菜單講完，開發沒有回問任何問題。
- 結論：**單子長不是因為需求複雜，是因為寫法。**

## 1. 字數上限

| 單型 | 內文字數上限 |
|---|---|
| 需求單（A、B、Bp，以及 C 的新增與優化） | **3,000 字** |
| 問題單（C 的修復、D 的異常處理） | **1,500 字** |

**字數用工具算，不要心算**：把內文從標準輸入餵給下面這行命令，不必先存檔。

```bash
node -e "console.log([...require('fs').readFileSync(0,'utf8').replace(/\s/g,'')].length)" <<'EOF'
<內文全文>
EOF
```

印出的數字就是預覽「字數」那一行的實際字數（不計空白）。`<<'EOF'` 的 EOF 要加單引號，內文裡的 `$` 與反引號才不會被 shell 展開。

超過上限時的處理順序：

- **先砍，不要先加。**
- 砍的順序固定是這三種：先砍緣由，再砍重複的表格，最後砍決策過程。
- **規格本身不砍。** 欄位、代碼、費率、回調參數該寫多細就寫多細。
- 主單裡有只給開發看的實作資訊（建表 SQL、欄位定義這類），先問使用者要不要搬到開發子任務的內文，搬走的部分不算主單字數。這是搬家不是刪減，規則見 `subtask-patterns.md` 的「子任務的內文寫什麼」。

**寫完先過這一關，才能送出。** skill 遇到超標時要做的事：

- 在預覽標 `✗ 擋下：超出字數上限（<實際字數> / <上限>）`，算進「擋下的項目」，**這時不送出**。
- 照上面的順序提出刪減版本，列出要刪哪幾段、刪完的字數，請使用者同意。
- 使用者同意才套用；套用後重新計字數，回到上限內才能送出。
- **使用者同意之前，不自行刪除任何內容。** 使用者要改用自己的刪法也可以，一樣要回到上限內。

## 2. 精簡八條

1. **粗體一段最多一處。** 同一段出現第二個粗體，就等於沒有重點了。`#4306` 平均不到兩行就一個粗體，全篇等於沒有強調。
2. **緣由最多 3 行**，只寫「不做會怎樣」。不要寫哪天發生什麼、不要寫決策怎麼演變、不要寫自己是怎麼查出來的。
3. **改單的時候直接刪掉被取代的內容。** 不要留 `~~刪除線~~`，也不要寫「原本是…改成…」。想留痕跡就去工單發一則留言，不要留在內文裡。
4. **同一件事在一張單裡只講一次。** 示意圖上已經畫出來的欄位表，正文不要再抄一遍。
5. **名詞定義只留會被誤會的那幾個**，最多三個，能不寫就整段拿掉。
6. **「不在本單範圍」只列會害測試誤報問題的項目**，理由寫一行就好，不解釋來龍去脈。
7. **「待確認」只列會擋住工程師動工的項目**，一條一行。
8. **預期結果一條一行**；測試子單的測試步驟每項最多 5 行。

## 3. 三種贅肉，看到就砍

以下三個例子全部取自 `#4306`。

| 類型 | 實際寫過的句子 | 為什麼該砍 |
|---|---|---|
| 決策過程 | 「2026-09-11 兩項變更：」「（2026-09-16 由 #4233 移入本單）」 | 工程師要知道的是現在要做什麼，不是這個需求怎麼演變來的。演變過程寫進共享記憶，不要寫進工單 |
| 刪除線留舊案 | 「~~「帳號」置於最左是否要改~~ 2026-09-16 已定案：維持…」 | 被劃掉的那半句已經沒有任何資訊，但每個讀單的人都還是要花時間讀過它 |
| 自己的查證過程 | 「（2026-09-08 於 dev 站實機核對表頭）」 | 那是 PM 怎麼確認的，不是規格 |

## 4. 預期結果寫在主單，測試步驟寫在測試子單

**主單用 PM 的角度寫。** 好幾種讀者都要看的內容留在主單，PM 不需要知道的細節放子單：

| 內容 | 放哪 |
|---|---|
| 需求說明、預期結果、不在本單範圍、待確認 | 主單 |
| 上線前後要 RD 以外的人配合、或會影響上線時間的事（例如「分兩階段上線」「上線前營運要提供白名單」），每條寫成勾選項 `- [ ]`，做完由負責的人勾掉 | 主單的「上線配合事項」段。這不是驗收條件，沒有過或不過，不寫進預期結果 |
| 邏輯、細部流程、資料表結構、部署順序與命令 | 開發子單 |
| 測試步驟（怎麼造資料、按哪裡、看哪裡） | 測試子單 |

主單每一項需求的格式：

```markdown
### N. <需求標題>

<需求說明、做到哪裡為止、資料從哪裡來>

**預期結果**
- <完成後應該看到什麼，可以直接判斷「過」或「不過」>
```

測試子單每一項的格式（對回主單的需求編號）：

```markdown
### 需求 N. <需求標題>

**測試步驟**
1. <從哪一頁、什麼條件開始>
2. <做什麼動作>
3. <看哪裡，對照主單需求 N 的預期結果>
```

寫的時候要注意：

- **預期結果要能直接回答「過」或「不過」。** 寫「金額合計等於明細加總」，不要寫「顯示正確」。
- **有驗算關係的，把算式寫進預期結果。**
- **邊界情況也要列在預期結果。** 造不出資料的，在測試步驟註明怎麼造，例如「請開發插一筆測試資料」。
- **已知做不到的限制寫進預期結果**，免得測試人員把限制當成問題回報。
- 刻意不做的事寫在主單的「不在本單範圍」，每一條寫「什麼事＋要找誰／往哪做」，例如「已轉進舊地址的款項處理，要另外向 CCPayment 確認如何處理」。
- 測試子單只寫「怎麼測」，不寫「做不做」：範圍與預期結果只在主單，測試步驟不重述、不改寫。
- C 功能優化類的骨架把預期結果放在「作法」裡每一項需求下方；A、B、Bp 寫在「預期結果」章節，D 寫在「驗收方式」章節。
- RD 自己做、不需要 QA 驗收的單不用這個格式：寫一兩句選填的「驗收方式」，說明怎樣算做完。舉例：「合併後開單流程第一題看得到內部工具選項」「照 README 的步驟能在本機把服務跑起來」。規則見 `description-schema/_schema-contract.md` 規則 9。

**為什麼範圍與預期結果只放主單**：同一件事寫在好幾張單，兩邊一定會對不上。2026-08-25 的 `#4204` 就發生過這件事：

- 主單寫「需求 1 在本次範圍」
- 開發子任務寫「尚未定案不做」
- 測試子任務寫「不在本次範圍」
- 同一件事，三張單三種說法

所以子單只寫各自讀者需要的「怎麼做」「怎麼測」，做什麼、做到怎樣算完成，一律以主單為準。

## 5. 問題單額外要做的三件事

- **先攔 API 看看問題出在前端還是後端**，再開單。API 是前端與後端之間傳資料的接口，攔下來看就知道錯的資料是哪一邊送出的。
- **用真實操作重現一次**，不要用改網頁原始碼的方式製造畫面，那樣看到的問題是假的。
- **動過的測試資料，測完要復原。**

## 6. 來自回報表單的單怎麼處理

來自「新版後台回報」Google 表單的回報，照這七步處理後才開單：

1. **讀回報一定要開截圖**，不能只看文字描述。
2. **先實機重現，再開單。** 沒有重現過的回報不開單。
3. **設對照組**，例如正常的站台或正常的帳號，確認問題只發生在回報的條件下。
4. **量化證據**，寫出實際數字，例如差了幾筆、差多少金額、幾次操作出現幾次。
5. **回報寫的範圍常常偏小**，要把實測得到的影響範圍寫成結論，不要只照抄回報內容。
6. **正式站與測試站（dev）的條件不一樣時，寫進備註**，例如資料量、設定值不同，免得工程師在測試站重現不出來。
7. **一筆回報開一張單。** 判斷依據是「修的地方是否相同」：修的地方一樣就併成一張，不一樣就分開。

標題照 `title-format.md`：表單來源不掛站別，尾端帶表單上的實際項次。

## 7. 內容慣例

- **金額與數值欄位：正數用綠色、負數用紅色。**
  - 只套用在**真的會出現負值**的欄位。
  - 永遠是正的金額、次數、時間不上色。
  - 零不上色。
  - 開單的時候就把這條寫進規格，示意圖也要照著上色。
- **單號與年份不加千分位逗號。**
- **帳號欄的兩項標準配備，規格出現帳號欄就主動寫進需求，不等使用者提：**
  - 會員帳號：點帳號可打開會員詳情抽屜（沿用 #4274 的共用元件），右側再加複製按鈕。
  - 代理帳號（含上級代理、總代、操作人員、股東帳號）：只加右側複製按鈕，**不可點**。會員詳情抽屜只給會員用，套到代理帳號會拿代理帳號去查會員。
  - 複製的是帳號本身，不是畫面上的顯示名稱；複製按鈕一直顯示，不是滑過才出現；按複製不會順帶打開抽屜；只做在表格裡，詳情頁的卡片和表單不做。
- **統計報表查詢底下的新報表要配 SR 編號**：主單、子任務標題與示意圖都帶編號，例如 `SR30`。開單前先在 GitLab 查目前用到第幾號，往下取；空著的號碼不補、不回收。同一張報表的變體用後綴，不配新號，例如 `SR02N` 是 SR02 的變體。
- **日期不知道就留空**，等工程師確認後再補，不要自己猜一個填進去。
- **平台的專有名詞要用正式名稱。** 幣別、代理組別、金額換算這類名詞，手邊有 APIs 專案的話，以它根目錄的 `GLOSSARY.md` 詞彙表為準；沒有的話就照使用者原本講的詞，不要自己猜正式名稱。工具參數名、欄位名、第三方回調的字面值一律照抄。使用者講的是縮寫或代號、又不在「產出一律白話、不用速記」一節的慣用縮寫表裡，先問全名再寫。

## 9. 產出一律白話、不用速記

**寫出去的每一句話，都要讓沒參與討論的人讀一遍就懂。** 工單的讀者是工程師、測試人員和其他 PM；題目、預覽、回報的讀者是開單的人。他們都不知道這支 skill 的內部代號，也沒看過你跟使用者的對話。

### 適用範圍

- 工單的標題與內文、子任務的標題與內文、留言
- 問使用者的題目與選項
- 寫入前的預覽、完成回報、錯誤訊息
- 示意圖上的文字：實作註記、圖例、標記

### 什麼算速記

| 類型 | 例子 | 改成 |
|---|---|---|
| skill 內部代號：題號、模式代碼、分類代碼、欄位代號、步驟編號、檔案路徑 | `Q3`、`PARENT_ONLY`、`C-feature`、`MOCKUP_LINK`、`Step 3.1`、`reference/scheduling.md` | 寫出它代表的意思，例如「不拆子任務」「功能優化」「示意圖連結」 |
| 慣用縮寫表以外的縮寫、自己縮短的詞 | `TW`（轉帳錢包）、`TBD`、`N/A`、`WIP` | 寫全名，例如「轉帳錢包」「待定」「不適用」「進行中」 |
| 能換成中文的英文行話 | preview、BLOCKED、placeholder、assignee、start／due、confirm | 預覽、擋下、待補文字、負責人、開始日／結束日、確認 |

### 不算速記，照原樣寫

- GitLab 標籤與里程碑的原名，例如「0. 分配開發」「TTN項目」。
- 正式的欄位名、參數名、API 名稱與網址，例如 API URL、Callback URL、IP 白名單。
- 畫面上實際的按鈕與選單文字，例如 `Share`、`Everyone in target`。使用者要照著畫面點，翻成中文反而找不到。
- GM 的單裡的 skill 名稱，例如 `pm-ticket-create`。那是實際找得到的名字，翻成中文反而找不到。內文第一次出現時在括號裡附一句中文說明，例如「pm-ticket-create（開需求單的 skill）」；標題照原文。skill 裡面的題號、模式代碼這些內部代號仍然算速記。

### 使用者自己講的是縮寫或代號時

- 在上面那張表裡：照用。
- 不在表裡：先問使用者全名是什麼，問到了再寫，不要自己猜。
- **標題照使用者的原文寫，不自己改字**（見 `title-format.md`）。標題裡有速記時，在預覽提示使用者，由使用者決定要不要改。
