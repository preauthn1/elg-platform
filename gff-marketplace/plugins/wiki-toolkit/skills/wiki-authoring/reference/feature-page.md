# 功能頁：完整範例與細則

這份文件給「要寫或要改一張功能頁」的時候讀。格式本身在 SKILL.md，這裡補每一段的細則與一張可以照抄的範例。

## 範例：05-01-ME 編輯商戶資料

放在：功能說明 › 05 遊戲與遊戲商 › 05-01 遊戲商與商戶 › 05-01-ME 編輯商戶資料。分類表上只有菜單「商戶資料管理」（05-01-MI）有編號，「編輯」這個操作沒有，所以 wiki 在 05-01 內新配 ME，標題用功能名。索引編號與既有縮寫查功能分類表或模組目錄頁的表格。

```markdown
> **模組**：05 遊戲與遊戲商\
> **子模組**：05-01 遊戲商與商戶\
> **索引編號**：05-01-ME\
> **功能**：編輯商戶資料\
> **校對日期**：2026-09-23\
> **狀態**：AI 草稿，待審

## 1. 這個操作在做什麼

用於編輯商戶的各項資料。

## 2. 實作的平台跟路徑

代理後台 › 遊戲商管理 › 商戶管理，在商戶那一列改狀態。

## 3. SSOT

| 編號 | 敘述 | 可否人工驗證 |
|---|---|---|
| SSOT-1 | 將啟用中的商戶改為停用，前台遊戲大廳會看不到該遊戲商的入口。 | 可 |
| SSOT-2 | 停用商戶時，系統清掉該站台的前台遊戲清單快取。 | 否，要查快取 |

## 4. 驗收

| SSOT | 方式 | 證據 |
|---|---|---|
| 1 | 人工 | QA 2026-09-25 於 dev 站驗證，op_tickets#2871 |

## 5. 編輯歷程

| 日期 | 誰 | 做了什麼 | 依據 |
|---|---|---|---|
| 2026-09-23 | Rhys | 建頁，寫下 SSOT-1 | 知識庫藍圖第一批範例頁 |
| 2026-09-25 | QA 小明 | 補 SSOT-1 的人工驗收紀錄 | op_tickets#2871 |
```

## 每一段的細則

### 頁首一行

- 用一個引用區塊（`>`）寫六項：模組、子模組、索引編號、功能、校對日期、狀態，一項一行。行尾放反斜線 `\` 做強制換行，Outline 才會把六行留在同一個引用區塊裡而不是接成一行。
- 模組與子模組寫帶編號的名稱，例如「01 會員」「01-02 認證與綁定」，編號照功能分類表。
- 索引編號是「子模組編號-兩碼縮寫」，例如 01-01-ST，每頁一個，同一子模組內不重複。功能剛好是分類表上的菜單或功能權限時用分類表的縮寫；分類表沒有的功能（列表頁操作、前台功能、排程、背景機制）自己配一個，先查目錄頁確認沒撞到，再登記到子模組目錄頁的「這個子模組新增的索引編號」表。
- 功能欄只寫動詞開頭的功能名；頁面標題才帶索引編號。
- 校對日期是最後一次對照程式碼的日期，不是最後編輯日。只改錯字不動校對日期。
- 狀態只有三種寫法：「AI 草稿，待審」「審查中」「已審」。審完的頁把狀態改成「已審」。

### 1. 這個操作在做什麼

- 讀者是 RD、PM、QA，不是客服。寫操作的對象與結果，一段話就好。
- 不寫怎麼按、不寫規則限制，那些在操作手冊。

### 2. 實作的平台跟路徑

- 只寫 UI 選單路徑，用「›」分隔，從平台名開始。
- 同一個操作在兩個平台都做得到，就各寫一行。
- 排程、事件觸發這類沒有畫面的功能，寫「沒有操作畫面」加上觸發時機，例如「由 RD-Studio 排程每小時 30 分執行」。
- 本機查不到選單名稱時寫「（待確認）」，不要照程式碼的路由名稱猜畫面上的字。

### 3. SSOT

SSOT 是「系統應該怎麼表現」的事實，一條一個。它不帶任何標記，用什麼方法證明它是第 4 段的事。

- 用三欄表格寫：「編號」欄放 `SSOT-n`，「敘述」欄放一句話，「可否人工驗證」欄放「可」或「否」。編號只在頁內連號，從 1 開始，不加功能名前綴。一個功能一頁，頁面本身就是命名空間。
- 「可否人工驗證」的判準：QA 不碰資料庫、不寫程式、只用畫面與一般工具（瀏覽器、測試帳號、調整代理設定）能不能親手重現情境並看到結果。能就是「可」，必要時補一句怎麼做（例如「可，先用錯誤密碼把測試會員鎖住」）；不能就是「否」，一定要接一句為什麼：要查資料庫、要直接呼叫 API、要跑指令、要刻意製造故障、測試站湊不出資料量。這一欄是這條事實的性質，不是有沒有驗過；驗過沒有看第 4 段。
- 「否」的 SSOT 只能靠 feature test 或 RD 查資料庫證明，所以第 4 段的驗收表裡它們的方式只會是「自動」或帶說明的「人工（RD 查庫）」。
- 一句話三樣都要有：在什麼情況下、做什麼操作、系統會怎麼做。只寫結果不寫情境的（例如「商戶停用後前台看不到」）要補上情境。
- 一條只講一件事。兩個結果就拆兩條。
- 寫看得到的行為，不寫實作：不寫欄位名、類別名、API 路徑。錯誤碼可以寫，因為 QA 測得到、客服也看得到。實作細節放操作手冊「APIS 工程師專用」那本。
- 寫進來的代表 RD 和 PM 認定這是系統應有的行為。還在討論、還沒定案的行為不要寫，寫在工單裡。
- 已發出的編號不改、不重用。作廢一條時把它從清單拿掉，在編輯歷程記「作廢 SSOT-n：原因」。新條件接在最後一號後面。
- 條目很多時可以拆成幾張表、各加三級標題分組，編號仍然全頁連號。
- 跨頁引用寫「頁名 SSOT-n」加頁面連結，例如「見 實名驗證 › 依實名狀態限制提款與領獎 SSOT-1」。用空格，不用連字號串成一個代碼。
- 跨模組的規則（例如「未實名不能提款」）放在狀態擁有者那一頁，被影響的那一頁用一條 SSOT 寫「見 …」，不重寫。

### 4. 驗收

驗收表記錄每一條 SSOT 被證明過的證據。SSOT 是事實，驗收是證明。

- 三欄：SSOT 編號、方式、證據。
- 方式只有「自動」或「人工」。自動的證據寫 feature test 的類別與方法（或 Group 標籤），人工的證據寫驗證人、日期、環境、依據工單。
- 「自動」只認 feature test。
  - feature test：`tests/Feature/` 下，從 HTTP 請求、Artisan 指令、排程等入口打進去，驗整條行為。
  - unit test 不對應 SSOT、不列進這張表。它只驗單一類別或方法，證明不了整條行為成立。
- 只寫有證據的列。沒有列的 SSOT 就是還沒被驗證，這是刻意讓缺口看得見，不要為了填滿表格寫「尚未驗證」。
- 一條 SSOT 可以有多列，例如先人工驗過、後來補了 feature test。
- RD 寫完測試要回來補一列，QA 驗完要回來補一列。這是審查分工裡各自的責任。
- 一頁一條 SSOT 都還沒驗證時，這一段只寫一句「目前沒有任何一條有驗證紀錄。」

### 5. 編輯歷程

- 每次新增、修改、作廢 SSOT，或補驗收紀錄，都記一列。只改錯字不用記。
- 「依據」寫工單編號，例如 `op_tickets#2871` 或 `tickets#4405`。沒有工單就寫這次改動的來由。
- 作廢某條時，「做了什麼」寫「作廢 SSOT-n：原因」，並把那一條從 SSOT 清單拿掉。

## 模組頁與子模組頁（目錄頁）

目錄頁只列底下有什麼，每頁一句話：

```markdown
> **層級**：子模組（目錄）\
> **編號**：05-01\
> **模組**：05 遊戲與遊戲商

遊戲商與商戶是遊戲與遊戲商模組裡跟遊戲商、廠商、商戶（站台）設定有關的資源，對應功能分類表 05-01。這一頁只是目錄，內容在底下的功能頁，一個功能一頁。

## 功能頁

* [05-01-ME 編輯商戶資料](網址)：改商戶的各項資料，例如啟用或停用。

## 這個子模組新增的索引編號

| 新編號 | 功能 | 所屬菜單 |

```

## 子模組表與功能總表

索引分兩層。每個模組目錄頁（例如「01 會員」）只有一張「子模組」表，欄位是：編號、子模組、說明、後台菜單與功能（縮寫）、功能頁。菜單欄列分類表的菜單與功能權限，wiki 新配的功能編號也列在這裡並標「wiki 新配」；功能頁欄放子模組目錄頁與底下每張功能頁的連結，順序就是側欄順序。每頁的 SSOT 條數與驗收進度看功能頁本身，目前不另外彙整。

子模組目錄頁底下固定兩節：「還沒確認的事」與「相關頁面」（對應的操作手冊）。「還沒確認的事」放分類表上有但還沒寫頁的菜單或權限、作廢的 wiki 新配編號與原因、人工驗證判斷還沒定的 SSOT，每項一句話說明卡在哪裡。功能說明根目錄的「功能總表」只列各模組功能頁數、模組頁連結、wiki 新配待回填的索引編號，以及還沒有子模組頁的待確認事項。

新增或修改功能頁後：先改模組目錄頁的子模組表（加連結、必要時加新配編號），再回功能總表改功能頁數與新配編號表。
