# 寫 APIS 知識庫 wiki

## 一句話版本

功能說明寫「系統對某個資源做某個操作時，應該怎麼表現」，給 RD、PM、QA 看；操作手冊寫「客服或工程師要怎麼做這件事」，給做事的人看；魔鏡的 pointer 把客服的問法導到操作手冊那一頁。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| wiki | 公司內部的 Outline 站台，是所有文件的正本。本 plugin 自帶的 `outline` MCP 就是連它。 |
| 魔鏡 | 團隊共用的記憶服務（memory MCP）。它不放正本，只存 pointer 與零散注意事項。 |
| pointer | 魔鏡裡的一筆記憶：標題是客服會怎麼問，內文是一句答案摘要加上 wiki 頁面網址。 |
| SSOT | 單一事實來源（single source of truth）。在這裡指功能頁裡「系統應該怎麼表現」的一條事實，在三欄表格裡一列一條（編號 SSOT-n、敘述一句話、可否人工驗證），講清楚在什麼情況下、做什麼操作、系統會怎麼做。其他地方只引用它、不重寫。 |
| 驗收 | 證明某一條 SSOT 成立的證據：feature test，或 QA 的人工驗證紀錄。SSOT 是事實，驗收是證明，兩者分開記。 |
| feature test | `tests/Feature/` 下的測試：從入口（HTTP 請求、Artisan 指令、排程）打進去，驗整條行為。驗收表「自動」列只認它。 |
| unit test | `tests/Unit/` 下的測試：驗單一類別或方法。RD 自己的工具，不對應 SSOT、不進驗收表。 |

## wiki 有六個分類

| 分類 | 放什麼 | 跟功能說明的關係 |
|---|---|---|
| 功能說明 | 照「模組 › 子模組 › 功能」分目錄，一個功能一頁。 | SSOT 的正本就在這裡。 |
| 操作手冊 | 一件事怎麼做的步驟、規則與限制、遇到狀況怎麼查。分三本：代理後台（給客服）、奧林匹斯、APIS 工程師專用。 | 不重寫系統行為，連結到對應的功能頁。魔鏡的 pointer 導到這裡。 |
| 事故紀錄 | 某一次事故的經過、怎麼查出來、怎麼修好，都帶日期。 | 從事故學到的規則寫進功能頁的 SSOT，這裡只留連結。 |
| 參考資料 | 清單與對照表，例如遊戲商清單。 | 功能頁連結過來，不複製表格。 |
| 環境工具 | 測試環境與開發工具怎麼用。 | 跟功能說明幾乎不重疊。 |
| 功能開發說明文件（待整合） | 每次上線一張主單一份的開發紀錄，由 `dev-toolkit:gitlab-release` 第 9 步產生，依大類 › 子類分資料夾。「待整合」指這裡的頁都等著整理進功能說明。 | 整理成功能說明時的原始素材，不是 SSOT。 |

一件內容要放哪裡，先問：「這是在描述系統行為，還是在教人怎麼做？」描述行為放功能說明，教人做事放操作手冊。同一個事實只寫在一個地方，其他地方放連結。

## 功能說明的目錄結構

這一步在決定新頁要掛在哪裡。放錯層，之後找不到，也會跟別人重複寫。

| 層 | 詞性 | 是什麼 | 例子 |
|---|---|---|---|
| 模組 | 名詞 | 業務領域，共八個，照功能分類表編號。 | 01 會員、03 金流、05 遊戲與遊戲商 |
| 子模組 | 名詞 | 模組裡的一種資源，編號「模組-序號」。 | 01-02 認證與綁定、03-02 會員提現（洗分） |
| 功能 | 動詞 | 對這個資源做的一個操作，一個功能一頁。 | 審核實名驗證申請、更新遊戲清單 |
| SSOT | 條列 | 做這個操作時系統應有的行為，一頁裡有很多條，頁內連號。 | SSOT-1 |

八個模組：01 會員、02 代理、03 金流、04 行銷活動、05 遊戲與遊戲商、06 風控、07 分潤與佔成、08 內容與通知。子模組的完整清單、每個子模組涵蓋哪些後台菜單、菜單的兩碼縮寫，都在使用者維護的「功能分類表」（Google Sheet）與 wiki 每個模組目錄頁的表格裡。索引編號寫成「子模組編號-兩碼縮寫」，例如 01-02-KY。每一張功能頁有自己的索引編號，同一個子模組內不重複：功能剛好就是分類表上的一個菜單或功能權限時用分類表的縮寫（例如「會員停用/啟用」ST）；分類表沒有編號的功能（列表頁上的操作、前台功能、排程、背景機制）由寫頁的人在該子模組內新配一個兩碼縮寫，先查模組目錄頁與子模組目錄頁確認沒撞到，並把新編號登記在子模組目錄頁的「這個子模組新增的索引編號」表，等使用者回填分類表。

規則：

1. 模組與子模組頁只是目錄，內容只列底下有哪些頁，每頁一句話說明。目錄頁標題帶編號，例如「01 會員」「01-02 認證與綁定」。模組目錄頁只有一張「子模組」表：分類表的子模組、菜單與縮寫、wiki 新配的功能編號（標「wiki 新配」），以及每個子模組底下已有的功能頁連結。子模組目錄頁底下固定有「還沒確認的事」與「相關頁面」（對應的操作手冊）兩節。「還沒確認的事」放三類：分類表上有但還沒寫頁的菜單或權限、作廢的 wiki 新配編號（作廢後不重用，記一行原因）、人工驗證判斷還沒定的 SSOT。
2. 功能頁的標題是「索引編號 名稱」。功能對應分類表上的菜單或功能權限時，名稱照分類表一字不改，例如「01-01-ST 會員停用/啟用」「01-03-IA 不活躍會員紀錄」；菜單打開看到的那一頁本身就算這個菜單，例如帳號管理的列表頁就是「01-01-AM 帳號管理」，不另配碼。wiki 新配編號的功能，名稱用動詞開頭的功能名，例如「01-01-VD 檢視會員詳情」。不要用「商戶資料說明」這種名詞標題。頁首的「功能」欄位一律寫動詞開頭的功能名。
3. 新頁要掛在哪個子模組，先看那個功能對應的後台菜單在功能分類表歸哪個子模組；沒有畫面的排程或機制，掛在它影響的資源所屬的子模組。
4. 平台（APIS、奧林匹斯、代理後台）不是目錄層。同一個功能在哪個平台的畫面上做，寫在功能頁第 2 段；平台上怎麼一步一步按，寫在操作手冊。
5. 開新頁前先用 `list_collection_documents` 看整棵樹，確認沒有同名或同義的頁。子模組目錄頁還不存在時先建目錄頁再建功能頁。

> 遷移注意：2026-09-23 拆出的「更新遊戲清單」六頁還掛在「模組 › 平台 › 子模組」底下；「系統」模組不在功能分類表裡，去留待定。新頁一律照上表放，不要再新增平台層；舊頁要搬時先問使用者。

## 功能頁的固定格式

每一頁照這個順序寫，不多也不少。完整範例與每段的細則見 `reference/feature-page.md`。

頁首一個引用區塊，一項一行：模組、子模組、索引編號、功能、校對日期（最後一次對照程式碼的日期）、狀態。

1. **這個操作在做什麼**：說清楚操作的對象和結果，讓 RD、PM、QA 都讀得懂，一段話就好。
2. **實作的平台跟路徑**：這個操作在哪個平台的畫面上做，只寫 UI 選單路徑，例如「代理後台 › 遊戲商管理 › 商戶管理」。不寫 API 路徑或類別名。
3. **SSOT**：三欄表格，一列一個事實：「編號」欄 SSOT-n、「敘述」欄一句話含情境、操作、結果、「可否人工驗證」欄寫「可」或「否」，否的話接一句為什麼（例如「否，要查資料庫」「否，畫面進不到，要直接呼叫 API」），可的話必要時補一句怎麼做。頁內連號，不帶已驗證與否的標記。寫進這裡的代表 RD 和 PM 認定這是系統應有的行為。
4. **驗收**：表格記每一條 SSOT 被證明過的證據，三欄：SSOT 編號、方式（自動或人工）、證據（feature test 的類別與方法，或驗證人、日期、環境、工單）。只寫有證據的列，沒有列的就是還沒驗證。
5. **編輯歷程**：表格記誰、在什麼時候、新增或改了哪一條、補了哪一筆驗收、依據哪張工單。

不放進功能頁的：客服在哪裡操作、怎麼按、規則與限制、常見狀況怎麼查。這些寫在操作手冊。

### SSOT 的寫法

- 一句話要能單獨讀懂：情境、操作、結果三樣都在。例：「將啟用中的商戶改為停用，前台遊戲大廳會看不到該遊戲商的入口。」
- 寫看得到的行為，不寫欄位名、類別名、API 路徑。錯誤碼可以寫，因為 QA 測得到、客服也看得到。
- 不帶 [自動] [人工] 之類的標記。用什麼方法證明是驗收表的事，SSOT 本身只講事實。
- 寫進 SSOT 的代表 RD 和 PM 認定這是系統應有的行為。還在討論、還沒定案的行為不要寫進來，寫在工單裡。
- 編號只在頁內連號，不加功能名前綴；跨頁引用寫「頁名 SSOT-n」加連結。編號由 RD 管，已經發出去的編號不改、不重用；某條作廢就在編輯歷程記一筆「作廢 SSOT-n」，並把那一條從清單拿掉。新條件接在最後一號後面。
- 工單要引用既有的編號，不另外重寫一份。
- 對應 SSOT 的自動測試一律是 feature test。
  - 理由：SSOT 是使用者看得到的行為，只有從入口打進去的測試證明得了。
  - unit test 不對應 SSOT、不進驗收表。要不要寫、怎麼命名由 RD 自己決定。
  - feature test 怎麼標記對到哪條 SSOT（例如 Group 標籤帶功能短編號）還沒定案，寫頁時不要自己發明。
  - RD 審查時確認 TestDox 描述跟 SSOT 寫的行為一致，並在驗收表補一列。

## 操作手冊

操作手冊的格式還沒在會議上定案，目前照 `reference/manual-page.md` 的草案寫，並在頁首狀態欄標「草案格式」。三本的分法已經定案：

| 手冊 | 讀者 | 放什麼 |
|---|---|---|
| 代理後台 | 客服 | 客服在代理後台自己能做的操作、規則與限制、什麼時候要開單、開單要附什麼。 |
| 奧林匹斯 | 營運與工程師 | 在奧林匹斯系統操作台上的操作。 |
| APIS 工程師專用 | RD | 工程師接單後要跑的指令、要查的資料表。客服那本不放這些。 |

## 寫一頁的流程

每一步都先說明在做什麼，做完才進下一步。

1. **確認要寫哪個功能、給誰看**：問使用者功能名、所屬模組與子模組、要不要一起寫操作手冊。使用者只給工單時，從工單的標題與驗收條件推，推完先講給使用者確認。
2. **讀來源**：讀程式碼、工單、既有頁面。本機沒有的程式碼（例如代理後台前端、API_Agent）不要猜，查不到的畫面名稱或路徑寫「（待確認）」。程式碼 repo 的位置問使用者，不要假設路徑。
3. **查重**：用 `list_collection_documents` 看功能說明與操作手冊的樹，確認這個功能沒有人寫過。有舊頁就改舊頁，不要另開一頁。
4. **寫草稿**：功能頁照固定格式；操作手冊照草案格式。寫完先把全文貼給使用者看，使用者點頭才寫進 wiki。
5. **寫進 wiki**：照「Outline 操作注意事項」建頁或改頁。新頁的頁首狀態寫「AI 草稿，待審」。SSOT 的「可否人工驗證」拿不準的，先照判準填，回報時把那幾條列出來給使用者判。
6. **更新索引**：在該模組目錄頁的子模組表加上新頁連結，wiki 新配的編號也加進菜單欄並標「wiki 新配」；再回根目錄「功能總表」改功能頁數與「待回填分類表的索引編號」表。側欄順序比照子模組表裡功能頁的順序。分類表上有、但這次沒寫頁的菜單或權限（例如要問 PM 才知道有沒有這個功能的），記在子模組目錄頁的「還沒確認的事」。
7. **規則有變就同步兩處**：頁面格式或目錄規則在跟使用者討論中改了，除了改這支 skill，也要改功能說明根目錄的「這個分類放什麼」，兩邊講的規則要一樣。
8. **送審**：告訴使用者這頁要誰審，審查分工見下一節。
9. **建 pointer**：只有操作手冊頁要建。等頁面審過再建，做法見 `reference/pointer.md`。

## 從上線的主單寫功能開發說明文件（由 gitlab-release 叫起）

這一節在做什麼：需求上了正式環境之後，`dev-toolkit:gitlab-release` 在回需求主單（target/tickets 上的需求工單）留言「已部署正式環境」之後，會用 Skill 工具叫起本 skill，把這批上線的功能寫進「功能開發說明文件（待整合）」文件集，一張主單一份。本 plugin 沒有連 GitLab 的工具，所以 GitLab 上的資料由 gitlab-release 讀好、整理成素材包交過來；本 skill 只負責文件怎麼寫、寫進 wiki，寫完把結果交回去。怎麼從 GitLab 讀這些資料見 gitlab-release 的「第 9 步」，這裡不寫。

**定位**：功能開發說明文件是這次上線的原始紀錄，不是 SSOT；之後有人把它整理成功能說明時，它是原始素材。所以本節不寫、不改「功能說明」文件集的任何頁，也不更新功能總表、不建 pointer、不送審（使用者在草稿階段已經看過全文）。「寫一頁的流程」不適用本節，照下面的步驟做。

**收到的素材包**：每張主單一份，內容如下。

| 項目 | 內容 |
|---|---|
| 主單 | 主單號與標題，例如 `target/tickets#4373` |
| 主單內文 | 工單描述全文 |
| 主單回覆 | 人工留下的回覆；指派、加標籤、掛子任務這類系統紀錄已經濾掉 |
| MR | 這張主單對應的 MR 編號 |
| MR 描述 | 每個 MR 的描述全文。「跟工單不一樣、已與 PM 或開發確認」這類說明通常寫在這裡 |
| 程式變更 | MR 的變更檔清單與 diff 摘要（鎖檔、vendor、打包產物已排除） |
| ADR | 這次 MR 動到的每一份 ADR 全文。ADR（architecture decision record，架構決策紀錄）記的是一個設計決定當時為什麼這樣選 |
| 上線版本 | 這次上線的 release tag、commit 與上線日期 |

**步驟**：每一步都先說明在做什麼，做完才進下一步。

1. **找文件集**：用 `list_collections(query="功能開發說明文件（待整合）")` 取文件集的完整 UUID，後面建文件都要用它。查不到，或查到不只一個，就停下來問使用者，不要猜。
2. **分類**：依 `reference/dev-doc-categories.md` 的分類表，替每張主單判斷**一個**大類與一個子類，寫進草稿讓使用者確認。表裡沒有合適的子類就問使用者，不自己新增子類。
3. **找資料夾與查重**：用 `list_collection_documents` 看文件集的樹。資料夾本身也是一份文件，分兩層：大類資料夾的標題含編號（例如「05 遊戲與遊戲商」），子類資料夾的標題不含編號（例如「遊戲商與商戶」）。同時確認這張主單有沒有已經寫過的文件：先在樹裡比對標題，再打開看「來源」區塊的主單號。已經有就改那一份，不另開一份。
4. **寫草稿**：標題與內容照下面「標題」與「內容區塊」兩段寫。素材不夠時才補讀本機程式碼，程式碼 repo 的位置問使用者；查不到的畫面名稱與選單路徑寫「（待確認）」。草稿最前面列出分類路徑、要新建哪些資料夾、這份是新建還是更新既有文件。寫完把全文貼給使用者看，使用者點頭才寫進 wiki，不因為是由 gitlab-release 叫起就省略。
5. **寫進 wiki**：照「Outline 操作注意事項」建文件或改文件。
   - 資料夾第一次用到才建，不預先建空資料夾。大類資料夾用 `collectionId` 建在文件集最上層，子類資料夾用 `parentDocumentId` 建在大類資料夾底下。資料夾內文寫一行，說明這個資料夾收什麼。
   - 文件用 `parentDocumentId` 建在子類資料夾底下。改既有文件用 `editMode: "patch"`。
   - 寫入被拒（權限不足）就停下來，告訴使用者要把 wiki 工具帳號加進「功能開發說明文件（待整合）」文件集的成員。**不改寫到別的文件集。**

**標題**：主單標題拿掉 `[GFF]`、`[站名]` 這類開單前綴，其餘照抄。

**內容區塊**：照下表的順序寫，每個區塊是一個二級標題。沒有內容的區塊整塊拿掉，不留空標題。不放頁首表格、不標狀態；內文不以一級標題開頭，也不用 `- [ ]` 核取清單語法。完整範例見 `reference/dev-doc-categories.md`。

| 區塊 | 寫什麼 |
|---|---|
| 這次做了什麼 | 一段話說清楚在哪個畫面、什麼情況下、多了或改了什麼，讓沒看過主單的人也讀得懂。 |
| 為什麼這樣做 | 條列這次的設計取捨，每條先用粗體寫決定，後面寫理由。 |
| 上線後的行為 | 條列，每條寫成「在 <情境> 下 <操作>，系統會 <結果>」，以程式實際行為為準。不會發生的情況與沒有變的部分也寫進來。 |
| 影響範圍 | 平台、選單路徑、後端、語系這類動到的範圍。跨專案的上線順序要求也寫在這裡。 |
| 跟主單不一樣的地方 | 兩欄表格「主單怎麼寫｜實際怎麼做」，主要取自 MR 描述，再對照 diff。主單寫的跟程式不一樣時，以程式為準。 |
| 這次刻意不做與還沒做的 | 同時收主單寫的「不在本單範圍」（較早的單叫「本次不做」），以及回覆裡討論過、這次沒有上線的項目。 |

## 寫作規則

- 用完整句子寫，不要用關鍵詞堆疊或速記。每一句讀一遍就懂。
- 術語第一次出現就用一句短句解釋，之後用原名詞。
- 不寫讀者查不到的代號，例如個人筆記的節號、只在某次對話成立的簡稱。
- 不要用全形破折號（U+2014）串句子，改用冒號、句號或拆成兩句。
- 帳號、密碼、金鑰、內部 IP 這類敏感資訊一律不寫進 wiki。wiki 能不能放敏感內容還沒定案，定案前以不放為準。
- 查不到的事實寫「（待確認）」並在回報時列出，不要猜。

## Outline 操作注意事項

這些是實際踩過的坑，每一條都會讓頁面壞掉或寫錯地方。

- `fetch`、`update_document`、`move_document` 要用完整的文件 UUID。只給網址尾巴的短 id 會回 `Authorization error`，這不是權限問題；先用 `list_collection_documents` 或 `list_collections` 拿到完整 id。
- 內容開頭不能放一級標題（`# 標題`）。標題用 `title` 參數設定，內文從一般段落或二級標題開始。
- 不要用 `- [ ]` 核取清單語法，Outline 會把整份文件的格式弄亂。
- 側欄的頁面順序要跟模組目錄頁子模組表「功能頁」欄的順序一致。`create_document` 一律把新頁排在最後，建完要用 `move_document` 帶 `parentDocumentId` 與 `index` 搬到對的位置；同一個父頁底下連續搬多頁時一次搬一頁、依序等結果，平行搬會互相蓋掉。
- 建頁時帶 `fullWidth: true`。全寬是每一頁自己的屬性，MCP 建的頁預設是窄版，功能頁的 SSOT 表格在窄版會折成很多行。
- 改既有頁面用 `editMode: "patch"`，`findText` 要逐字複製頁面現在的 markdown。表格的空白常常對不上（Outline 會把儲存格補成固定寬度），先 `fetch` 全文再從結果複製那一段。
- 整頁結構要換掉（例如目錄頁改版）才用 `editMode: "replace"`，先 `fetch` 全文，把要留的內容搬進新稿再送，不要憑記憶重寫。
- patch 新增的段落或表格不要接在清單（`*`、`-`、`1.`）後面，Outline 會把接在清單後面的新內容吃掉。改成錨在下一個二級標題上，用 `findText` 找「## 下一節」並把新內容放在它前面。
- 改標題後若幾十秒內被還原，是使用者開著那一頁的瀏覽器分頁，協作同步把舊標題寫回去了。重下一次只改 `title` 的更新、`fetch` 確認，並請使用者關掉或重新整理那一頁再繼續。
- 搬頁用 `move_document`，網址的 id 不會變，別的頁面連過來的舊連結還能開。
- 頁面改名或搬移之後，魔鏡裡指向這頁的 pointer 標題與內文要跟著改，見 `reference/pointer.md`。
