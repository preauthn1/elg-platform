# tech-doc-writing：技術文件要長什麼樣

一句話版本：**先判斷讀者是誰、這是哪一類文件，套那一類的結構；每一句話照 plain-writing 寫；repo 自己有目錄、版本、CHANGELOG 規則時以 repo 為準。**

| 名詞 | 意思 |
|---|---|
| 流程手冊 | 讀者要照著做的文件：接入流程、上線步驟、測試步驟 |
| 機制說明 | 讀者要理解系統怎麼運作的文件：某個子系統的資料流、狀態機、規則 |
| 決策紀錄 | 記「當時決定了什麼、為什麼」的文件：ADR（architecture decision record，架構決策紀錄）、盤點後的定案表 |
| 調試手冊 | 給工程師排查用的文件：SQL、log 檔名、內部代碼邏輯都可以寫 |
| 詞彙表 | repo 裡定義領域名詞的檔案，常見檔名 `GLOSSARY.md` 或 `CONTEXT.md` |

## 一、先叫起 plain-writing

**開始寫之前，用 Skill 工具叫起 `dev-toolkit:plain-writing`**，之後每一句話照它的規則寫：讀者判斷、四條判準、中立客觀、句子完整、列點、格式細節、送出前檢查。**用字規則一律由 `plain-writing` 決定，本 skill 不複述**；兩邊各寫一份的話，改了一邊另一邊就會過期。

叫不起來也不要停：照本 skill 把文件寫完，事後跟使用者說一聲 plain-writing 沒載入、用字沒經過它的檢查。

本 skill 只管技術文件**多出來**的事：結構、步驟寫法、術語一致、程式碼註解。

## 二、先判讀者與文件類型

動筆前定兩件事，定了才知道用哪種結構：

| 讀者 | 通常是哪類文件 | 結構 |
|---|---|---|
| 要照著做的人（新手工程師、QA、營運） | 流程手冊 | 依序編號的步驟，每步「在哪個畫面、做什麼、看到什麼」 |
| 要理解系統的人（接手的工程師、PM） | 機制說明 | 先一段白話說它在做什麼，再分節講規則；資料表、狀態、例外各自成節 |
| 要知道為什麼的人（半年後看代碼納悶的人） | 決策紀錄 | 決定、理由、放棄的做法；修訂舊決策寫「原本怎麼寫、錯在哪、為什麼改」 |
| 要排查問題的人（值班工程師） | 調試手冊 | 症狀、查哪裡（SQL、log、命令）、怎麼判讀、怎麼處理 |
| agent（Claude Code 這類工具） | 規則檔（`.claude/rules/`、`CLAUDE.md`） | 只寫規則與判準，不寫背景故事；路徑與命令寫完整 |

一份文件只服務一種讀者。同一件事要給兩種讀者看，就拆成兩份互相連結，不混在一起。

## 三、流程手冊：步驟怎麼寫

- 每一步寫到「照著做就能完成」：在哪個畫面、做什麼、填什麼、怎麼確認成功。
- 驗收標準是**介面上看得到的結果**，例如「訂單狀態變成『已上分』」。不用 SQL、log 檔名或內部代碼邏輯當驗收標準；那些放調試手冊，用連結指過去。
- 每一步開頭先一句「這步在做什麼、為什麼」，再寫操作。
- 固定會有的前置條件（權限、環境變數、測試帳號）集中寫在最前面，不散在各步。

## 四、決策紀錄：結構

- 總表只放結論，一項一行。複雜的項目另立小節，用「做什麼／為什麼／要注意什麼」展開。
- 設計決定用三欄表：決定、理由、放棄的做法。「放棄的做法」填不出來就不是決定，不列。
- `檔案:行號`、查詢結果、盤點數據放附錄或獨立文件，不夾在論述中打斷閱讀。
- 修訂舊決策時寫明「原本怎麼寫、錯在哪、為什麼改」，不直接覆蓋成新版讓人看不出改過。
- 要不要寫成 ADR、ADR 的格式與編號，由 `dev-toolkit:domain-modeling` 決定，本 skill 不複述。

## 五、計畫與測試結果

- 開發計畫和測試計畫都用表格，細到步驟層級，每一步寫出檔案和內容。
- 測試跑完之後條列所有測試項目：新增的逐項列出，原有的寫總數，失敗的寫出名稱與錯誤訊息。
- 寫明測試的限制，例如「這是本機沙箱的結果，三方服務都是假的」。
- 解釋程式碼時附完整的 function，不寫「修改前」「修改後」的片段說明。

## 六、術語一致

- 介面上的按鈕、欄位、狀態文字照抄原文，不改寫。
- 同一份文件內不切換同義詞：一個概念從頭到尾用同一個詞。
- 出現三個以上容易混淆的近義概念時，文件開頭列一張名詞說明表。
- repo 有詞彙表（`GLOSSARY.md` 或 `CONTEXT.md`）就以它為準，用正名、不用它標為避免的說法；沒有詞彙表就在文件開頭自己定義，不要求讀者去讀別的 repo。詞彙表要不要新增條目，交給 `dev-toolkit:domain-modeling`。
- 多階段流程文件各自有的用語對照（例如接入流程開頭的名詞對照）與詞彙表衝突時，以詞彙表為準。

## 七、程式碼註解

- 寫**為什麼**，不寫程式碼本身就看得出來的事。
- 用中文、句子寫完整。
- 規則有例外時寫出例外和原因，例如「跟其他回調相反：簽名欄位缺少時不拒絕，只記 log。這家金流商的舊版回調沒有簽名，拒絕會讓既有訂單全部卡住」。
- 只寫現在的做法，不寫未來規劃或預測；取捨放 commit body。
- 註解的密度跟周圍的程式碼一致。

## 八、修正既有文件裡的事實

- 修正一個事實（數字、路徑、行號、狀態、節名）時，第一步先在整個 repo 搜尋舊值，找出還有哪些檔案帶著它，一起改完才算修好。
- 只改主文件、沒改其他帶著舊值的檔案，是最常見的漏改。

## 九、repo 專屬規則的分工

repo 自己的規則檔（例如 APIs 的 `.claude/rules/docs.md`）管這些事，本 skill 不覆蓋：

- 文件放哪個目錄、怎麼命名、`index.md` 與子文件怎麼分。
- 版本號、`CHANGELOG.md` 怎麼更新。
- 該 repo 各領域流程用語的連結。

兩邊衝突時以 repo 的規則檔為準；規則檔沒寫到的，照本 skill。

## 對話範例

> 使用者：「幫我寫一份新金流商的接入流程，給第一次接金流的同事看。」
> AI：載入本 skill，先用 Skill 工具叫起 `dev-toolkit:plain-writing`。讀者是要照著做的新手，文件類型是流程手冊：前置條件集中寫在最前面，之後依序編號，每步寫在哪個畫面、做什麼、看到什麼，驗收標準用後台看得到的訂單狀態；SQL 與 log 檔名另寫成調試手冊用連結指過去。檢查 repo 的 `.claude/rules/docs.md` 有沒有目錄、`CHANGELOG`、版本號規則，有就照它放檔案與更新版本。寫完照 plain-writing 的「送出前檢查」逐條對。
