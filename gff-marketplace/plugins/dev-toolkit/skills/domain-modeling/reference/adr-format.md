# ADR 格式

ADR（architecture decision record，架構決策紀錄）放在 `docs/adr/`，檔名用流水號：`0001-slug.md`、`0002-slug.md`，依此類推。

`docs/adr/` 目錄等到真的要寫第一份 ADR 時才建，不預先開空目錄。

## 模板

```md
# {這個決定的短標題}

{一到三句：當時的處境是什麼、我們決定了什麼、為什麼。}
```

就這樣。一份 ADR 可以只有一段話。價值在於留下「**有**做過這個決定」以及「**為什麼**」，不在於把每個欄位填滿。

## 選填段落

只有在真的能增加價值時才加，多數 ADR 都用不到：

- **考慮過的選項**：只有在「被否決的方案值得被記住」時才寫
- **後果**：只有在有不明顯的連鎖影響需要點出來時才寫

狀態（Status）也是選填，但它有明確的使用時機，獨立寫在下一節。

## 狀態（Status）：什麼情況下該標、怎麼標

狀態寫在 ADR 最上方的 frontmatter（檔案開頭用兩行 `---` 夾住的設定區），一行就夠：

```md
---
status: accepted
---

# {這個決定的短標題}
```

四個值的意思：

| 值 | 意思 |
|---|---|
| `proposed` | 提出了，還沒拍板 |
| `accepted` | 已拍板，現在照這個做 |
| `deprecated` | 這個決定不做了，也沒有新的決定取代它 |
| `superseded by ADR-NNNN` | 這個決定被編號 NNNN 的那份 ADR 取代了 |

**多數 ADR 不用標。** 寫下來就一直有效、沒有人回頭動的 ADR，沒有狀態欄一樣讀得懂。下面兩種情況才標：

1. **寫的當下還沒拍板**：標 `proposed`，使用者拍板後改成 `accepted`。設計訪談當場寫下、還等使用者確認的 ADR 屬於這種。
2. **這個決定被換掉了**：在**舊**的那份標 `superseded by ADR-NNNN`，`NNNN` 填取代它的新 ADR 編號（四位數，與檔名前綴一致）；新的那份照常寫，不必回指舊的，讀者從舊的走得到新的就夠了。整個決定不做了、又沒有替代方案時，舊的那份改標 `deprecated`。

什麼時候算「決定被換掉」（要寫新的）、什麼時候只是把同一個決定寫得更清楚（直接改原檔，不標狀態、不開新的），判準見 `domain-modeling` 的「規格變了，已經寫下去的文件怎麼辦」。

掃一次 `docs/adr/`，找出現有最大的編號，加一。

## 什麼時候才提議寫 ADR

三個條件**全部**成立：

1. **難以反悔**：之後改變主意的代價是實在的。
2. **沒有上下文會覺得奇怪**：未來的讀者看到代碼會想「這到底為什麼要這樣寫」。
3. **真的做過取捨**：當時有其他可行選項，因為具體理由挑了這個。

容易反悔的決定不用寫，反正要改就改了；不奇怪的決定不用寫，沒人會來問；沒有其他選項的決定不用寫，除了「做了理所當然的事」以外沒東西好記。

### 哪些決定通常符合

- **架構形狀**：「我們用 monorepo。」「寫入端走事件溯源，讀取端投影到 Postgres。」
- **上下文之間的整合方式**：「訂購與帳務用領域事件溝通，不用同步 HTTP 呼叫。」
- **會被綁住的技術選擇**：資料庫、訊息匯流排、認證供應商、部署目標。不是每個套件都要記，只記那種要換掉得花一季的。
- **邊界與範圍的決定**：「客戶資料由客戶上下文擁有，其他上下文只能用 ID 引用。」講清楚「不做什麼」跟講「做什麼」一樣有價值。
- **刻意偏離常規做法**：「這裡用手寫 SQL 而不是 ORM，因為 X。」凡是講理的讀者會預期相反做法的地方都算。記下來，下一個工程師才不會把刻意的設計當成 bug「修好」。
- **代碼上看不到的限制**：「因為法遵要求，不能用 AWS。」「因為合作方 API 的合約，回應時間必須在 200 毫秒內。」
- **被否決的方案，當否決理由不明顯時**：如果評估過 GraphQL、基於一些細微理由選了 REST，就記下來；否則半年後還是會有人再提一次 GraphQL。
