# `GLOSSARY.md` 格式

## 結構

```md
# {上下文名稱}

{一到兩句：這套上下文是什麼、為什麼存在。}

## 詞彙

**訂單**：
{一到兩句描述這個詞是什麼}
_避免使用_：採購、交易

**發票**：
出貨後寄給客戶的請款單據。
_避免使用_：帳單、請款通知

**客戶**：
下訂單的個人或組織。
_避免使用_：客人、買家、帳號
```

## 規則

- **要有主張**：同一個概念有好幾種講法時，挑一個最好的當正名，其餘全部列進 `_避免使用_`。不要「兩種都可以」。
- **定義寫緊**：一到兩句為上限。寫它**是什麼**，不要寫它**做什麼**。
- **只收這個專案特有的詞**：一般程式概念（逾時、錯誤型別、工具類的通用模式）就算專案裡用很多次也不收。加一個詞之前先問：這是這套上下文獨有的概念，還是一般程式概念？只有前者該收。
- **詞多了就分小標**：自然形成群集時用小標分組；如果所有詞本來就屬於同一個主題，平鋪一列也可以。

## 單一上下文與多上下文

**單一上下文（多數 repo）**：repo 根目錄一份 `GLOSSARY.md`。

**多上下文**：repo 根目錄放一份 `GLOSSARY-MAP.md`，列出有哪些上下文、各自在哪、彼此怎麼互動：

```md
# 上下文地圖

## 上下文

- [訂購](./src/ordering/GLOSSARY.md)：接收並追蹤客戶訂單
- [帳務](./src/billing/GLOSSARY.md)：開立發票、處理收款
- [出貨](./src/fulfillment/GLOSSARY.md)：管理倉庫揀貨與寄送

## 關係

- **訂購 → 出貨**：訂購發出 `OrderPlaced` 事件，出貨收到後開始揀貨
- **出貨 → 帳務**：出貨發出 `ShipmentDispatched` 事件，帳務收到後開立發票
- **訂購 ↔ 帳務**：共用 `CustomerId` 與 `Money` 型別
```

用哪一種結構由偵測結果決定，不要憑印象假設：

- 有 `GLOSSARY-MAP.md` → 讀它找出各套上下文
- 只有 repo 根目錄的 `GLOSSARY.md` → 單一上下文
- 兩個都沒有 → 等到敲定第一個詞，才在 repo 根目錄建 `GLOSSARY.md`

有多套上下文時，先判斷現在討論的主題屬於哪一套；判斷不出來就問使用者，不要猜。
