# domain-modeling：把講定的詞與決定寫下來

一句話版本：**討論過程中發現用詞含糊或互相打架就當場點出來、定名，定下來的那一刻就寫進 `GLOSSARY.md`；只有「難以反悔、後人會問為什麼、真的做過取捨」三個條件同時成立的決定，才提議寫成 ADR。**

| 名詞 | 意思 |
|---|---|
| 領域模型 | 這個專案用哪些名詞描述它的業務、每個名詞精確指什麼 |
| `GLOSSARY.md` | 詞彙表檔案：一個詞一條定義，外加該避免的同義說法 |
| `GLOSSARY-MAP.md` | 上下文地圖：一個 repo 內有多套詞彙表時，列出各套在哪、彼此怎麼互動 |
| ADR（architecture decision record） | 架構決策紀錄：一份短文件，記下「當時決定了什麼、為什麼」 |

**本 skill 管的是「改動模型」**：挑戰用詞、定名、寫詞彙表、寫 ADR。單純**讀** `GLOSSARY.md` 來對齊用語不算本 skill，那是任何 skill 都該有的一行習慣。

## 一、先找出詞彙表在哪（每次開始前做一次）

不同 repo 的擺法不一樣，**不要假設路徑、不要硬寫任何路徑**，依序偵測：

1. repo 根目錄有 `GLOSSARY-MAP.md` → 這個 repo 是**多上下文**：讀地圖，照它指的位置找到各自的 `GLOSSARY.md`；再判斷現在討論的主題屬於哪一套，判斷不出來就問使用者。
2. 沒有地圖、但 repo 根目錄有 `GLOSSARY.md` → **單一上下文**，就用它。
3. 兩者都沒有 → 現在**先不要建檔**。等到這次討論真的敲定第一個詞，才在 repo 根目錄建 `GLOSSARY.md`；沒有敲定任何詞就不留空檔案。

ADR 目錄同理：有 `docs/adr/` 就沿用它的編號往下接；沒有就等到真的要寫第一份 ADR 時才建。

典型擺法（單一上下文）：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-orders-event-sourcing.md
│       └── 0002-postgres-write-model.md
└── src/
```

多上下文時，系統層級的決定放 repo 根的 `docs/adr/`，只屬於某一套上下文的決定放那套自己的 `docs/adr/`：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 跨上下文、系統層級的決定
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 只屬於這套上下文的決定
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

> 已知慣例：APIs 專案已經有 repo 根目錄的 `GLOSSARY.md` 與 `docs/adr/`（檔名以 `0001-`、`0002-` 編號），格式與本 skill 的規範一致，直接沿用、不要另起一套。其他 repo 一律照上面的偵測步驟走。

## 二、討論進行中要做的五件事

### 1. 跟詞彙表衝突就當場點出來

使用者用的詞跟 `GLOSSARY.md` 現有定義對不上時，**立刻**講出來，不要順著用下去：

> 「詞彙表把『取消』定義成 X，但你這裡講的比較像 Y。要哪一個？」

兩種收場都可以：改用詞彙表的正名，或是改詞彙表的定義。但一定要選一個，不能兩套並存。

### 2. 模糊或一詞多義的詞，提出精確定名

聽到含糊、或在不同句子裡指不同東西的詞，提出一個精確的正名讓使用者選：

> 「你講的『帳號』，是指會員這個人，還是他登入用的使用者？這是兩個東西。」

### 3. 用具體場景壓測概念邊界

討論到概念之間的關係時，自己編出具體場景去壓它的邊界，逼出精確的界線：

> 「一張訂單裡三個品項，其中一個缺貨退款。這張訂單算『部分取消』還是『部分退款』？如果剩下兩個已經出貨了呢？」

場景要挑會打到邊界的，不要挑一看就知道答案的順風局。

### 4. 跟代碼交叉查核

使用者說「這東西現在是這樣運作的」時，去代碼裡確認一下。對不上就把矛盾攤出來：

> 「代碼裡取消是整張訂單一起取消，但你剛才說可以只取消一部分。哪一個才是現況？」

### 5. 詞一敲定就立刻寫進 `GLOSSARY.md`

定下來的那一刻就寫檔，**不要累積到討論結束再一次補**。累積的結果一定是漏掉或走樣。

格式照 [reference/glossary-format.md](reference/glossary-format.md)。

## 三、`GLOSSARY.md` 只是詞彙表

`GLOSSARY.md` 裡**不放實作細節**：不放資料表結構、不放流程步驟、不放待辦。它不是規格書、不是設計文件，也不是草稿紙，就是一份「這個專案的詞是什麼意思」的清單。

實作決定要留紀錄就寫 ADR（見下一節）；過程中的草稿寫在別的地方。

## 四、ADR 要省著提議：三條件全中才提

三個條件**同時成立**才提議寫 ADR：

1. **難以反悔**：之後要改變主意的代價是實在的。
2. **後人會問為什麼**：未來的人看到代碼會納悶「為什麼要這樣做」。
3. **真的在幾個選項間做過取捨**：當時有別的可行做法，因為具體理由選了這個。

少一條就不寫。容易反悔的決定，之後直接改掉就好；不奇怪的決定，沒人會來問；沒有別的選項可選，那就只是「做了唯一能做的事」，沒什麼好記的。

哪些決定通常三條全中、格式怎麼寫，見 [reference/adr-format.md](reference/adr-format.md)。

**提議，不是代寫**：判斷三條件成立時，跟使用者說「這個值得記一份 ADR，因為 …」，由他決定要不要寫。

## 五、規格變了，已經寫下去的文件怎麼辦

上線測試完成前，規格還會變。變了之後，先前寫下的詞彙表與 ADR 處理方式**剛好相反**，因為兩種文件回答的問題不一樣：`GLOSSARY.md` 回答「現在這個詞指什麼」，ADR 回答「當時為什麼這樣決定」。

### `GLOSSARY.md`：直接改，不留歷史

詞義變了就就地把那一條改掉：不保留舊版本、不加一條標著「已廢棄」的舊定義、不讓新舊兩條並存。詞彙表是查一個名詞時的唯一權威，查下去讀到三個過期版本，等於沒有權威。

改一條的同時，照「跟詞彙表衝突就當場點出來」的做法，把受影響的其他條目一起對齊。

### ADR：原則上不改，寫新的取代

ADR 的價值就是保留決策歷史，所以原則上不回頭改已經成立的 ADR：改變主意時寫一份新的，讓新的取代舊的。

但如果機械地「一改就開新的」，寫 ADR 會變成苦差事，結果是大家乾脆不寫。**分界不是「有沒有合併」，是「決定本身變了，還是只是把同一個決定寫得更清楚」。** 換個寫法把同一個決定講得更明白，沒有歷史可言，直接改原檔就好；決定本身換掉了，才有「舊決定」與「新決定」兩件事要分別留下來，這時才寫新的。

| 情況 | 處理 |
|---|---|
| ADR 還在工作分支、還沒合併進發布分支 | 直接改。它還沒成為任何人的參考基準 |
| 已合併，但決定本身沒變（修筆誤、補細節、寫得更清楚） | 直接改。同一個決定寫得更好，沒有歷史可言 |
| 已合併，且決定真的變了 | 寫一份新的 ADR，舊的那份標 `superseded by ADR-NNNN` 指向新的 |

判斷不出來屬於哪一種時問使用者，不要自己挑省事的那條。

狀態要怎麼標（frontmatter 寫哪個值、新舊兩份各要動哪裡）見 [reference/adr-format.md](reference/adr-format.md) 的「狀態（Status）」。
