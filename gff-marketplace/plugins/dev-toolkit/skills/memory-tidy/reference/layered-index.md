# 分層索引：結構與契約

本檔只在 memory 目錄裡有 `idx_*.md`（第二層索引）時讀。單層清單的 `MEMORY.md` 不必讀；它遠低於 80% 時，也不要主動改成分層。

🔴 **分層索引的整理方式是「往下搬」，不是「把行壓短」。** 沒讀這份就動手，會把已經下放的內容又搬回頂層。

## 頂層只有三塊

`MEMORY.md` 頂層**只有三塊**，其餘一律放在第二層：

| 區塊 | 放什麼 | 為什麼留在常駐層 |
|---|---|---|
| **紅線** | 護欄（🔴 別翻回／⛔ 已推翻／禁跑類），按領域分組 | grep 產生不了「這條會讓你做錯事」；漏讀會出事 |
| **待辦** | 進行中專案的下一步，每條一行 | 每天開工唯一必看；下放等於每天多讀一個檔 |
| **導航** | 領域索引入口，**行數固定、不得新增** | 頂層長度與記憶檔數量脫鉤，這是整個結構的重點 |

## 第二層

第二層是 `idx_*.md`：前幾個按**領域**切（如 payment／vendor／git／claude／db），後兩個按**可行動性**切（規則總表、進行中專案總表）。**兩邊重疊是刻意的**：重複索引成本低，找不到的代價高。第二層在啟動時不載入，被讀到才進 context。

## 契約

- 單行 ≤ 150 字元
- 導航區行數不得超過既定值（`check.py` 的 `NAV_MAX`，依該專案的導航設計調整）
- 全檔 ≤ 20,000 字元

本 plugin 不附寫入當下的把關。使用者若在本機裝了寫入後的檢查（hook 或 mod），有的只提醒、有的會擋：**會擋的被擋就照它說的搬，不要繞過**，這道把關存在的理由見主檔「內容歸位」節的實證；只提醒的不會攔下超標寫入，整理完一樣要跑 `check.py verify`。沒裝任何檢查時，用主檔「驗證」節的 `check.py verify` 驗同一份契約。

## 常態區間

分層後常態約在 35–40%。**達到 80% 通常代表有東西該下放或該淘汰，而不是「又要壓一次行」**。整理目標是回到常態區間，不是剛好壓到 19,999。
