整理本地記憶（Claude Code auto-memory，`~/.claude/projects/<專案 slug>/memory/`）的流程。**這是低頻、高風險的多步驟作業**：不常做，但分類搬錯會讓防翻回護欄失效、重踏覆轍。照流程走，不要憑感覺砍。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 索引 | `MEMORY.md`，session 啟動時常駐載入，只列「有哪些記憶、該不該去讀」 |
| 記憶檔 | 索引指向的個別 `.md`，被 recall（自動調出來讀）時才載入 |
| `feedback_*`／`project_*`／`reference_*` | frontmatter `metadata.type` 的三類記憶：規則、工作進度、技術事實。判類以 frontmatter 為準，檔名前綴只是常見命名慣例 |
| 防翻回護欄 | 記著「別翻回／已推翻／別再撿／禁跑」的內容，形式上是歷史、功能上是當前約束 |
| digest | 結案摘要檔 `project_closed_items_digest.md`，收已結案的 project 記憶 |
| 分層索引 | 頂層 `MEMORY.md` 加第二層 `idx_*.md` 的結構，見「先看索引結構」節 |

## 先看索引結構

這步決定要不要多讀一份 reference。先看 memory 目錄裡有沒有 `idx_*.md`：

| 情況 | 做法 |
|---|---|
| 有 `idx_*.md`（分層索引） | 動手前先讀 [reference/layered-index.md](reference/layered-index.md)：頂層三塊、第二層、契約。沒讀就動手，會把已下放的內容搬回頂層 |
| 沒有（單層清單） | 不必讀那份 reference。遠低於 80% 時，照「判斷該不該動」節回報餘裕即可，**不主動改成分層** |

## 判斷該不該動

這步先量字元數，決定是否需要整理。

```bash
cd ~/.claude/projects/<專案 slug>/memory   # <專案 slug> 換成實際目錄名，ls ~/.claude/projects/ 可查
python3 -c "print(len(open('MEMORY.md', encoding='utf-8').read()))"
```

| 字元數 | 動作 |
|---|---|
| < 20,000（80%） | **什麼都不做**。回報數字與百分比，說明還有餘裕 |
| ≥ 20,000 | 執行本流程（本機若裝了會擋寫入的檢查，也會在寫入當下擋） |
| > 25,000 | 已超限：**下次 session 啟動時超出部分會靜默不載入**（不是報錯），優先處理 |

🔴 **絕對不要用 `wc -c` 判斷**。上限是 **25,000 字元**（code point），不是 bytes。中文一字佔 3 bytes，`wc -c` 會虛報約 1.5 倍，讓人以為早就爆了。系統提醒裡的「19.6KB」也是字元數 ÷ 1024，不是檔案大小。

**Claude Code 的內建門檻**（從 v2.1.266 二進位讀到的實際常數，非設定項、改不動）：提醒觸發 `0.8`、要求壓到 `0.7`、索引上限 `25000`、索引與個別記憶檔的行數上限皆 `200`、**個別記憶檔的 recall 上限是 `4096`**。本 skill 的 80% 門檻已與系統提醒對齊，收到提醒即照本流程處理。

🔴 **個別記憶檔超過 4096 就會在 recall 時被截斷**（實測有專案 68 支超過，最大 20 倍）。但**超標本身不是問題**：長設計文件不可能把所有護欄塞進前段，也不需要。要問的是「recall 到它時，**前段看不看得出這裡有雷**」，分三類：

| 類別 | 情況 | 處置 |
|---|---|---|
| A | 護欄全在前段 | 無事 |
| B | 後段有護欄，但前段已有護欄或導引詞（「動工前先讀首節」「見檔內」） | 無事，前段已經把人導去讀全文 |
| C | 後段有護欄，**前段毫無警示** | **要修** |

**C 類為什麼危險**：實測唯一那支的後段有一整段校準，推翻了前段的兩個排查前提，而推翻它們的內容剛好在可見範圍外。結果 recall 時只看得到已作廢的前提，照著查會找錯對象。**修法是在檔案最前面補一行警示、`description` 也標一句，把人導向後段；不要為此拆檔**：拆會破壞單一主題的完整性，代價大於收益。`check.py` 會自動分類並列出 C 類（首次全掃 68 支超標：A 18、B 49、C 1）。

## 範圍與前置

這步劃出能動與不能動的範圍，並先備份。

- 整理針對 **`project_*`**（已結案或停滯的工作）與 **`reference_*`**（可能漂移或已外移的技術事實）；**`feedback_*`**（使用者糾正過的做法）照下一條處理。
- **`feedback_*` 逐條處理，不整份重新摘要**：整份重寫會讓細節逐步流失。
  - 不新建 feedback 記憶，也不把其他類型的檔改分類成 feedback。做法類規則要寫在每次都會載入的地方（CLAUDE.md、skill、hook）；記憶要主動去讀才生效，規則寫成記憶，犯錯當下正好讀不到。
  - 規則已經寫進 CLAUDE.md、skill 或 hook 的 feedback 記憶：在檔案開頭加一行，寫明規則在哪個檔的哪一節。內文的實例（哪次出錯、證據在哪）留著當佐證，不刪。
  - 刪除的依據是這條已經沒用：已改成 hook、已被別條取代、不靠它也做得對。內容舊或長不是刪除理由：規則久未異動代表它穩定生效，不是過期訊號。
  - 要刪或要合併的 feedback 記憶，照本節最後一條列清單給使用者核准再動。
- **動存量檔前先查 mtime 判冷熱**（`ls -lt *.md | head -15`）：近日被其他 session 寫過的熱檔不動，會製造寫入衝突，且可能動到活躍 session 正依賴的接手點。**開工先跑 `check.py snapshot`（見「驗證」節）記下基準，每次寫回 MEMORY.md 前重量一次字元數，數字不是自己改出來的就停手重讀**：並行 session 實測會在整理途中改寫索引。
- **動任何檔之前先備份**（memory 目錄無版控，這是唯一的回復手段）：
  ```bash
  B=$(mktemp -d) && tar czf "$B/memory-backup.tgz" *.md && echo "備份: $B/memory-backup.tgz"
  ```
- **淘汰、刪除、外移候選先列清單經使用者確認再動**；把內容從索引搬進記憶檔或第二層（見「內容歸位」節）與驗證不需確認。

## 內容歸位（第一順位，多數情況只需這步）

這步把不該待在索引裡的內容搬回它該在的地方。**索引的功能是「讓人知道有這筆記憶、該不該去讀」，不是取代那筆記憶。**

索引超標時，**先問「這段該不該待在索引」（分層索引就問「它屬於頂層三塊的哪一塊」），不該就往下搬**，而不是把它壓短：

| 出現在索引的內容 | 處置 |
|---|---|
| 背景敘述、這個 bug 是什麼、怎麼發現的 | **搬進該記憶檔**（那裡本來就有，索引不必重述） |
| 完成狀態、MR 號、發版 tag | **刪**（git log 與 GitLab 查得到），除非它本身是護欄（如「tag ≠ 已上線」） |
| 某領域的檔案清單 | 分層索引：**搬進對應 `idx_*.md`** |
| 護欄（🔴⛔⚠️） | 分層索引：**留頂層紅線區**，一條都不下放 |
| 下一步（▶️） | 分層索引：**留頂層待辦區**，壓成一行 |

🔴 **護欄不可下放，這有硬數據**：Vercel 的 agent eval 顯示常駐檔 100%、改成按需載入只剩 79%，且 **56% 的案例根本沒去讀**；SkillsBench（34,198 個真實 skill）只有 49% 的執行載齊該載的 skill，有干擾項時掉到 31%。判準是「**漏讀會不會出事**」，不是「內容長不長」。

⚠️ **分層索引的頂層不放長清單行**：清單一律在 `idx_*.md`，單行 150 字元的契約也不容許一行塞多個連結。在 `idx_*.md` 內部則不必群組化，一檔一行即可（第二層沒有字元壓力）。

**更新既有內容時：改寫，不要往後追加。** 追加就是膨脹的機制本身。

🔴 **只搬不淘汰撐不久**：一份 1,867 個 repo、247,694 條指令的研究顯示，指令檔一生平均成長 226%，大手術砍掉約 40% 後**十個 commit 內胖回九成**。所以「淘汰」節每次都要掃。

## 淘汰：把不再需要的移出索引（容量的長期解）

這步把已結案或已失效的記憶移出索引，容量才不會很快又滿。

**project_*（結案）**：移進結案摘要檔 `project_closed_items_digest.md`（沒有就建立，導言寫明「新結案項目加到本檔，不要加回 MEMORY.md」）。可移出條件（三者皆需）：①功能已合入發布分支且已部署 ②無殘留待辦 ③內容的權威來源已在別處（代碼、`docs/`、skill、git log）。

**reference_*（過時或已外移）**：符合**任一**即移出索引，檔案併入 digest 一行或刪除：
- **事實已失效**：版本升級、機制已改、指涉的檔案或流程已不存在（引用前本就要重驗，驗出失效就地淘汰）
- **權威來源已進 repo**：程式碼註解、`docs/`、skill（見下方外移雙軌）
- **一次性事故已收官**：根因已修、防線已進代碼、零殘留尾巴

**外移雙軌（穩定知識的最終歸宿是 repo，不是記憶）**：整理時看到符合形狀的 reference，登記成外移候選清單交給使用者，整理當下不動 repo：
- **schema 或類別層級的陷阱**（欄位語意重載、某測試 trait 會炸庫）→ 寫成**程式碼註解**，緊貼會踩雷的位置
- **跨檔或流程層級的事實**（判準、對照表、排查工法）→ 進 **`docs/`** 或對應 skill

動 repo 要開分支走 MR；**MR 合併後**該記憶即滿足「權威來源在別處」，下輪整理刪除。

**不可淘汰的例外（凌駕以上全部）**：檔內帶「別翻回／別再撿／禁跑」類反悔防護，或記著只存在於對話中的取捨理由；那正是記憶的核心價值，功能上線也要留。

## 個別記憶檔的考古分流（只在必要時）

這步把單一大檔裡的純歷史搬到 archive 檔，只在值得時做。

**成本閘門：只對「檔案 ≥ 5,000 字元且可搬 ≥ 2,000 字元」的檔專程做**；小檔不專程動，等日後碰到該主題時順手改。要做時讀 [reference/archive-triage.md](reference/archive-triage.md) 依規格分流。

🔴 先記住唯一不可讓步的原則：**防翻回護欄（⛔已推翻／別再撿／禁跑類）一律完整留主檔**。它形式上是歷史、功能上是當前約束，搬走等於攔截失效。

⚠️ 分流時順手確認**主檔屬於「判斷該不該動」節的哪一類**。C 類就補前段警示（不是拆檔）；A、B 類不必動。

## 驗證（每次整理完都要跑）

這步用驗證器確認沒有弄丟任何記憶。用 skill 附帶的 `check.py`（與本檔同目錄；`<skill 目錄>` 即 skill 載入訊息列出的 Base directory），在 memory 目錄下執行：

```bash
S=$(mktemp -d)
python3 <skill 目錄>/check.py snapshot > "$S/before.json"   # 動任何檔之前
python3 <skill 目錄>/check.py verify "$S/before.json"       # 整理完成後
```

涵蓋：字元數與百分比、**契約檢查**（全檔 20,000 一律檢查；單行 150 與導航行數只在有 `idx_*.md` 的分層索引檢查，單層清單印「略過」）、**兩層可達性**（每支記憶檔是否能從頂層經 `idx_*.md` 或 digest 到達）、**recall 可見性三分類**（「判斷該不該動」節的 A／B／C，C 類逐支列出）、**連結 manifest 對帳（逐筆列出新增與移除）**、索引的懸空連結、**記憶檔內文的 `[[wikilink]]` 懸空**、archive 檔雙向配對。

🔴 **manifest 對帳涵蓋 `MEMORY.md` 加上全部 `idx_*.md`**，不是只看頂層。只看頂層的話，把清單搬到第二層會被誤報成「移除了 180 個連結」。

**對帳判準**：內容只在兩層之間搬動，移除清單應為空；有淘汰，移除清單必須**逐筆對得上去向**（digest、已外移、archive），對不上就是弄丟了。裸總數相同不能證明零損失（可能刪 A 誤加 B）；🔴 更不能用 `grep -c` 數連結：它數的是「含連結的行數」，一行多連結必失真。`archive_*.md` 依規約本就不入索引，不算懸空。

⚠️ **懸空檢查分兩段**：索引檔的 `](xxx.md)` 指到的檔案在不在，以及各記憶檔內文的 `[[wikilink]]` 解析不解析得到。後者在刪除、合併、改名之後尤其該看，`check.py` 會逐筆列出解析不到的連結與它出現在哪些檔。它怎麼比對有兩個要點，判讀結果前要知道：

🔴 **比對時連結與目標兩側的連字號都當成底線**：檔名一律底線，但不少檔的 frontmatter `name` 與內文連結寫連字號；不正規化光這一類就會產出 50 筆以上的假懸空，把真的那筆淹掉（實測 54 筆命中裡 53 筆屬此類）。

🔴 **目標集是檔名加上 frontmatter `name`，只比對檔名會誤報**：記憶規約規定 `[[wikilink]]` 指向的是對方的 `name:` slug，**不是檔名**，而兩者不一致的檔並不少。單用檔名當目標集，會把這類**完全正確**的連結報成懸空。實測 11 筆命中有 1 筆屬此類，而它的長相與「缺前綴」的真缺陷幾乎一樣，照著修就是把好連結改壞。

**真缺陷幾乎只有一種形狀**：連結漏掉 `project_`／`reference_` 前綴，而目標檔確實存在（例：`[[backlog-todo-doc]]` ↔ `name: project_backlog_todo_doc`）。修法是補前綴，但**動手前先讀目標檔的 `name:`，照它的原樣寫**（該用連字號就連字號，別擅自換成檔名格式）；ASCII token 取代用 `perl -i`（不加 `-CSD`），改完重跑 `check.py` 確認該筆消失。⚠️ 掃描時的正規化只用於**比對**，不代表可以照正規化後的樣子回寫。

判讀時這三類命中**不是缺陷、不要修**：

- **教學用的示範連結**：講解 wikilink 懸空檢查的那份記憶自己就寫了數個不存在的示範連結，去修等於把教學範例改壞；`archive_*` 內的同型佔位詞同理。
- **skill 名被誤寫成 `[[wikilink]]`**：skill 不是記憶，去括號改純文字即可。
- **反向檢查（檔案存在但不在索引）不是錯誤清單**：`check.py` 的兩層可達性已涵蓋此項；真正要看的只有「有沒有**進行中**的項目掉出索引」。

## 回報格式

給使用者的回報要有：**前後字元數與百分比**、**契約檢查結果**（單行、導航行數、全檔）、**兩層可達性**（N／N，遺失幾支）、**連結 manifest 差異**（移除清單逐筆標去向：digest、已外移、archive；新增清單）、**外移候選清單**（若有，含建議落點）、**動了哪些區塊、沒動哪些**（`feedback_*` 逐筆列出：加了規則位置註記的、列入刪除或合併清單待核准的）、**懸空連結掃描結果**、**熱檔檢查是否曾觸發停手**。

如果判斷結果是「不需要整理」，直接說數字與餘裕，**不要為了有產出而硬做**。
