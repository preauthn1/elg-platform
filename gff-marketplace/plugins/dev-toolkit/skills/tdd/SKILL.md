# tdd：紅綠迴圈的紀律

一句話版本：**先寫一支會失敗的測試，再寫剛好讓它通過的實作；測試只寫在講好的縫上，一次一個縫、一支測試、一份最小實作。**

| 名詞 | 意思 |
|---|---|
| 縫（seam） | 要觀察行為的公開介面邊界：從外面就看得到、不用伸手進去內部的那條線 |
| 紅 → 綠 | 先寫一支會失敗的測試（紅），再寫剛好讓它通過的實作（綠） |
| 公開介面 | 這段代碼給外面用的入口：service 的公開方法、HTTP 路由、command 等 |
| 內部協作者 | 只有這段代碼自己會用到的類別或方法，外面的人不會直接碰 |
| 垂直切片 | 一支測試配一份實作，做完一刀再做下一刀；相對於「先寫完所有測試再寫實作」 |
| 曳光彈 | 每一刀都是一次試射：打完看結果，再決定下一刀往哪打 |

**本 skill 不會自動觸發。** 只有三種進來的方式：`design-grilling` 訪談時使用者答「這一件要走測試先行」後用 Skill 工具叫起；`bug-diagnosis` 在修 bug 前要寫回歸測試時用 Skill 工具叫起；或使用者手動輸入 `/dev-toolkit:tdd`。

**每一輪迴圈都要遵守下面每一節**，不是做完再回頭對照。

## 開工前：對齊專案的領域語言

探索代碼之前，先讀 repo 的 `GLOSSARY.md`（詞彙表，如果有的話），讓測試名稱與介面用詞跟專案既有的領域語言一致；同時尊重你要動的那塊區域已有的 ADR（架構決策紀錄，通常在 `docs/adr/`）。

沒有 `GLOSSARY.md` 就跳過這步，不要為此建檔（詞彙表要不要建、怎麼建是 `dev-toolkit:domain-modeling` 的事）。

## 一、什麼是好測試

好測試**透過公開介面驗行為**，不驗實作細節。內部怎麼寫可以整個換掉，測試不該跟著改。

一支好測試讀起來像一句規格：「會員可以用有效的購物車結帳」一看就知道系統具備什麼能力，而且它能撐過重構，因為它根本不在乎內部長什麼樣。

對照範例見 [reference/good-and-bad-tests.md](reference/good-and-bad-tests.md)，什麼時候可以用替身見 [reference/mocking.md](reference/mocking.md)。

## 二、縫：測試該寫在哪

**縫（seam）＝你要觀察行為的那條公開介面邊界。** 判斷一條線是不是縫，看兩件事：

1. 外面的呼叫者本來就會經過它（它是這段代碼對外的入口，不是內部的中繼站）。
2. 從它身上就看得出行為對不對，不需要伸手進去看內部狀態。

**測試只寫在縫上，不碰內部。** 私有方法、只有自己用的協作者、內部的中間狀態，都不是縫。

**寫任何測試前，先把要測哪些縫列出來，跟使用者確認。**

> 「這次的公開介面是 X，我打算測這幾個縫：…。每個縫一行：它抓得到什麼、漏掉什麼。這樣可以嗎？」

每個提議的縫都附一行「抓得到什麼、漏什麼」，讓使用者在縫之間選的時候不是用猜的。

**沒有確認過的縫不寫測試。** 理由：你不可能什麼都測；先講好測哪裡，測試的力氣才會落在關鍵路徑與複雜邏輯上，而不是平均灑在每個邊角。

## 三、三個反模式

### 1. 跟實作綁死

三種常見形態：

- mock 內部協作者（把自己家的類別換成替身）
- 測私有方法（用反射硬撬開來測）
- 繞過介面從側面驗證（不用讀取介面，直接去查資料庫確認寫進去了）

**辨識訊號：重構之後測試壞了，但行為根本沒變。**

### 2. 自我證明

預期值用跟實作同一套算法算出來，所以測試從一開始就注定會過，永遠不可能跟代碼唱反調。

例：預期值也拿 `array_sum` 算一次、自己按同一套邏輯手推出來的快照、或是斷言一個常數等於它自己。

**預期值必須來自獨立的來源**：已知的字面值、手算過的例子、規格書上的數字。

### 3. 水平切片

先把所有測試寫完，再開始寫實作。

這樣寫出來的測試驗的是**想像中的行為**：你測到的是東西的形狀，不是使用者真正在乎的行為；測試會對真正的改動變得遲鈍；而且在還沒搞懂實作以前就把測試結構定死了。

改用**垂直切片**：一支測試 → 一份實作 → 再下一支。每一支測試都是一顆曳光彈，根據上一輪學到的東西決定下一輪打哪裡。

## 四、迴圈紀律

- **先紅再綠**：先寫會失敗的測試，然後只寫剛好讓它通過的代碼。不要預先為之後的測試鋪路，不要加還沒人要的功能。
- **一次一刀**：一個縫、一支測試、一份最小實作，做完再下一刀。
- **重構不屬於這個迴圈**：重構歸審查階段，不要夾在紅綠迴圈裡做。

## 五、重構與審查交給誰

紅綠迴圈跑完、代碼會動了之後，重構與品質檢討交給審查官，分工固定，同一件事只找一位：

| 要看的東西 | 找誰 |
|---|---|
| 金流正確性、併發、事務 | `apis-toolkit:timo` |
| 可維護性、可讀性、測試覆蓋 | `apis-toolkit:rhyse` |

兩位都是唯讀審查、只診斷不改檔；他們給的意見要不要落地，由使用者決定。
