# plain-writing：第一次讀就懂、內容一分不減

一句話版本：**動筆前先回答「誰會讀、什麼時候讀、讀完要做什麼」；寫的時候用完整句子、多列點、不評價、不速記；寫完照「送出前檢查」逐條對。**

| 名詞 | 意思 |
|---|---|
| 白話 | 沒參與討論的人，不用先學代碼或行話，讀一遍就知道在說什麼、要做什麼。不是「講給外行聽」的簡化，規則、數字、事實一個都不少 |
| 速記 | 用箭頭、斜線、代號把幾件事串成一行的寫法，例如「token 錯 → 401 → log」 |
| 佔位符 | 範本裡等著被填掉的角括號，例如 `<一句話說明>` |

本 skill 管的是**所有給人讀的文字共通的寫法**。專案自己有規定格式的文件（MR 描述的九節、技術文件的結構、工單的欄位）先照專案或對應 skill 的規定，格式之內的每一句話照本 skill 寫。

## 一、動筆前先想清楚

先回答三個問題：**誰會讀、什麼時候讀、讀完要做什麼**。答案決定要寫什麼、寫多少。

- 讀者沒看過你的對話、沒看過你的思考過程。寫成**單獨拿出來也看得懂**的樣子。
- 讀者要做決定的：把**選項、取捨、推薦**放在前面。
- 讀者要照著做的：寫成**依序編號的步驟**，每一步寫到照著做就能完成（在哪個畫面、做什麼、怎麼確認成功）。
- 讀者只是要知道結果的：**結論先講**，細節放後面。

## 二、四條判準，任一不過就重寫

1. **不用讀者查不到的代碼**：模式、步驟、分類一律有中文名稱（「讀單模式」「第 4 步：確認同名 tag 不存在」）。對應檔名或 schema id 的代碼（`Mode A`、`Phase 2`、`Q3`）放括號當別名。章節互相引用用節名，不用 `§2.4` 這類節號；個人 backlog 的編號、計畫文件的 task 編號、只在某次對話裡成立的簡稱，都不能出現。
2. **術語第一次出現就解釋**：一句短句說它是什麼、在這裡做什麼，例如「PAT（personal access token，登入 GitLab API 的個人金鑰）」。英文行話能換中文就換：deterministic 改固定規則、fallback 改退路、abort 改中止、dry-run 改預覽、atomic 改一次到位。換成中文時用台灣的譯名，沒把握就保留英文原文。例如 port 寫「埠」「連接埠」或保留 `port`，不寫「端口」（中國大陸譯名），也不寫「港口」（誤譯）。工具參數名、命令、欄位名原樣保留。專案已定義的編號（需求單 `4137`、驗收條件 `AC-3`、SSOT 編號）可以直接用。領域名詞用該 repo 詞彙表（`GLOSSARY.md` 或 `CONTEXT.md`）的正名，不用它列為避免的詞；沒有詞彙表就在文件裡自己定義，不要求讀者去讀別的 repo。
3. **一句話講一件事**：不用全形破折號（U+2014，單個或連用兩個都不用）串轉折，改冒號、句號或拆句。表格空格寫「無」。每個步驟開頭先一句「這步在做什麼、為什麼」。
4. **內容一分不減**：規則、數字、實測事實、禁止清單原樣保留。改寫只動措辭與結構；改寫別人的文字時，在 commit message 或回覆裡明寫「未改任何規則」。純機器規格（schema、cheatsheet、設定檔）不套本條。

## 三、三條核心規則

### 中立客觀

- 寫事實與理由，不寫評價。不用「很好」「優雅」「完美」「大幅改善」「非常重要」這類形容詞；重要性由內容本身說明，例如「少了這一步，金流商回調進來會重複入帳」。
- 不誇大，也不貶低。有代價就寫出代價，例如「代價是回應多約 0.3 秒」。

### 句子寫完整，不用速記

- 每一項都寫成主詞、動詞齊全的句子，不用箭頭、斜線或代號串起來。
- 縮寫第一次出現時要說明。
- 名稱與說明都直述實際做的事。制度、角色、流程用台灣職場的說法（例如「審核人」「MR 審批流程」），不用比喻、生活化類比或中二的說法（例如「守護者」「過門」「敲門」「對暗號」）。術語用正名，再加一句解釋。取名前先想一下：台灣同事開會時會不會這樣講。
- 自己訂編號或代號之前，先查同一個目錄有沒有別的文件已經用同一組符號表示別的意思。例如同目錄另一份文件的 `P0` 到 `P5` 是「階段」，這份就不要拿 `P0` 表示「優先級」。

### 多用列點，不寫長段落

- 一段超過三行就拆成列點；一個列點只講一件事。
- 有兩個以上的維度要比較時用表格，例如「做法、優點、缺點」或「欄位、必填、寫什麼」。
- 有先後順序用編號列表，沒有就用一般列點。

| 不要這樣寫 | 要這樣寫 |
|---|---|
| 這個設計非常優雅，大幅提升了可維護性 | 簽名邏輯抽成一個 trait 共用，代收與代付不必各寫一份 |
| 簽名錯 → 401 → log，回應 ok | 簽名驗證失敗時，金流商回 401，程式記下一筆錯誤，回應照樣是成功 |
| 改 env 後 redeploy | 改完環境變數之後，要重新部署 |

更多對照見 [reference/examples.md](reference/examples.md)。

## 四、結構

- **用標題分段**：讀者掃標題就知道每一段在講什麼。
- **重點放前面**：結論、要讀者決定的事、會造成損失的風險，放最前面。
- **固定的格式就固定到底**：同一類文件每次都用一樣的段落和順序；某一段沒有內容時寫「無」，不整段刪掉。這樣回頭查時每份文件都在同一個位置找得到同一類資訊。
- **一份文件只有一個事實來源**：其他地方要提到同一件事時用連結指過去，不複製一份。真的要重複時，寫明兩份要一起改。

## 五、寫「為什麼」，不只寫「做了什麼」

- 做了什麼，看程式碼或 diff 就知道。文件的價值在那些看不到的東西：為什麼這樣做、放棄了哪個做法、為什麼放棄、有什麼代價。
- 設計決定用三欄表格：**決定**、**理由**、**放棄的做法**。「放棄的做法」填不出來，就代表它不是一個決定，不用列。
- 有多個方案時：先用表格列每個方案的優點和缺點，再給推薦並說明為什麼，推薦的那一個標「（推薦）」，然後讓使用者選，不替使用者決定。

## 六、準確

- **只寫確定的事**：每一條都要對得到某個檔案、某個指令的結果，或使用者做過的決定。不確定的寫「不確定」或列成待決，不用猜的補上。
- **日期寫絕對日期**，例如「2026-10-11 起」，不寫「上週」「前天」。
- 數字寫這次實際算出來的，不抄前一次的結果。
- **寫錯了就直接更正**：明確說出哪一句錯了、正確的是什麼，不含糊帶過。

## 七、格式細節

- 用繁體中文。中文用全形標點（，。：；「」），程式碼和英文裡用半形。引用一段話或畫面上的文字時用「」。
- 人名照團隊的寫法：RB 全大寫，其他人首字大寫（例如 Mars、Daniel、Rhys），不照抄 GitLab 上的小寫帳號。這條只管給人看的名字；要填進 GitLab 的帳號欄位（指派人、`assignee_usernames`）時，照 GitLab 實際的帳號原樣填。
- 中文與英文、數字之間加一個半形空白，例如「共 5 張單」「`git push` 只推 HEAD」「GitLab 工單」。
- 檔名、指令、函式、變數、屬性名稱、網址片段一律用反引號標起來。
- 粗體只用在會造成損失或一定要做的地方，例如「**不要新建部署，網址會變**」。整段都粗體，就等於沒有重點。
- 不用表情符號。唯一的例外是狀態表格裡的 ✅、⬜，因為它們比文字好掃讀。
- 不用驚嘆號，標語式的句子也不用。
- 稱呼不確定性別的人時用「對方」，不從名字猜性別。

## 八、長度

- 每一項只回答一個問題，一句話講得完的不寫兩句。
- 不重述讀者的問題，不寫「以下是……」這類開場白，也不在結尾把內容再總結一遍。
- 細節分成兩層：一定要知道的放正文；想深入了解才需要的，放表格或後面的段落。
- 討論過程不寫進文件，只留結論。過程留在對話或需求單的沿革裡。

## 送出前檢查

- [ ] 讀者沒看過對話，單獨看這份也懂
- [ ] 結論、要決定的事、風險放在前面
- [ ] 沒有讀者查不到的代碼；術語第一次出現有解釋
- [ ] 沒有評價性的形容詞，也沒有誇大
- [ ] 每一項都是完整的句子，沒有箭頭、斜線串起來的速記
- [ ] 沒有超過三行的段落；要比較的內容用了表格
- [ ] 有多個方案時，附了比較表和推薦
- [ ] 每個數字、日期都實際查證過，日期是絕對日期
- [ ] 中英文之間有空白，程式相關的名稱都用了反引號
- [ ] 粗體只用在會造成損失或一定要做的地方
- [ ] 沒有全形破折號：`grep -c $'\u2014' <檔案>` 為 0
- [ ] 改寫別人的文字時，規則、數字、事實一個都沒少

## 對話範例

> 使用者：「幫我把這段部署說明改白話一點，給新同事看。」
> AI：載入本 skill。先確認讀者是要照著做的新同事，把說明改成編號步驟，每步寫在哪個畫面、做什麼、怎麼確認成功；「redeploy」改成「重新部署」並在第一次出現時說明是什麼；把「token 錯 → 401」這類速記改成完整句子；回覆時註明「未改任何規則，只動措辭與結構」。
