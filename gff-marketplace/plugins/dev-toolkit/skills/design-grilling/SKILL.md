# design-grilling：動手前把需求逼問到沒有隱含假設

一句話版本：**把要做的事攤成一棵決策樹，一輪一輪把「現在就能問」的題目全部問完、每題附上推薦答案，問到沒有任何事情是偷偷假設的；使用者確認共識之後，才開始寫計劃。**

| 名詞 | 意思 |
|---|---|
| 決策樹 | 把這次要做的事拆成一個個決策，每個決策底下再掛出它一旦定了才會浮現的決策 |
| 前緣（frontier） | 決策樹上「前提都已經定了、現在就能問」的那一圈題目。前提還沒定的題目不在前緣 |
| 一輪（round） | 一次把整個前緣的題目全部問完，然後停下來等使用者回答。前緣超過 4 題時先收斂到 4 題以內，見「一輪問完整個前緣」 |
| `AskUserQuestion` | Claude Code 的提問工具，把題目變成使用者可以直接點選的選項，不必自己打字。一次最多 4 題、每題 2 到 4 個選項 |
| 計劃模式（plan mode） | Claude Code 的規劃階段：只讀不改，最後用 ExitPlanMode 把計劃交給使用者核准 |
| 工單 | GitLab 上的需求單或子任務（網址長得像 `.../-/work_items/<id>`） |
| `GLOSSARY.md` | 詞彙表檔案：一個詞一條定義，講清楚這個專案裡這個詞精確指什麼 |
| ADR（architecture decision record） | 架構決策紀錄：一份短文件，記下「當時決定了什麼、為什麼」 |

## 這支 skill 站在流程的哪一段

固定順序，不可跳步：

1. **讀工單或聽需求**：使用者貼工單網址就先去把工單讀回來（見「從 GitLab 工單開始時」），沒有工單就以使用者說的話為起點。
2. **分輪提問**：本 skill 的主體，見下面各節。
3. **使用者確認共識**：由使用者明說「就這樣」「可以了」之類的確認，AI 不替他確認。
4. **才進計劃模式**：把訪談結果寫成實作計劃，用 ExitPlanMode 交出去。
5. **核准後才實作**：計劃經 ExitPlanMode 核准後才動代碼。

**訪談插在計劃模式前面，不取代計劃模式。** 訪談的產物是「共識」，計劃模式的產物是「要改哪些檔、每步做什麼、怎麼驗收」。問完就直接改代碼、或是跳過訪談直接寫計劃，兩種都是錯的。

**前緣還沒清空以前不要動實作代碼。** 原意是別還沒問清楚就急著改東西：這段期間要交付的代碼一行都不改，只做唯讀動作，讀代碼、讀工單、查事實。

**例外是訪談自己的產物：詞彙表（`GLOSSARY.md`）與 ADR 可以在訪談期間當場寫。** 它們是訪談問出來的結論本身，不是這次要交付的代碼；當場寫下來才不會走樣，做法見「訪談期間把定下來的詞與決定寫下來」。

**但寫之前工作分支必須已經建立。** `dev-toolkit:release-workflow` 的「0. 新需求 gate」明文把設計文件與計劃文件也算成檔案修改，寫入前工作分支要先開好。分支還沒開就先照那支的程序開，開分支的步驟看那支，本 skill 不重述。

## 與其他 skill 的分工

| skill | 它管什麼 | 本 skill 管什麼 |
|---|---|---|
| `dev-toolkit:release-workflow` | 分支要不要另開、從哪開、develop gate、MR、發布、清理 | 動手前把需求問清楚 |
| `op-toolkit:sure-score` | 評估一張工單對開發者夠不夠清楚，只評不改單 | 把「不夠清楚」的地方變成問題問出來 |
| `dev-toolkit:tdd` | 測試先行的紅綠迴圈紀律 | 問使用者這一件要不要走測試先行 |
| `dev-toolkit:domain-modeling` | 挑戰模糊用詞、定名、寫詞彙表、判斷哪些決定值得寫成 ADR | 逼問出「要定名的詞」與「要拍板的取捨」，當場交給它寫下來 |

- **和 `release-workflow` 並行、不互相取代**：使用者一句「我要開始做 X」會同時觸發兩支。那支處理「開不開新分支、開在哪」，本支處理「這件事到底要做成什麼樣」。兩邊的提問可以合併成同一次詢問，但不要因為載入了其中一支就略過另一支。
- **訪談進行中一路叫起 `dev-toolkit:domain-modeling`**：敲定一個詞、拍板一個取捨，當下就交給它寫進詞彙表或提議寫 ADR，不要等訪談結束再統一整理。做法見「訪談期間把定下來的詞與決定寫下來」。
- **使用者已經跑過 `op-toolkit:sure-score`**：把分數低的維度直接轉成第一輪的題目。分數低的維度就是工單沒講清楚的地方，那正是前緣最前面該問的東西，不要重新從零想一套問題。

## 一、先把設計攤成決策樹

開口問之前，先在心裡（或寫在草稿裡）把這次要做的事拆成決策：每個決策底下掛的是「這個決策定了之後才會浮現」的決策。

例：「訂單要不要支援部分取消」是上層決策；它底下才會有「部分取消之後餘額怎麼退」「已出貨的品項算不算在內」。上層沒定，底下這些問了也是白問，因為你得先猜一個答案才問得出口。

**判準：一個題目要問出口，必須不用猜任何還沒聽到的答案。** 需要猜的，就代表它的前提還沒定，它屬於後面的輪次。

## 二、一輪問完整個前緣

一輪就是把當前前緣的題目**一次全部**問完，然後停下來等答案。不要一題一題擠牙膏，也不要把還沒解鎖的題目提前塞進來。

### 用 `AskUserQuestion` 問，不要印文字清單

**預設一律用 `AskUserQuestion` 工具發問**，讓使用者直接點選。不要把整輪題目印成一長串 markdown 文字，那種形式使用者點不了，每題都得自己打字回答。

**推薦答案就是第一個選項**，`label` 結尾標「（推薦）」。這就是「每題附上推薦答案」在工具上的做法：使用者一路點推薦選項就等於回「照你的」，只在想改的那幾題挑別的。

推薦答案要是真的推薦，不是客套。在選項的說明文字裡講清楚你為什麼推薦這個、放棄的那個差在哪。

**開放式的設計決策同樣走這條路。** 使用者要的答案不在你列的選項裡時，可以用工具內建的「Other」自由輸入，所以不要因為「這題不是選擇題」就退回文字清單。你的工作是先把最可能的兩三種走法攤出來，不是把空白丟給使用者。

工具的欄位限制照下表寫，寫錯就跑不動：

| 欄位 | 限制 |
|---|---|
| `header` | 最多 12 個字元。它是這題的短標籤（例「退款路徑」），不是題目本身 |
| `question` | 完整的問句，把這題在取捨什麼講清楚 |
| `options` | 每題 2 到 4 個：推薦答案排第一，其餘是合理的替代方案 |
| 一次幾題 | 一次最多 4 題（工具硬上限） |

### 前緣超過 4 題就收斂，不要分批硬問

一輪最多 4 題是硬上限。算出來的前緣超過 4 題時，**不要拆成好幾次連續發問把人問到煩**，而是把這一輪收斂成最關鍵的 4 題以內：挑那些一旦定了、其餘題目的答案會自己浮現的；剩下的等下一輪重算前緣再說。

收斂不下來、每題看起來都非問不可，代表決策樹拆得不夠細：回頭把上層決策重拆，讓這一輪只剩真正能解鎖後續的那幾題。**題目被迫收斂通常比問得多更有價值**，它逼你分辨哪些是真的要使用者拍板、哪些只是你自己還沒想清楚。

### 退路：真的列不成選項時才用文字

只有在題目無法列成選項時才改用文字問：需要使用者貼一段規格、給一個網址、給一段自由描述的題目。問的時候要順帶說明這題為什麼沒有選項，讓使用者知道不是你偷懶。

文字退路要編號、要附推薦答案，讓使用者可以只回「1、3 照你的、2 我要改成 …」，格式：

```
❓ **Q1** - **<題目標題>**：<題目內容，可以多段，可以列出幾個選項>

➡️ <你的推薦答案>

---

❓ **Q2** - **<題目標題>**：<題目內容>

➡️ <你的推薦答案>
```

**這是退路，不是預設。** 列得成選項的題目一律走 `AskUserQuestion`。

## 三、每輪之後重算前緣

使用者的答案會重塑整棵樹：已定的決策把前緣往外推，原本卡住的題目解鎖，有些題目則因為某個分支被否決而整條消失。

所以每收到一輪答案，重新算一次前緣，再問下一輪。**不要拿上一輪算好的題目清單照唸**，那份清單在使用者回答的當下就過期了。

## 四、找事實是 AI 的事，做決策是使用者的事

- **事實**（代碼現在怎麼寫、某個欄位存不存在、某支服務叫什麼、線上資料長什麼樣）：AI 自己去查。只有範圍大、彼此獨立的查證（例如跨多個 repo 盤點）才值得派 subagent。
- **決策**（要做成哪一種、取捨怎麼選、範圍到哪）：一律問使用者，問完等他回答。

**不要問使用者你自己查得到的東西。** 「請問目前的退款是走哪個 service」這種題目不該出現在提問清單裡，那是你該查完再來問的。使用者的時間只花在真正需要他拍板的取捨上。

## 五、查事實不要卡住其他題目

正在跑的查證，等同一個「還沒定的前提」：**只有依賴那個事實的題目要等**，其餘前緣的題目照樣在這一輪問出去。

不要因為還有查證沒做完，就整輪停下來等。

## 六、固定要問的題目：這一件要不要走測試先行

每次訪談都要問這題，通常放在第一輪。它跟其他題目一樣走 `AskUserQuestion`，佔掉這一輪 4 題額度的其中一題：

- `header` 寫「測試先行」。
- `question` 寫：這一件要不要走測試先行（先寫會失敗的測試，再寫剛好讓它過的實作）？
- 兩個選項：走測試先行、不走測試先行。哪一個標「（推薦）」依這次要改的東西判斷，判斷方向見本節最後一段。

收到答案之後：

- 使用者答**要** → 用 Skill 工具叫起 `dev-toolkit:tdd`，後續實作照那支的紅綠迴圈紀律走。
- 使用者答**不要** → 完全不載入 `dev-toolkit:tdd`，後面也不要再自己把測試先行塞回流程。

**這題由使用者依這次要改的東西自己決定，AI 只提供判斷材料、不代答。** 常見的判斷方向：演算法、金流邊界、規則複雜且錯了代價很大的東西通常走測試先行；改前端排序、調文案、換樣式這類通常不走。

## 七、訪談期間把定下來的詞與決定寫下來

訪談會逼出一大堆取捨。問完就進計劃模式、實作、合併的話，那些取捨會在路上蒸發：半年後看代碼的人只知道結果，不知道當時為什麼這樣選。所以**不要等訪談結束再統一整理**，一個詞被敲定、或一個決策成立的當下就寫下來。

做法：**在訪談進行中用 Skill 工具叫起 `dev-toolkit:domain-modeling`**，把這件事交給它做。

- **一個詞被敲定**（使用者拍板某個名詞從此指什麼、或是在兩種講法之間選了一個）→ 交給它寫進詞彙表 `GLOSSARY.md`。
- **一個決策成立**（某個取捨拍板了）→ 交給它判斷這個決定值不值得寫成 ADR，值得就由它提議寫。

**判準與格式一律由 `domain-modeling` 決定，本 skill 不複述。** 什麼樣的決定才值得寫成 ADR、詞彙表一條要寫成什麼樣、檔案放哪、編號怎麼接，全部是那支的規矩。兩邊各寫一份的話，改了一邊另一邊就會過期。

**寫之前工作分支要先建立**，理由見「這支 skill 站在流程的哪一段」的那條例外。

**叫不起來也不要中斷訪談。** 兩支 skill 都在 `dev-toolkit`，裝了就都有，正常不會叫不起來；真的載入失敗時照樣把前緣問完，提問是本 skill 的本份，文件沒寫成不是停下來的理由。事後跟使用者說一聲有哪些詞與決定還沒被記下來。

## 八、從 GitLab 工單開始時

使用者貼的網址形如：

- `<gitlab>/target/tickets/-/work_items/<id>`：需求單（主單），GitLab project `target/tickets`（365）
- `<gitlab>/target/ticket_tasks/-/work_items/<id>`：子任務，GitLab project `target/ticket_tasks`（544）

規矩：

1. **先讀工單再提問**：經 gitlab MCP（`gitlab-mcp` plugin 提供的工具）取回 title、description、labels，網址末段的 `<id>` 就是 `issue_iid`。本 instance 的 `get_work_item` / `list_work_items` 不可用（上游 MCP 的 GraphQL 查詢寫死了本 instance 沒有的型別），改用 `get_issue` 搭配 `project_id` 與 `issue_iid`。
2. **貼的是子任務時，連主單一起讀**：主單寫範圍與預期結果，開發子單寫邏輯、流程與資料表結構，測試子單寫測試步驟；子單也可能還是空的。`get_issue` 讀不到跨專案的父子關係，要用工單小工具 `mcp__plugin_gitlab-mcp_gitlab-workitem__list_child_items`（`project_id="target/ticket_tasks"`, `iid=<id>`）查，回傳的 `parent`（例如 `target/tickets#4426`）就是主單，再用 `get_issue` 讀它。範圍與預期結果以主單為準，作法以開發子單為準。`parent` 是 `null` 就只讀子任務本身。查主單失敗時據實說讀不到主單，請使用者貼主單網址，不要只憑子任務的標題猜需求。
3. **不要自己直打 `api/v4` 網址**，也不要在 skill 或對話裡持有 token；GitLab 位址與憑證由 `gitlab-mcp` plugin 管理。
4. **只就工單沒講清楚的地方提問**。工單已經寫明的內容不要再問一次，那會讓使用者覺得你沒讀單。
5. 讀不到工單（權限不足、MCP 連不上、單號不存在）時據實說讀不到、說明原因，請使用者貼內容或改給單號，**不要猜工單內容**。

## 九、什麼時候算問完

**前緣清空才算完成**：決策樹的每條分支都走過，沒有任何事情是偷偷假設的。

完成之後不是直接動手，而是把共識整理成一段摘要交給使用者確認。**使用者確認共識以前不要動實作代碼**，也不要送出計劃。訪談期間寫下的詞彙表與 ADR 不受這一條限制，它們是訪談自己的產物（見「這支 skill 站在流程的哪一段」的那條例外）。確認之後才進計劃模式。
