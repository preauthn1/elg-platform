# bug-diagnosis：先確定怎麼重現，再有紀律地找原因

一句話版本：**開工先問使用者這次要不要走測試先行。測試先行就先做出一條會變紅的重現命令，才開始推原因；先找原因就只要說得出怎麼重現，修完再補回歸測試。兩種模式中段都一樣：縮小重現、列出可證偽的假設、一次只動一個變數去驗證，收尾時把 debug 痕跡清乾淨。**

| 名詞 | 意思 |
|---|---|
| 回饋迴圈 | 一條命令：bug 還在時它變紅，修好之後它變綠。測試先行模式靠它判斷每一步對錯；先找原因模式不強制做成命令，但重現方式要記下來 |
| 紅／綠 | 紅＝命令偵測到 bug（測試失敗、斷言不過）；綠＝命令判定 bug 不在了 |
| 緊（tight） | 迴圈夠好用的四個條件：幾秒跑完、每次跑結果一樣、只要一條命令、不用人在旁邊按 |
| 可證偽假設 | 講得出預測的假設：「如果是 X 造成的，改 Y 就會消失，改 Z 會更糟」。講不出預測的只是感覺 |
| 縫（seam） | 與 `dev-toolkit:tdd` 同義：從外面觀察行為的公開介面邊界，例如 service 的公開方法、HTTP 路由、command |
| 最小重現 | 還會變紅的最小情境：裡面剩下的每一樣東西，拿掉任何一樣就會變綠 |
| 測試先行模式／先找原因模式 | 開工時由使用者選的兩種排查方式。測試先行模式：先做出一條會變紅的重現命令才開始推原因，修之前先寫會失敗的回歸測試。先找原因模式：說得出怎麼重現就開始推原因，修完再補回歸測試 |

這是一套給難纏 bug 的紀律。六個階段依序走，**只有講得出理由時才跳過某個階段**。

## 開工前：對齊專案的領域語言

探索代碼時先讀 repo 的 `GLOSSARY.md`（詞彙表，如果有的話），讓你對相關模組的理解跟專案用語一致；同時看一下你要碰的那塊區域有沒有 ADR（架構決策紀錄，通常在 `docs/adr/`）。

## 與其他 skill 的分工

領域裡已經有專用排查 skill 的問題，走那支，不走本 skill。那些 skill 知道該查哪幾張表、哪幾個設定，比通用紀律快得多。

| 問題類型 | 走哪支 | 本 skill 管什麼 |
|---|---|---|
| 要查某站的 GCP log（Tid、trace_id、ErrorCode） | `apis-toolkit` 的 `gcp-log-troubleshoot` | log 查完仍找不到原因、需要建重現迴圈時才接手 |
| 前台或會員 App 看不到某家銀行 | `apis-toolkit` 的 `bank-why-missing` | 無 |
| 遊戲商注單對不上（三方、BR、TBR、SBR 對帳） | `apis-toolkit` 的 `reconcile-bet-records` | 無 |
| 大額通知沒發 | `apis-toolkit` 的 `large-amount-notify-debug` | 無 |
| 使用者直接要查某站的資料、統計數字或跑 SQL，即使目的是找原因 | `apis-toolkit` 的 `whitelabel-db-query` | 查完資料仍要建重現迴圈時才接手 |
| 以上都不是的 bug：API 壞了、偶發 500、修了又復發、變慢 | 本 skill | 先問要不要測試先行、建迴圈、縮小、列假設、驗證、修、收尾 |

修完之後交審查。裝了 `apis-toolkit` 的專案有審查官可以找，分工固定、同一件事只找一位；其他專案照該專案自己的審查流程：

| 要看的東西 | 找誰 |
|---|---|
| 金流正確性、併發、事務 | `apis-toolkit:timo` |
| 可讀性、可維護性、測試 | `apis-toolkit:rhyse` |

兩位都是唯讀審查、只診斷不改檔；他們的意見要不要落地，由使用者決定。

## 開工前先排除：修了卻沒生效

這一步在分清兩件事：程式碼對不對，以及線上跑的是不是這份程式碼。修正已經進了主幹、線上卻還是舊行為時，先不要回頭讀代碼找邏輯問題。

1. 找一個只有舊寫法才會產生的 log 事件（例如舊版會發告警、新版不會發的那一筆）。
2. 查這個事件在部署時間之後還有沒有出現。查 log 走 `apis-toolkit` 的 `gcp-log-troubleshoot`。
3. 還在出現，就證明線上跑的是舊版，原因在部署面：例如沒有部署，或 PHP 的 opcache（把編譯好的程式留在記憶體的快取）沒有重新載入。
4. 結論寫成「程式碼沒問題（附該修正的測試通過結果），線上跑的是舊版」，交回負責部署的人。部署細節自己沒查證的，標「未驗證」，不自己推測。

使用者說「已經部署成功了」也照這個方法驗，以 log 證據為準。

## 開工先問一題：這次要不要走測試先行

這一步在讓使用者決定這次排查的節奏。測試先行在難纏的 bug 上很值得；但在原因大致有譜的小 bug 上，先做命令的成本可能高過它省下的。兩種模式都是合法流程，由使用者依這次的情境選。

用 `AskUserQuestion` 工具問，佔一題。欄位照工具限制寫，寫錯就跑不動：

| 欄位 | 寫什麼 |
|---|---|
| `header` | 「排查方式」（工具限制最多 12 個字元） |
| `question` | 這次排查要不要走測試先行（先做出一條會變紅的重現命令，才開始推原因）？ |
| `options` | 下面兩個選項。推薦的那個排第一，`label` 結尾標「（推薦）」 |

兩個選項：

- **先找原因再補測試**：說得出怎麼重現就夠（一組輸入、手動步驟、log 證據都算），不強制做成命令；先推原因、修好，修完再補回歸測試。
- **測試先行**：先做出一條會變紅的重現命令，才開始推原因；修之前先寫會失敗的回歸測試。

哪一個標「（推薦）」由 AI 依這次的 bug 判斷，推薦理由寫在選項的說明文字裡。**使用者決定，AI 不代答。** 判斷方向：

- **推薦測試先行**：偶發、併發、時好時壞、修了又復發、要改的地方怕牽動別處。這類 bug 沒有穩定重現，推原因只是在猜。
- **推薦先找原因再補測試**：log 或錯誤訊息已經指出位置、原因大致有譜、小範圍修正。這類 bug 先做命令的成本，高過它省下的。

使用者已經在對話裡講明要哪一種，就不問，照他說的走。例如「先別寫測試，直接找」是先找原因模式；「照 TDD 來」（TDD 是 test-driven development，就是測試先行）是測試先行模式。

### 重現命令不是修法

「先做出會變紅的命令」常被讀成「先修好才算」，這是誤解。

重現命令只是餵一組固定輸入（真實請求、假資料、固定參數），讓**現在的**代碼跑出使用者說的那個症狀。bug 還在它就紅，跟有沒有修好無關。

「修好就變綠」只是說：同一條命令之後可以拿來驗證修好了沒。

## 先遮祕密

這一步在防外洩：本 skill 會要你把命令、輸出、抓下來的請求顯示出來，裡面常常夾著憑證與個資。

- **顯示之前先把每個祕密換成 `<REDACTED>`**：token、密碼、個資（姓名、手機、身分證號、銀行帳號）都算。
- **迴圈用環境變數帶憑證**：憑證留在環境裡，不出現在你顯示的命令或輸出裡。
- **抓下來的 HTTP 紀錄常帶認證 header**：只引出有訊號的那幾行，不整段貼。

遮完之後的內容不夠拿來診斷，就直接說出來，問使用者怎麼處理。

## 第一階段：有辦法重現

兩種模式的差別主要在這一階段與第五階段，中間三個階段一樣。

這一步在確保後面的推理有東西可以驗證：沒辦法重現，就分辨不了哪個假設對，也確認不了修好了沒。測試先行模式要求把重現做成一條會變紅的命令；先找原因模式只要求說得出怎麼重現。

### 重現的建法（兩種模式共用）

測試先行模式從這張清單挑一種做成命令。先找原因模式想把重現做得更穩、或之後補回歸測試時，也從這裡挑。大致照這個順序試：

1. **PHPUnit 測試**：寫在能走到 bug 的那個縫上，單元、整合、feature 任一層都可以。
2. **對 dev 容器的 curl 腳本**：直接打跑在 dev 環境的 API。
3. **`artisan` 命令或 `tinker`**：餵一組固定輸入，把輸出跟已知正確的結果比對。
4. **Playwright 驅動前後台**：用腳本操作畫面，對 DOM（頁面元素）、console、network 下斷言。`qa-toolkit` 的 `web-browser` 可以用。
5. **重放抓下來的真實請求**：把一筆真實的 HTTP 請求或金流回調 payload 存成檔案，單獨餵進那條程式路徑重放。
6. **拋棄式 harness**：只起系統的一小塊（一個 service、依賴全部換成 mock（替身：行為固定的假物件）），用一次函式呼叫就走到 bug 的程式路徑。
7. **隨機輸入迴圈**：bug 是「有時候輸出錯」的話，跑 1000 次隨機輸入，找出會壞的那種輸入。
8. **`git bisect run` 自動二分**：bug 出現在兩個已知狀態之間（兩個 commit、兩份資料、兩個版本），把「切到狀態 X、檢查、重複」寫成腳本交給 `git bisect run`。
9. **差異比對迴圈**：同一組輸入分別跑新舊版本（或兩組設定），比對輸出差在哪。
10. **人在旁邊按的腳本**：最後手段。一定要人去點畫面時，寫一支腳本一步一步印出「現在請按什麼」，再把結果抓回來餵給 agent，讓迴圈仍然有固定結構。

迴圈建對了，bug 就修好九成。

### 不固定發生的 bug：目標是抬高重現率（兩種模式共用）

偶發的 bug 不求一次就重現乾淨，求的是**重現率夠高**。把觸發動作迴圈跑 100 次、並行跑、加壓、縮小時間窗、刻意插 sleep。50% 會出現的 bug 查得下去，1% 的查不下去，所以一路抬高重現率，直到查得下去為止。

### 測試先行模式

**在這個模式裡，這一步就是排查的全部。** 其餘階段都是機械性的：只要你手上有一條夠緊、而且會因為「這個」bug 變紅的命令，二分、驗證假設、加觀測點都只是在消耗這條命令，原因一定找得到。沒有這條命令，盯著代碼看再久也沒用。

在這一步花不成比例的力氣：**積極、有創意、不輕易放棄。**

#### 迴圈要收緊

把迴圈當成產品來磨。有了第一版之後問三件事：

- **能不能更快？** 快取準備步驟、跳過無關的初始化、縮小測試範圍。
- **斷言能不能更準？** 斷言使用者描述的那個症狀，不是「沒有報錯」。
- **能不能更固定？** 釘住時間、固定亂數種子、隔離檔案系統、凍結網路。

一條 30 秒又時好時壞的迴圈，比沒有好不了多少；一條 2 秒、每次結果一樣的迴圈，才是排查的利器。

#### 真的建不出來時

停下來明講建不出來，列出你試過哪些建法。接著向使用者要三樣東西之一：

1. 能重現的那個環境的存取權限。
2. 遮過祕密的紀錄：HAR 檔（瀏覽器匯出的網路請求紀錄）、log 匯出、core dump（程式當掉時的記憶體快照）、附時間戳的錄影。
3. 暫時在正式環境加 log 的許可。

**沒有迴圈就不要進到列假設。**

#### 完成判準：一條夠緊、會變紅的命令

這個階段做完的意思是：你說得出**一條命令**（腳本路徑、測試命令、一行 curl），而且**已經實際跑過至少一次**（把命令和輸出遮完祕密後顯示出來），它同時符合下面四條：

- [ ] **會變紅**：它真的走到 bug 的程式路徑，斷言的是**使用者描述的那個症狀**，所以 bug 在時會紅、修好會綠。「跑完沒報錯」不算，它必須抓得到這一個 bug。
- [ ] **固定結果**：每次跑結論都一樣。偶發 bug 則要有固定、夠高的重現率（見「不固定發生的 bug：目標是抬高重現率」一節）。
- [ ] **幾秒跑完**：秒級，不是分鐘級。
- [ ] **agent 自己能跑**：不用人在旁邊；真的需要人時，只能透過上面第 10 種「人在旁邊按的腳本」。

**還沒有這條會變紅的命令之前，不准讀代碼推理論。發現自己在做，就停。** 直接跳到假設，正是本 skill 要防的那個失誤。沒有會變紅的命令，就沒有第二階段。

### 先找原因模式

這個模式不強制把重現做成命令，但一樣要有重現：沒有它，第四階段沒東西可驗證，第六階段也確認不了修好了沒。

#### 完成判準：說得出怎麼重現

下面三者有其一即可：

- 一組會出錯的輸入（參數、payload、資料狀態），餵進去就看得到使用者說的那個症狀。
- 一串手動步驟，照著做就會出錯。
- 一段 log 或錯誤訊息，能對到某一次具體的請求。

不強制做成命令，但要把它記下來（遮完祕密後顯示出來）。第五階段補回歸測試、第六階段驗證修好了沒，都會用到它。

偶發 bug 在這個模式下仍建議至少抬高重現率（見「不固定發生的 bug：目標是抬高重現率」一節），否則第四階段驗不了假設。

連怎麼重現都說不出來時，跟測試先行模式一樣停下來，照「真的建不出來時」一節向使用者要東西。

#### 可以直接讀代碼，但假設照樣要列

這個模式允許直接讀代碼推原因。但第三階段「先列 3 到 5 個可證偽假設再測」照樣要做，不能跳到第一個想到的原因就改。

讀代碼時看到可疑的地方（例如對稱的兩個方法少了一段、某個分支沒有 `return`），先標「疑似」，不直接說它是 bug。下結論之前，至少查過所有呼叫端，並確認上游有沒有已經擋掉這個情況。上游已經擋掉的，那段只是不會執行到的程式碼；補上去也無害的修改算整理（commit type 用 `chore`），不算修 bug（不用 `fix`）。

## 第二階段：重現並縮到最小

這一步在確認你抓到的是對的 bug，並把它縮成最小，讓後面要懷疑的東西變少。

兩種模式都走這一階段。先找原因模式沒有做成命令時，下文的「跑迴圈」就換成：照第一階段記下的重現方式再走一次。

跑迴圈，看它在 bug 出現時變紅。然後確認三件事：

- [ ] 迴圈抓到的是**使用者描述的那個失敗**，不是剛好在旁邊的另一個失敗。抓錯 bug 就會修錯東西。
- [ ] 失敗可以重複出現：跑很多次都紅，或者偶發 bug 的重現率高到查得下去。
- [ ] 已經把確切的症狀記下來（錯誤訊息、錯的輸出、慢的耗時），之後才能驗證修的是不是它。

### 縮到最小

變紅之後，把重現縮到**還會變紅的最小情境**。輸入、呼叫者、設定、資料、步驟，**一次只砍一樣**，每砍一樣就重跑一次迴圈，只留下撐著這個失敗的東西。

為什麼要縮：最小重現讓第三階段要懷疑的東西變少，也會直接變成第五階段那支乾淨的回歸測試。

做完的判準：**剩下的每一樣都是拿掉就變綠的。**

先找原因模式在這裡放寬：能縮就縮；縮不了，至少把觸發條件寫清楚（哪種輸入、哪個資料狀態、什麼時機會出錯）。

重現了、也縮到最小了（先找原因模式：或至少寫清楚觸發條件），才進下一階段。

## 第三階段：列假設

這一步在避免一頭栽進第一個想到的原因：只想一個假設，就會被它綁住。兩種模式都要做這一步，先找原因模式也不例外。

**測任何一個之前，先列出 3 到 5 個排序過的假設。** 每一個都要可證偽，也就是寫得出它的預測：

> 格式：「如果 X 是原因，那改 Y 會讓 bug 消失／改 Z 會讓它更糟。」

講不出預測的假設只是感覺：丟掉，或把它磨到講得出預測為止。

**測之前先把排好的清單給使用者看一眼。** 他們常有領域知識，一眼就能重排（「我們剛部署了第 3 個」），或知道哪幾個早就排除了。這個檢查點很便宜，省下的時間很多。使用者不在就照你自己的排序走，不要卡住等。

## 第四階段：驗證

這一步在用最少的動作分辨哪個假設是對的。兩種模式都適用。

每一個探針（你加的觀測點或做的實驗）都要對應第三階段的某一個預測。**一次只動一個變數。**

工具的優先順序：

1. **debugger 或 REPL**（互動式執行環境，輸入一行程式立刻看結果；Laravel 用 `tinker`），環境支援就先用。一個中斷點勝過十行 log。
2. **有針對性的 log**：只加在能分辨兩個假設的邊界上，不整批印出來再 grep。

**每一行 debug log 都加上統一前綴**，例如 `[DEBUG-a4f2]`。收尾時一個 grep 就能清光。沒加前綴的 log 會活下來，加了前綴的才清得掉。

**效能問題另走一條路。** 變慢的問題通常不該用 log 查，而是先量出基準（計時、profiler（量各段耗時的工具）、資料庫的 query plan（執行計畫）），再用二分找出哪一段變慢。先量，再修。

## 第五階段：修，並補回歸測試

這一步在把 bug 鎖住，讓它不會悄悄回來。兩種模式都要補回歸測試，差別在測試寫在修之前還是修之後。

### 正確的縫（兩種模式共用）

回歸測試只能寫在**正確的縫**上。正確的縫，是測試走得到 bug 真正發生時的那種呼叫方式。可用的縫太淺時，例如 bug 要多個呼叫者才會出現、測試卻只有單一呼叫者，或是單元測試重現不了觸發 bug 的那串呼叫，在那裡寫的回歸測試只會給你假信心。

**沒有正確的縫，這件事本身就是發現。** 記下來並回報：代碼的架構讓這個 bug 鎖不住，這要交給收尾階段與使用者知道。

### 測試先行模式：先寫測試再修

回歸測試要**在修之前寫**。有正確的縫時，照五步走：

1. 把最小重現變成一支在那個縫上會失敗的測試。
2. 看它失敗。**若是靠改代碼或 fixture（測試用的固定資料）強迫它變紅，要拿一份乾淨副本 `diff` 一次，證明你的改動真的落地了，才相信那個紅。**
3. 修。
4. 看它通過。
5. 用第一階段的迴圈，對原本（沒縮小的）情境再跑一次。

### 先找原因模式：先修再補測試

有正確的縫時，照五步走：

1. 修。
2. 修完在正確的縫上補一支回歸測試，用第一階段記下的重現方式（或第二階段縮小後的情境）當輸入。
3. 看它通過。
4. 把修法暫時還原一次，確認測試會紅。這一步在證明測試真的抓得到這個 bug，而不是怎樣都會過。確認紅了之後，再把修法放回去。
5. 用第一階段記下的重現方式，對原本（沒縮小的）情境再驗一次。

沒有正確的縫，在這個模式一樣是發現：記下來回報，做法同「正確的縫（兩種模式共用）」一節。

兩種模式都一樣：測試先行的紅綠紀律（什麼是好測試、三個反模式）細節在 `dev-toolkit:tdd`，需要時用 Skill 工具叫起 `dev-toolkit:tdd`。

## 第六階段：收尾

這一步在確保修好的東西乾淨地交出去。下面每一項都要勾完，才能說做完：

- [ ] 原本的重現不再發生（測試先行模式重跑第一階段的迴圈；先找原因模式照第一階段記下的重現方式再驗一次）。
- [ ] 回歸測試通過，或已經記錄「沒有正確的縫」。
- [ ] 用 `grep` 搜統一前綴，所有 `[DEBUG-...]` 觀測點都已清光。
- [ ] 拋棄式程式已刪掉，或搬到明確標示為 debug 用途的位置。
- [ ] commit message 寫出最後證實的那個假設，讓下一個來排查的人學得到。寫法照 `dev-toolkit:git-commit` 的「涉及取捨的變更：body 必須寫選了什麼、沒選什麼、為什麼」一節。

## 對話範例

> 使用者：會員改綁手機號碼的 API 一天會有兩三次 500，log 只看到 Call to a member function on null，重跑同一組參數又正常。
>
> AI：（先用 `AskUserQuestion` 問「排查方式」這一題）這次排查要不要走測試先行？兩個選項是「測試先行（推薦）」與「先找原因再補測試」。我推薦測試先行，理由是：這是偶發的 bug，重跑同一組參數又正常，沒有穩定的重現，直接推原因只是在猜。
>
> 使用者選**測試先行**時，AI 接著說：我先不猜原因，第一步是做出一條會穩定變紅的命令。我打算把那組參數寫成一支 feature test，打同一條改綁手機的路由，斷言「回應不是 500、而且沒有 `Call to a member function on null`」，再用迴圈連跑 50 次，看重現率有多高；重現率太低就改成並行打、加壓，或縮短兩次請求的間隔。這條命令會變紅之後，我才會列 3 到 5 個假設給你看，在那之前我不會去讀代碼推理論。
>
> 使用者選**先找原因再補測試**時，AI 接著說：我先把 log 裡那幾次 500 對到具體的請求，記下參數與時間點，當作這次的重現方式。接著讀改綁手機那條路徑的代碼，列 3 到 5 個假設給你看，每個都附「改哪裡會消失」的預測；修完再補回歸測試。
>
> 不論選哪一種，AI 都先確認一件事：方便給我一組 dev 環境可以用的測試會員嗎？憑證我會用環境變數帶，不會顯示在輸出裡。
