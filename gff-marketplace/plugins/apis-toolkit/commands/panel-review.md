審查目標：$ARGUMENTS

---

> **這是圓桌會審，審查官最多五位。** 你（主對話）負責決定目標、建議陣容並交給發起者選、並行派遣選定的 subagent、收斂報告。你自己**不審代碼**，只當主持人與彙整者。

> **選哪個 review 入口？**
> - 單一檔案 / 目錄、想順手 refactor → `/code-quality <路徑> [任務]`
> - 當前分支 / MR，要多角度（金流+遷移+安全+架構+文件一致性）會審 → 本命令 `/panel-review`
> - 只要單一角度點審 → 直接找對應 agent：timo（金流正確性+併發）/ marz（舊系統遷移+查詢效率）/ rorin（安全+應變）/ rhyse（SOLID+可讀性+測試+現代 PHP/套件）/ bonn（實作與設計文件對不對得上）
> - 雲端深審、計費 → `/code-review ultra`（使用者觸發，Claude 無法代跑）

> **觸發說法**：「圓桌會審／進行圓桌會審／開圓桌／召開圓桌會議／針對今天的異動進行圓桌會審／指派審查官會審／請審查官們看一下」，或打 `/panel-review`。

## Step 0：確定審查目標（派工前先算好，所有審查官共用同一目標）

- `$ARGUMENTS` 留空 → 當前分支 diff（先看未提交變更，無則相對 master）：
  ```bash
  git diff HEAD --stat        # git 在 host 跑（cwd 即當前 checkout／worktree；容器只掛主 checkout）
  # 若空，改 git diff master...HEAD --stat
  ```
- `$ARGUMENTS` 是檔案/目錄 → 該路徑
- `$ARGUMENTS` 是純數字 → 當作 GitLab MR 編號

先輸出一行「🎙 圓桌會審目標：<說明>（N 個檔案）」。若目標為空（master 乾淨、無 diff），直接告知並停手，不要空派。

**文件型變更分流**：若變更檔案**全部**是文件（`.md`／`.txt`／`docs/` 下），代碼審查四人會幾乎空手，**改為只派 Bonn 主審**，Timo／Marz／Rorin／Rhyse 不派（使用者明確要求才派）。開場改寫成「🎙 本次為文件型變更，由 Bonn 主審」。這種情況只派一位，**不必問發起者、直接派**。**混合變更（代碼 + 文件）照下一步建議陣容。**

## Step 1：建議陣容，由發起者選定

這步在決定這次要派哪幾位。五位審查官的守備範圍不同，改動沒碰到的範圍派了多半空手回來，所以先看這次改了什麼，再建議陣容，由發起者選。（Step 0 判定為文件型變更時跳過本步。）

**判斷規則**（只看 Step 0 的檔案清單與 diff 內容，不另外開工具深挖）：

| 審查官 | 什麼時候派 |
|---|---|
| Timo（金流正確性 + 併發） | 有代碼變更就派 |
| Rorin（安全 + 應變） | 有代碼變更就派 |
| Rhyse（可讀性 + 測試 + 現代 PHP） | 有代碼變更就派 |
| Marz（舊系統遷移 + 查詢效率） | diff 動到資料庫查詢（Eloquent 查詢、`DB::`、raw SQL）、migration 或索引；或這段邏輯是從舊專案（API_Agent / API_Frontend / API_External）搬來的；或發起者提到要對照舊系統 |
| Bonn（實作與設計文件一致性） | 找得到這條分支對應的設計或計劃文件；或 diff 同時改了規則文件（CLAUDE.md / AGENTS.md / skill）或 `docs/`；或發起者提到要核對文件 |

判斷不出某位該不該派時，列進建議陣容，並在理由寫明「不確定」。

**用 AskUserQuestion 問一次，固定三個選項**：

1. **建議陣容（放第一個，標「推薦」）**：逐位寫一句為什麼派；被省掉的也各寫一句為什麼省。
2. **全部五位**。
3. **精簡**：Timo、Rorin、Rhyse 三位裡跟這次改動最相關的兩位，並寫明是哪兩位。

建議陣容剛好就是全部五位時，第一個選項寫「全部五位（推薦）」，不重複列第二個選項。發起者在訊息裡已經點名陣容（例如「派 Timo 跟 Rorin 會審」）時照他說的派，不再問。

## Step 2：並行派遣選定的審查官

（Step 0 判定為文件型變更時只派 `apis-toolkit:bonn`。）在同一則訊息裡用 **Agent 工具一次發出 Step 1 選定的每一位**（`subagent_type` 為 `apis-toolkit:timo`、`apis-toolkit:marz`、`apis-toolkit:rorin`、`apis-toolkit:rhyse`、`apis-toolkit:bonn` 中被選到的），每位拿**同一份目標**，各自跑完整流程回報。Bonn 會在自己的流程裡額外探測對應的設計／計劃文件，你不必替他找。

> ⚠️ **載入前提**：五位都是 apis-toolkit plugin 提供的檔案型 subagent，需在 session 啟動時被掃到才能派。若 Agent 工具回報找不到該 agent type，先確認 `subagent_type` 有帶 `apis-toolkit:` 前綴；仍找不到再提示使用者重開 session 或 `/agents` 重載後再跑。
>
> 💰 **額度護欄（對齊全域 subagent 規則：< 20% 須先人工審核，非強制禁止）**：派工前先評估可用額度。**若 < 20%，不要自動派遣**。即使降為 sequential、依序一位一位跑，仍是 spawn 多個 subagent，須先經使用者審核。此時在 Step 1 的提問裡**一併告知使用者目前額度狀況與選定陣容的預估開銷，停手等使用者明確指示**；使用者同意續跑時，再以 sequential（依序，不並行）執行。

派工 prompt 各自帶上：目標說明、「按你自己的 instruction 跑完整流程並輸出含裁決的報告」，以及**本次在場名單**：「本次在場：<名單>。不在場的審查官，他守備範圍內你看到的明顯問題列進你的「範圍外觀察」（Bonn 列在「順帶一提」），不要只寫『留給某某』。」**MR 編號情境**：主持人先用 gitlab MCP（`get_merge_request_diffs`）取好 diff，把 diff 內容一併帶進派工 prompt，因為審查官的 tools 白名單叫不到 MCP 工具。

## Step 3：依嚴重度合併各份報告

收齊在場審查官的報告後，**你**做收斂，不要原封轉貼：

1. **去重**：同一 `檔案:行號` 同一問題被多人提 → 合成一條，標出所有來源（如 `[Timo+Rhyse]`）。
   - 兩位以上獨立提出的同一條，標為高信心。
   - 只有一位提出的發現，以及審查官給的數量（筆數、檔案數），由你用唯讀命令自己查證或重數；查不到的在該條標「未驗證」，照樣列出。數字對不上時寫你重數的結果與掃描範圍。查證只確認既有發現，不算新增 finding。
   - 每條標「現在會發生」或「理論風險」；合議結論建議本次修正的只放前者，理論風險建議另外記。
2. **依 P0/P1/P2 合併**，每條標來源 `[Timo]` / `[Marz]` / `[Rorin]` / `[Rhyse]` / `[Bonn]` / 組合。
3. **衝突處理**（下列規則指定的定調者本次未派時，該爭議直接列入 `⚖️ 分歧` 並陳，並建議發起者補派那一位，不由其他人代為定調）：
   - **查詢寫法之爭（raw SQL vs active record）** → 由 **Marz** 定調（他是 panel 的 SQL 主責）。**前提**：只有複雜度高且跨多表的查詢才可主張 raw，而且要附行內註解說明為何不用 Model；單表查詢即使較快也維持 Eloquent。符合前提後，判準是**效能提升是否顯著**：附得出 query 數／耗時數量級改善才採 raw SQL，提升不顯著或拿不出數字就維持 active record（好維護優先）。**綁定參數與業務邏輯下沉 Service 仍是紅線**，效能再顯著也不讓；有爭議列 `⚖️ 分歧` 並陳。
   - **Rorin 的「可利用」安全問題** → **優先級最高**，合議結論先點安全止血；「臨時止血 vs 根治」原樣保留。
   - **Rhyse 的架構級大改提案** → **不混進 Critical/Warning**，獨立放 `🏗 架構提案` 區塊；若與 Rorin 的 production 顧慮對立，**並陳 bold vs safe**，交人類選，不自動裁定。
   - **API 設計分歧**（Timo+Rhyse 主張拆成 focused API vs Marz 主張新舊結構一致、護前端）→ 由 **Rorin**（守 API 契約/breaking changes）以實際 breaking 風險定調，列入 `⚖️ 分歧` 並陳，不自動判誰對。
   - **Bonn 的 A 類「與已拍板決議／設計文件衝突」** → 不是代碼 bug，但**方向做錯的代價高於 bug**：列進 Critical 區並註明「需回頭找拍板者確認」，不與技術型 Critical 混為一談。Bonn 回報「本次無對應設計文件可對照」時**如實寫出來**，不可當成「一致性沒問題」。
   - **規則文件與代碼同 diff 變動**：Timo 的內建規則表是條文快照——以 diff 後的新條文為準；Bonn 標「規則已變更」時，Timo 對同段代碼的違規判定加註「依舊條文」，新舊哪版算數交人類確認。
   - **Rhyse 的套件導入／版本升級建議** → 一律進 `📦 套件 / 版本建議` 區塊，**不擋本次 diff**；需核准才能動依賴（專案慣例）。
4. **保留每位在場審查官的裁決**：各自一句裁決原樣保留，最後你下一句合議結論。本次未派的審查官在裁決區寫「本次未派」，不替他補意見。
5. **表決 / tie-break**：在場審查官**平權各 1 票**，表決**只用於判斷/取捨類爭議**（要不要上、bold vs safe、主觀 trade-off），以**在場票數的多數決**定案。**Bonn 探測不到對照文件時棄權**。票數**平手**（例如 2 vs 2）時**不自動裁定**：把兩種立場並陳，交由**會議發起者（使用者）投下決定票**。**事實型 finding（標「需確認」的疑點不算，照原樣帶過、不投票）不靠投票推翻**：真 bug 就是真 bug，再多票也投不掉。
6. **範圍外觀察**：各審查官報告最後的「範圍外觀察」（Bonn 為「順帶一提」）由你去重後，列在報告最後一節「範圍外觀察」，不分級、不參與表決。某位在場審查官的守備範圍內若已有同一問題的分級 finding，併進那條，不重列。

### 輸出格式

```
🎙 圓桌會審目標：<說明>（N 個檔案）

🔴 Critical
- 檔案:行號 — 問題  [來源]
🟡 Warning
- 檔案:行號 — 問題  [來源]
🟢 Suggestion
- 檔案:行號 — 說明  [來源]

🛡 安全 / 應變（Rorin）
- 檔案:行號 — 攻擊路徑摘要（非攻擊面 finding 寫 N/A） ｜ ⏱ 止血：<臨時／回滾方案> ｜ 🔧 根治：<root-fix>

🏗 架構提案（Rhyse，較大工程，非本次必改）
- <提案> — 效益：<長遠 craft> ｜ 代價/風險：<遷移成本、Rorin 的 production 顧慮>

📦 套件 / 版本建議（Rhyse，需核准才能動依賴，非本次必改）
- <自幹的邏輯> — 可用 <套件>：<解決什麼> ｜ 現況：<已裝 / 需新增> ｜ 風險：<...>
- <做法受限於 PHP / Laravel 版本> — 升級解鎖：<...> ｜ 成本/風險：<...>

📖 一致性（Bonn）
- 對照文件：<清單，或「本次無對應設計文件可對照」> ｜ 權威順序：<...>
- <代碼:行號> ↔ <文件:行號> — <對不上的點，或「核對過一致」>

⚖️ 分歧（規範優先，列雙方論點供你裁決）
- <議題> — 規範側：<結論>；另一方：<論點，留作 P2>

🪑 審查官裁決（本次未派的寫「本次未派」）
- Timo：擋下 / 有條件 / 勉強過 —— 一句
- Marz：能不能上看那條規則 —— 一句
- Rorin：可利用 / 理論風險 / 無 + 多快內止血 —— 一句
- Rhyse：可維護 / 有技術債但可上 / 結構需重整 —— 一句
- Bonn：相符 / 有偏離但不影響 / 與決議衝突需回頭確認 / 無對照對象（棄權）—— 一句

合議結論：<綜合在場審查官的一句話：能不能上、最該先處理哪條（安全可利用項優先；方向與決議衝突需先確認）>

範圍外觀察（去重後；不分級、不參與表決；沒有就寫「無」）
- 檔案:行號：一句問題（該找誰：<審查官>）  [來源]
```

去重與分級要忠實，**不可為了好看刪掉任一人有憑據的 finding**；在場的人都說乾淨時，照實說「在場 N 位都沒挑出 Critical/Warning」，並列出本次未派的是誰。

## 約束

- 你是主持與彙整，**不新增自己的 finding**，也不替任何一位 subagent 補論述，包括本次未派的。
- 審查官的守備**不等於 CLAUDE.md 全覆蓋**：實作前復用檢查、測試庫紀律等其餘條文屬主對話與 CI 把關，panel 不重複、也不假裝有守。
- 全程唯讀，不改任何檔案；是否修正交由使用者下一步決定。
