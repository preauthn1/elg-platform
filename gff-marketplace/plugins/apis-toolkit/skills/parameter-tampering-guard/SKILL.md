# 防止參數竄改

一句話版本：**允許的值 ＝ 畫面能選的範圍 ∪ 這筆資料目前已經存著的值。只對「這次新增的值」驗範圍；原本就存著的值原樣放行、保留不動。**

例：畫面只能選 1、3，資料原本存著 5。
- 送來 `[1, 5]`：1 在範圍內、5 是原本就有的，**放行**。
- 送來 `[1, 6]`：6 不在範圍內、原本也沒有，**擋下**。

## 名詞速查

| 名詞 | 意思 |
|---|---|
| 參數竄改 | 攻擊者不經過畫面，直接改請求裡的參數值（id、狀態、類型）送給接口 |
| 選擇範圍 | 畫面允許使用者選的值。下拉、清單、勾選、隱藏按鈕、唯讀欄位都在劃定選擇範圍 |
| 提供選項的方法 | 算出選擇範圍的方法，例如 `dropdown`、`options`、`getUsable…` |
| 寫入端 | 會把使用者送來的值存進資料庫的接口：新增、編輯、存檔、批次、同步、匯入 |
| 新增的值 | 送來的值減掉這筆資料目前已存的值。新建資料時，全部都是新增的值 |
| 9003 | 平台的「無權限」錯誤碼，`error_message.9003` |

## 為什麼

畫面上的限制不是防護。攻擊者會直接改請求參數：例如下拉只列出操作者管得到的 2 個代理，攻擊者把 `agent_id` 改成任何代理的 id；寫入端如果只檢查「存在」，任何代理都能被操作。

實例（target/tickets#4542）：API_Agent 的角色下拉用「可用角色」規則過濾，但寫入角色的 `agent/edit` 只擋 admin 角色。有人直接帶角色 id 呼叫 `agent/edit`，把權限比自己大的角色套到自己身上。那條規則寫好時只接到下拉，沒接到寫入端；`agent/edit` 又允許對象是自己，所以變成自己幫自己升權限。

## 為什麼一定要放行既有的值

「不在選項裡就擋」會讓正常操作壞掉。畫面編輯時，前端常會把資料原本的值原樣送回，而這些值可能已經不在選項裡：

| 情況 | 例子 |
|---|---|
| 已綁定的值後來停用了 | 方案綁的設定被停用、活動目標的群組被停用、會員所屬的群組被停用 |
| 整批送回時夾帶操作者看不到的既有值 | 個人權限裡有 admin 給的權限、角色裡有操作者後來失去的選單、群組綁著操作者看不到的銀行帳號 |
| 前端把不可選的既有值補回選項顯示 | 已綁定但目前不可用的角色、停用的方案設定 |

這些都是正常資料，擋下來就會「改個名稱也存不了」。所以只對新增的值驗，既有的值一律放行、保留不動，也不可以因為看不到就刪掉。

## 寫的當下必做

1. **找出這次劃定的選擇範圍**。需求或改動出現「只列出」「只能選」「限制誰能」「可用」「自己線的」「下線的」，就是一條選擇範圍規則。
2. **分清楚範圍裡哪些是權限、哪些只是顯示**。只驗權限那部分：
   - 要驗：屬於哪條線、在不在操作者下線、權限是不是操作者的子集、有沒有對應權限碼。
   - 不能拿來驗：關鍵字、筆數上限、排序、篩選條件（例如先選遊戲商才列遊戲）。這些只是讓清單好選，拿來驗會擋掉幾乎所有存檔。
   - 「只列啟用中」：只擋新選，已綁定的停用值照樣放行。
   - 業務條件：金額上下限、支援的銀行、名額。提供選項的方法常把權限條件和業務條件混在一起算（例如代付渠道清單同時看代理群組和金額上限），這時不能直接拿它的結果當可用範圍，要拆開：權限部分不符回 9003，業務部分沿用原本看得懂的錯誤訊息。
3. **找出所有寫入同一個欄位的接口**，不只這次改的那一支。用欄位名全專案搜尋：`'<欄位>' =>`、`$data['<欄位>']`、`->update(`、`->create(`、`->insert(`、`->sync(`。新增、編輯、批次、同步、匯入、從「設定」頁編輯自己，全部都算。
4. **每個寫入端，對新增的值用跟選項同一套權限規則驗**，範圍外回 9003：

   ```php
   DB::transaction(function () use ($operator, $recordId, $submittedIds) {
       // 先鎖住要寫的那一筆，而且這一筆本身要先通過範圍檢查（不能讓人指向別人的資料，把值偽裝成「既有」）
       $record = Record::query()->whereKey($recordId)->lockForUpdate()->firstOrFail();
       $this->assertRecordInScope($operator, $record);

       // 新增的值 = 送來的值 − 這筆資料目前已存的值；在整批刪除之前讀
       $current = $record->groups()->pluck('id')->all();
       $added = array_diff($submittedIds, $current);

       $usable = $this->scope->usablePermissionGroupIds($operator);   // 跟下拉同一套權限規則
       if (array_diff($added, $usable) !== []) {
           throw new ApiException(__('error_message.9003'));
       }
       // ……寫入
   });
   ```

   - **單一值欄位**：值跟目前已存的相同就不驗，有變動才驗。現成寫法：API_Agent `agent/edit` 的角色只在有變動時用 `getUsablePermissionGroupIds` 驗。
   - **「目前已存的值」要算完整**：一筆資料有多個欄位或多個子列存同一類值（例如方案主表加上每一列特殊用戶），要把它們全部取聯集，而且要在鎖住這筆之後、整批刪除之前讀。
   - **定義範圍的欄位有變動時**（例如換了這筆資料所屬的代理、換了目標類型），範圍已經不同，全部的值都當成新增的值重驗。
   - **範圍很大時不要先算出完整清單**（例如下線會員有數萬筆），改成反查：用 `whereIn(新增的值)` 加上範圍條件計數，數量對不上就擋。
   - **錯誤碼**：值不在操作者範圍或不屬於他，回 9003。值本身在範圍內、只是剛好停用了，回看得懂的訊息（例如「已停用」）。功能原本已有專用錯誤碼的，可以沿用。
   - **新建資料或「複製」成新資料**時沒有既有的值，送來的全部算新增。

5. **整批覆寫時，範圍外的既有值要保留**：刪除只刪操作者範圍內、而且這次沒送的值，不要把操作者看不到的既有值一起刪掉。
6. **對象是操作者自己時**，確認能不能藉此提升自己的權限（改自己的角色、權限、狀態、白名單）。能的話要擋，或另外限制。
7. **同一個 commit 附兩種測試**：
   - 擋得住：送「範圍外、原本也沒有」的值，預期被拒，而且資料沒被寫進去；對象可以是自己的，再用自己打一次。
   - 不誤擋：把「原本就存著、但現在不在範圍內」的值原樣送回（例如已停用的、操作者看不到的），預期存檔成功，而且這些值還在。

## 不套用這條規則的情況

| 情況 | 原因 |
|---|---|
| 系統自動寫入：預設值、同步、排程、seeder、補丁指令 | 沒有使用者選擇，沒有可竄改的參數 |
| 接口不收這個參數，值由伺服器自己算出 | 請求裡沒有東西可改 |
| 選項只用來顯示或篩選，寫入端不讓使用者選（例如固定記成建立者本人） | 寫入端用固定值驗才正確，套用反而會放寬 |
| 業務狀態的檢查：渠道維護中、金額超限、名額已滿 | 這不是竄改，保留原本看得懂的錯誤訊息，不要改成 9003 |
| 時效條件：在線、未過期 | 列表載入到送出之間會自然變化，不是權限範圍 |

## 動手前先確認兩件事

- **前端實際送了什麼**：讀前端存檔的程式，確認是不是把原值或整包原樣送回、有沒有送錯欄位。前端送錯欄位時，先修前端，不要用後端驗證去擋。
- **拿哪一支方法當規則**：選項和寫入端條件不一樣時，用比較嚴的那一支。選項比寫入端寬（例如少了路徑的斜線邊界），要修的是選項，不是讓寫入端跟著放寬。選項和寫入在不同專案（例如選項在 apis、寫入在 API_Agent）時，兩邊寫等價的方法，並在兩邊的註解互相標註。

## 回報

做完在回覆裡列這張表：

| 選擇範圍規則 | 提供選項的地方 | 寫入端（逐一列出） | 新增的值有沒有驗 | 既有的值有沒有放行並保留 | 測試（擋得住／不誤擋） |
|---|---|---|---|---|---|
| 例：可套用的角色 | `dropdown` → `getUsablePermissionGroupIds` | `agent/add`、`agent/edit`（含改自己） | 有 | 有（角色沒變動不驗） | 有／有 |

任何一格是「沒有」，就是還沒做完。

## 對話範例

> 使用者：「新增一支接口，可以編輯代理的角色，下拉只能選自己線的角色。」
> AI：載入本 skill。先找出「自己線的角色」由哪個方法算出來，再搜尋所有寫入 `agent_permission_group_id` 的接口（新增代理、編輯代理、從設定頁編輯自己、權限同步）。每個使用者寫入端都改成：角色跟目前相同就不驗，有變動才用同一個方法驗，範圍外回 9003；權限同步由伺服器算出角色，不套用。確認編輯自己時不能換成超出自己權限的角色。補兩種測試：送別條線的角色會被拒；角色已停用、原樣送回時存檔成功。最後列出回報表。
