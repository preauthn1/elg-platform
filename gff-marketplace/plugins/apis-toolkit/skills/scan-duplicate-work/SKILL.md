# 重工掃描（新邊界 × 既有實作）

## 這支 skill 只做三件事

實測顯示：模型本來就會查重複實作，**不需要人教查法**。所以本 skill 不教怎麼查，只管三件你不做就不會發生的事：

1. **什麼時候該查**——觸發條件（下節）
2. **什麼時候不該查**——零輸出紀律，這是它能長期活著的前提
3. **已知案例不重查**：`reference/baseline-cases.md`

比對本身自己判斷怎麼做最有效；只有下面「查法踩雷」那節列的坑是實測過會漏的，那些要避開。

## 使用者點名叫用

- **說法**：「跑重工掃描」「查有沒有重造輪子」「這張表是不是已經有人做過」「新增的東西跟既有有沒有撞」。點名時仍先跑下節的偵測命令，沒有新增四類邊界就照零輸出紀律結束，不要為了「順便看看」而啟動。
- **🚫 不歸本 skill**：「誰呼叫這個方法／改這裡影響多大」走 `codegraph_explore`。

## 觸發條件（唯一，不符即結束）

```bash
APIS=$(git worktree list --porcelain | awk '/^worktree /{print $2; exit}')   # APIs 主 checkout，在 APIs 任一工作區內執行
BASE=origin/master   # 比對基準；歷史重演時換成該 commit 的 ^1
HEAD=HEAD

# 新表與新 Enum：命中即算
git -C "$APIS" diff --diff-filter=ACR --name-only "$BASE...$HEAD" \
  | grep -E 'database/migrations/.*create_.*_table.*\.php|^app/Enums/.*\.php'

# 新金流商／新遊戲商：只算「基準上不存在的目錄」
git -C "$APIS" diff --diff-filter=ACR --name-only "$BASE...$HEAD" \
  | sed -nE 's#^(app/Services/Payment/Providers|app/Vendors)/([^/]+)/.*#\1/\2#p' | sort -u \
  | while read -r d; do
      [ -z "$(git -C "$APIS" ls-tree -d "$BASE" -- "$d")" ] && echo "$d"
    done
```

🔴 **provider／vendor 必須判「目錄是否為新」，不能只看路徑前綴。** 實測 `80e10b859` 有 135 個檔落在 `app/Vendors/`，但全是既有廠商加檔——用 `^app/Vendors/` 當條件會整批誤判。

🔴 **`--diff-filter` 要含 `R`。** 只寫 `A` 的話，`git mv` 進新目錄會被記成 rename 而漏掉。

實測近 30 天 275 支 merge 只有 59 支（21%）含新邊界 ⇒ **79% 的分支在這一步就結束**。任何放寬觸發條件的修改都會破壞它。

**掛載點**：`release-workflow` §3.0.6（首次 push 前）。此時分支仍純本地，掃出重複還能直接改。

## 流程

1. **偵測**：跑上面的命令。
2. **砍假陽性**：
   - 同一批 migration 裡跟著主表一起建的子表（不論後綴叫什麼），**併入主表算一項**——實測一次 8 張 `event_progressive_jackpot_*` 表其實是一個功能。
   - Enum 的 case 只是該功能自己的流程狀態（待處理／成功／失敗這類），**排除**；case 在描述「對象是哪一類東西」「作用範圍到哪一層」的，**保留**——後者才是會跟別人撞的那種。
3. **比對**：對留下來的每一項，查「這件事是不是已經有人做過」。查法自己決定，避開下節的坑。
4. **對照基線**：讀 `reference/baseline-cases.md`。🔴 **先自己查完第 3 步再讀它**——那份檔案含已知案例的結論，先讀會讓你照抄而非獨立驗證。
5. **輸出**：見下節。
6. **裁決回寫**：使用者裁決後（處理／不處理／已收斂），把結論追加進 `reference/baseline-cases.md` 的裁決表，否則下次會再報一次。⚠️ 該檔在 GFF-Marketplace repo（另一個 repo，路徑依本機 clone 位置而定，不是 plugin 快取），回寫要照該 repo 的分支紀律開工作分支，不可直接改 `main`。

## 查法踩雷（實測會漏的三個坑）

| 坑 | 實測結果 |
|---|---|
| **用問題語言問 `codegraph_explore`** | 中文問句零命中；英文描述句（刻意不含答案名字）漏掉正典 `CredentialGuardTrait`、12 家只撈到 2 家、還塞 5 個無關檔的源碼。**「不知道該用什麼詞」正是重造輪子的成因本身**。codegraph 在這裡只當 blast radius 用 |
| **拿新表的欄位名去搜既有表** | 同一個模型可以用 morph 實作。案例 5 兩張表撞的是「限制對象＝會員 or 群組」，但其中一張用 `target_type`/`target_id`，**欄位名一個字都不會撞** |
| **只搜繁體中文註解** | `git grep -l '會員群組' -- app/Enums` 零命中——那支 Enum 的註解寫的是**簡體「会员群组」**。repo 內簡繁混用，搜註解時兩種都要搜 |

## 輸出

**命中**：一項一段，`file:line` 要寫全（既有實作常橫跨 migration ＋ Enum ＋ service 多個檔，不必硬塞成一行）。附既有實作的作者與日期，那決定了是跨人還是同人。

**零命中**，依進入路徑分兩種：

| 進入路徑 | 輸出 |
|---|---|
| 自動掛載（`release-workflow` §3.0.6） | **不輸出任何文字**，直接進下一步 |
| 使用者主動要求掃描 | 回一行：掃了幾項新邊界、無命中，**並附一句這不等於沒有重複**（理由見下節） |

🔴 **不要寫成「已完成復用檢查」。** 本 skill 的零命中只代表「新增的邊界沒撞到既有」，不涵蓋在既有檔案裡改出來的重複。把它講成復用檢查完成，就是這支 skill 自己紅旗表在防的假證據。

## 已知限制（誠實寫明，不要誇大守備範圍）

🔴 **抓不到的形狀只有一種：在既有檔案裡加一個 private method。** 凡是新表／新 Enum／新 provider 目錄／新 vendor 目錄，形狀上一律看得出來。基線案例 1 的 ②④、案例 8 的 ③④ 都屬這一類。

🔴 **抓不到「第 1 次」，只抓得到「第 N 次」（N≥2）。** 案例 4 是硬證據：12 家金流商各自寫空憑證防護落在 2026-01～03（6 個不同的人），共用的 `CredentialGuardTrait` 2026-08-27 才出生，比最後一家晚 5 個月。那 12 支 MR 當下沒有任何既有實作可比對——因為能力本身還不存在。**技術債發散最貴的第一階段，本 skill 天生看不見。**

⚠️ 基線調查是三路交叉抽樣**非全庫窮舉**，且「A 不知道 B 寫過」全從時間軸與程式碼形狀推出、**沒有 MR 討論串佐證**。

## 紅旗——出現這些就是掃錯了

| 徵兆 | 真相 |
|---|---|
| 零命中就下結論「沒有重複」 | 零命中只代表「新邊界沒撞到」。既有檔案裡的重複不在守備範圍 |
| 為了「順便看看」在沒有新邊界的分支上啟動 | 破壞 79% 零輸出的前提，等於自己把自己弄死 |
| 把疑似的全列出來 | 假陽性洗版 → 沒人看 → 兩週內退化成儀式 |
| 只因為「結構長得像」就判重複 | 語意不同卻硬合成一張表，會退化成一堆 nullable 欄位。判準是「同一件事有兩套實作」，不是「欄位排列相似」 |
| 報告寫「已完成復用檢查」但沒有具體比對過的 `file:line` | 那是假證據。沒查到就寫沒查到 |
