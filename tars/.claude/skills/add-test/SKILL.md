# 新增回歸測試 SOP

依序執行,不可跳步。全程遵守專案 CLAUDE.md 的慣例(測試樹結構、Page Object、不寫死秘密)。

## 三階段工作流程(總則,不可跳過)

| 階段 | 做什麼 | 誰決定 |
| --- | --- | --- |
| **討論期** | 確認需求範圍,由 AI 擬定測試案例清單 | **使用者拍板** |
| **實作期** | 實走流程 → 撰寫 Playwright 測試 → 跑到綠 | AI 執行 |
| **確認期** | 交付執行結果與報告,使用者確認有無疑慮 | **使用者確認才算完成** |

🚧 **討論期 → 實作期之間是硬性關卡**:必須先明確取得使用者對測試案例的同意,才可以開始動手寫。
使用者沒有明確表示「可以 / 開始 / 照這樣做」之前,**不准進入實作期,也不准先產出任何檔案**。

下面 §1～§7 是各階段的細部步驟,標題已標示所屬階段。

## 1. 確認分類與範圍【討論期】

跟使用者確認這支測試:
- **測什麼行為、怎樣算通過**(斷言要驗到的業務結果),整理成測試案例名:「驗證…」句式,前綴 `[前台]`/`[後台]`/`[前後台]`
- **會不會在 dev 產生新資料**(帳號、訂單、申請單)?會 → `tests/dangerous/`;不會但要登入 → `tests/logged/`;免登入 → `tests/guest/`(完整規則見 CLAUDE.md「測試分類」)
- 檔名 `<模組>_<子模組>.spec.ts`(如 `member_login.spec.ts`);同模組已有檔案就加進該檔,不另開
- 若是 dangerous 類,提醒:每次執行都會在 dev 留下資料,確認可接受再繼續
- 對照 CLAUDE.md「目前的測試案例」清單:**已有涵蓋相同行為的測試就停下告知使用者**,改為擴充既有測試或確認真的要另立一支

## 1.5 擬定測試案例並取得同意【討論期・硬性關卡】🚧

**這是整份 SOP 唯一的強制停等點。沒過這關,不准往 §2 走。**

把 §1 談出來的東西整理成一份「測試案例草案」給使用者過目,至少包含:

- **測試案例名**:`[前台]`/`[後台]`/`[前後台]` + 「驗證…」句式,一行一條
- **分類與檔案**:放 `guest` / `logged` / `dangerous` 哪一類、寫進哪個 `<模組>_<子模組>.spec.ts`
- **每條案例的原子操作**:預計拆成哪幾步(對應 `test()` 層)
- **斷言驗什麼**:講清楚「怎樣算通過」的業務結果,不是「頁面有載入」
- **風險告知**:dangerous 類要明說「每次執行都會在 dev 留下真實資料」;會扣點的要明說會扣點

用 `AskUserQuestion` 讓使用者選:**照這樣做 / 要修改(請說哪裡) / 取消**。

- 選「要修改」→ 改完**重新出草案再問一次**,直到使用者點頭
- 選「取消」→ 直接結束,不留任何檔案
- **使用者沒有明確回答之前,不准自行認定通過**;沉默、已讀、講別的事都不算同意

## 2. 用瀏覽器實走一遍【實作期】

- 從 `.env` 讀站台網址與帳密(**不把密碼印進對話**)
- 用 Playwright MCP 把流程完整走一遍:`browser_navigate` → `browser_snapshot` 找元素 → 操作
- 邊走邊記:每一步用什麼 selector(優先 `getByRole`/`getByLabel`/`getByText`)、哪裡要等待、成功畫面長怎樣
- 走不通就停下回報,不要憑想像寫測試

## 3. 產出測試檔【實作期】

- `import { test, expect } from '../../fixtures/sites'`;前台操作用 `frontendPage`、後台操作用 `backendPage`、需要當場註冊用 `member`
- 結構:`test.describe.serial('[站台] 驗證…')` = 測試案例,內層每個 `test('[站台] …')` = 原子操作;操作內用 `test.step('中文說明', …)` 包關鍵動作、斷言帶中文說明
- 案例之間完全獨立(各自準備自己的狀態);需要延續瀏覽器 session 的登入類案例,參考 `tests/logged/agent_login.spec.ts` 的 beforeAll 共用 page 模式
- 可重用的頁面互動抽到 `pages/<site>/<Name>Page.ts`(先看有沒有現成的 Page Object 可用)
- 斷言驗業務結果,不只驗頁面載入

## 3.5 斷言設計的地雷【實作期】(涉及金額/結算的測試必看)

- **不要用「值一定會變」當斷言**。金額類的結算,結果可能剛好回到原值——例如老虎機押 3.75 中 3.75,輸贏 0,餘額前後一模一樣;寫成「餘額應該變少/應該有變動」會在這種局誤報失敗。
- **改用另一個系統的紀錄互相核對**:拿「前台餘額變動額」去對「後台注單記的輸贏」(差額 0 也成立),或拿「後台報表的當下點數」去對「前台看到的餘額」。跨系統對得上,才是真的有記帳。
- **等待要等「事件」不要等「畫面變化」**:讀不到結果的頁面(canvas、第三方 iframe)就攔關鍵請求當憑據,例如老虎機下注是一支帶 `doSpin` 的 POST,等到它回應才算這一注真的送出;等不到就明確報「動作沒送出」,不要用固定 sleep 賭它成功。
- **沒有元素可定位時才用比例座標**(canvas 遊戲畫面),而且要在 Page Object 註明校準條件(視窗大小、哪一款遊戲),並固定測試視窗大小,例如 `browser.newPage({ viewport: { width: 1280, height: 720 } })`。
- **先確認報表是「逐筆」還是「彙總」**再決定斷言對象:同一件事在兩張報表的樣子可能不同(逐筆注單 vs 當日彙總成一列、時間停在當日第一筆),挑錯報表會寫出一個永遠對不上的斷言。
- **報表有寫入延遲**:查不到就輪詢重試(每次間隔幾秒),並在錯誤訊息寫清楚「查不到什麼、重試幾次」。
- **時間窗容忍度不要放寬**:用「動作之後」的時間過濾資料時,容忍值放到幾分鐘會把上一次執行留下的資料也算進來,連跑兩次就掛;抓 30 秒級即可。

## 4. 跑到綠【實作期】(硬規則)

```bash
npx playwright test tests/<分類>/<檔名>.spec.ts --project dev-<分類>
```

- **跑不綠不准 commit**。失敗就修(看 `test-results/` 截圖、報告附件「失敗當下畫面」),連續修不動就如實回報卡點
- 跑綠後**再跑一次**確認穩定;selector 用了 `nth()` 或深層 CSS 就重找穩定的
- 第二次跑掛掉先想「是不是被前一次影響」:上一次留下的資料落進查詢範圍(見 3.5 的時間窗),或**同一個帳號被互踢**——前台會員與後台管理帳號都是「同帳號重複登入會頂掉舊 session」,被頂掉那邊的 API 會回 0/空值(例如餘額顯示 0.00),看起來像「沒有餘額」「查不到資料」。跑測試時不要自己也登著同一個帳號、不要留著上次的遊戲視窗;探索用的瀏覽器記得關掉再跑
- 跑綠後**不要自行宣告完成**,接 §4.5 更新清單,再依 §4.6 交付使用者確認

## 4.5 更新測試案例清單【實作期】(必做,不可跳過)

- 把新測試以「檔案 + 一句話測試案例」補進 **CLAUDE.md「目前的測試案例」表格**
- 同步更新 **README.md 第四節**「目前的測試案例」的對應條目(QA 面向,用非工程用語描述)
- 若是修改/刪除既有測試,也要同步這兩處

## 4.6 交付使用者確認【確認期】🚧

跑綠不等於完成,**要交給使用者確認過才算數**。把下列內容一次講清楚:

- **執行結果**:通過幾支 / 耗時 / 跑了哪些 project
- **測試報告**:`npx playwright show-report` 可開;有失敗過的話說明修了什麼
- **實際驗到什麼**:用白話覆述斷言驗的業務結果,讓使用者判斷「這樣測對不對」
- **這次在 dev 留下了什麼**(dangerous 類必說):產生了哪些帳號/資料

然後明確問:「**有疑慮就說,我改;確認沒問題我才 commit。**」

- 使用者提出疑慮 → 回 §2 或 §3 修正,修完重跑,**再交付一次**
- 使用者確認沒問題 → 才可以進 §5 commit

## 5. 開分支 commit【確認期通過後】

- 分支:`qa/<使用者名>/<主題>`(先問使用者名字,同分支可累積多支相關測試)
- `git status` 確認只有預期檔案(spec、Page Object、CLAUDE.md/README.md 的清單更新);**不可包含 `.env`、`.auth/`、`test-results/`、`playwright-report/`**
- commit message 繁中一行,說明測了什麼行為

## 6. 詢問是否 push + 開 MR【確認期通過後】

- 問使用者要不要現在 push 並開 MR 給工程師 review;不催促,QA 可能想累積幾支再送
- 開 MR 時:target `main`,描述附「測試目的 + 執行結果證據」,**不代按合併**

## 7. 知識庫判斷【收尾】(每次收尾必做)

回顧這次探索與測試過程,判斷有沒有**值得寫進共享知識庫(memory MCP)的系統行為知識**——重點是「下一個人不知道就會踩坑或查很久」的事實,不是測試代碼本身。典型訊號:

- **後台設置影響前台行為**:某設置值不同,前台出現不一樣的畫面/流程(開關、上限值、權限碼)
- **隱藏的前置條件**:要先在後台開通/設定 X,前台才看得到 Y
- **特殊訊息或錯誤碼的含義**:某錯誤碼實際代表什麼業務狀態
- **跨站因果**:後台某操作會讓前台立即/延遲產生什麼效果(含快取延遲)
- **與直覺不符的行為**:實走時「咦,原來是這樣」的瞬間,通常就是知識

有符合的就**逐條列出並詢問使用者**:「這次發現了以下系統行為,要不要加入共享知識庫?」(可用 AskUserQuestion 列選項讓使用者勾選)。使用者同意的條目,依 `memory-mcp:memory-store` skill 的模板寫入:標題用「使用者會問的問句」、內文含具體設置名/值與前後台行為對照、出處寫「<git user.name> 分享」。使用者拒絕或這次沒有新知識,直接結束,**不要硬找內容湊數**。
